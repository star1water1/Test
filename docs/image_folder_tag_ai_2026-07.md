## 0. 착수 전 확인 — 전제 정정 3건

이 저장소의 로드맵 항목은 착수할 때마다 전제가 틀렸다(`remaining_work` 5장: 네 번 연속).
그래서 설계 전에 현행 코드로 대조했고, **셋이 틀렸다.**

### (가) `기타/` 폴더는 지금 요청과 정반대로 동작한다

폴더 왕복 설계의 `<기타 이름>/`은 **"캐릭터와 이름이 일치하지 않는 아무 폴더"**를 뜻하는
자리표시자였다. 문자 그대로의 '기타' 폴더가 아니다. 그래서 지금 `기타/`를 만들면:

```
기타/ (5장) → classify → Location.Named("기타") → CharacterResolver → NotCharacter
            → 폴더끼리 링크 세트로 묶임
```

요청("각자 단일 개체로 링크 없이")과 **정확히 반대**다. 그러므로 이 작업은 동작 변경이
아니라 **분류 신설**이다.

### (나) `_미배정/` 직속이 이미 절반을 한다 — 그러나 파괴적이다

| | 신규 파일 | 토큰 파일 |
|---|---|---|
| `_미배정/` 직속 | 편입 + 미배정 + **링크 없음** ← 요청과 동일 | **배정·링크 전부 해제** ← 파괴적 |

신규 파일만 보면 요청은 이미 구현돼 있다. `기타/`의 값어치는 **토큰 파일에 대해 비파괴**라는
데 있다(11-1장의 "되돌리는 자리"와 역할이 갈린다). 이 사실이 아래 D-2 결정의 근거다.

### (다) "흩어진 묶음의 나머지"는 현재 상태에서 셀 수 없다

`ImageMetaDao.clearGroupIfSingleton`이 **모든 해제 경로에서** 1장짜리 링크 그룹을 즉시 없앤다:

```sql
UPDATE image_meta SET linkGroupId = NULL WHERE linkGroupId = :groupId
  AND (SELECT COUNT(*) FROM image_meta WHERE linkGroupId = :groupId) <= 1
```

`AutoLinkPlanner`도 "그룹은 최종 인원 2장 이상일 때만 만든다(**1장 링크 배지는 오해**)"라고
못박는다. 즉 **"혼자 남은 링크 그룹"은 상태로 존재하지 않는다** — 그렇게 정의한 어시스턴트
카드는 언제나 0건이 되어 있는 것처럼 보이기만 하는 기능(원칙 02 위반)이 된다.

**따라서 이 카드는 파생이 아니라 기록으로 만든다**(5-1장 장부 ③). 고른 기준
("원래 2장 이상이던 묶음에서 혼자 남은 것")이 애초에 **역사적 서술**이므로, 기록은
우회가 아니라 그 의미론의 정직한 구현이다.

**검사했고 이상 없던 축:** `image_tags`는 휴지통 스냅샷에 실리지 않는다(`EntitySnapshots`·
`CharacterSnapshot` 어디에도 없음) → AI 태그가 스냅샷 payload를 키우지 않는다(9장 판정 ③).

## 2. 분류 확장 — '기타' 서랍

### 2-1. 네 갈래가 된다

| 위치 | 신규 파일(토큰 없음) | 토큰 파일(기존 이미지) | AI 태그 |
|---|---|---|---|
| `<캐릭터명>/` | 편입 + 그 캐릭터 배정 | 배정을 그 캐릭터로 **이동** | ✗ |
| **`기타/`·`_기타/`** 신설 | 편입 + 미배정 + **링크 없음** | **링크만 해제**(배정 유지) | ✗ |
| `<그 외 이름>/` | 편입 + 미배정 + 링크 세트 | 그 폴더 세트로 링크 | **✓ 대상** |
| 정리 폴더 직속 · `_미배정/` 직속 | 편입 + 미배정(링크 없음) | 배정·링크 **전부 해제** | ✗ |
| `_미배정/<세트명>/` | 편입 + 미배정 + 링크 세트 | 배정 해제 + 그 세트로 링크 | ✗ (2-4 참조) |
| `_공유/` · `_처리됨/` | 기존 그대로 | 기존 그대로 | ✗ |

### 2-2. 캐릭터 우선(D-1)을 어디서 구현하는가

`classify`는 순수 함수이고 캐릭터 사전을 모른다. 그러니 **`classify`에서 갈라서는 안 된다.**

```
classify(["_기타"])  → Location.Misc          // 예약 접두라 무조건 서랍
classify(["기타"])   → Location.Named("기타")  // 지금과 동일 — 판정은 plan()이 한다
```

`plan()`이 `Named` 폴더를 해석할 때:

| `CharacterResolver.resolve("기타")` | 결과 |
|---|---|
| `Found(id)` | **그 캐릭터 폴더**(캐릭터 우선) + 요약에 고지 |
| `NotCharacter` **이고** 이름이 `기타` | **서랍으로 강등** = `Misc`와 동일 처리 |
| `NotCharacter` (그 밖의 이름) | 종전대로 링크 세트 |

이 배치의 이점: 캐릭터 우선이 **분류가 아니라 해석 단계**에서 일어나므로,
동명이인 보류(`ambiguousFolders`)·`#코드` 병기 같은 기존 해소 사다리(10장)를
`기타`라는 이름이 우회하지 못한다. 규약을 하나 더 만드는 대신 **기존 사다리에 태운다.**

`_기타`는 예약이므로 `classify`의 예약 분기에 명시 등재한다 — 지금 `classify`는
`folders.size == 1`에서 **모든 미등재 `_xxx`를 `Named`로 흘려보내므로**(실측),
등재하지 않으면 `_기타/`는 "이름이 `_기타`인 캐릭터를 찾는" 폴더가 된다.

### 2-3. `기타/`의 토큰 파일 — 링크만 푼다(D-2)

기존 `DetachAction`은 `unlinks: Boolean`으로 "배정 해제 + 링크 해제"를 함께 태운다
(11-1장 (나)의 수리 결과). '기타'는 **그 반대 조합**(배정 유지 + 링크 해제)이 필요하므로
액션을 새로 만든다:

```kotlin
/** '기타' 서랍 — 묶음만 푼다. 캐릭터 배정은 건드리지 않는다(D-2). */
data class UnlinkOnlyAction(val path: String, val groupId: String)
```

**`DetachAction`에 플래그를 더하지 않는 이유:** 그 자료형은 "배정을 뗀다"가 본체이고
`unlinks`는 그 안의 갈래다. 배정을 떼지 않는 동작을 거기 실으면 이름이 거짓이 되고,
11-1장이 딱 그 혼선("계획이 정한다 vs 실행부가 판정한다")으로 값을 치렀다. R-13
("셀 단위가 다르면 함수를 나눈다")의 자료형 판이다.

실행부는 링크 해제 뒤 `clearGroupIfSingleton(oldGroup)`을 부른다(기존 해제 경로와 동일 규약).
**그 호출이 남긴 흔적이 5-1장 장부 ③의 입력이다.**

### 2-4. `_미배정/<세트명>/`을 AI 태그 대상에서 뺀 이유

세트명도 사람이 붙인 의미 있는 이름이라 후보로 볼 만하다. 그러나 그 자리는 **묶는 자리**로
의미가 이미 확정돼 있고(11장), 사용자가 `_` 접두 예약 폴더에 넣는 행위는 "규약대로 처리하라"는
지시에 가깝다. 태그까지 붙이면 예약 폴더의 계약이 넓어진다.

**재개 조건:** 1차 사용에서 "세트명에도 태그를 달고 싶다"가 실제 마찰로 확인될 때.
그때는 대상 선택을 받아오기 확인 다이얼로그의 체크박스 두 개로 가른다(그 외 폴더 / 세트 폴더).

## 3. AI 폴더 태그 제안

### 3-1. 계약 (기존 AI 불변 계약을 그대로 상속)

`ai_integration.md`가 못박은 것을 이 기능도 예외 없이 따른다:

1. **온디맨드 전용.** 받아오기 확인 다이얼로그에서 사용자가 체크할 때만 돈다.
2. **`hasUsableProvider()` 진입 가드.** 미설정이면 체크박스를 **감춘다**(R-24 — 성립하지
   않는 조합의 설정은 보이지 않는다). 감출 때는 사유를 남긴다(설정 화면 안내 1줄).
3. **실행 전 비용 고지.** "그 외 폴더 N개 → 요청 M건".
4. **AI 출력은 절대 자동 적용하지 않는다.** 검토 시트에서 사용자가 골라 적용한다.
5. **실패해도 받아오기는 완주한다.** AI는 부가 단계다 — 실패 시 태그만 빠지고 편입·배정·링크는
   그대로 반영되며, 사유를 결과 요약에 싣는다(R-17).

### 3-2. 프롬프트에 싣는 것

| 축 | 내용 | 상한 |
|---|---|---|
| **대상** | 그 외 폴더의 이름 + 그 폴더의 이미지 수 | 요청당 폴더 `MAX_FOLDERS_PER_REQUEST` (청킹) |
| **어휘 ①** | 기존 `image_tags`의 distinct 태그, 빈도 상위 | `MAX_VOCAB_TAGS` |
| **어휘 ②** | '기조에 포함' 필드의 사용값 | 필드당 `MAX_VALUES_PER_FIELD`, 총 `MAX_VOCAB_VALUES` |
| **기조** | 사용자가 쓴 자유 서술(4장) | `MAX_POLICY_CHARS` |

어휘 ②의 **선별은 새로 만들지 않는다** — `CharacterFieldAiSuggester.selectUsageExamples`가
이미 "앞 2/3은 빈도 상위(주류 기조), 나머지 1/3은 균등 간격으로 훑어(분포의 폭)"를 난수 없이
수행한다. 같은 문제이므로 같은 함수를 쓴다(단일 소스).

**잘라낸 것은 전부 개수로 고지한다**(R-14) — 비용 고지 칩에 "태그 어휘 120개 중 80개 사용"
형태로. 조용히 자르면 사용자는 왜 어떤 태그가 안 나오는지 영영 모른다.

### 3-3. 출력과 검증 (환각 드롭)

응답은 `{"folders":[{"name":"...","tags":["...","..."]}]}`. 파싱은 기존
`AiJsonExtractor`(관대 JSON 추출) 재사용.

| 검증 | 처리 |
|---|---|
| 요청하지 않은 폴더명 | 드롭 + 개수 보고 |
| 빈 태그·공백만·길이 초과 | 드롭 + 개수 보고 |
| 폴더당 태그 수 초과 | 상한까지만 + 초과분 개수 보고 |
| 중복 태그(대소문자·공백 차이) | 정규화 후 합침 |
| **어휘 밖의 새 태그** | **드롭하지 않는다** — 검토 시트에 `새 태그` 표식을 달아 보여 준다 |

마지막 행이 이 기능의 요점이다. 어휘는 **일관성을 위한 참고**이지 허용 목록이 아니다.
폴더 이름에서 새 개념이 나오는 것은 정상이며, 어휘 밖이라고 버리면 "폴더 이름을 읽는다"는
목적 자체가 반쯤 사라진다. 대신 새 태그임을 **보이게** 해서 사용자가 판단하게 한다
(자율성 우선 + 변수 제어).

### 3-4. 적용 범위 (D-4)

태그는 **이번 받아오기에서 그 폴더로부터 편입·반영된 이미지에만** 붙인다.
링크 세트가 기존 그룹과 병합되더라도(검토 C-8의 "기존 링크 N개가 합쳐집니다" 경로)
**원래 그룹에 있던 이미지에는 붙지 않는다.**

근거: 사용자가 폴더에 넣은 것과 화면에 나타나는 결과가 일치해야 한다. 병합으로 딸려 온
이미지까지 태그가 번지면, 사용자는 폴더에 넣은 적 없는 이미지에 태그가 생긴 것을 보고
그것을 되돌리려 일일이 지워야 한다 — 조용한 확대이자 조작 마찰이다.

## 4. 설정 — 신설 3곳

셋 다 화면에 노출되는 설정이므로 **R-25 목적문("무엇이 어디서 어떻게")이 의무**다.
문구는 `text_style_guide_2026-07.md` 3장 톤 표(합니다체)를 따르고, 초안은 아래 그대로 쓴다.

### 4-1. 설정 → AI 연동 → 「AI 이미지 태그 기조」 (자유 서술)

```
AI 이미지 태그 기조
쓰면 폴더 이름으로 태그를 제안할 때 이 지침을 함께 전달합니다.
예: "장면 종류(전투·일상)와 복장을 우선으로, 인물 감정은 넣지 마세요."
```

저장은 `AiPromptSettings`(SharedPreferences). 값 범위·상한은 `AiPromptPolicy`에 순수
상수로 두어 단위 테스트한다 — 두 곳에 적으면 갈린다는 그 파일의 기존 교훈 그대로.

### 4-2. 필드 편집 다이얼로그 → 「AI 이미지 태그 어휘에 포함」 (D-3)

```
AI 이미지 태그 어휘에 포함
켜면 이 필드에 입력된 값들이 AI 이미지 태그 제안 때 어휘 후보로 함께 전달됩니다.
기조 문구에 적히지는 않으며, 이 필드의 값이 바뀌지도 않습니다.
```

**이름을 '기조에 포함'이 아니라 '기조 어휘에 포함'으로 둔 이유**(D-3 결정의 실행):
사용자가 우려한 그대로, '기조에 포함'은 "내가 쓴 기조 문구에 이 값들이 덧붙는다"로 읽힌다.
실제 동작은 "AI에 함께 전달"이므로 목적문 2·3문장이 그 오해를 정면으로 막는다.

저장은 `FieldAiPolicy`와 같은 관행 — `FieldDefinition.config` JSON의 새 키
(`imageTagVocab`), **기본값(false)은 저장하지 않는다.** 단 `aiSuggest`와 기본값 방향이
반대다(`aiSuggest`는 기본 켜짐, 이건 기본 꺼짐): 모든 필드의 값을 무조건 어휘로 보내면
프롬프트가 폭발하고 무관한 필드(메모·나이)가 태그 어휘를 오염시킨다.

**R-24 적용:** 사건 필드(`entityType = event`)에는 이 토글을 **감춘다** — 이미지 태그
어휘와 사건 필드는 성립하는 조합이 아니다(`aiSuggest`가 같은 이유로 감추는 것과 동형).

### 4-3. 받아오기 확인 다이얼로그 → 「폴더 이름으로 태그 제안」 (체크박스)

```
□ 폴더 이름으로 태그 제안
  그 외 폴더 N개의 이름을 AI가 읽고 태그를 제안합니다. 요청 M건 · 적용 전에 검토합니다.
```

AI 미설정이면 이 줄을 통째로 감춘다(3-1의 가드). 체크 상태는 기억하지 않는다 —
비용이 드는 동작의 기본값은 꺼짐이어야 하고, 폴더 구성은 매번 다르다.

## 5. 관리 자리 (D-5)

### 5-1. 어시스턴트 카드 — 「흩어진 묶음의 나머지」 (D-6)

0장 (다)에서 확인한 대로 **현재 상태에서 셀 수 없으므로 기록으로 만든다.**

**장부 ③ — 흩어진 나머지** (`FolderRoundtripLedger` + `FolderRoundtripPrefs`)

| 항목 | 값 |
|---|---|
| 무엇을 적는가 | 받아오기가 링크를 풀어 **묶음이 2장 미만이 된** 그룹의 남은 이미지 경로 |
| 언제 적는가 | 실행부가 `clearGroupIfSingleton` 뒤, 그 그룹이 실제로 해제됐을 때 |
| 언제 지우는가 | ① 그 이미지가 다시 링크되거나 ② 사용자가 카드를 숨길 때 ③ 이미지가 사라졌을 때(스캔 시 정리) |
| 상한 | `DEFAULT_CAP`(2000) 공유 규칙 — 오래된 것부터 폐기 |

**의도한 잡동사니는 적지 않는다.** `기타/`에 **통째로** 넣어 그룹 전원이 함께 풀린 경우는
사용자가 원한 결과이므로 장부에 남기지 않는다. 남기는 것은 **일부만 옮겨 묶음이 쪼개진**
경우뿐이다 — 이 구분이 D-6의 본체이고, 이것이 없으면 카드가 매번 떠서 꺼진다.

카드는 어시스턴트 **데이터 건강** 갈래에 붙인다:

```
제목: 묶음에서 떨어져 나온 이미지 %1$d장
본문: %1$s 등 — 링크 묶음이 나뉘면서 혼자 남았습니다. 다시 묶거나 그대로 두어도 됩니다.
액션: 이미지 탭에서 보기
```

본문 마지막 절("그대로 두어도 됩니다")은 의도적이다. 이것은 **결함이 아니라 알림**이므로,
고치라고 압박하는 문구는 정직하지 않다.

### 5-2. 이미지 탭 — 링크 상태 필터

`ImageFilterHelper.BaseFilter`는 지금 `ALL / CHARACTER / NOVEL / UNIVERSE / UNASSIGNED /
ORPHAN / TRASH`뿐이라 **링크 상태로 거를 방법이 없다**(실측). 카드의 액션이 데려갈 자리가
없으므로 함께 만든다.

`BaseFilter`에 값을 더하지 않고 **독립 축**으로 만든다:

```kotlin
enum class LinkFilter { ANY, LINKED, UNLINKED, AUTO_LINKED }
```

**이유:** `BaseFilter`는 소유·상태의 배타 분류(캐릭터냐 고아냐 휴지통이냐)인데 링크 여부는
그와 **직교**한다. "캐릭터에 배정됐고 링크는 없는 것"은 두 축의 교집합이라 한 enum에
욱여넣으면 값이 곱으로 늘어난다. `Criteria`에 필드를 하나 더하고 `matches`에 한 줄을 얹는다.

`AUTO_LINKED`를 분리하는 근거: `linkGroupId`가 `char:<id>` 접두면 캐릭터 자동 링크이고
(`AutoLinkPlanner.AUTO_TOKEN_PREFIX`), 그건 사용자가 만든 묶음이 아니다. 둘을 합치면
"내가 묶은 것"을 찾을 수 없다.

## 8. 구현 순서 (PR 분할)

앞 단계가 뒤 단계의 **선행**이다. 각 PR은 그 자체로 완결이며 중간 상태에서도 앱이 정상이다.

| PR | 범위 | 왜 이 순서인가 |
|---|---|---|
| **T-1** | '기타' 서랍 (2장 전부) + 고지 | AI 없이 단독으로 쓸모 있다. 요청의 본체 |
| **T-2** | 링크 필터 (5-2) | 작고 독립적. T-3의 카드가 데려갈 자리를 먼저 만든다 |
| **T-3** | 장부 ③ + 어시스턴트 카드 (5-1) | T-1이 만든 기록을 T-2가 만든 자리로 데려간다 |
| **T-4** | 설정 2곳 (4-1·4-2) + 어휘 수집 | AI 호출 없이 "무엇을 보낼지"까지만. 순수 로직 검증 가능 |
| **T-5** | AI 제안 + 검토 시트 (3장·4-3) | 위 전부가 갖춰진 뒤 |

**T-1만으로도 요청의 첫 문장은 충족된다.** AI 태그는 T-4·T-5이며, 그 전에 멈춰도
앱은 온전하다.
