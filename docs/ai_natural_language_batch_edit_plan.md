# AI 자연어 일괄편집 — 현재 코드 기반 구현 계획

기준: `master` `946ddcbe` (PR #411 병합 후). 사용자가 제공한 「AI 자연어 일괄편집 Master Spec」을 현재 코드와 대조해 등록한 계획이다. 제품 범위는 유지하되, 예시 클래스명·구현 순서는 코드의 실제 저장 계약에 맞게 조정한다. **M1의 순수 입력·Plan 검증 기반을 구현했으며, 분석 호출·화면·DB 적용은 아직 연결하지 않았다.** 기존 [AI 창작 입력·음성 계획](creative_ai_voice_plan.md)은 이미 구현한 기반의 기록이고, 이 문서가 자연어 일괄편집의 범위와 완료 조건을 맡는다.

## 목표와 불변식

사용자가 세계관 또는 작품을 먼저 고르고, 텍스트나 기존 음성 입력으로 여러 인물의 설정을 설명한다. 앱은 이를 **필드·관계·세력 소속의 변경 후보**, 상대 조건, 해석하지 못한 내용, 창작 참고 메모로 분리한다. 사용자는 전용 검토 화면에서 원문과 기존값을 보며 선택·수정하고, 선택한 항목만 적용한다. AI는 DB에 쓰지 않는다.

- AI 출력은 불신하는 제안이다. 허용된 typed operation만 앱이 해석하며, 대상·필드 ID는 앱이 제공한 요청 한정 참조에서만 풀린다. 유효하지 않은 응답은 DB에 닿지 않는다.
- 원문/전사 수정은 분석 결과 전체를 stale로 만든다. 제안값 직접 수정은 해당 항목만 다시 검증한다. 오래된 AI 응답·다른 창의 저장이 최신 검토를 덮지 않는다.
- 출처(`EXTRACTED`/`DERIVED`/`CREATIVE`), 변경 위험(추가/교체/제거), 검토 상태(준비/확인 필요/해석 불가/충돌/무변경)는 서로 다른 축이다. 숫자 confidence나 모델 자기신고가 안전 판정을 대체하지 않는다.
- 창작 후보는 처음부터 보여줄 수 있지만 기본 선택은 꺼 둔다. 제거·탈퇴·관계 삭제도 기본 꺼짐이다. 애매한 대상·필드, DB 충돌, 불완전한 분석은 자동 적용할 수 없다.
- 입력 segment와 연결되지 않은 내용도 보존해 표시한다. 일부 청크 실패·출력 절단·미처리 segment가 있으면 **분석 불완전**으로 표시하고 완료로 가장하지 않는다.
- 적용 직전 현재 DB를 다시 읽고, 예상한 값·관계·소속과 달라졌으면 해당 변경을 멈춘다. 부분 성공·건너뜀·실패·자동 관계 파급을 각각 집계해 보여 준다. 되돌리기는 적용 후 상태가 그대로인 대상에만 허용한다.

새 핵심 추상화는 **입력 세션/segment**, **검증된 Change Plan**, **범위 한정 후보 참조와 해석 결과**, **항목별 Review 결정**, **DB 재검증을 포함한 실행기와 영속 실행 기록**이다. UI와 모델 출력 형식은 이 경계를 소비한다. 범용 DB 명령 프레임워크는 만들지 않는다.

## 입력·해석 계약

1. 범위는 세계관 또는 작품 중 하나다. 작품의 세계관이 없으면 인물과 전역 필드의 실제 소속 규칙을 따른다. 다른 세계관의 동명이인을 후보로 슬쩍 끌어오지 않는다. 범위를 바꾸면 기존 Plan을 stale로 만들고 재분석한다.
2. 입력은 원문과 offset을 보존한 안정적 segment ID로 나눈다. 문장부호만으로 자기 정정·부정·비교의 문맥을 잘라내지 않는다. 분석 결과는 segment ID를 인용하고, 화면은 모델이 재구성한 문장 대신 앱이 보관한 원문을 보여 준다. 인용이 실제 요청 자료에 있었는지 확인해도 의미적 참임까지 증명된 것은 아니다.
3. 대상 후보는 선택 범위 안의 이름·이명(`Character.aliases`)·코드·작품 정보로 찾는다. 동명·이명 충돌은 후보 모두를 남겨 Review로 보낸다. 앱이 후보 목록에 붙인 요청 한정 참조만 AI가 반환할 수 있다. 알 수 없는 참조, 없는 캐릭터, 범위 밖 캐릭터는 mutation으로 승격하지 않는다.
4. 필드는 범위의 `FieldDefinition(entityType=character)`에서 이름·키·설명·타입·설정으로 찾고, 복수 후보나 없는 필드는 unresolved로 남긴다. 현재 값은 후보 인물·필드에 한정해 조회한다. **전역 필드(`universeId=null`)와 세계관 필드를 섞지 않는다.** 제한값·구조화 입력·계산 필드·시맨틱 역할은 기존 규칙으로 검사한다.
5. 처음에는 범위 안의 가벼운 이름/이명/코드 색인과 입력 언급으로 후보를 좁힌 뒤 관련 필드·현재값·관계·세력만 가져온다. 선택 범위의 상세 DB 전량을 프롬프트에 보내지 않는다. 누락되거나 잘린 재료의 수와 이유를 사용자에게 표시한다. 모델이 필요하다고 요청한 추가 문맥도 범위를 재검증한다.
   캐릭터 메모·필드값·가져온 자료·사용자 전사는 모두 **자료 블록**으로만 전달한다. 그 안의 “이전 지시를 무시하라” 같은 글을 시스템 지시로 승격하지 않는다.
6. JSON 루트에는 `schemaVersion`, 입력/범위 revision, `operations`, `constraints`, `unresolved`, `suggestionNotes`, segment별 처리 상태를 둔다. operation은 `Set/Add/Remove/ClearFieldValue`, `Add/Update/RemoveRelationship`, `Join/LeaveFaction` 등의 **폐쇄된 종류**만 허용한다. 알 수 없는 종류·필수 속성 누락·잘못된 타입·중복 ID·크기 초과 등 schema 자체의 실패는 해당 응답 전체 실패다. 유효한 schema 안의 대상/필드 불일치는 항목을 unresolved로 보존한다.
7. 멀티값 후보는 항목별 선택·근거를 갖되 DB에는 `CharacterFieldValue`가 `(characterId, fieldDefinitionId)`당 한 행이다. `FieldValueTokenizer`로 실제 타입에 맞게 분해·재조합하고 해당 셀의 전체 원시값을 비교한 뒤 쓴다. 단일값, 구조화값, 계산값을 쉼표 기준으로 억지 분해하지 않는다.
8. 상대 비교는 별도 constraint다. 기존 숫자 등으로 결정적으로 판정되는 경우 충족/불충족/자료 부족을 표시한다. 의미적 비교는 창작 후보나 메모로 이어질 수 있어도 임의의 정확한 수치로 확정하지 않는다. 명확한 자기 정정은 앞 후보를 대체하되 원문 둘 다 남기고, 범위·모순은 충돌로 남긴다.
9. segment마다 operation/constraint/unresolved/명시적 중복·무시 사유가 하나 이상 연결돼야 한다. 여러 응답을 합칠 때 같은 셀·관계·소속의 중복과 충돌을 해소하거나 표시한다. 청크별 성공을 합산한 것만으로 전체 성공이라 하지 않는다. 실패한 청크는 원문과 재시도 범위를 유지하며 자동 유료 재요청하지 않는다.

모델의 `EXTRACTED` 주장은 앱이 기록한 당시 입력·segment와 비교한다. 인용의 존재만으로 부정·추측·정정의 의미를 증명할 수 없으므로 직접성 검증이 모자라면 확인 필요로 내린다. `DERIVED`는 입력과 현재 DB에서 앱이 재현할 수 있는 추론만 확정 표시하며 나머지는 Review다. `CREATIVE`는 원문 사실과 다른 시각적 표식·기본 OFF를 유지한다. 짧은 suggestion note는 영감으로만 쓰며 사용자가 목적지를 골랐을 때만 별도 검증을 거쳐 저장한다.

### M1에서 확정한 응답 계약

`NaturalBatchInput`은 session ID, 세계관/작품 범위, 범위·입력 revision과 UTF-16 offset이 붙은 원문 segment를 가진다. 자동 segment 경계는 빈 줄뿐이다. 한 문단 안의 부정·자기 정정을 문장부호로 자르지 않는다. 입력이나 범위가 바뀌면 검토 Plan 전체를 stale로 만들고, 이전 요청의 응답은 버린다.

응답 JSON v1은 `schemaVersion`, `sessionId`, `scopeRevision`, `inputRevision`, `operations`, `constraints`, `unresolved`, `suggestionNotes`, `segmentStatus`가 필수다. 불명 키·종류·타입·필수값 누락·중복 항목 ID는 해당 응답 전체를 실패로 처리한다. 캐릭터·필드·관계·세력 참조는 앱이 **그 요청에 발급한 참조 집합**과 대조한다. 형식은 맞지만 그 집합에 없는 참조는 실행 후보에서 빼고 원문 인용과 함께 `unresolved`로 보존한다. 출처 인용은 실제 segment에 있는지 별도 표식으로 남기며, 인용이 일치해도 사실성 검증을 통과한 것으로 취급하지 않는다.

같은 셀·관계·소속에 둘 이상의 operation이 있으면 둘 다 `CONFLICT`로 남긴다. 각 segment는 처리 항목 또는 명시적 무시 사유가 있어야 하며, 응답 누락·청크 실패·처리 항목 없는 `PROCESSED`·처리 항목이 있는데 `IGNORED`는 불완전으로 표시한다. **불완전과 충돌은 별도 축**이다. 청크의 항목 ID는 응답 안에서만 유일하면 되고, 합칠 때 앱이 요청 범위와 요청 순서로 이름을 붙인다. 일부를 재시도할 때 앞서 받은 성공분을 유지하고 같은 segment의 이전 실패분을 교체한다. 여러 segment를 함께 인용한 항목이 있으면 그 인용 범위 전체로 재시도를 넓힌다. 응답 도착 순서가 바뀌어도 앱이 발급한 요청 순서의 최신 결과만 남긴다. M1의 항목은 모두 확인 전 상태이고 기본 선택은 꺼져 있다. M2~M3에서 실제 대상·값을 검증한 뒤에만 안전 항목의 기본 선택 여부를 정한다.

## 관계·세력·실행 경계

- `CharacterRelationship`은 양 끝, 방향(`isBidirectional`), 유형, 강도, 설명과 `factionId`(수동/자동)를 가진다. DB 유니크 제약은 **순서가 있는** `(characterId1, characterId2, relationshipType)`에 걸리므로 역방향·양방향 중복은 앱도 판정해야 한다. 자동 관계는 세력 가입/탈퇴의 파급이다. 관계 유형은 해당 세계관의 현재 설정과 대조한다. Plan은 **수동 관계**만 직접 조작하며, 자동 관계와 충돌하면 세력 operation의 결과로 설명하거나 Review 충돌로 남긴다. “관계가 끝났다”는 시점이 없으면 임의의 연도별 `CharacterRelationshipChange`를 만들지 않는다. 기존 관계를 삭제하라는 명확한 요청은 기본 OFF로 제안한다.
- `FactionMembership`은 세력별 복수 활성 소속과 재가입 이력이 가능하다. 단순 “소속 변경”을 단일 `factionId` 덮어쓰기로 해석하지 않는다. 가입은 `FactionRepository.addMember`, 현재 소속의 순수 제거는 `removeMember`, 연도가 있는 설정상 탈퇴는 `departMember`의 서로 다른 의미를 따른다. 출발 세력이 여러 곳이면 사용자가 고르기 전 모두 지우지 않는다. “무소속”은 현재 활성 소속 전체의 제거 후보와 파급 건수를 보여 주는 파괴적 묶음으로 취급한다.
- preflight는 선택된 항목의 실제 DB 행과 파급 대상을 한 번에 다시 읽는다. 삭제된 대상·필드, 타입/제한값 변화, 기존값 변화, 자동 관계 중복, 이미 충족된 operation을 구분한다. 한 operation의 예상 전 상태와 적용 대상은 트랜잭션 안에서도 재확인한다. 값 하나의 변경 때문에 무관한 인물의 안전한 항목까지 무조건 막지 않는다.
- 적용은 UI가 DAO를 순서대로 호출하는 방식이 아니라 도메인 실행기가 맡는다. 기존 저장 경로의 검증·자동 관계·시맨틱 동기화·값 라이브러리 후처리를 공통화해 재사용한다. 파급을 숨기며 예외를 삼키는 기존 경로가 있다면 그대로 연결하지 않고 결과 계약을 보강한다. 부분 적용이 필요하면 operation/의존 묶음마다 원자적 경계와 명시적 결과를 두고, 독립 항목만 계속한다.
- 중복 탭·재시도·프로세스 종료 후에도 같은 operation이 다시 쓰이지 않도록 Plan/실행/operation ID를 DB에서 확인한다. 정확한 Undo에는 전후 값뿐 아니라 생성·수정·삭제된 관계/소속/시맨틱 파급의 실제 ID와 버전이 필요하다. 따라서 `OperationLog`는 요약 표시로만 쓰고 **별도의 Room 실행 기록**을 트랜잭션과 함께 설계한다. 이 저장 형식을 도입하는 milestone에서 schema JSON·migration·실제 Room migration test·복원/백업 영향을 함께 검증한다. 파일 journal과 DB를 별도 커밋해 정확히 한 번 실행을 약속하지 않는다.
- Undo는 해당 실행에서 실제로 바뀐 행과 파급을 다시 읽어 **현재가 적용 후 상태와 같은 부분만** 복원한다. 후속 사용자 변경·다른 batch·삭제된 참조가 있으면 충돌로 보여 주고 덮지 않는다. 기존 사용자 확정의 “되돌리기가 후속 수정을 덮지 않는다”는 원칙을 따른다. 전부/일부 Undo 결과와 다시 시도 가능한 범위를 기록한다.

## 검토 경험과 수명

세계관/작품 선택 → 원문·음성 입력 → 전송할 문맥과 요청 수 고지 → 분석 → 전용 검토 화면 → 적용 전 재검증 → 결과/되돌리기 순서다. 검토는 작은 Dialog가 아닌 Fragment/RecyclerView 기반 화면으로 둔다. 상단에는 제안·선택·확인 필요·창작·unresolved·불완전 segment 수를 보여 주고, 인물/종류/상태별로 접어 본다. 한 행은 대상, 기존→제안값, 출처, 제거 위험, 원문, AI 참고 메모, 충돌 사유, 선택과 직접 수정을 제공한다. 유효한 직접 수정은 무료이며 다른 항목 상태를 유지한다.

검토 화면의 기본 축은 **한눈에 전체 규모 확인 → 안전한 후보부터 검토 → 애매한 항목만 상세 열기**다. 요약과 적용 버튼은 긴 목록에서도 접근 가능하게 두되, 필터를 켜도 전체 선택·확인 필요·불완전 건수는 사라지지 않는다. `CREATIVE`와 제거·탈퇴는 색과 문구로 구분하고 일괄 선택에 섞지 않는다. 중복·충돌·범위 밖 참조는 사라진 결과처럼 보이지 않게 별도 묶음으로 남긴다. 적용 버튼에는 **선택 건수와 재검증 필요 상태**를 함께 표시한다. 직접 수정 뒤에는 해당 행의 확인만 다시 요청하고 다른 행의 선택·스크롤 위치를 유지한다. 분석이 부분 실패해도 성공한 제안과 원문을 같은 화면에서 확인하고 실패 구간만 재요청한다.

검토 snapshot은 범위·입력 revision·Plan ID에 묶어 `ReviewJournal`의 백업 제외 저장/lease 패턴을 따른다. 원문·Plan·선택·직접 수정·확장/스크롤 위치를 보존하고, 손상·다른 창 충돌 시 원본을 지우거나 새 AI 요청을 자동 시작하지 않는다. 회전/재생성/앱 종료 후 복구와 오래된 응답 보류를 별도로 검증한다. 전사만으로 분석이나 DB 저장을 자동 시작하지 않는다. 비용은 분석·보완·청크 각각 기존 `AiService` 집계로 남기고, 요청 전에 **예상 요청 수**와 과금 불확실성을 구분해 고지한다.

## Milestone과 의존 관계

| 단계 | 산출물 | 통과 조건·의존 |
|---|---|---|
| P0 (이 문서) | 코드 대조·제품 계약·위험/검증 계획을 등록 | 다음 단계의 기준. 기능 구현이나 실기기 통과로 세지 않는다. |

| M2 | 범위 한정 대상/필드 해석과 필요한 문맥 조회, 전용 prompt, `AiService` 분석 연결 | M1 후. 동명이인·이명·코드·작품/세계관·전역 필드·미존재·제한값 테스트. 선택 범위 밖 자료 미전송. |
| M3 | 공통 도메인 preflight/실행 계약, 전후/파급 기록과 migration, 필드 operation | M1~M2 후. 현재 폼/일괄 검증과 같은 판정, stale·부분실패·중복실행·시맨틱 연동·Undo 충돌을 실제 Room으로 검증. UI에서 실행은 아직 열지 않는다. |
| M4 | 전용 Review/결과 UI, 텍스트·기존 음성 입력 연결, 선택·직접 수정·복구 | M2~M3 후. 여러 인물/필드 실제 적용이 가능하고 회전·프로세스 복구·원본 변경 stale·오래된 응답 차단을 검증. |
| M5 | 수동 관계와 세력 가입·변경·제거/탈퇴, 파급 preflight/Undo | M3~M4 후. 방향·자연키·자동 관계·복수 소속·재가입 이력·의존 순서·파급 수를 검증. 이 단계 전에는 해당 operation을 적용 버튼에 노출하지 않는다. |

작은 milestone을 병합하더라도 **v1 완료 선언은 M1~M7의 제품 범위와 안전 게이트가 모두 끝난 뒤**에만 한다. 중간 단계는 미구현 operation을 JSON에서 조용히 무시하거나 부분 성공으로 표시하지 않는다.

## 검증 계획과 남길 범위

- 순수 JVM: schema 버전/필수 필드/상한, 요청 한정 참조, 범위·별칭·동명이인, 필드 타입/멀티값, 출처와 원문 연결, 부정·추측·범위·정정·상충 발화, constraint, 청크 병합·완전성, Review 기본 선택과 revision.
- Android 계측/실제 Room: 필드·관계·세력 각 operation의 preflight와 파급, 기존 validation/라이브러리/시맨틱 동기화, transaction 중단, 동일 실행 재시도, migration, 부분 성공 집계, stale-aware Undo. UI는 20~50행 선택·직접 수정·접기/스크롤·회전·프로세스 재생성·다른 편집 창 충돌을 확인한다.
- 성능: 대상 후보 색인과 필요한 값만 조회, `SqlInChunks`를 통한 IN 절 상한, 관계 양 끝 일괄 조회, 세력 관계 팬아웃을 계측한다. 실제 데이터 규모는 [확장성 목표](scalability_performance_2026-07.md)를 참고하되 관계·세력 축은 미측정이므로 새로 잰다.
- 실기기: 5분 이상 음성, 10명 이상 언급, 필드/관계/세력 혼합, 20~50개 제안, 긴 Review, 직접 수정·창작/파괴적 선택, 회전·프로세스 재생성, 실제 적용·결과·Undo를 항목별로 확인한다. **현재는 미실시**다.

v1에서 캐릭터·작품·세계관·세력·새 필드 정의 생성, 사건/타임라인 수정, 범용 자연어 삭제, 복잡한 제약식 solver, 장기 대화형 편집은 하지 않는다. 적절한 필드가 없을 때는 원문과 후보 필드명을 참고로 남기고 자동 생성하지 않는다. 이 제외는 필드·관계·세력 변경, 창작 후보, 긴 입력 완전성, 안전한 적용/Undo라는 v1 약속을 줄이는 뜻이 아니다.
