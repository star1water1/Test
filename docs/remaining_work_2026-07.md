|------|------------|-----------|
| **B-4** 사건 필드의 교차분석 축 편입 | "사건 필드는 단일 분포까지만 보인다 — 사건 축은 별도 함수로" | 착수 전 조사가 **더 나쁜 상태**를 밝혔다: 사건 필드는 이미 교차분석 **다이얼로그 목록에 실려 있었다**(`computeFieldInsights`가 캐릭터+사건을 한 목록으로 돌려주므로). 그런데 `computeCrossAnalysis`는 `s.fieldDefinitions`(캐릭터 전용)만 조회해 **null을 돌려줬고**, Fragment 관찰자는 null이면 아무것도 하지 않는다 — 사용자가 사건 필드를 골라 '분석 실행'을 누르면 **아무 일도 일어나지 않았다.** 없는 기능이 아니라 **조용히 실패하는 기능**이었다 |

**B-4에서 고른 설계와 그 이유:**

- **축을 나눈다.** 셀 값이 "캐릭터 수"인지 "사건 수"인지는 표 전체의 의미를 정한다. 그래서
  `computeCrossAnalysis`(캐릭터)와 `computeEventCrossAnalysis`(사건)를 **다른 함수**로 두고,
  공통 조립만 `buildCrossAnalysis`로 뺐다. 문서의 지시("한 표에 섞으면 셀의 의미가 무너진다")
  그대로다.
- **섞으면 거절하되 이유를 준다.** `resolveCrossAxis`가 `Mismatch`(어느 필드가 걸렸는지 이름 포함)
  / `UnknownField`를 돌려주고, ViewModel이 그것을 문구로 바꿔 `error`로 흘린다. UI는 애초에
  섞을 수 없게 **축 선택기**를 두어 그 축의 필드만 세 스피너에 싣는다 — 판정은 두 겹이다
  (UI가 막고, 계산이 다시 확인한다). 어떤 경로로 들어와도 조용한 무반응은 없다.
- **인사이트 목록이 보여준 범위와 같은 범위를 센다.** 인사이트는 같은 `(key, type)` 필드를
  세계관 통합으로 한 장에 보여주는데(Pre-Analysis Merge), 교차분석이 대표 id 하나만 집계하면
  사용자가 본 것보다 **조용히 좁은 결과**가 나온다. `crossFieldGroup`이 그룹 전체를 모으고,
  값마다 **그 값을 소유한 필드의 설정**으로 해석한다(세계관마다 라벨·구간이 다를 수 있다).
  2개 이상이면 화면에 "세계관 N개를 합산했다"고 적는다.
- **CALCULATED 사건 필드도 축이 된다.** 계산 필드는 저장 행이 없어 합치지 않으면
  인사이트에는 보이는 필드가 교차분석에서만 빈 표가 된다.

**B-5에서 고른 설계와 그 이유:**

- **기본은 보이는 쪽**(`CardDisplayConfig.show = true`). 값을 넣었는데 목록에서 안 보여
  하나씩 열어봐야 아는 상태가 원칙 04 위반이다. 넘치면 사용자가 끄는 방향으로 조절한다.
- **상한(4개)은 두되 감추지 않는다.** 필드 수십 개짜리 세계관에서 사건마다 전부 그리면
  카드가 화면을 넘는다. 그래서 자르되 **남은 개수를 반드시 함께 표시**한다("+3개 더").
  사용자가 직접 끈 필드는 '잘린 값'이 아니므로 이 개수에 세지 않는다.
- **요약은 항목에 실어 보낸다.** 어댑터 바깥 맵으로 두면(`novelNamesMap` 방식) 값이 바뀌어도
  항목이 같아 보여 `notifyItemRangeChanged`로 목록 전체를 다시 그려야 한다.
  `EventItem`에 담으면 DiffUtil이 바뀐 카드만 다시 그린다.
- **화면에 실린 사건만 조회한다.** `getAllValuesList()` 전량 조회는 보이는 사건 수와 무관하게
  테이블 전체를 읽는다. `getValuesByEvents`를 900개씩 청크한다(SQLite 999-변수 상한).

검증: 순수 JVM 테스트 **297건**(+24: `StatsCrossAnalysisTest` 13, `CardFieldSummaryTest` 11),
차분 컴파일 신규 메시지 0(노이즈 제외 — 아래 2장 참조), 리소스 점검 통과.
마이그레이션 하네스는 돌리지 않았다 — **스키마 변경이 없다**(설정은 기존 `config` JSON의
새 키, DAO는 쿼리 추가뿐).

**이번 세션이 하네스에 더한 것:** `StatsDataProvider`가 순수 JVM 테스트에서 **실제로 실행**된다.
생성자가 받던 `NovelCharacterApp`을 `loadSnapshot(app)`의 인자로 내렸기 때문이다 —
나머지 `compute*`는 스냅샷만 보는 순수 계산이라 Android 런타임 없이 집계 규칙을 검증할 수 있다.
하네스 전용 스텁은 `tools/jvm-stubs/`에 있다(Gradle 소스셋 밖이라 실제 빌드와 충돌하지 않는다).
**이 방식은 다른 대형 계산기에도 그대로 쓸 수 있다** — 앱 의존이 로딩 함수 하나뿐이라면
그 의존을 인자로 내리는 것만으로 계산 로직 전체가 실행 검증 대상이 된다.

| **S-5** 월드패키지 임포터 부재 | "WorldPackageImporter 신설 + ZIP 판별 3분기 + 충돌 3분기 다이얼로그 + 원인별 메시지" | 착수 재확인이 색출 문서 미검증 항목을 **전부 실재로 확정**: 내보내기 자체가 ① 사건 필드 정의를 안 실었고(`getFieldsByUniverseList` 기본 인자 = 캐릭터 전용) ② 사건 필드값·값 라이브러리 엔트리를 아예 안 실었고 ③ 세계관·작품 직접 등록 이미지를 안 실었으며 ④ **전역 이름 은행을 통째로 실었다**(패키지 공유 = 무관한 개인 데이터 유출). 그래서 임포터 신설과 함께 **내보내기를 schemaVersion 3으로 완결**(①②③ 추가, ④는 내보내는 캐릭터가 사용 중인 이름으로 한정). 임포터는 v1~v3 전부 읽고 구버전에 없는 엔트리는 "없음"으로 처리하며 무엇이 빠진 형식인지 결과에 고지한다 |
| **가져오기 진입부** | "ZIP 판별 3분기" | `ImportFileFormat`(순수, 실제 ZIP으로 테스트): data.xlsx→백업 ZIP / manifest.json→월드패키지 / xl/workbook.xml→평범한 xlsx / 그 외 ZIP→**원인별 안내**(종전: POI 파싱 실패 후 일반 오류) / ZIP 아님→POI 판별. 앱 백업 판정이 먼저다(종전 동작 보존) |
| **충돌 3분기** | "죽은 문자열 share_world_conflict_* 활용" | code 일치(정체성)와 이름 일치(동명 타 세계관)를 구분해 문구를 다르게 쓰고, **동명이 여럿이면 덮어쓰기 선택지를 내리지 않는다**(대상 모호 — 임의 삭제 금지). 덮어쓰기는 캐릭터 수를 담은 2차 확인(R-4) 후 `deleteUniverse`(휴지통 작업 단위 스냅샷, R-9)로 보낸다. 덮어쓰기 후 임포트가 실패하면 **기존 세계관의 행방(휴지통)을 실패 토스트에 명시**한다 — 안 알리면 "실패했는데 세계관이 사라진" 것으로 보인다 |

**설계 선택과 이유:**

- **id는 전부 재배선한다.** 패키지의 id는 원 기기 DB id다. 삽입 순서(세계관 → 필드 정의 →
  작품 → 캐릭터 → 값·태그·상태변화 → 세력 → 소속 → 세력 관계 → 사건 → 연결 → 사건 필드값 →
  관계 → 관계변화 → 값 라이브러리 → 이름 은행 → 이미지 연동 참조)대로 old→new 매핑을 만들고,
  매핑이 없는 참조는 조용히 넣지 않고 **세어 고지**한다(변수 제어).
- **code는 정체성이다(R-1).** 기존 엔티티와 충돌하는 code는 가로채지 않고 재발급한다
  (`WorldPackageCodes.Registry`, 순수) — 재발급 건수도 고지. 세력 간 관계의 역방향 해석
  (`fromPortable`)은 **원 code → 새 id** 매핑으로 하고, 이름 폴백은 패키지 안에서 유일한
  이름만 쓴다(중복 이름으로의 해석은 오배정).
- **DB 삽입 전체가 한 트랜잭션이다.** 절반만 들어온 세계관은 복원이 아니라 유실이다(R-9와
  같은 취지). 이미지 파일은 트랜잭션 전에 복사하되 실패 시 복사본을 삭제해 파일도 되돌린다.
  이미지 파일명은 원 접두사(char_/universe_/novel_/img_)를 보존한다(엑셀 G3 교훈 재적용).
- **파서는 순수 계층이다.** `WorldPackageParser`가 JSON 엔트리 맵 → 내용물 파싱과 원인별
  실패(NotAPackage/UnsupportedVersion/MissingEntry/Malformed)를 담당하고, R-2(Gson null 주입)를
  패키지 JSON에도 적용해 **필수 문자열이 null인 행은 행 단위로 걸러 계수**한다(세계관 본체면
  Malformed). 엔트리 부재(구버전)와 JSON 파손은 다르게 처리한다 — 전자는 빈 목록, 후자는 거부.
- **이름 은행은 패키지 캐릭터가 실제로 쓰는 이름만 들여온다.** v1·v2 패키지는 원 기기 은행
  전체가 실려 있다 — 그대로 들이면 수신자의 은행이 오염된다. code가 이미 있으면 중복 삽입하지
  않고 사용 표시만 새 캐릭터로 잇되, **남이 쓰는 중이면 빼앗지 않는다**(B-3 규약 재사용).

검증: 순수 JVM 테스트 **509건**(+28: WorldPackageParserTest 11, WorldPackageCodesTest 7,

| 결함 | 무엇이 잘못됐나 |
|------|----------------|
| **nullable LHS `in` 컴파일 불가** | 내보내기의 이름 은행 필터 `it.usedByCharacterId in characterIds`는 `Long?`을 `Set<Long>.contains`에 넘겨 실빌드가 깨진다 — 스텁 실컴파일 준비 중 발견, `?.let(::contains)`로 교정. *차분 컴파일 노이즈에 묻힐 뻔한 진짜 오류* |

### 1-9. 이번 세션이 한 일 — 색출 개혁 로드맵 3 (통계 조용한 실패 일소: S-7·S-8·S-9·S-19)

로드맵이 지목한 **공통 뿌리 둘**을 각각 근본에서 고쳤다. 착수 전 네 항목을 전부 현행 코드로
직접 재확인했고 **넷 다 문서 그대로 실재**했다.

| 항목 | 뿌리 | 수리 |
|------|------|------|
| **S-7** 머지 카드의 드릴다운 과소집계 | 드릴다운이 대표 def 하나만 안다 | `FieldInsightResult.mergedFieldDefIds` 신설(`computeFieldInsights`가 `fds.map{it.id}`로 채움, 첫 원소 = 파싱 기준 def). `getCharactersByFieldValue`가 **id 목록**을 받아 그룹 전체를 기준 def config로 조회 — 차트 조각 수치와 목록 인원이 항상 일치 |

| **S-9** 사건 차트 탭 → 빈 캐릭터 시트 | 조회 경로가 캐릭터 전용인데 리스너는 사건 카드에도 붙었다 | `getEventsByFieldValue`·`computeEventSubgroupAnalysis` 신설 + 시트를 **엔티티 인지형**으로 일반화(`isEventAxis`). 리스너를 떼는 간소화(원칙 03 위반) 대신 사건 축을 완결 |

**설계 선택과 이유:**

- **머지 축은 하나다.** 카드가 `(key,type)`로 합산했으면 드릴다운·하위 그룹·필드 선택 목록이
  전부 같은 축을 써야 한다. 그래서 `getMergedFieldGroups`를 두어 선택 목록도 머지하고,
  **'현재 필드 제외'도 그룹 단위**로 건다 — 대표 id 하나만 빼면 형제 세계관 def가 같은 이름의
  다른 항목인 척 목록에 남고, 고르면 조용히 빈 분포가 나온다.
- **파싱 기준은 첫 원소다.** 차트가 그룹 전체를 primary def의 config·resolver로 파싱해 분포를
  냈으므로(`buildFieldInsight(primaryFd, …)`), 드릴다운도 같은 def로 파싱해야 값 공간이 맞는다.
  그래서 `mergedFieldDefIds`의 **순서가 계약**이다(첫 원소 = `fieldDefinition.id`).
- **"못 찾음"과 "없음"을 나눈다.** 대상 필드 정의를 못 찾으면 빈 목록이 아니라 **null**을 돌려주고
  호출부가 사유를 고지한다. 종전 `?: return emptyList()`는 필터를 바꾼 뒤의 옛 선택을 "0명"으로
  위장했다. 진짜로 값이 없을 때만 '데이터 없음'이 뜬다.
- **빈 결과도 말을 한다.** 교차표가 비면 조용히 `return`하지 않고 축별 사유를 표시한다.
  이것은 S-8의 근본 수리 **뒤에 두는 방어선**이다 — 계산값을 합쳐도 진짜로 데이터가 없는
  경우는 남고, 그때도 사용자는 이유를 알아야 한다. 하위 그룹 버튼이 고를 것이 없을 때의
  무반응도 고지로 바꿨다(버튼이 반응하지 않는 것은 고장과 구분되지 않는다).
- **사건 상세 화면은 없다 — 없는 것을 지어내지 않았다.** 사건 행 탭은 전역 검색이 이미 쓰는
  규약(`timeline_ui_state`의 `center_year`+`pending_navigate`, `TimelineFragment.onResume`이 소비)을
  그대로 재사용해 연표를 그 연도로 연다. 새 내비게이션 규약을 만들면 두 경로가 갈린다.
- **축이 다르면 함수를 나눈다(R-13 재적용).** 사건 하위 그룹 분석은 셀 단위가 '명'이 아니라
  '건'이라 `computeEventSubgroupAnalysis`로 분리했고, 문구도 축별로 갈랐다.
- **레거시 필드 분석 화면은 머지하지 않았다.** 그 화면의 분포는 def 하나 단위로 계산되므로
  (`computeFieldAnalysis`) 드릴다운도 def 하나가 맞다 — 머지 id를 넘기면 거꾸로 차트보다 많은
  인원이 나온다. 두 화면의 통합은 별건(S-14~S-18, 로드맵 4)이다.

(`listOf(fieldDefinition.id)`)이 단일 세계관·구경로와 동일 동작.

**남긴 것(이번 범위 아님):** 미배정 스코프에서 CALCULATED 값이 아예 생성되지 않는다
(`computeAllCalculatedValues`가 `novelId == null`을 건너뛴다 — 캐릭터의 세계관을 작품 경유로만
해석하기 때문). 이 스코프는 데이터 건강 경로에서도 CALCULATED를 **의도적으로 제외**해 왔고
(`:1082`·`:1089`), 고치려면 "작품 없는 캐릭터에 어느 세계관 수식을 적용할 것인가"와
"필터된 스냅샷의 불완전한 `universeFields`로 평가해도 되는가"를 먼저 정해야 한다.
백로그 **B-30**으로 등재했다. 다만 이번 수리로 그 경우도 **무통보가 아니게** 됐다 —
교차표가 비면 사유가 표시된다.

#### 이번 묶음이 답한 질문: '통계에 포함'은 어디에 적용되는가

세 항목(S-14·B-35·B-34)이 같은 질문이었으므로 **하나의 규칙**으로 답하고 `StatsFieldPolicy`를
단일 소스로 세웠다.

> **자동 선택은 설정을 따르고, 명시적 선택은 존중한다.**

| 경로 | 성격 | 적용 |
|------|------|------|
| 인사이트 카드 목록 / 패턴 감지 / 레거시 분포·요약 / 요약 TOP5 / 작품 간 비교 / 순위 가능 필드 / 하위 그룹 선택 목록 | 앱이 스스로 고른다 | **거른다** |
| 교차분석 축 자동 확장(형제 세계관 def) | 사용자는 필드 하나만 골랐다 | **형제만 거른다.** 고른 def는 설정과 무관하게 남긴다 |
| 드릴다운 / 하위 그룹 계산 / 순위 계산 / 교차분석 계산 | 사용자가 이미 골랐다 | **거르지 않는다** — 고를 수 있는데 빈 결과가 나오면 그것이 조용한 실패다(R-17) |
| 필드 완성도 / 데이터 건강 | '분석'이 아니라 '입력 현황' | **거르지 않는다**(이유를 코드에 적었다) |

이 규칙은 `getMergedFieldGroups`의 **종전 결정을 뒤집는다**. 그 함수는 "통계 비활성 필드도
부분집합 분석 대상으로 허용해 왔다(자율성 우선)"는 KDoc과 함께 일부러 거르지 않았고, 형제 목록인
`getRankableFields`는 걸렀다 — 같은 성격의 목록 둘이 반대로 동작한 것이 정확히 로드맵 4가
없애려는 상태다. 거르는 쪽을 택한 근거는 R-14의 본문이다: **"사용자가 직접 끈 항목은 '잘린 것'이
아니다"** — 그러므로 개수 고지 대상도 아니고, 되돌리는 경로(필드 편집의 토글)도 그대로다.
뒤집었다는 사실과 근거를 그 함수 KDoc에 남겼다.

#### 레거시 '필드 분석' 화면의 운명 — **유지하고 규칙만 통일**

로드맵이 "한쪽 소거도 검토할 것"이라 했으나 **통합하지 않았다.** 그 화면에만 있는 것이 둘이다
(필드별 완성도, 필드별 상태변화 수). 지우면 기능 간소화(원칙 03 위반)이고, 인사이트로 옮기면
그 화면의 축((key,type) 통합)과 맞지 않는다 — R-15가 "화면마다 머지 축이 다를 수 있다"고
명시한 그 지점이다. 대신 **같은 질문에 다른 답을 주던 원인**(데이터 준비 규칙과 드릴다운 매칭)을
전부 공용 헬퍼로 통일했다. 두 화면은 이제 축만 다르고 규칙은 같다.

#### 신설한 순수 헬퍼 (전부 순수 JVM 테스트로 실행 검증)

| 헬퍼 | 무엇의 단일 소스인가 |
|------|---------------------|
| `util/StatsFieldPolicy` | '통계에 포함' 판정. `expandGroup`이 그룹 자동 확장 규칙(고른 def 우선·첫 원소 계약)까지 담는다 |
| `util/ValueDistributions` | 전량 분포·표시 상한·비율 분모·'기타' 집계. **자르는 일은 여기 한 번뿐** |
| `util/NumericBinning` | 구간 생성·경계 규칙(마지막만 상한 포함)·라벨·파트 값 추출 |
| `util/FieldValueMatchSpec` + `FieldValueMatcher` | 드릴다운 매칭 규칙(값 집합 / 파트 수치 구간) |
| `ui/stats/StatsErrorToast` | 오류 고지 — 사유가 있으면 사유, 없으면 통짜 문구, **어느 쪽이든 반드시** |
| `ui/stats/PatternTypePrefs` | 인사이트 유형 설정의 저장·해석(세 곳이 각자 파싱하던 것) |

#### 설계 선택과 이유

- **상한은 표시 계층의 관심사다.** `computeFieldDistribution`이 전량을 돌려주고 `ValueDistributions.view`가
  표시 직전에 한 번만 자른다. 계산이 자르면 **분모와 잘린 개수가 함께 소실**되어 소비처가 참값을
  복원할 방법이 없다. 잘린 것은 '기타 N종' 조각·행으로 접고, **누르면 그 값들의 목록**이 나온다
  (개수만 알리고 내용을 못 보면 R-14를 절반만 지키는 것이다).
- **라벨은 매칭 키가 아니다.** 조각이 뻗는 조회는 라벨이 아니라 **그 조각을 만든 규칙**을 받는다.
  BODY_SIZE 구간처럼 라벨이 계산 결과인 분포는 문자열 비교로는 영원히 0명이다. 우연히 일치하던
  경로(값 그대로인 분포)도 같은 스펙 타입으로 통일해 두 번 다시 갈라지지 않게 했다.
- **계산기의 파생 상태는 인자에서만 나온다.** 값 라이브러리 해석기가 `loadSnapshot`이 채우는
  provider 가변 필드였다. 그래서 (a) 다른 스냅샷을 넘기면 별칭 접기가 조용히 사라지고,
  (b) **순수 JVM 테스트에서 별칭 경로가 죽은 코드**였다 — 고쳐도 고쳐졌는지 확인할 수 없었다.
  스냅샷에서 파생하도록 바꾼 뒤에야 S-18이 요구한 "별칭 필드에서 분포와 순위가 일치한다"를
  테스트로 고정할 수 있었다.
- **취소는 오류가 아니다.** `CancellationException`도 `Exception`이라 catch에 걸린다.
  작품 필터를 로딩 중에 바꾸는 **정상 조작이 오류 토스트를 낳고 있었다**. `reportError`가
  되던지므로 21곳이 한 번에 고쳐진다.
- **보여준 오류는 비운다.** `_error`는 10개 화면이 공유하는 보통의 LiveData이고 비우는 곳은
  전부 로더 진입부인데 로더는 캐시가 있으면 조기 반환한다. 회전·복귀 때 **이미 지나간 오류가
  다시 뜨고**, 다른 화면에서 난 오류가 엉뚱한 화면에 나타났다.
- **머지 카드의 설정은 그룹 전체가 기본, 끄는 것은 사용자 몫.** 체크박스(기본 켜짐)로 범위를
  주고, 형제들의 현재 설정이 서로 다르면 그 사실을 먼저 알린다. **형제의 나머지 설정은 건드리지
  않는다** — 대표의 config를 통째로 복사하면 세계관별로 일부러 다르게 둔 값 라벨·구간·'통계에
  포함'까지 덮어써 자율성을 침해한다. 다이얼로그가 실제로 편집한 항목만 얹는다.
- **빈 상태에서도 카드는 남는다.** 카드를 통째로 숨기면 그 안의 설정 버튼까지 사라져
  모든 유형을 끈 사용자는 되돌릴 경로를 영원히 잃었다. 비어 있어도 머리글을 남기고
  **왜 비었는지**를 적는다("감지된 패턴이 없습니다" / "모든 유형이 꺼져 있습니다" — 둘은 다른 사실이다).

검증: 순수 JVM 테스트 **629건**(+55: `StatsConsistencyTest` 30, `NumericBinningTest` 10,
`ValueDistributionsTest` 8, `StatsFieldPolicyTest` 7 — 러너 SOURCES·TESTS 갱신 포함),
리소스 점검 통과, 스키마 무변경(마이그레이션 하네스 불요 — 설정은 기존 `config` JSON,
새 컬럼 없음), 차분 컴파일 **신규 메시지 0**(노이즈 10종은 기준선에도 있는 부류로 확정 —
`A + B` 리스트 결합이 오류 타입 위에서 `String.plus`로 해석되는 4건과 stdlib 미해석 457건).

**차분 컴파일이 실제 결함 1건을 잡았다:** `StatsViewModel`이 `FieldValueMatchSpec`을 import 없이
썼다. 순수 JVM 하네스는 이 파일을 컴파일하지 않으므로(Android 의존) **테스트 618건이 전부
통과하는 상태에서도 실빌드가 깨질 뻔했다.** 하네스가 닿지 않는 파일을 고쳤다면 차분 컴파일은
선택이 아니다.

**자기 재공격이 잡은 것(5개 렌즈 → 코드 실독으로 확정 후 전부 수정):**

| # | 결함 | 무엇이 잘못됐나 |
|---|------|----------------|
| 1 | **고지를 정교하게 만들다가 고지를 없앴다** | `reportError`가 `CancellationException`을 되던지게 했는데, `loadAllStats`는 계산 10개를 `async`로 돌린다 — 하나가 터지면 다른 `await`가 **원래 예외를 cause로 단** JobCancellationException을 던진다. 그것까지 되던져 **진짜 실패가 무고지로 사라지고 화면이 백지**가 됐다(B-32가 없애려던 그 상태를 새 안전망이 되살렸다). cause가 있으면 취소가 아니라 그 원인을 보고하도록 교정 |
| 2 | **키와 값을 따로 게시해 짝이 어긋난다** | `@Volatile` 두 필드로 만든 캐시는 각 필드의 가시성만 보장할 뿐 **짝을 묶지 않는다.** 서로 다른 스냅샷을 동시에 계산하면(작품별 비교는 원본, 나머지는 필터본) "A의 키 + B의 값"이 남아 필터 밖 캐릭터의 계산값이 필터된 화면에 섞인다. 키·값을 **한 객체로** 게시하도록 교정 |
| 3 | **한 칸 캐시가 값마다 무효화된다** | 해석기 캐시를 스냅샷 동일성으로 잡았는데 원본·필터본을 오가는 경로에서 매 호출 미스가 나고, 이 함수는 **값 하나를 파싱할 때마다** 불린다 → 값마다 해석기 전량 재구축. 키를 `valueEntries` 동일성으로 바꿨다(필터본은 `copy`로 같은 리스트를 물려받는다). 계산값 캐시는 스냅샷 동일성 맵(`computeIfAbsent`)으로 바꿔 동시 요청이 하나로 묶이게 했다 |
| 4 | **필터본을 매번 새로 만들어 캐시가 영원히 빗나갔다** | 로더마다 `filterByNovel`을 다시 불러 **다른 객체**를 만들었다 → 동일성 캐시가 호출 간에 한 번도 적중하지 못한다. ViewModel이 필터본을 캐시하도록(원본 무효화·필터 변경 시 함께 버림) |
| 5 | **로케일이 값을 바꾼다** | `"%.2f".format(v)`는 기본 로케일을 쓴다. 이 문자열은 표시용이 아니라 **분포의 키이자 드릴다운 매칭 키이며 레거시 요약에서 다시 파싱된다** — 소수점이 콤마인 환경에서 되파싱이 실패해 그 캐릭터가 조용히 사라진다. `Locale.US` 고정(규약 R-22) |

| 22 | **빈 목록의 사유가 사실과 다르다** | 하위 그룹 목록이 '통계에 포함' 필터로 비었는데 "필드를 더 만들면"이라고 안내했다. 필드는 있고 꺼져 있을 뿐이며 되돌리는 경로도 있다 — 제외된 개수와 함께 그 경로를 안내하도록 |

| 25 | **그룹 적용이 형제의 분석 항목을 지웠다** | B-34로 넣은 '전체 적용'이 `analyses = listOf(entry)`로 덮어, 형제 def에 따로 만들어 둔 두 번째 분석 항목이 **차트 종류를 바꾼 것만으로** 사라졌다. 그 손실을 막으라고 넣은 '설정이 다릅니다' 경고는 **첫 항목만** 비교해 이 차이를 못 잡았다. 첫 항목만 교체하고 나머지는 보존하도록, 경고는 목록 전체를 비교하도록 |

렌즈 5개(안전망·규모·고지왜곡·회귀·조용한실패)가 낸 지적을 **전부 코드로 직접 확인**한 뒤 반영했다.

정정한 사례다(값 건수 분모를 '고쳤다'고 적어 놓고, 라벨이 '명'이라는 사실을 보지 못했다).
"안전망을 새로 만든 코드를 의심하라"는 5장의 교훈이 네 세션 연속으로 맞았다.

**반증 단계는 돌리지 않고 중단했다.** 렌즈 5개의 지적을 전부 코드로 확인해 **이미 수정한 뒤**였으므로,
반증자들이 읽을 코드는 지적이 가리키던 코드가 아니다(대부분 "이미 고쳐져 있다"는 판정만 나온다).
게다가 반증자 하나가 임시 테스트를 러너 목록에 넣고 원복하지 않아 **검증 러너 자체를 깨뜨렸다** —
작업 트리를 건드리는 검증 에이전트는 그 자체가 위험 요소다. 다음 세션이 같은 구성을 쓴다면
**반증은 수정 전에** 돌리거나, 작업 트리를 건드리지 못하게 할 것.

### 새로 세운 규약 (다음 작업자가 반드시 알아야 함)

기존 감사 문서 4장 규약에 더해 이번 세션이 코드로 확립한 것:

#### R-1. 스냅샷도 안정 식별자를 병기한다 (4-4의 확장)
`SnapshotRefs` / `SnapshotRefResolver`가 단일 소스다. **코드(자연키)가 대상을 정하고, DB id는
코드가 함께 일치할 때의 확인 수단이다.** 안정 식별자가 있는데 대상을 못 찾으면 **id로 폴백하지
않는다** — 테이블 재생성 마이그레이션(`DROP TABLE`+`RENAME`)은 sqlite_sequence를 생존 최대
id로 되돌리므로 다른 엔티티가 옛 id를 물려받을 수 있고, **오배정은 생략보다 나쁘다.**
`getById(...) != null`은 "같은 대상인가"를 원리적으로 판별하지 못한다.

`FieldDefinition`에는 code가 없으므로 자연키는 `(세계관코드, entityType, key)`다.
universeId 자체가 재발급되는 id이므로 세계관을 **코드로 승격**해야 성립한다.

#### R-2. Gson 스냅샷에 추가하는 필드는 전부 nullable
Gson은 Kotlin 생성자 기본값을 실행하지 않고 Unsafe로 객체를 할당한다. **구버전 payload에 없는
필드는 선언이 non-null이어도 런타임에 null이 주입된다.** non-null로 선언하고 곧바로 순회하면
사용자가 이미 갖고 있던 휴지통 항목 **전량**이 복원 불가가 된다.
기존 필드의 **타입도 절대 바꾸지 말 것** — `eventIds: List<Long>`에 코드를 담을 자리가 없어
`refs`로 병기하는 형태를 택한 이유가 이것이다. 계약은 `CharacterSnapshotPayloadTest`가 고정한다.

#### R-3. 보관 한도가 방금 만든 백업을 파괴해서는 안 된다 (4-6의 확장)
`TrashRepository`는 자기 인스턴스가 만든 스냅샷을 정리에서 보호한다. 세계관 삭제처럼 한 번에
수백 건을 스냅샷하는 경로에서 종전 구현은 `count - MAX_ITEMS`만큼을 오래된 순으로 지워
**그 작업이 방금 만든 백업과 이미지 파일까지** 태우면서 "휴지통에서 복구할 수 있습니다"라고
안내했다.

**한 작업은 하나의 인스턴스를 공유해야 한다.** 스냅샷을 만든 인스턴스와 정리하는 인스턴스가
다르면 보호 목록이 비어 결함이 그대로 재현된다. 엑셀 임포트가 정확히 그 함정이었다 —
세계관 이동 스냅샷은 캐릭터마다 새 인스턴스가 만들고 정리는 삭제용 인스턴스가 돌아서,
같은 임포트가 방금 만든 백업을 그 자리에서 태웠다(`ExcelImportService.trashForImport()`).

**보호는 그 작업 범위까지다.** 한도를 넘긴 잔여분은 *다음* 삭제 작업의 정리에서 소진된다.
따라서 UI 문구는 "무조건 보관된다"가 아니라 "그 삭제 중에는 지워지지 않는다"여야 한다
(사실과 다른 안심은 거짓 경고와 같은 부류다). 지속적인 해결은 백로그 B-14 참조.

#### R-4. 파괴적 동작은 실행 전에 결과를 알리고 취소 경로를 남긴다
복원은 성공 시 스냅샷을 소각하므로, 되살릴 수 없는 부분이 있으면 그 원본이 그 순간 영구
소멸한다. `previewRestore`가 먼저 무엇이 안 되살아나는지 알리고, 취소하면 스냅샷이 그대로
남아 세계관·필드 정의를 복구한 뒤 재시도할 수 있다. **"삭제하되 스냅샷을 남긴다"로 때우지 말 것**
(4-6) — 남긴 스냅샷을 다시 복원하면 캐릭터가 복제된다.

#### R-5. 폼의 권한은 폼이 실제로 렌더한 것까지다
`CharacterFieldValueMerge`가 단일 소스다. `replaceAllByCharacter`는 "폼이 전체 진실"을
요구하는데, 폼은 언제나 *현재 선택된 작품의 세계관에 속한 캐릭터 필드*만 렌더한다.
저장 경로는 **커버 집합**을 함께 넘겨야 하며, 커버 밖 기존 값은 건드리지 않는다.
`collectFieldValues()`가 빈 목록을 돌려주는 데는 두 이유가 있다 — "값이 전부 비었다"와
"애초에 렌더할 필드가 없다". 이 둘을 구분하지 못한 것이 N2의 원인이었다.

**사건 편집 폼도 같은 규약이다(S-6, 1-7장).** `EventFieldValueMerge`가 사건판 단일 소스이고,
커버 반영은 `EventFieldValueDao.replaceForFields`(커버 범위 교체)가 맡는다 — 사건 단위
전량 교체 API는 제거했다.

#### R-6. 예약 시트명은 소유자만 가질 수 있다 (4-5를 규칙으로)
`assignSheetName(name, usedNames, ownerOf)`이 단일 소스다. 종전 4-5는 "캐릭터 루프 앞에서
만들어라"라는 **호출 순서 규약**이라 옵션 OFF·데이터 0건이면 무너졌고, 예약 시트 20개 중
2개만 무조건 보호됐다. 이제 세계관 캐릭터 시트는 `ownerOf` 없이 부르므로 어떤 예약명도
차지할 수 없다. **새 예약 시트는 `RESERVED_SHEET_NAMES`에 넣는 것만으로 보호된다.**

시트명 정규화는 `sanitizeSheetNameBase`가 내보내기·가져오기 단일 소스다. POI 제약을 반드시
반영할 것: 중복 판정은 **대소문자 무시**, 앞뒤 **아포스트로피 금지**(둘 다 `createSheet`가
예외로 죽어 백업 파일 자체가 안 만들어진다).

#### R-7. 시트의 정체는 이름이 아니라 헤더가 정한다 — 단, **첫 열 하나로는 부족하다**
`findSheet(spec)`은 정확 일치의 헤더가 spec과 맞을 때만 그것을 쓰고, 아니면 헤더가 맞는
접미사 변형(`이름(2)`)을 찾는다. 이름만으로 잡으면 같은 이름의 세계관 캐릭터 시트를 데이터
시트로 오인하고, 밀려난 진짜 데이터는 아무도 읽지 않는다.

**함정:** 세계관·이름 은행·세력·필드 템플릿·검색 프리셋·목록 프리셋의 첫 열은 전부 '이름'이라
`isValidHeader(row, "이름")`으로는 캐릭터 시트와 구분되지 않는다. 이 검사는 4-6 삭제 가드
(`canRestore`)가 쓰는 바로 그 검사이기도 하다. 그래서 앞쪽 3열이 **자리까지** 일치할 것을
요구하는 `headersMatchSpec`을 쓴다 — 내보내기가 spec 순서대로 쓰므로 진짜 그 시트라면 반드시
일치하고, 남의 시트는 두 번째 열에서 갈린다.

**가드와 조회는 같은 판정을 봐야 한다.** `canRestore`와 `findSheet`가 다른 조회를 쓰면 같은
시트에 "없다"와 "읽었다"가 동시에 성립해 덮어쓰기가 조용히 병합으로 바뀐다
(`resolveSpecSheet`가 두 곳의 단일 판정이다).

**POI의 `getSheet`는 대소문자를 무시한다.** 대소문자만 다른 두 세계관이 같은 시트로 해석되지
않도록 대소문자 구분 일치를 먼저 찾고, 유일할 때만 관대한 조회로 폴백한다.

#### R-8. 스냅샷은 겹치지 않고 이어붙는다 (B-1)
두 엔티티를 잇는 데이터(사건↔캐릭터, 사건↔작품, 세력↔소속, 세력의 자동 관계, 세력↔세력)는
`TrashSnapshot.restorePriority`가 **더 나중인 쪽**이 담는다. 같으면 결정적으로 한쪽이 담는다
(세력 간 관계는 `factionId1` 쪽). 양쪽이 담으면 복원이 중복되고, 먼저 복원되는 쪽은 상대가
아직 없어 **"못 찾았다"는 거짓 경고**를 낸다. 어느 쪽도 담지 않으면 조용히 사라진다.

복원 순서는 세계관(0) → 세계관 부가 데이터(1) → 작품(2) → 세력(3) → 사건(4) → 캐릭터(5) →
상태변화(6)다. 이 순서는 컬럼이 아니라
entityType에서 파생한다 — 저장하면 타입과 어긋날 수 있고, 어긋나면 참조가 조용히 유실된다.

세계관 스냅샷이 담는 것은 "함께 죽지만 **다른 스냅샷이 담지 않는 것**"이다: 필드 정의,
값 라이브러리, 그리고 **삭제되지 않는** 캐릭터·사건이 갖고 있던 이 세계관 필드의 값
(미분류 캐릭터의 보관 값 — N2. 여기서 담지 않으면 필드 정의 CASCADE로 조용히 소멸한다).

#### R-10. payload 한 행은 읽을 수 있는 크기여야 한다
Android의 CursorWindow는 기본 2MB이고 **한 행이 그것을 넘으면 읽지 못한다.** 그 순간 백업은
사라진 것과 같은데, 삭제 화면은 이미 "복원할 수 있습니다"라고 약속한 뒤다 — 4-6이 말하는
"복원할 수 없는 것"을 새로운 방식으로 만드는 길이다.

그래서 **크기가 프로젝트 규모에 비례하는 것은 스냅샷 한 행에 담지 않는다.**
- 다시 만들 수 있는 것은 담지 않는다 — 값 라이브러리의 자동 수확분(AUTO, 무큐레이션)은
  실제 필드값에서 재생성되므로(`harvestUniverses`) 담을 이유가 없다.
- 그래도 자라는 것은 **이어붙임 행으로 쪼갠다**(`TYPE_UNIVERSE_DATA`, `PAYLOAD_BUDGET_CHARS`).
  이어붙임 행은 본체보다 나중에 복원되고, 참조는 전부 자연키·코드로 다시 찾는다(R-1).

도달 경로를 얕보지 말 것: 캐릭터를 전부 '작품 미지정'으로 일괄 변경하면(3탭) 프로젝트 전체의
필드값이 그 세계관의 '고아 값'이 된다 — 재공격의 반증 담당이 실제 UI 경로로 짚어낸 것이다.

#### R-11. 보류 판정은 **참조 종류마다** 키가 있어야 한다 (R-1·R-8의 짝)
"같은 작업이 곧 되살릴 대상은 유실이 아니다"라는 보류 판정(`RestoreTally.pendingCodes`)은
**코드로 조회한다.** 코드가 없는 참조 종류를 `note(res, null)`로 부르면 그 종류만 보류 판정이
**구조적으로 성립하지 않는다** — 조건이 `code != null && code in pendingCodes`이기 때문이다.

필드 정의가 정확히 그랬다. code가 없어(자연키 `(세계관코드, entityType, key)`가 정체성이다)
줄곧 null로 불렸고, 세계관을 지우면 정의도 함께 사라지므로 '전체 복원' 미리보기는
캐릭터·사건의 필드값과 값 라이브러리 엔트리를 **전량** "필드 정의를 찾을 수 없음"으로 예고했다.
실제 복원은 세계관(0)을 먼저 되살려 하나도 잃지 않는데도. **자연키의 세계관 코드가 그 키다.**

새 참조 종류를 스냅샷에 추가할 때 반드시 답할 것: **이 참조의 보류 키는 무엇인가.**
답이 없으면 그 종류는 묶음 복원 미리보기에서 영원히 거짓 유실로 집계된다.
판정 자체는 `RestoreTally`(순수 클래스)로 떼어 `RestoreTallyTest`가 실행 검증한다 —
저장소 안의 private 중첩 클래스로 두면 이 결함처럼 아무도 실행해 보지 못한다.

**보류 자리표시자(`PENDING_ID = 0`)를 중복 판정에 넣지 말 것.** 서로 다른 대상이 전부 같은 0이
되므로, 세지 않으면 거짓 경고의 칸만 '못 찾음'에서 '합쳐짐'으로 옮겨 갈 뿐이다
(`isResolved`가 그 가드다).

#### R-9. 정리도 복원도 '삭제 작업' 단위다 (B-14, R-3의 확장)
**묶기 전에 "이 묶음에 실리면 안 되는 것"부터 정할 것.** `operationKind`로 삭제와
편집 직전 백업을 가르는 이유가 이것이다 — 지워진 적 없는 항목에 '전체 복원'을 내주면
거짓 안내이자 원클릭 복제가 된다(B-2).

`TrashSnapshot.operationId`가 한 번의 삭제가 만든 스냅샷을 묶는다. 한도는 항목 30개가 아니라
**작업 30건**(`MAX_OPERATIONS`)이고, 한 작업은 **통째로 남거나 통째로 사라진다.** 반쪽으로
남으면 "세계관은 되살아나는데 캐릭터 71명은 없는" 백업이 되는데 그것은 복원이 아니라 유실이다.

- 인스턴스 하나 = 작업 하나다. R-3의 "한 작업은 하나의 인스턴스를 공유해야 한다"가 그대로
  강해진 형태이고, 보호도 id 집합이 아니라 작업 키로 한다.
- 구버전 행(`operationId = null`)은 자기 자신만의 작업이다(`row:<id>`). **백필하지 않는다** —
  null이 이미 "독립된 삭제"라는 올바른 의미를 갖는다.
- SQL 표현 `COALESCE(operationId, 'row:' || id)`와 Kotlin의 `TrashSnapshot.operationKey`는
  **같은 문자열을 만들어야 한다.** 어긋나면 보호 목록이 빗나가 방금 만든 백업을 태운다.
  `tools/verify_room_migration_43.py`가 실제 SQLite로 이 일치를 검사한다.
- '작업 전체 복원'은 코드를 재발급한 엔티티를 뒤 항목이 찾도록 세션(`RestoreSession`)을 공유한다.
  없으면 뒤 항목이 옛 코드로 조회해 **살아 있던 남의 엔티티**에 붙는다 — R-1이 막으려는 오배정이
  복원 안에서 재현된다(엑셀 덮어쓰기로 같은 코드가 되살아난 뒤 휴지통을 복원하면 실제로 일어난다).
- 그룹 미리보기는 "같은 작업이 곧 되살릴 코드"를 알고 계산해야 한다. 모르면 순서만 지키면 될 일을
  유실로 예고한다(사실과 다른 경고).

#### R-12. 스냅샷의 종류는 인스턴스가 아니라 **호출**이 정한다 (B-2/B-21)
R-3/R-9의 "한 작업 = 한 인스턴스" 때문에 **삭제와 편집 백업이 같은 인스턴스를 쓰는 경로가
실재한다**(엑셀 임포트: 세계관 이동 백업과 '엑셀에 없는 항목 삭제'). 종류를 인스턴스 기본값에
맡기면 편집 백업이 delete로 각인되어 복원이 복제가 된다. `snapshotCharacter(character, imagePaths,
kind, revertScope)` — 종류와 파괴 범위는 그 호출이 아는 사실이므로 호출부가 명시한다.

- **편집 백업은 `revertScope`(그 편집이 실제 파괴한 갈래)를 함께 기록한다.** 경로마다 파괴 범위가
  다르므로(작품 이동: 필드값+소속 / 편집 화면 저장: +캐릭터 행 / 라이브러리 삭제: 필드값+상태변화)
  합집합으로 되돌리면 원래 편집이 손대지 않은 것을 지운다. 기록이 없는 구버전은
  `LEGACY_REVERT_SCOPE`(필드값)만 — 덜 되돌리는 것은 고지로 메울 수 있지만 더 지우는 것은 못 메운다.
- **되돌리기는 새 안전망이므로 스스로 취소 경로를 만든다**: 덮기 직전 상태를 편집 백업으로 한 번 더
  스냅샷한다(R-4). 대상 선정은 code 단독 — id 폴백을 재사용하면 재발급된 옛 id의 남을 덮는다(R-1).
- **묶음 표시는 (작업, 종류) 단위, 정리는 작업 단위.** `TrashGrouping`이 가르고, prune은 그대로
  작업 통째다(R-9 유지).
- 판정은 전부 `RestoreModes`(순수 클래스)에 있다 — `RestoreModeTest`가 실행 검증한다(R-11의 교훈).

#### R-13. 집계의 셀 단위가 다르면 함수를 나눈다 (B-4)

교차표의 셀이 "무엇의 개수"인지는 표 전체의 의미를 정한다. 캐릭터 수와 사건 수를 한 표에
섞으면 어떤 셀도 읽을 수 없게 되므로, **축마다 계산 함수를 따로 둔다**(공통 조립만 공유).

- 축이 섞인 요청은 **계산하지 않고 이유를 돌려준다** — `CrossAxisResolution.Mismatch`는
  걸린 필드 이름까지 담는다. `null`을 돌려주고 화면이 아무 반응도 하지 않는 것이
  정확히 B-4가 고친 결함이다. **계산 못 하는 것과 조용히 안 하는 것은 다르다.**
- 판정은 **두 겹**이다: UI가 애초에 섞을 수 없게 막고(축 선택기), 계산이 다시 확인한다.
  UI만 막으면 다른 호출부가 생겼을 때 조용한 실패가 되살아난다.
- **모수는 축 전체로 잡는다.** 필드가 속한 세계관으로 좁히면 미분류 캐릭터(novelId=null)나
  세계관이 지워진 사건(universeId=null)이 값을 가진 채 표에서 빠진다. 둘 다 정상 상태다 —
  *모수가 넓은 것은 부정확할 뿐이고, 셀이 빠지는 것은 틀린 것이다.*

#### R-14. 목록에서 잘라낸 것은 개수로 존재를 알린다 (B-5)

카드·요약처럼 자리가 한정된 표시에는 상한이 필요하다(규모). 그러나 상한은 **감추는 장치가
아니라 접는 장치**다 — 잘라냈으면 남은 개수를 반드시 함께 표시한다.

- 사용자가 **직접 끈** 항목은 '잘린 것'이 아니다. 초과 개수에 세지 않는다(자율성 우선).
- 상한 숫자는 **상수가 단일 소스**다. 안내 문구에 숫자를 박아 두면 상한을 옮길 때 문구가
  거짓이 된다 — 문구는 상수로 채운다.
- 목록에 얹는 표시 데이터는 **어댑터 바깥 맵이 아니라 항목 자체에 담는다.** 맵으로 두면
  값이 바뀌어도 항목이 같아 보여 DiffUtil이 못 잡고 목록 전체를 다시 그려야 한다.
  그리고 그 전체 갱신이 **드래그 재정렬 중이면 사용자의 순서를 지운다.**

#### R-15. 머지된 카드가 약속한 범위 = 그 카드에서 뻗는 모든 경로의 범위 (로드맵 3)

인사이트 목록은 같은 `(key, type)` 필드를 세계관 통합으로 **한 장**에 보여준다(Pre-Analysis
Merge). 그 카드에서 뻗어 나가는 것 — 차트 조각 드릴다운, 하위 그룹 분석, 필드 선택 목록,
'현재 필드 제외' — 은 **전부 같은 머지 축**을 써야 한다. 하나라도 대표 def 하나로 좁히면
사용자가 본 수치와 다른 답이 조용히 나온다.

- 단일 소스는 `FieldInsightResult.mergedFieldDefIds`이고 **순서가 계약**이다:
  첫 원소는 항상 `fieldDefinition.id`(= 그룹 primary)이며, **파싱 기준 def**다.
  차트가 그룹 전체를 primary의 config·값 라이브러리 resolver로 파싱했으므로, 다르게 파싱하면
  같은 값이 다른 칸으로 떨어져 수치가 어긋난다.
- **제외도 그룹 단위다.** 대표 id 하나만 빼면 형제 세계관 def가 "같은 이름의 다른 항목"으로
  목록에 남고, 고르면 그 세계관에 값이 없어 빈 분포가 된다.
- 머지 조회는 한 엔티티가 여러 def·다중값으로 **여러 번 매칭될 수 있다.** 차트 조각은
  엔티티 수를 세므로 목록도 엔티티당 1회만 계수해야 한다.
- **화면마다 머지 축이 다를 수 있다.** 레거시 필드 분석 화면은 def 하나 단위로 분포를 내므로
  드릴다운도 def 하나가 맞다. *카드를 만든 함수가 무엇을 합쳤는지가 그 화면의 축이다* —
  머지 id를 무조건 넘기는 것도 틀린 답이다.

#### R-16. 계산 필드는 저장 행이 없다 — 저장 값을 읽는 모든 경로가 그것을 알아야 한다

CALCULATED 필드는 `character_field_values`/`event_field_values`에 행이 없고
`computeAllCalculatedValues`/`computeAllEventCalculatedValues`가 값을 만든다. 그래서
`s.fieldValues`·`s.eventFieldValues`를 직접 읽는 경로는 **계산 필드를 조용히 빈 값으로 취급**한다.

**사용자가 그 필드를 고를 수 있는 화면이라면 그 경로는 계산값을 합쳐야 한다.** 인사이트 카드는
합쳤고(`:1151`) 사건 축 교차분석도 합쳤는데(`:1493`) 캐릭터 축 교차분석과 하위 그룹 분석은
안 합쳐서, **자기 카드에서는 분포가 그려지는 필드가 다른 화면에서만 항상 비었다**(S-8·S-19).

- **한 축만 고치지 말 것.** 캐릭터/사건은 항상 짝이다 — 한쪽을 고치면 다른 쪽 대칭 함수를
  같은 커밋에서 확인한다. S-8은 정확히 이 짝 중 한쪽만 고쳐져 남아 있던 것이다.
- 선택 목록에서 계산 필드를 **숨기는 것은 수리가 아니다**(원칙 03 위반). 목록이 약속한
  필드는 실제로 분석되게 만든다.
- 예외를 두려면 그 이유가 코드에 적혀 있어야 한다(미배정 스코프의 의도적 제외 — B-30).

#### R-17. 빈 결과는 사유를 말한다 — "못 찾음"과 "없음"은 다르다

조회 대상(필드 정의 등)을 **못 찾은 것**과 조건에 맞는 데이터가 **없는 것**은 사용자에게
전혀 다른 사실이다. 전자를 `emptyList()`로 돌려주면 "0명입니다"라는 **거짓 사실**이 된다.

- 대상을 못 찾으면 **null**(또는 사유 객체)을 돌려주고 호출부가 고지한다 —
  R-13의 `CrossAxisResolution.Mismatch`와 같은 취지를 조회 함수로 넓힌 것이다.
- 화면 쪽 `if (x.isEmpty()) return`은 **표시할 것이 없다**가 아니라 **왜 없는지**를 그려야 한다.
  버튼을 눌렀는데 아무 일도 일어나지 않는 것은 사용자에게 고장과 구분되지 않는다.
- 근본 수리와 고지는 둘 다 필요하다. 고지는 근본 수리를 대신하지 못하고(그러면 방편식 패치),
  근본 수리도 "진짜로 데이터가 없는 경우"를 없애지 못한다.

#### R-18. 설정은 '자동 선택'에만 적용된다 — 사용자가 고른 것은 계산한다 (로드맵 4)

`FieldStatsConfig.enabled`('통계에 포함') 같은 **표시/집계 설정**은 판정 지점이 셋으로 갈린다.
`StatsFieldPolicy`가 단일 소스이고 규칙은 하나다:

- **앱이 스스로 필드를 고르는 경로**(목록·자동 감지)는 설정을 따른다.
- **사용자가 이미 고른 필드의 계산**은 설정을 보지 않는다 — 고를 수 있는데 빈 결과가 나오면
  그것이 조용한 실패다(R-17).
- 그 사이의 **자동 확장**(고른 것은 하나인데 계산은 형제까지 합산)은 형제만 설정을 따르고,
  **고른 def는 언제나 첫 원소로 남긴다**(R-15의 파싱 기준 계약).

같은 성격의 목록 둘이 반대로 동작하고 있다면 그 자체가 결함이다 — 하나로 정하고 **뒤집은 쪽의
근거를 그 자리에 적을 것**(종전 결정에는 대개 이유가 있었다).

#### R-19. 상한은 표시 계층의 관심사다 (R-14의 실행 규칙)

계산은 **전량**을 돌려주고, 자르는 일은 화면이 표시 직전에 한 번만 한다.
계산이 자르면 잘린 개수뿐 아니라 **비율의 분모까지 함께 소실**되어 소비처가 참값을 복원할 수 없다
(각 화면이 자기 나름대로 분모를 재구성하면 화면마다 다른 %가 나온다).

- 잘린 묶음은 접어서 보이되(`기타 N종 M건`) **누르면 그 값들의 목록**이 나와야 한다.
  개수만 알리고 내용을 못 보는 것은 R-14를 절반만 지키는 것이다.
- 차트에도 같은 '기타' 조각을 넣는다. 조각 합이 전체가 아니면 **그림과 숫자가 다른 말**을 한다.

#### R-20. 라벨은 매칭 키가 아니다 (S-16)

차트 조각에서 뻗는 조회는 **라벨 문자열이 아니라 그 조각을 만든 규칙**을 받는다
(`FieldValueMatchSpec`). 라벨이 값 그대로인 분포에서는 문자열 비교가 우연히 동작하지만,
라벨이 계산 결과인 분포(수치 구간 등)에서는 **어떤 입력에서도 일치하지 않는다.**

- 분포를 만든 쪽이 스펙을 실어 보낸다. 구간 생성은 `NumericBinning`이 단일 소스이고
  경계 규칙(마지막 구간만 상한 포함)도 거기 하나뿐이다.
- 우연히 동작하던 경로도 같은 스펙 타입으로 통일한다 — 한쪽만 타입화하면 다시 갈라진다.
- 구간 라벨은 **유일해야 한다**. 폭이 좁아 정수 라벨이 겹치면 맵 키가 충돌해 뒤 구간이
  앞 구간을 덮어쓰고 건수가 조용히 사라진다.

#### R-21. 계산기의 파생 상태는 인자에서만 나온다 (S-18 수리의 선행 조건)

스냅샷을 받아 계산하는 클래스가 **로딩 함수에서만 채워지는 가변 필드**를 갖고 있으면,
그 필드에 의존하는 경로는 다른 스냅샷에서 조용히 다르게 동작하고 **순수 테스트에서는 죽은 코드**가
된다(고쳐도 고쳐졌는지 확인할 수 없다). 파생 데이터는 스냅샷 인자에서 만들고, 비용이 문제면
**스냅샷 동일성(===) 캐시**를 쓴다.

- 캐시 게시는 `@Volatile` 값 먼저·키 나중. 읽는 쪽은 키를 먼저 본다.
- 값 하나마다 불리는 경로에는 잠금을 걸지 않는다 — 불변 값이면 두 번 계산해도 무해하다.

#### R-22. 서식이 곧 값의 정체성인 문자열은 로케일을 고정한다 (로드맵 4 재공격)

계산값을 문자열로 만들어 **분포의 키·드릴다운 매칭 키·되파싱 대상**으로 쓴다면 그 서식은
표시 규칙이 아니라 **데이터 규칙**이다. 기본 로케일로 만들면 소수점이 콤마인 환경에서
같은 값이 다른 키가 되고 되파싱이 실패해 그 항목이 집계에서 조용히 사라진다.
사람에게 보이기만 하는 문구(비율 %, 설명문)는 그대로 기본 로케일을 쓴다 — 구분해서 정할 것.

## 2. 검증 환경 (Android 빌드 불가)

`dl.google.com`이 차단되어 `./gradlew`는 무엇을 하든 실패한다. 구축 절차와 필요한 jar 목록은
`docs/excel_roundtrip_audit_2026-07.md` 3장 그대로이며 이번 세션에서도 그대로 재현됐다.

```
JARS_DIR=/path/to/jars tools/setup_jvm_env.sh        # jar 수집 + androidx 스텁 (세션마다 1회)
JARS_DIR=/path/to/jars tools/run_jvm_tests.sh        # 순수 JVM 단위 테스트 — 현재 297건 통과
JARS_DIR=/path/to/jars tools/differential_compile.sh  # 차분 컴파일 (메시지 단위로 비교할 것)
python3 tools/verify_room_migration.py                # 41→42 하네스 35건
python3 tools/verify_room_migration_43.py             # 42→43 하네스 39건 (B-1에서 추가)
tools/check_resources.sh                              # strings.xml 중복 name 등
```

**`tools/setup_jvm_env.sh`가 이 준비를 전부 한다**(jar 수집 + 스텁 컴파일). 세션마다 스크래치패드가
비므로 매 세션 1회 돌린다. 스텁에서 막히기 쉬운 세 지점(ForeignKey 상수 / @Ignore의 PROPERTY_GETTER /
@Relation.associateBy가 KClass여야 하고 LiveData는 `open var value` 하나여야 함)은 스크립트 주석에 있다.

`JARS_DIR`에는 2장 목록의 jar과 함께 **androidx 스텁을 컴파일한 `out-room/`** 이 있어야 한다
(`androidx.room` 어노테이션 + `androidx.lifecycle.LiveData`). `@Ignore`는
`AnnotationTarget.PROPERTY_GETTER`까지 받아야 `Character.displayName`이 컴파일된다.

**차분 컴파일이 못 보는 것을 보는 방법(이번 세션에서 가장 값졌다):** Room 런타임이 없는
차분 컴파일은 DAO 반환 타입을 해석하지 못해 그 위의 모든 멤버 접근이 "unresolved"로 뜬다.
`TrashRepository` 같은 신규 대형 파일은 **작은 스텁을 만들어 실제 클래스패스로 컴파일**하면
진짜 타입 검사가 된다 — `AppDatabase`(DAO 접근자만), `RoomDatabase`+`withTransaction`,
`android.util.Log`, `GsonTypes`/`ImageOwnershipGuard`/`FieldValueLibraryRepository` 스텁이면
`data/model` + `data/dao` + 대상 저장소가 통째로 컴파일된다(이번엔 216 클래스, 오류 0).
이 방법으로 차분 컴파일이 "새 오류"로 표시한 40여 건이 전부 노이즈임을 증명했다.

**하네스 전용 스텁은 이제 저장소 안에 있다(`tools/jvm-stubs/`).** `StatsHarnessStubs.kt`가
`NovelCharacterApp`과 그것이 노출하는 DAO·저장소의 **시그니처만** 선언하고,
`AndroidLogStub.kt`가 `android.util.Log` 자리를 채운다. Gradle 소스셋 밖이라 실제 빌드와
충돌하지 않는다. `loadSnapshot`이 부르는 메서드가 사라지거나 시그니처가 바뀌면
**하네스 컴파일이 깨진다 — 그것이 목적이다.**

`StatsDataProvider`가 이 방식으로 실행 검증 대상이 됐다(생성자 대신 `loadSnapshot(app)`이
앱을 받는다). 앱 의존이 로딩 함수 하나뿐인 대형 계산기는 같은 방법으로 옮겨올 수 있다.

이번 세션에서 얻은 검증 요령 두 가지:

- **차분 컴파일은 파일 단위가 아니라 메시지 단위로 비교하라.** 신규/대폭 수정 파일은 파일 경로가
  키에 섞이면 모든 오류가 "새 것"으로 보인다. `sed -E 's/^[^:]+:[0-9]+:[0-9]+: (error: .*)$/\1/'`로
  경로를 지우고 `comm -13`하면 실제 신규 메시지만 남는다. `unresolved reference 'let'`,
  `should be called only from a coroutine` 등은 기준선에 수십~수백 건 있는 노이즈 클래스다.
- **차분 컴파일이 못 보는 구문은 떼어내 실제 클래스패스로 컴파일하라.** 이번에는
  `withTransaction` 람다의 캡처 var 대입 + 바깥 elvis, suspend 람다를 받는 제네릭 헬퍼,
  루프 안 조건부 `continue`를 이 방법으로 확인했다(참고: Kotlin 2.0에서 **inline 람다 안의
  `continue`는 컴파일 오류**다 — `?: run { ... continue }` 형태를 쓰지 말 것).
- **POI 제약은 실제 POI로 확인하라.** 규칙만 검사하는 테스트는 "내보내기가 예외로 죽는" 경로를
  잡지 못한다. `SheetNameAssignmentTest`가 적대적 이름 20개로 실제 `createSheet`를 돌린다.

**주의:** 이번 세션은 스키마를 건드리지 않았다(상태변화 스냅샷은 `entityType` 문자열 값을
하나 늘렸을 뿐 컬럼 변경이 없다). 따라서 v43 그대로이며 재검증이 필요 없다.

### 3-2. B-1 산출물의 실기기 확인 — ✅ 1~5번 전부 통과

1. **세계관 삭제 → 전체 복원.** 작품 2개·캐릭터 10명·세력 2개·사건 5건이 있는 세계관을 지운다.
   휴지통에 "세계관 'X' 삭제 · 항목 20개" 머리글 하나와 그 아래 항목들이 **세계관 → 작품 →
   세력 → 사건 → 캐릭터 순으로** 보여야 한다. '전체 복원'을 누르면 전부 되살아나고 캐릭터의
   작품 소속·세력 소속·사건 연계가 그대로여야 한다.
2. **보관 한도가 묶음을 자르지 않는가 (B-14).** 위 상태에서 캐릭터를 하나 더 지운다.
   종전 규칙이면 20개 묶음이 잘렸다 — 이제 묶음이 그대로 남아야 한다.
3. **세력만 개별 복원.** 세계관을 먼저 지우고 세력 행만 '복원'을 누르면
   "세계관이 없어 복원할 수 없습니다" 다이얼로그가 뜨고 **항목은 휴지통에 남아야** 한다.
   그다음 세계관을 복원하고 세력을 다시 복원하면 성공해야 한다.
4. **출생 사건 삭제 → 복원.** 캐릭터에 출생 사건을 만들고 연표에서 길게 눌러 삭제한 뒤 복원한다.
   캐릭터의 `__birth` 상태변화가 돌아오고, "파생 필드값(생년·나이)은 덮어쓰지 않았다"는
   안내가 떠야 한다.
5. **엑셀 왕복 후 복원(오배정 확인).** 세계관을 지운 뒤, 그 세계관이 들어 있는 엑셀을
   **덮어쓰기**로 가져와 같은 코드의 세계관을 되살린다. 그 상태에서 휴지통의 '전체 복원'을
   누르면 사본 세계관이 생기고, **복원된 캐릭터·세력·사건은 원본이 아니라 사본에 붙어야 한다.**

### 3-3. 앞선 세션(N1~N3) 산출물의 실기기 확인 — ✅ 전부 통과
스키마 무변경이라 위험도는 낮다. 값진 확인 순서:

1. **N2** — 필드값이 있는 캐릭터를 편집 화면에서 열어 작품을 '작품 없음'으로 바꿔 저장한다.
   "화면에 없는 필드값 N개는 지우지 않고 보관했습니다" 스낵바가 뜨고, 상세 화면에서 그 값들이
   그대로 보이는지 확인한다. 다시 원래 작품에 배정하면 폼에 값이 채워져야 한다.
2. **N1** — 캐릭터를 몇 명 삭제해 휴지통에 넣고, 엑셀로 전체 내보내기 → **덮어쓰기**로 다시
   가져온 뒤(세계관·필드 정의 포함) 휴지통에서 복원한다. 종전에는 필드값·관계·세력 소속이
   전부 생략됐다. 이제 "참조 N건은 id가 바뀌었지만 코드로 다시 연결했습니다"가 떠야 한다.
3. **N1 정리 보호** — 캐릭터가 30명 넘게 소속된 세계관을 삭제한 뒤 휴지통을 연다.
   종전에는 30개만 남고 나머지는 이미지 파일까지 사라졌다. 이제 전부 남아야 한다.
4. **N3 — 예약 시트명 충돌.** ("내보내기 → 가져오기"는 **엑셀 파일**을 말한다. 설정의
   *엑셀로 내보내기*로 .xlsx를 만들고, 그 파일을 다시 *엑셀에서 가져오기*로 읽는 것이다.)

   *무엇을 보는 확인인가:* 엑셀 파일에는 `세력`·`미분류 캐릭터` 같은 **앱이 예약한 시트 이름**이
   있고, 세계관마다 자기 이름으로 된 시트도 하나씩 생긴다. 세계관 이름이 하필 예약 이름과
   같으면 두 시트가 한 이름을 두고 부딪친다. 종전에는 먼저 쓴 쪽이 이겨서 **진짜 '세력' 시트가
   세계관 시트로 덮여 세력이 통째로 사라졌다.**

   *순서:* ① 세계관 하나의 이름을 정확히 `세력`으로 바꾼다. **그 세계관에 작품 1개와 그 작품
   소속 캐릭터 1명 이상이 반드시 있어야 한다** — 번호가 붙는 시트는 세계관의 *캐릭터 시트*인데,
   캐릭터 없는 세계관의 시트는 아예 만들어지지 않아(`ExcelExporter.kt`의
   `if (universeChars.isEmpty()) continue`) 충돌 자체가 일어나지 않는다. 캐릭터가 작품
   미지정이면 '미분류 캐릭터' 시트로 빠지므로 역시 안 된다. 세력도 1개 이상 있어야 예약
   `세력` 시트가 생겨 양쪽을 다 확인할 수 있다.
   ② 엑셀로 내보낸다. ③ **만들어진 .xlsx를 열어 시트 탭 이름을 눈으로 본다** —
   예약된 `세력` 시트는 그대로 있고, 캐릭터 시트는 `세력(2)`처럼 번호가 붙어 있어야 한다.
   ④ 그 파일을 덮어쓰기로 다시 가져온다. ⑤ 세력 목록·세계관·그 캐릭터가 **전부** 원래대로여야
   한다. ⑥ 세계관 이름을 `미분류 캐릭터`로 바꿔 ①~⑤를 한 번 더 한다.

   *2026-07-26 1차 시도:* 캐릭터 없는 세계관으로 진행되어 `(2)` 시트가 생기지 않았다(정상 —
   충돌이 없었을 뿐). *재시도:* 전제 조건을 채워 진행, **통과** — 접미사 배정과 왕복 복원이
   실기기에서 정상 동작 확인됨. 3-3은 이것으로 4건 전부 실기기 확인 완료다.

   *그냥 내보내고 덮어쓰기했을 때 원래대로인 것은 이 확인이 아니다* — 이름을 예약 이름과
   똑같이 만들어 **충돌을 일부러 일으키는 것**이 이 항목의 전부다. 충돌이 없으면 종전 코드도
   통과한다.

### 3-4. 이번 세션 산출물의 실기기 확인 — ✅ 전부 통과 (2026-07-26)

1. **유령 유실 예고가 사라졌는가.** 필드값을 많이 채운 캐릭터가 여럿 있는 세계관을 지운 뒤
   휴지통에서 **'전체 복원'**을 누른다. 확인 다이얼로그에 "필드값 N개(필드 정의를 찾을 수 없음)",
   "필드 데이터(값 라이브러리) 항목 N개", "보관 중이던 필드값 N개"가 **더 이상 뜨지 않아야**
   한다. 복원 후 캐릭터의 필드값이 그대로인지도 함께 본다(종전에도 값은 멀쩡했다 — 경고만
   거짓이었다).
2. **진짜 유실은 여전히 예고하는가(반대 방향).** 세계관을 지운 뒤, **캐릭터 한 명만** 개별
   '복원'을 누른다. 이때는 세계관이 없으므로 "필드값 N개(필드 정의를 찾을 수 없음)"가
   **떠야 한다** — 사실이기 때문이다. 여기서 경고가 사라졌다면 무음 유실로 바뀐 것이다.
3. **상태변화 삭제 → 복원.** 캐릭터 상세의 상태변화 목록에서 한 줄을 눌러 '삭제'한다.
   휴지통에 "상태변화 · `__birth → 1200`" 형태의 항목이 생기고, 복원하면 그 이력이 목록에
   돌아와야 한다. 출생·사망 이력이면 "파생 필드값(생년·나이)은 덮어쓰지 않았다"는 안내가 뜬다.
4. **상태변화가 중복으로 쌓이지 않는가.** 출생 사건을 연표에서 삭제한다. 휴지통에는 **사건
   항목 하나만** 생겨야 한다 — 상태변화 항목이 따로 또 생기면 파생 정리 경로가 스냅샷을
   남기고 있는 것이고, 복원하면 이력이 두 벌이 된다.
5. **캐릭터를 먼저 지운 뒤 상태변화만 복원.** 상태변화를 지우고 → 그 캐릭터를 지운 다음 →
   상태변화 행만 '복원'을 누른다. "캐릭터가 없어 복원할 수 없습니다" 다이얼로그가 뜨고
   **항목은 휴지통에 남아야** 한다. 캐릭터를 먼저 복원하면 그때는 성공해야 한다.
6. **캐릭터 화면에서 사건 편집·삭제.** 캐릭터 상세의 사건 목록에서 한 건을 **누르면** 편집
   다이얼로그가 열리고, **길게 누르면** 편집 / 이 캐릭터에서 연결 해제 / 삭제가 나와야 한다.
   - '연결 해제'는 그 캐릭터의 목록에서만 사라지고 연표 탭에는 사건이 남아야 한다.
   - '삭제'는 다른 캐릭터도 걸려 있으면 **몇 명이 함께 잃는지** 확인 문구에 나와야 하고,
     지운 뒤 휴지통에서 복원하면 참가 캐릭터 연결까지 돌아와야 한다.
   - 출생 사건을 이 경로로 지우면 연표 탭에서 지웠을 때와 **똑같이** 동작해야 한다
     (`__birth` 이력이 함께 정리되고, 복원하면 함께 돌아온다).

### 3-5. 우선순위 1 산출물(B-2·B-21·B-3)의 실기기 확인 — ⬜ 미검증

1. **편집 백업 되돌리기.** 필드값·태그·세력 소속이 있는 캐릭터를 편집 화면에서 다른 세계관의
   작품으로 옮겨 저장한다("보관했습니다" 스낵바 = 편집 백업 생성). 그 뒤 **태그를 하나 더 붙이고
   관계를 하나 만든다.** 휴지통에서 그 항목의 '복원'을 누르면 "되돌리는 것입니다 — 덮어써지는
   갈래 목록" 동의 다이얼로그가 떠야 하고, 진행하면 **사본이 생기지 않고** 원본이 옛 세계관
   상태로 돌아가야 한다. **나중에 붙인 태그와 관계는 남아 있어야 한다**(교체 범위 밖).
   휴지통에는 "덮기 직전 백업"이 새로 생겨 있어야 하고, 그것을 복원하면 다시 이동 후 상태로
   돌아와야 한다(왕복).
2. **엑셀 임포트의 세계관 이동 백업.** 캐릭터의 작품을 다른 세계관 작품으로 바꾼 엑셀을
   가져온다(경고: "세계관 이동 감지 — 휴지통에 스냅샷 보관"). 휴지통에서 그 항목이 **'편집 직전
   백업'으로 표시**되고(종전에는 삭제로 표시), 복원 시 1번과 같은 되돌리기 동의가 떠야 한다.
   같은 임포트가 '엑셀에 없는 항목 삭제'도 했다면 삭제 묶음 머리글에 편집 백업이 **섞여 있지
   않아야** 하고, 삭제 묶음의 '전체 복원'이 편집 백업을 건드리지 않아야 한다.
3. **상태변화 중복 차단.** 상태변화 이력을 삭제 → 같은 캐릭터·같은 필드로 새 이력을 만든 뒤
   휴지통에서 복원한다. "같은 이력이 이미 있어 복원하지 않았습니다" 다이얼로그가 뜨고 **항목이
   휴지통에 남아야** 한다(종전에는 사본이 생겼다). 기존 이력을 지운 뒤 다시 복원하면 성공해야 한다.
4. **이름 은행 링크 왕복.** 이름 은행에서 이름을 골라 캐릭터를 만들고(사용 표시 켜짐), 캐릭터를
   삭제한다(사용 표시 풀림 확인). 휴지통에서 복원하면 **사용 표시가 그 캐릭터로 되돌아와야** 한다.
   반대로: 삭제 후 그 이름을 **다른 캐릭터에 배정**한 뒤 복원하면 빼앗지 않고 "이름 은행 사용
   표시 1개" 유실 고지가 떠야 한다.
5. **사본 복원의 무경고.** 캐릭터를 지우고 같은 code가 살아나게 엑셀 덮어쓰기로 되살린 뒤
   휴지통에서 복원한다(사본 생성 경로). 결과에 "이름 은행 사용 표시 N개" 유실이 **뜨지 않아야**
   한다 — 원본이 링크를 쥐고 있는 것은 유실이 아니다.

### 3-6. 우선순위 2 산출물(B-4·B-5)의 실기기 확인 — ⬜ 미검증

> 이 세션은 Android 빌드가 불가능하므로 집계 규칙만 순수 JVM으로 실행 검증했다.
> **화면 동작은 사용자 확인이 필요하다.**

**B-4 — 교차분석 사건 축**

1. **사건 축이 실제로 표를 만든다.** 사건 필드를 2개 이상 만들고(예: '회차' TEXT, '사건 유형'
   SELECT — 둘 다 통계 포함 켜기) 사건 여러 건에 값을 채운다. 통계 → 필드 인사이트 → '교차 분석'
   → **'집계 축'에서 '사건 필드'** 선택 → 두 필드를 골라 실행. 표가 나오고 캡션 첫 줄이
   **"셀 값 = 해당 조합을 가진 사건 수"** 여야 한다. 제목 앞에 "사건 ·"이 붙는다.
   *(종전 결함: 사건 필드를 고르고 실행하면 아무 일도 일어나지 않았다.)*
2. **캐릭터 축은 종전대로.** 축을 '캐릭터 필드'로 두고 실행하면 예전과 같은 표가 나오고
   캡션은 "셀 값 = 해당 조합을 가진 캐릭터 수"여야 한다.
3. **축이 하나뿐이면 선택기가 숨는다.** 사건 필드가 0~1개인 세계관에서는 '집계 축' 줄이
   보이지 않고 캐릭터 필드만 실린다. 양쪽 다 2개 미만이면 "같은 축의 ... 2개 이상 필요합니다"
   안내가 뜬다.
4. **필터도 같은 축.** 사건 축에서 필터 필드 스피너에 **캐릭터 필드가 실리지 않아야** 한다.
   필터를 걸면 캡션이 "(N/M건)"으로 나온다(캐릭터 축은 "명").
5. **미분류 캐릭터가 표에 남는다.** 캐릭터의 작품을 '없음'으로 두고 필드값을 채운 뒤 캐릭터 축
   교차분석을 실행하면 그 캐릭터가 **표에 포함**돼야 한다(자기 재공격이 잡은 결함).
6. **세계관 통합 고지.** 같은 필드 key를 쓰는 세계관이 2개 이상이면 캡션에
   "세계관 N개의 같은 필드를 합산했습니다"가 나온다.

**B-5 — 연표 카드 사건 필드값**

7. **값이 목록에 보인다.** 사건에 필드값을 채우고 연표로 돌아오면 카드에 `필드명: 값` 줄이
   보여야 한다(사건을 열지 않고). 값을 지우면 줄도 사라진다.
8. **표시 끄기.** 필드 관리 → 사건 필드 탭 → 필드 편집 → **'목록 카드에 값 표시'** 를 끄면
   그 필드만 카드에서 사라진다(다른 필드는 남는다). 캐릭터 필드 편집 화면에는 이 스위치가
   **보이지 않아야** 한다.
9. **초과 개수 고지.** 한 사건에 값 있는 표시 필드를 5개 이상 만들면 카드에 4줄까지 보이고
   그 아래 **"+N개 더 (열어서 확인)"** 가 떠야 한다.
10. **묶음 보기에는 안 나온다.** 줌을 낮춰(10년/100년 묶음) 머리글 카드가 되면 필드값 줄이
    보이지 않아야 한다(재활용된 뷰의 잔상 확인).
11. **재정렬이 안 깨진다.** 연표 재정렬 모드에서 사건을 끌어 옮긴 뒤 모드를 끄면 **끌어 옮긴
    순서가 저장**돼야 한다(자기 재공격이 잡은 결함 — 요약 조회가 끼어들어 순서를 지웠다).

### 3-7. 이번 세션 산출물(S-6·S-12)의 실기기 확인 — ⬜ 미검증

> 집계·병합 규칙은 순수 JVM으로 실행 검증했다(481건). **화면 동작은 사용자 확인이 필요하다.**

**S-6 — 사건 필드값 보호**

1. **작품 소실 사건의 편집이 값을 지우지 않는다.** 사건 필드값(회차 등)을 채운 사건이 있는
   작품을 삭제한다(사건은 남는다). 그 사건을 연표에서 열면 **필드 입력란이 여전히 보이고
   기존 값이 채워져 있어야 한다**(세계관 폴백). 설명만 고치고 저장 → 다시 열면 필드값이
   그대로여야 한다. *(종전: 열면 필드란이 사라지고, 저장하면 값 전량이 소리 없이 삭제됐다.)*
2. **작품 체크 해제 저장이 값을 지우지 않는다.** 정상 사건을 열어 작품 체크를 전부 해제하고
   저장한다. 필드 섹션은 폴백으로 계속 보이므로 값이 그대로 저장되고, 연표 필터에서 그
   세계관을 골랐을 때 사건이 **여전히 그 세계관에 남아 있어야 한다**(universeId 보존 —
   종전에는 세계관 연결도 말없이 끊겼다).
3. **다른 세계관으로 이동 시 보존 고지.** 사건을 세계관 X 작품에서 세계관 Y 작품으로 바꿔
   저장한다. X 필드값은 지워지지 않고 **"화면에 없는 사건 필드값 N개는 지우지 않고
   보관했습니다"** Toast가 떠야 하며, 작업 이력에도 같은 줄이 남아야 한다. 작품을 X로
   되돌리면 값이 다시 보여야 한다(문구의 교정 경로 확인).
4. **빠른 저장(로딩 미완 창).** 필드가 많은 세계관의 사건을 열자마자(필드 섹션이 그려지기
   전에) 즉시 저장을 누른다. 저장 후 다시 열면 필드값이 **하나도 사라지지 않아야 한다.**
   4-1. **회전 변형(재공격 F1·F3).** ① 필드값 있는 사건을 열자마자 즉시 회전 → 폼에 기존
   값이 채워져 렌더되어야 한다(공란 렌더면 결함). ② 사건을 열어 필드값을 고치고 → 회전 →
   재생성 직후 곧바로 저장 → 다시 열면 **고친 값이 저장돼 있어야** 하고, "보관했습니다"
   토스트는 뜨지 않아야 한다.
5. **비움 의도는 존중된다.** 사건을 열어 필드값 하나를 지우고 저장하면 그 값만 삭제되고
   보존 고지는 뜨지 않아야 한다(커버 안의 비움은 보존이 아니라 삭제다).
6. **연도 이동 경로도 동일.** 3번을 연도까지 바꿔 저장해 '다른 사건도 함께 이동' 다이얼로그를
   거쳐도 필드값 보존·고지가 같아야 한다.
7. **캐릭터 화면 경로도 동일.** 1~3을 캐릭터 상세의 사건 목록에서 열어 반복한다(저장 경로가
   CharacterViewModel로 분리돼 있다 — 한쪽만 고쳐졌는지 확인).

**S-12 — 관계변화 다이얼로그**

8. **연도 공란 저장이 입력을 버리지 않는다.** 관계 변화 추가에서 유형·설명·강도·사건 연결을
   채우고 연도만 비운 채 저장을 누른다. **다이얼로그가 닫히지 않고** 연도 입력란에
   "연도를 입력해주세요" 인라인 오류가 떠야 하며, 입력값이 전부 남아 있어야 한다.
   연도를 채우면 오류가 사라지고 저장이 되어야 한다. *(종전: 다이얼로그가 닫히며 전부 소멸.)*
9. **편집 다이얼로그도 동일 + 삭제·취소는 종전대로.** 기존 관계 변화를 열어 연도를 지우고
   저장 → 같은 인라인 오류·유지. '삭제'와 '취소' 버튼은 검증 없이 종전처럼 즉시 동작해야 한다.

### 3-8. 이번 세션 산출물(S-5 월드패키지)의 실기기 확인 — ⬜ 미검증

> 파서·코드 정책·판별기·세력 관계 역해석은 순수 JVM으로 실행 검증했고(509건), 임포터·내보내기
> 본체는 실클래스패스 스텁 컴파일로 타입 검사만 했다. **DB 삽입·다이얼로그·이미지 복원의
> 실동작은 사용자 확인이 필요하다.**

1. **왕복 기본.** 필드값·사건(사건 필드값 포함)·세력(세력 간 관계 포함)·태그·관계·상태변화·
   이미지가 있는 세계관을 설정 → 세계관 패키지로 내보낸다. 그 .ncworld를 설정의 *엑셀에서
   가져오기*로 고른다. *(종전: "가져오기에 실패했습니다"만 떴다.)* 이제 충돌 다이얼로그
   (같은 세계관이 있으므로)가 떠야 한다. **'새로 생성'**을 고르면 "이름 (2)" 세계관이 생기고
   캐릭터·필드값·사건·사건 필드값·세력·세력 간 관계·관계·상태변화·태그·이미지가 전부
   원본과 같아야 한다. 결과 다이얼로그에 "코드를 재발급한 항목 N건" 안내가 떠야 한다.
2. **덮어쓰기.** 같은 파일을 다시 가져와 **'덮어쓰기'** 선택 → "캐릭터 N명…휴지통에 보관"
   확인 다이얼로그(R-4) → 진행하면 기존 세계관이 휴지통에 가고 패키지 내용으로 교체된다.
   휴지통에서 그 삭제 묶음을 '전체 복원'하면 사본으로 되살아나야 한다(원본 자리는 새 임포트).
3. **건너뛰기.** 같은 파일 → '건너뛰기' → 아무 변화 없어야 한다.
4. **값 라이브러리 큐레이션 왕복.** 필드 하나에 표시 라벨·별칭·카테고리를 큐레이션하고
   내보내기 → 삭제 없이 '새로 생성'으로 가져오기 → 새 세계관의 값 라이브러리에 라벨·별칭이
   그대로 있어야 한다. *(종전: 값 라이브러리 자체가 패키지에 없었다.)*
5. **이름 은행 링크.** 이름 은행에서 고른 이름을 쓰는 캐릭터를 내보내고, 캐릭터를 지운 뒤
   (이름 사용 표시 풀림) 가져오기 → 그 이름의 사용 표시가 **가져온 캐릭터로 이어져야** 한다.
   다른 캐릭터가 그 이름을 쓰는 중이면 빼앗지 않고 "사용 표시 N건은 다른 캐릭터가 사용 중"
   안내가 떠야 한다. 은행에 없던 이름은 새로 등록된다(패키지 캐릭터가 쓰는 이름만).
6. **이미지 미포함 패키지.** '이미지 포함'을 끄고 내보낸 파일을 **다른 기기(또는 앱 데이터
   삭제 후)**에서 가져오면 "이미지 미포함 패키지 — 이미지 연결 N개 제외" 안내가 떠야 한다.
   같은 기기에서 가져오면 원 파일이 살아 있으므로 이미지가 그대로 보여야 한다.
7. **지원하지 않는 ZIP.** 아무 ZIP(사진 압축본 등)을 가져오기로 고르면 "지원하지 않는 ZIP
   파일입니다"가 떠야 한다. *(종전: "가져오기에 실패했습니다".)* 엑셀 백업 ZIP과 .xlsx는
   종전대로 동작해야 한다(회귀 확인).
8. **동명 세계관 여럿.** 같은 이름의 세계관을 두 개 만든 상태에서 그 이름의 패키지(코드는
   다른 것 — 다른 기기에서 만든 파일이거나, 내보낸 뒤 두 세계관을 새로 만든 경우)를 가져오면
   충돌 다이얼로그에 **덮어쓰기 선택지가 없어야** 한다(대상 모호).

### 3-9. 이번 세션 산출물(S-7·S-8·S-9·S-19 통계 드릴다운)의 실기기 확인 — ⬜ 미검증

> 집계 규칙은 순수 JVM으로 실행 검증했다(528건 — 머지 조회·사건 드릴다운·계산 필드 하위 그룹·
> 캐릭터 축 CALCULATED 교차분석). **시트 전환·차트 탭·연표 이동의 실동작은 사용자 확인이 필요하다.**
>
> 준비물: **세계관 2개**(A·B)에 **같은 이름·같은 타입의 필드**(예: '직업' TEXT)를 각각 만들고
> 양쪽에 같은 값(예: '검사')을 가진 캐릭터를 여러 명 둔다. 통계 화면의 작품 필터는 **전체**로 둔다.

1. **머지 드릴다운(S-7).** 통계 → 필드 인사이트에서 '직업' 카드를 찾는다(세계관 A·B가
   **한 장**으로 합쳐져 있어야 한다). '검사' 조각의 숫자를 확인하고 **탭한다.**
   → 시트의 "N명의 캐릭터"가 **차트 숫자와 같아야** 하고 목록에 A·B 양쪽 캐릭터가 모두 있어야
   한다. *(종전: A세계관 캐릭터만 나왔다.)*
2. **하위 그룹 머지(S-7·S-19).** 그 시트에서 **'이 그룹의 다른 필드 분포 보기'** →
   필드 목록에 **'직업'이 없어야** 하고(형제 세계관 def까지 함께 제외), 같은 이름의 필드가
   **중복으로 나열되지 않아야** 한다. 다른 필드를 고르면 A·B 양쪽 값이 합산돼 나온다.
3. **계산 필드 하위 그룹(S-19).** 수식 필드(CALCULATED, 예: `field('힘') * 2`)를 만들고
   2번의 목록에서 그것을 고른다. → **분포가 실제로 나와야 한다.**
   *(종전: 항상 '데이터가 없습니다'.)*
4. **캐릭터 축 교차분석 + 계산 필드(S-8).** 인사이트 화면 상단 **교차 분석** →
   축을 **캐릭터 필드**로 두고 축1에 그 수식 필드, 축2에 아무 필드나 골라 실행한다.
   → **표가 실제로 그려져야 한다.** *(종전: 제목만 있고 표가 비었으며 아무 안내도 없었다.)*
   축2·필터에 수식 필드를 놓아도 같아야 한다.
5. **빈 표의 고지(S-8 방어선).** 교차분석의 필터 값에 아무 캐릭터도 갖지 않은 값
   (예: `존재하지않는값`)을 넣고 실행한다. → 표 자리에 **"조건에 맞는 캐릭터가 없어…"**
   안내가 떠야 한다. *(종전: 아무것도 그려지지 않고 조용했다.)* 사건 축이면 "…사건이 없어…"다.
6. **사건 필드 드릴다운(S-9).** 사건에 커스텀 필드(예: '사건 유형')를 만들어 값을 채우고
   통계 → 필드 인사이트에서 **'사건 · …'** 접두사가 붙은 카드를 찾는다. 조각을 **탭한다.**
   → **"N건의 사건"**과 사건 목록(설명 + 날짜 · 값)이 나와야 한다.
   *(종전: '0명의 캐릭터'와 빈 목록.)*
7. **사건 행 탭 → 연표.** 6번 목록의 행을 탭한다. → 연표 탭이 열리고 **그 사건의 연도로
   이동**해 있어야 한다(전역 검색에서 사건을 탭한 것과 같은 동작).
8. **사건 하위 그룹.** 6번 시트의 **'이 사건들의 다른 필드 분포 보기'** → 사건 필드만
   나열돼야 하고(캐릭터 필드가 섞이면 안 된다), 결과가 **'건' 단위**로 표시돼야 한다.
9. **필드가 하나뿐일 때의 고지.** 사건 필드가 하나뿐인 상태에서 8번을 누르면
   **"함께 볼 다른 필드가 없습니다…"** 안내가 떠야 한다. *(종전: 아무 반응 없음.)*
10. **회귀 — 레거시 필드 분석 화면.** 통계 → (필드 분석 상세) 화면의 파이 차트 조각을 탭하면
    종전과 **똑같이** 그 필드 하나의 캐릭터 목록이 떠야 한다(이 화면은 세계관 통합을 하지
    않으므로 머지되면 오히려 틀린다).
11. **회귀 — 작품 필터.** 작품을 하나 고른 상태에서 1·6번을 반복한다. 카드가 그 세계관만
    보여주고 드릴다운도 그 범위여야 한다.

### 3-10. 이번 세션 산출물(로드맵 4 — 통계 정합성)의 실기기 확인 — ⬜ 미검증

> 순수 JVM 테스트 618건과 차분 컴파일로 계산 규칙은 고정했으나, **화면에 실제로 그렇게 그려지는지**는
> 실기기에서만 확인된다. 아래는 이번 수정이 바꾼 화면 동작 전부다.

**준비:** 세계관 2개(A·B)에 같은 이름·같은 타입의 필드(예: '성별' SELECT, '직업' TEXT)를 두고
양쪽 작품에 캐릭터를 몇 명씩 만든다. 값 종류가 12개 이상인 필드(예: '거주지')도 하나 만든다.

1. **'통계에 포함' 끄기.** 필드 편집에서 세계관 B의 '성별'만 '통계에 포함'을 끈다. 그다음 통계 →
   - 패턴 인사이트 카드에 **B의 성별 관련 편중 카드가 사라져야** 한다(종전: 그대로 떴다).
   - 필드 분석 상세(레거시)의 값 분포에서도 빠져야 한다. 단 **필드 완성도 목록에는 그대로 있어야**
     한다(입력 현황은 분석이 아니다).
   - 교차분석에서 '성별'을 축으로 고르면 **A만 집계**되고, 카드의 수치와 표의 셀 합이 같아야 한다.
     "세계관 2개를 합산했습니다" 문구가 뜨지 않아야 한다.
2. **어시스턴트 연동.** 통계 → 패턴 인사이트 톱니에서 '편중'을 끈 뒤 어시스턴트 화면을 연다.
   **편향 카드가 뜨지 않아야** 한다(종전: 통계에서 꺼도 어시스턴트에는 그대로 떴다).
3. **일방통행 함정.** 톱니에서 **모든 유형의 체크를 해제**하고 저장한다. 카드가 사라지지 않고
   "모든 인사이트 유형이 꺼져 있습니다…" 안내와 **톱니가 그대로 남아야** 한다. 다시 켜면 복구된다.
   *(종전: 카드가 통째로 사라져 되돌릴 방법이 없었다.)*
4. **비율과 '기타'.** 값 종류가 12개 이상인 필드의 인사이트 카드에서
   - 표의 비율 합이 **100%**여야 하고(종전: 상위 10종만으로 100%가 되어 각 값이 부풀려졌다),
   - 표 마지막에 **'기타 N종'** 행이 있고, 파이차트에도 같은 조각이 있어야 하며,
   - **'기타' 조각을 탭하면** 잘린 값들을 가진 캐릭터 목록이 떠야 한다(0명이 아니어야 한다).
5. **BODY_SIZE 구간 드릴다운.** 신체 사이즈 필드에 값이 5명 이상 있는 상태에서
   통계 → 필드 분석 상세 → '신체 — 키' 파이의 구간 조각(예: '160~170')을 탭한다.
   **그 구간에 실제로 속한 캐릭터가 떠야** 한다. *(종전: 어떤 조각을 눌러도 항상 0명.)*
   조각의 건수와 시트의 인원 수가 같은지 확인한다.
6. **수식 필드가 모든 화면에 나온다.** CALCULATED 필드를 하나 만들고(예: `field('키') / 100`)
   - 필드 분석 상세의 **수치 요약**에 나와야 하고(종전: 통째로 없었다),
   - 통계 메인 요약의 '주요 필드 값 TOP 5'와 작품별 비교의 TOP 5에도 집계되며,
   - **순위 탭의 값과 인사이트 카드의 분포 값이 같은 문자열**이어야 한다(예: 둘 다 `1.75`).
7. **순위 빈도.** 표시 형식이 '콤마 구분 목록'인 TEXT 필드(예: 무기 = "검, 활")를 순위 대상으로 고른다.
   - 전원 1회 동률이 아니라 **토큰별 빈도**로 순위가 나와야 한다.
   - 같은 필드의 인사이트 분포 차트 수치와 순위의 회수가 **일치**해야 한다.
   - 값 라이브러리에 별칭을 등록한 필드(예: '장검' → '검')에서도 두 화면 수치가 같아야 한다.
8. **머지 카드의 톱니.** 두 세계관에 같은 필드가 있는 상태에서 인사이트 카드(세계관명이 안 붙은 카드)의
   톱니를 연다. **"같은 이름의 다른 세계관 필드에도 적용 (2개)"** 체크박스가 보이고 기본 켜짐이어야 한다.
   차트 종류를 바꿔 저장한 뒤 **작품 필터를 B로 바꿔** 같은 필드 카드를 본다 — 바꾼 차트 종류가
   유지돼야 한다. *(종전: 대표 def에만 저장돼 옛 설정이 되살아났다.)*
   체크를 끄고 저장하면 그 세계관만 바뀌어야 한다.
9. **오류 고지.** 작품 필터를 **로딩 중에** 연속으로 바꿔 본다. "통계를 처리하지 못했습니다
   (JobCancellationException)" 같은 토스트가 **뜨지 않아야** 한다(취소는 오류가 아니다).
   또 통계 화면을 회전하거나 다른 탭에 갔다 돌아왔을 때 **이전에 본 오류 토스트가 다시 뜨지 않아야**
   한다.
10. **회귀 — 종전 동작.** 인사이트 카드의 차트 조각 탭, 하위 그룹 분석, 사건 필드 카드의 조각 탭,
    교차분석 실행, 순위 탭의 정렬·필터 복원이 전부 종전대로 동작해야 한다.

   B-1 세션은 그 함정을 알고 집계 규칙을 뒤집었다 — **표가 돌아오지 않으면 생존으로 센다**
   (`votesReturned == 0 → survives`). 그리고 지적은 **전부 내가 코드를 직접 읽어 실재를
   확인한 뒤에만** 반영했다. 8건 모두 그렇게 확인해 고쳤다.

   다음 세션도 같은 규칙을 지킬 것: **판정이 돌아오지 않은 것을 '통과'로 세지 말 것.**
   그리고 반증이 늦더라도 지적을 코드로 직접 확인하는 것이 최종 관문이다 — 에이전트의
   판정은 보조이지 근거가 아니다.
