# Room 마이그레이션 검증 절차

> **상태: 현행 절차 — 스키마를 건드릴 때마다 쓴다.** (현재 DB **v44**, 마이그레이션 **43개** — v1→v44는 43단계다. 종전의 "44개"는 오기이며 `architecture` v1.2가 자기 문서에서 같은 오기를 이미 고쳤는데 **이 문서에는 소급되지 않았다**. 세는 법: `grep -rhoE 'MIGRATION_[0-9]+_[0-9]+' app/src/main/java --include=*.kt | sort -u | wc -l`)
> 이 문서는 끝난 계획서가 아니라 **살아 있는 절차서**다.

DB 스키마 변경은 실패하면 **사용자 기기에서 앱이 기동하지 못한다**. 이 저장소는
`fallbackToDestructiveMigration()`을 쓰지 않으므로 데이터가 지워지지는 않지만,
마이그레이션이 잘못되면 Room이 시작 시 예외를 던져 앱을 열 수 없다.

에뮬레이터·실기기를 쓸 수 없는 환경(CI, 원격 개발 컨테이너)에서도 위험의 대부분을
사전에 걸러내기 위해 3단계 절차를 쓴다.

## 1단계 — 자동 검증 (기기 불필요, 즉시 실행)

**하네스는 마이그레이션마다 하나씩 있다** — 스크립트 하나에 계속 덧붙이지 않고, 검증할
마이그레이션별로 파일을 나눈다(옛 하네스가 여전히 대조군으로 돌아야 하기 때문이다).

```
python3 tools/verify_room_migration.py       # 초기 하네스 (대조군 포함)
python3 tools/verify_room_migration_43.py    # v42 → v43 — 49건
python3 tools/verify_room_migration_44.py    # v43 → v44 (image_meta.adoptSource) — 25건
```

새 마이그레이션을 추가하면 **`_<새버전>.py`를 새로 만든다.** 건수는 각 스크립트의 실행 결과를
믿을 것(문서의 숫자는 작성 시점 스냅샷이다).

의존성 없이 파이썬 내장 `sqlite3`만 사용한다. 하는 일:

1. **AppDatabase.kt에서 실제 마이그레이션 SQL 문장을 추출**해 실행한다.
   테스트가 SQL 사본을 갖고 있으면 코드와 어긋나므로, 항상 배포될 문장 그 자체를 검사한다.
2. 변경 직전 버전의 테이블을 실제 SQLite에 만들고 표본 행을 넣은 뒤 마이그레이션을 실행한다.
3. 실행 후 상태를 검사한다 — 기존 데이터 무변경, 전 행 백필, 값 고유성,
   기존 인덱스·외래키 유지, 유니크 제약 실동작.
4. **Room 스키마 검증 통과 조건**을 대조한다. Room은 시작 시 실제 스키마와 엔티티에서
   유도한 기대 스키마를 비교해 하나라도 어긋나면 예외를 던진다. 특히 자주 어긋나는 지점:
   - 컬럼 타입 affinity (TEXT/INTEGER/REAL/BLOB)
   - notNull 여부 — 엔티티가 `String?`이면 `ADD COLUMN ... TEXT` (NOT NULL 금지)
   - DEFAULT 절 — 엔티티에 `@ColumnInfo(defaultValue)`가 없으면 SQL에도 DEFAULT를 두면 안 된다
   - 인덱스 이름 — Room 규약은 `index_<table>_<col1>_<col2>`
5. 빈 테이블·재실행(컬럼이 이미 있는 기기) 안전성을 검사한다.
6. **대조군**: 이미 배포되어 정상 동작 중인 과거 마이그레이션을 같은 하네스로 돌려
   하네스 자체가 올바른지 교차 검증한다.

새 마이그레이션을 추가하면 이 스크립트의 대상 버전·테이블 정의를 갱신한다.

## 2단계 — 컴파일 (개발 기기에서 1회)

```
./gradlew :app:assembleDebug
```

Room 애노테이션 프로세서가 엔티티에서 기대 스키마를 생성한다. 엔티티 선언이 잘못됐거나
버전만 올리고 마이그레이션을 등록하지 않았으면 **여기서 빌드가 실패**한다.
`exportSchema = true`이므로 `app/schemas/<버전>.json`이 생성된다 —
1단계에서 가정한 스키마와 이 JSON을 대조하면 확신이 더 올라간다.

## 3단계 — 실기기 업그레이드 (배포 전 필수 1회)

가장 중요하다. 1·2단계가 잡지 못하는 것은 "기존 데이터가 있는 실제 DB에서의 동작"뿐이다.

1. **변경 전** 커밋으로 빌드해 설치하고, 데이터를 몇 건 만든다(관계·사건·세력 소속 포함).
2. 앱을 **지우지 말고** 변경 후 빌드를 덮어 설치한다.
3. 앱을 켠다. 정상 기동하면 마이그레이션과 Room 스키마 검증을 모두 통과한 것이다.
4. 기존 데이터가 그대로인지, 새 열이 채워졌는지 확인한다
   (예: 엑셀로 내보내 새 코드 열에 값이 있는지).

실패 시 로그에 `Migration didn't properly handle` 또는 `Migration from X to Y` 예외가 남는다.

## 체크리스트

- [ ] 엔티티 필드가 nullable이면 SQL도 NOT NULL 없이 추가했는가
- [ ] `@ColumnInfo(defaultValue)`를 쓰지 않았다면 SQL에도 DEFAULT가 없는가
- [ ] 인덱스 이름이 Room 규약과 일치하는가
- [ ] `@Database(version = N)`을 올렸는가
- [ ] `addMigrations(...)`에 새 마이그레이션을 등록했는가
- [ ] 백필이 유니크 인덱스 **생성 전에** 끝나는가
- [ ] 컬럼이 이미 존재하는 기기에서 재실행해도 안전한가
- [ ] 새 마이그레이션용 `tools/verify_room_migration_<버전>.py`를 **만들었고** 통과하는가
- [ ] 기존 하네스(대조군)도 여전히 통과하는가
- [ ] 실기기 업그레이드 1회 확인
