## 0. 왜 — 무엇이 "직관적이지 않은가"

사용자 피드백은 두 겹이다: ① 🎲 몸매 생성이 "그닥 만족스럽지 않다" ② "딱 이 부분만이
아니라 전반적으로 직관적이지 않다"(막연한 인상). 현행 코드를 실측하니 그 인상의 구조적
원인이 다섯 개다:

1. **넣는 것도 숫자, 나오는 것도 숫자다.** 입력은 파트별 숫자 칸, 🎲 결과도 숫자 갱신,
   읽기 화면 '체형 분석'은 인사이트 13종이 전부 텍스트 행이다. `실루엣`이라는 인사이트조차
   문장 문자열이다(`BodyAnalysisHelper.buildSilhouetteDescription`). 어느 지점에서도 몸매가
   *보이지* 않는다 — 90-58-88을 넣어도, "WHR 0.66"이라 답해도, 숫자를 숫자로 설명하는
   순환이다.
2. **용어가 전문어다.** WHR·골든 비율·보정 UB·볼륨 지수·프레임 사이즈 — "몸매에 대해 뭘
   알겠냐"는 바로 그 사용자(체형 수치를 모르는 창작자)에게 분석 결과가 외국어로 온다.
3. **설정 토글 이름 ≠ 화면 이름(B-61).** `FieldEditDialog.setupBodyAnalysisSection`의 토글
   라벨이 코드 하드코딩이고 읽기 화면은 `strings.xml`을 써서, 같은 인사이트를 두 곳이 다른
   이름으로 부른다(`B/W/H 차이`↔`측정값 분석`이 가장 벌어진 자리). 켠 것과 나타난 것의
   짝이 안 맞는다.
4. **13종이 위계 없이 나열된다.** 핵심(체형 태그·분류)과 참고 지표(키 대비 비율 3행,
   골든 비율 상세 4행)가 같은 크기의 행으로 이어져, 정보가 많을수록 안 읽힌다.
5. **분석 화면에서 설정으로 가는 길이 없다.** 분석 카드를 보다가 "이건 어디서
   조절하지?"가 끊긴다(설정은 필드 편집 다이얼로그 안의 '체형 분석 설정').

그리고 사용자가 정의한 이 기능의 본질(대화에서 확정):

> "몸매에 대해 뭘 알겠냐. 모르는 사람이 많을 거야. 하지만 대강 선호하는 실루엣을 잡는 건
> 다들 할 수 있을 거 아니야? **수치만 보고는 몰라.**"

즉 이 작업은 "시각화 추가"가 아니라 **역방향 입력 경로**다 — 실루엣을 잡으면 수치가
따라온다. 이 앱의 원칙 04(이중 경로: 러프 입력 → 정밀 조정)의 첫 번째 본격 구현이 된다.
시각화 단독의 쓸모도 둘 확정됐다: **🎲를 굴리는 사람**(결과를 숫자가 아니라 실루엣으로
체감 — "만족감이 안 좋다"의 절반은 생성 품질이 아니라 결과를 느낄 수 없는 것)과
**그림 그릴 때 참고하려는 사람**(크게 보기가 필요한 이유).

**구색 금지(사용자 명시).** v1 완결 기준: 입력·🎲·분석·크게 보기가 전부 실루엣을
경유할 수 있어야 한다. 실루엣이 읽기 화면에 그림 하나 얹고 끝나면 이 작업은 실패다.

## 1. 현행 구조 실측 (2026.07.31, 파일:심볼 기준 — 행 번호는 밀리므로 적지 않는다)

| 층 | 현행 | 파일 |
|----|------|------|
| 값 저장 | BODY_SIZE 필드값 문자열(구분자 `-`/`/`/공백), 구조화 입력 파트는 사용자 정의(`StructuredInputConfig.parts`), 미설정 시 B·W·H 3칸 자동 | `DynamicFieldFormBuilder.buildForm`(BODY_SIZE 분기) |
| 연동 필드 | 키·체중은 별도 필드에서 `SemanticRole.HEIGHT/WEIGHT`로 찾는다(BODY_SIZE도 role 우선, type/key 폴백) | `SemanticRole`, `DynamicFieldRenderer.computeBodyAnalysis` |
| 값 해석 | **렌더러 안 인라인**: `split(Regex("[-/\\s]+"))` 후 **무조건 앞 3개 숫자 = bust/waist/hip**. 파트 라벨·개수 무시. 3개 미만이면 분석 전체 null | `DynamicFieldRenderer.computeBodyAnalysis` |
| 분석 엔진 | `analyze(bust, waist, hip, height?, weight?, config)` → 인사이트 13종(컵·BMI·WHR·차이·비율·키 대비·프레임·볼륨/곡선·골든·체형 규칙 2계열·실루엣 문장·작품 내 순위) — 전부 순수 계산 | `util/BodyAnalysisHelper` |
| 설정 | `BodyAnalysisConfig`(config JSON `bodyAnalysis` 키): 컵 매핑·체형 규칙·다층 태그 규칙·ribOffset·골든 이상값·`enabledInsights` 토글 | `data/model/BodyAnalysisConfig` |
| 생성 | `BodyGenerator`: 키 4옵션 × 체형 5옵션 × 가슴/엉덩이 오버라이드 × 컵 역산 + 기준 캐릭터 상대 생성 + 작품 분포 기반 추천 | `util/BodyGenerator`, `ui/character/BodyGeneratorBottomSheet` |
| 표시 | 텍스트 행 나열(`addRow`/`addSubRow`), 시각 요소 0 | `DynamicFieldRenderer`(체형 분석 카드) |

## 2. 확정된 설계 결정 (대화 근거 — 재론 불요)

- **D1. 실루엣이 이 영역의 중심축이다.** 입력(편집기), 🎲 결과 미리보기, 분석 카드,
  크게 보기 전부 같은 실루엣 렌더를 쓴다.
- **D2. 편집은 이중 경로 양방향.** 실루엣 위 드래그 핸들(러프) + 파트별 슬라이더·수치
  칸(정밀). 어느 쪽을 만져도 서로 실시간 동기화. **저장 전까지 초안**이며 취소하면 원값
  그대로(변수 제어). 편집기는 폼 상태만 고친다 — DB 직접 쓰기 없음(저장은 기존 저장 경로).
- **D3. 파트→부위 매핑을 설정에 둔다**(3장). 실루엣과 분석이 "앞 3개 = B/W/H" 억지 해석
  대신 명시 매핑을 쓰고, 미설정 시 라벨 추론 → 현행 호환 폴백.
- **D4. 🎲는 편집기 안에서, 결과는 실루엣로 먼저.** 굴리기 → 실루엣 변화 → 다시 굴리기
  또는 드래그 미세 조정 → 적용의 루프. 기존 생성 옵션(키·체형·오버라이드·상대 생성)은
  그대로 유지한다.
- **D5. 크게 보기(전체 화면) 뷰.** 그림 참고용 — 수치·비율 라벨 표시/숨김 토글 포함.
  이미지 내보내기는 v2.
- **D6. 사람 형태를 하드코딩하지 않는다(원칙 01).** 실루엣은 매핑된 슬롯으로만 그린다.
  매핑이 안 되는 파트(예: '날개 길이')는 실루엣이 아니라 **파트 바(bar)로 폴백**. 매핑
  불가 사유는 표시한다(무음 금지).
- **D7. B-61을 이번에 함께 처리한다**(6장) — 토글 라벨을 읽기 화면과 같은 리소스로.
- **D8. 용어·위계 재편**(5장) — 전문 지표에 쉬운 설명 병기, 핵심 위로 + 나머지 접기.
- **D9. 분석 카드 → 체형 분석 설정 바로가기**를 단다.
- **범위: 체형 영역만.** 앱 전반 UX 점검은 별건(사용자가 실기기 확인 중 "직관적이지 않은
  순간"을 모아 오면 그때 별도로).

## 3. 파트→부위 매핑 — `BodySlot` (순수 계층)

### 3-1. 모델

```kotlin
enum class BodySlot { BUST, UNDERBUST, WAIST, HIP, SHOULDER, NONE }
```

`UNDERBUST`(밑가슴)는 선택 슬롯이다 — 매핑돼 있으면 흉곽 폭과 컵 계산이 **실측 밑가슴**을
쓰고(갈비뼈가 큰 캐릭터를 정확히 표현할 수 있다 — 4-1 분리 규정), 없으면 현행 근사
(허리 + `ribOffset` 보정 — `BodyAnalysisConfig.underbustEstimation`이 이미 이 대체를
예비해 둔 자리다)로 동작한다. 추론 라벨: `밑가슴`/`언더`/`underbust`.

- 저장: `BodyAnalysisConfig`에 `partSlots: List<BodySlot>`(파트 인덱스 순) 추가 —
  config JSON `bodyAnalysis.partSlots` 배열. **기본값(추론과 같음)은 저장하지 않는다**
  (기존 필드 정의의 JSON이 불어나지 않게 — `ribOffset` 선례).
- 엑셀 왕복: config JSON은 '필드 정의' 시트의 설정 열에 통째로 실리므로 **왕복 규약
  무변경**으로 자동 편승한다.

### 3-2. 해석 사다리 (미설정 시 추론)

1. 명시 매핑(`partSlots`)이 있으면 그대로.
2. 없으면 파트 라벨로 추론: `B`/`가슴`/`bust`→BUST, `W`/`허리`/`waist`→WAIST,
   `H`/`힙`/`엉덩이`/`hip`→HIP, `어깨`/`shoulder`→SHOULDER (대소문자 무시, trim).
3. 추론이 하나도 안 되고 **숫자 파트가 3개 이상이면 앞 3개 = B/W/H** — 현행 동작
   보존(기존 데이터·기존 사용자 무변경, 마이그레이션 불요).
4. 그 외 → 매핑 없음: 분석 불가 사유 표시 + 실루엣 대신 바 폴백(D6).

### 3-3. 파서 단일 소스화 (기존 부실 수리)

현행 값 해석이 렌더러 안 인라인이라(1장) 실루엣이 같은 파싱을 복제하면 B-55류 산재가
가중된다. 신규 순수 객체 **`BodyMeasurements`**(가칭)로 옮긴다:

```
BodyMeasurements.resolve(field: FieldDefinition, rawValue: String,
                         heightText: String?, weightText: String?)
  → { slot별 수치, 매핑 방식(명시/추론/위치폴백), 미매핑 파트 목록 }
```

소비자: 분석(`computeBodyAnalysis` — 위임으로 축소), 실루엣 스펙(4장), 편집기(5장).
분석 엔진 `analyze()`의 계약(B/W/H 3값 필수)은 **v1에서 유지한다** — 부분 슬롯일 때
분석은 현행대로 null이되 사유를 표시하고, 실루엣은 있는 슬롯만으로도 그린다(엔진 개편까지
하면 범위가 터진다).

## 4. 실루엣 스펙 — `BodySilhouetteSpec` (순수 지오메트리)

### 4-1. 입력과 좌표

- 입력: 키(cm, 없으면 후술), BUST/WAIST/HIP/SHOULDER 수치(부분 허용), 오버레이용 두 번째
  스펙(선택).
- **방식: 베이스 템플릿 + 부위 변형** (2026.07.31 확정 — 1차 목업이 대안을 반증했다:
  "둘레÷π=폭"으로 윤곽을 **계산해 내는** 방식은 팔 없는 관 모양·과폭·밋밋한 곡선이
  나와 품질이 안 선다. 잘 그린 몸을 수치가 **변형**해야 어느 값에서도 그림이 산다).
  - **선례 검증(2026.07.31, 사용자 제안으로 조사):** 수치→체형 시각화의 기존 도구들 —
    bodyvisualizer류 웹 도구(수치 입력→3D/2D 체형), **Clip Studio 3D 데생 인형**(부위
    선택→두께·길이 슬라이더 — 대상 사용자층의 표준 도구), DesignDoll(비례 슬라이더
    모핑), VRoid Studio(슬라이더 모프) — 는 예외 없이 **"잘 만든 기준 모델 + 부위
    변형(모프)"** 방식이다. 수치에서 형태를 직산하는 도구는 없다 — 이 문서의 방식
    전환과 일치한다. CSP의 '부위별 두께+길이 2축 조정' 관례에서 v2 씨앗 하나:
    **체형 스타일 파라미터**(등신·다리 길이 비율 등 수치와 무관한 기준 몸 미세 조정 —
    자율성 우선. 7장 v2에 등재).
  - **기준 몸(정본 상수) — 서브컬쳐풍으로 저작한다**(2026.07.31 사용자 방향: "대상자가

    아크 기준 18.5px). 확정 규칙 원문("핸들은 가슴 볼륨의 바깥 가장자리")의 해석 정정.
  - **측면 뷰(P10) — 같은 수치에서 파생되는 표시 전용 뷰.** 새 데이터·핸들·엑셀 규약
    무변경(핸들·드래그는 정면 전용, 측면은 관찰용). 저작(측면 튜토리얼 레퍼런스 1종
    추가 반영 — 胸板 위에 가슴·胸郭 기울이기·骨の出っ張り): **흉곽 기울임**(전경 목·
    흉판 앞선의 전방 경사·등 흉추 볼록 — 기울어진 흉곽 달걀), 측면 정점 S_FRONT·
    S_BACK·S_HEAD(요추 오목·둔부 융기·늑골 융기·전진 발), **가슴 = 매달린 물방울
    가산 융기**(깊이 = 컵차 비례·캡, 대역 상단은 쇄골 쪽 연장 + **윗면은 직선에 가까운
    긴 사면**(볼록 호면 공이 된다) + 봉우리는 낮게(t≈.30) + 언더는 깊은 훅 — 밑가슴·
    행은 정면과 공유), 부위 깊이 스케일(배·요추=허리, 둔부=힙, 등 상부=어깨 — 표시
    클램프 공유), **팔 생략**(컵 차트·비례 튜토리얼 측면 관행 — 돌출·S라인·둔부의
    계측 가독 우선), 셀 표기 = 밑가슴 턱 라인(컵 게이팅 공유)+둔부 밑 크리즈.
    UI: 크게 보기 정면/측면 토글 + 편집기 미리보기 토글(치수는 이식 시 조정).

### 4-2. 클램프와 표현 한계

극단값에서 곡선이 뭉개지지 않게 **표시만** 클램프한다(값은 절대 건드리지 않는다).
클램프가 걸린 상태는 시각 표시(예: 핸들 색)로 알린다 — "그림의 한계이지 값의 한계가
아니다"가 사용자에게 보여야 한다(변수 제어).

### 4-3. 오버레이 (유령 실루엣)

같은 스펙 둘을 겹쳐 그린다(뒤 스펙은 반투명 윤곽선). v1 대상은 **작품 평균**(순위 주입
경로가 이미 작품 캐릭터 전체의 수치를 모은다 — 1장 표) — 상대 조정("이 애보다 조금 더")을
가능하게 하는 최소 형태. **옵션이다(9장 P3 확정): 크게 보기·편집기 양쪽에 켬/끔 토글,
기본 끔.** 캐릭터 선택 오버레이는 v2.

### 4-4. 테스트 (순수 JVM)

변형 스케일·역산(왕복 항등)·클램프·부분 슬롯 보간·오버레이 좌표가 전부 순수 함수라
러너에 태운다. 스냅샷 비교(좌표 배열)로 회귀 고정. 기준 몸 정점 배열도 이 스펙
객체가 정본으로 든다(뷰는 그리기만).

### 5-1. 읽기 화면 — 분석 카드 재편 (위계 + 실루엣 + 바로가기)

```
[체형 분석] ─────────────── ⚙(체형 분석 설정 바로가기 — D9)
  ┌────────┐  체형 태그 · 체형 분류 (한 줄 요약)

  └────────┘
  ▸ 자세히 (접힘 — 펼치면 현행 나머지 인사이트 전부: 차이·비율·키 대비·골든·순위…)
```

- 접기 상태는 화면 상태 prefs에 저장하지 않는다(카드 단위 일시 상태 — 단순 유지).

  `INSIGHT_SILHOUETTE` 키에 편입 — 문장 설명과 그림이 같은 토글을 쓴다. 끄면 현행처럼
  문장도 그림도 없음).
- 탭 → **크게 보기 다이얼로그**: 전체 화면 실루엣 + 라벨(수치·부위명) 표시/숨김 토글 +
  오버레이 켬/끔. 그림 참고용(D5).

### 5-2. 편집기 — `BodySilhouetteEditorSheet`

- 진입: BODY_SIZE 구조화 입력 옆 실루엣 버튼(아이콘+"실루엣으로 조정"). 기존 🎲 버튼은
  편집기 안으로 이동하되, **폼의 기존 🎲 진입도 유지**(제거하면 기존 사용자의 동선이
  끊긴다 — 눌렀을 때 편집기가 열리고 🎲 패널이 펼쳐진 상태로).
- 구성: 상단 실루엣(핸들 드래그 가능) / 중단 파트별 슬라이더+수치 칸(양방향 동기) /
  하단 🎲 패널(기존 BodyGeneratorBottomSheet의 옵션 재사용 — 키·체형·가슴/엉덩이·컵
  역산·상대 생성) + [적용] [취소].
- 쓰기 대상: **폼 위젯만**(BODY_SIZE 파트 칸 + SemanticRole 연동 키/체중 폼 필드 —
  기존 🎲 적용과 같은 경로). 저장·검증·보존 고지는 전부 기존 저장 파이프라인 그대로.
- 키/체중 필드가 폼에 없으면: 실루엣은 상대 모드(4-1), 🎲의 키·체중 출력은 버리고
  그 사실을 고지(현행 🎲 동작과 대조 확인 후 동일하게).

### 5-4. 세부 UI 명세 (2026.07.31 추가 — 치수는 지침이며 구현이 ±로 조정 가능, 상태·구조는 규격)

**5-4-1. 실루엣 렌더 스타일 (세 화면 공통)**

- 정면 여성형(9장 P2, 서브컬쳐풍 기준 몸 — 4-1), 좌우 대칭. 채움은 **중간 명도의
  마네킹 톤 솔리드 + 진한 테마색 윤곽선** — 반투명은 형태가 안 잡히고(목업 2차 판정),
  **짙은 덩어리 채움은 볼륨 음영을 삼킨다**(목업 6차 판정 — 음영이 읽히는 명도가 조건).
  다크/라이트 모두 기존 앱 테마 리소스에서 파생(하드코딩 색 금지). 팔처럼 획으로
  그리는 사지는 윤곽 2패스(윤곽색 굵게 + 채움색). 핸들은 밝은 원 + 색 테두리.
  **음영은 셀(cel) 문법**(13차 — 소프트 그라데이션·근육 면 셰이드가 "실사체 느낌"의

  윤곽선은 만화체 무게로 굵게(240px 기준 본체 ≈2px, 팔 외곽 패스는 그보다 굵게).
  근육 구조는 '음영 면'이 아니라 **형태**로만 표현한다(아래 볼륨 표기층의 대흉근 항).
  머리는 몸통과 **별도 패스**로(한 패스에 합치면 서브패스 윤곽선이 목 고리로 나타난다 —
  목업 6차 판정).
- **2.5D 볼륨 표기층**("2.5D 마네킹" — 2026.07.31 사용자 요청: 정면 외곽이 못 담는
  "이 수치면 이렇게 형성된다"를 내부 음영으로): 실루엣 채움 위에 값 비례 음영 —
  가슴(아래 작도 규칙 — 채움은 플랫, 언더 라인 아래 **컵 비례 캐스트 섀도 밴드**,
  13차 셀 전환. 언더 라인 굵기·농도도 컵 비례), **대흉근 사면은 형태로만**(물방울
  상단 가장자리가 사면을 따라 바깥으로 갈수록 내려가고, 폭이 넓을수록 기울기를
  세운다(선반화 방지) — 12차 도입, 사용자: "상부는 근육 구조 맞춰서". 12차의 '얕은
  면 셰이드'는 13차에서 실사감 원인으로 제거),

  라인**(흉골 홈에서 어깨로 뻗는 얕은 S커브 — 어깨 폭 추종, 2026.07.31 사용자 요청),

- 머리: 목적문 1줄(R-25) — 예: "실루엣을 잡으면 수치가 따라옵니다. 저장 전까지는
  초안입니다."(문구는 구현 시 가이드 톤 검사)
- 상단(약 55~60%): 실루엣 + 부위 핸들.
  - 핸들: 매핑된 부위 높이의 좌우 끝에 원형(시각 약 12dp, 터치 48dp). **한쪽만
    잡아도 좌우 대칭으로** 움직인다. 드래그 중 해당 부위 수치를 핸들 옆 말풍선으로
    실시간 표시.
  - 보간 부위(값 없음)는 핸들 비활성(점선 + 반투명). 우상단에 오버레이 토글 아이콘.
- 하단(약 40~45%, 스크롤):
  - 부위별 행: `[부위명] [슬라이더] [수치 입력칸]` — 3자 동기(핸들·슬라이더·수치).
    슬라이더 범위는 키 연동 그럴듯 범위, **수치 입력칸은 범위 밖도 허용**(클램프는
    표시만 — 변수 제어).
  - 키·체중 행: 연동 필드(SemanticRole)가 폼에 있을 때만 같은 형식으로 노출.
  - 🎲 패널(기본 접힘): 기존 생성 옵션 전부(키·체형·가슴/엉덩이 오버라이드·컵

## 8. 새 기능 체크리스트 판정 (CLAUDE.md)

1. **확장성** — 매핑은 사용자 설정(추론은 기본값일 뿐), 실루엣은 슬롯 기반이라 파트
   구성 자유 유지, 표시 여부는 기존 토글 체계 편입. 고정 프리셋 없음.
2. **실질성** — 역방향 입력 + 🎲 체감 루프 + 그림 참고. 구색 기준을 0장에 명문화.
3. **완결성** — 인라인 파서를 단일 소스로 수리(방편식 아님), B-61 동시 해소.
4. **연결성** — 분석 엔진·생성기·순위 주입 경로·토글 체계 전부 재사용. 새 섬 없음.
5. **조작성** — 진입 1탭(폼 버튼·카드 탭), 이중 경로 양방향, 저장은 기존 플로우.
6. **의도 부합 4질문** — ① 받쳐주는 확장성(`scalability` 7장 4단계): 새 상한 없음 /
   비용은 캐릭터 1명 단위 O(파트 수) 지오메트리 + 카드 렌더 1회(오버레이의 작품 평균은
   기존 순위 계산이 이미 모으는 데이터의 재사용이라 추가 조회 0~1회) / 스냅샷 무관 /
   엑셀 왕복 무관(저장 형식 불변, config 키는 기존 설정 열에 편승) ② 변수 제어: 초안
   편집·취소 원복·클램프는 표시만·미매핑 사유 표시 ③ 자율성: 기본 추론 + 명시 매핑 +
   토글 ④ 왕복 무결성: 규약 무변경.
7. **텍스트** — 새 문구 `strings.xml` + R-25 목적문(편집기·크게 보기) +
   `check_text_style.sh` 통과. B-61 해소로 코드 한국어 리터럴이 검사 대상으로 들어온다.
