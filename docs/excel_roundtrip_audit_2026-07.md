## 3. 검증 도구 사용법 (새 세션에서 반드시 알아야 함)

### 환경 제약
- **Android/Gradle 빌드가 불가능하다.** `dl.google.com`이 네트워크 정책으로 차단되어 AGP를 받을 수 없다.
  `./gradlew`로 무엇을 하든 실패한다. 파이프로 연결된 명령의 종료 코드를 성공으로 오해하지 말 것.
- 따라서 아래 4가지로 검증한다.

### 환경 구축 (2차 세션에서 실제로 통한 방법 — 그대로 재현 가능)

Maven Central은 접근 가능하다. `kotlin-compiler-embeddable`·`kotlin-stdlib`·`trove4j`는
`/opt/gradle-8.14.3/lib/`에서 복사하면 되고(trove4j는 `trove4j.jar`로 이름 변경), 나머지는 받는다:

```
annotations-13.0, kotlinx-coroutines-core-jvm(1.9.0), kotlinx-coroutines-test-jvm-1.9.0,
junit-4.13.2, hamcrest-core-1.3, json-20240303, gson,
poi, poi-ooxml, poi-ooxml-lite, commons-collections4,
commons-io, commons-compress, xmlbeans, log4j-api,
commons-lang3, SparseBitSet
```

> **정본은 `tools/setup_jvm_env.sh`이고, 버전의 정본은 `tools/jvm_env_versions.sh`다**
> — 위 목록은 그 스크립트가 없던 2차 세션의 기록이라 **무엇이 필요한가만** 남기고
> **버전은 지웠다**(2026.08.02, B-84). 여기 적어 두면 스크립트와 갈리기 때문이며,
> 실제로 갈렸다: 하네스가 POI 5.2.5로 도는 동안 앱은 5.3.0을 싣고 있었다.
> 이제 POI·gson 버전은 그 스크립트가 **앱의 `app/build.gradle.kts`에서 읽는다** —
> 앱이 올리면 하네스가 다음 실행부터 따라 올라간다(단일 소스를 양쪽에 따로 두면 반드시
> 드리프트한다 — 7장 규약 그대로).

androidx 스텁(`$JARS_DIR/out-room`)에서 막히기 쉬운 점 셋 — 미리 알고 가면 시간을 아낀다:
- `ForeignKey`에 **companion object로 CASCADE/SET_NULL/NO_ACTION/RESTRICT/SET_DEFAULT** 상수가 있어야 한다.
- `@Ignore`의 `@Target`에 **PROPERTY_GETTER**를 포함해야 한다(`Character.displayName`이 getter에 붙인다).
- 스텁 컴파일 시 **컴파일러 클래스패스에 coroutines jar가 필요**하다(없으면 `NoClassDefFoundError`).

### (1) 순수 JVM 단위 테스트 — 실제 실행됨
```
JARS_DIR=/path/to/jars tools/run_jvm_tests.sh
```
표준 kotlinc로 Android 비의존 소스만 컴파일하고 JUnitCore로 실행한다.
**감사(2차 세션) 시점 148건 통과**(1차 세션 66건). 현행 건수는 `tools/run_jvm_tests.sh`
실행 결과와 `remaining_work` 5장의 재현 기준선을 볼 것.

테스트 가능한 형태로 뽑아낸 순수 로직(2차 세션에서 6개 추가):
`CharacterFieldValueOverflow`, `PresetTemplateMatcher`, `FactionRefResolver`(+`ExcelRefColumns`),
`ImageZipReport`/`ImagePathClassifier`, `ImageMetaRowResolver`, `SheetSpec`의 값 해석 함수들
(`parseSheetBoolean`/`sheetBooleanOrKeep`/`matchDropdownValue`/`parseRelTypeTokens`/`parseRelColorTokens`).

**새 로직을 순수 함수로 분리하면 실제 실행 검증이 가능해진다** — 두 세션 모두에서 가장 효과가 컸다.
특히 **spec 열 순서 = 내보내기 셀 인덱스** 계약을 테스트로 고정하는 패턴이 유용하다
(차분 컴파일로는 절대 잡히지 않는 조용한 열 밀림을 막는다).

### (2) 차분 컴파일 — 신규 오류만 골라냄
```
git stash push -m base && JARS_DIR=... tools/differential_compile.sh /tmp/base.txt && git stash pop
JARS_DIR=... tools/differential_compile.sh /tmp/cur.txt
comm -13 /tmp/base.txt /tmp/cur.txt   # 두 출력은 스크립트가 이미 정규화·정렬해 둔다
```
기준선에서도 약 3.5만 줄의 오류가 난다(Android SDK 부재).

**판정 기준(2차 세션에서 정교화):** 같은 **오류 메시지**가 손대지 않은 파일에도 기준선에 존재하면 노이즈다.
파일 단위가 아니라 **메시지 단위**로 비교해야 한다 — 신규 파일은 모든 오류가 "새 것"으로 보이기 때문이다.
`unresolved reference 'HashMap'/'Pair'/'mapNotNull'/'runCatching'` 같은 stdlib 심볼은 전부 노이즈이며,
그로부터 파생된 캐스케이드(`actual type is 'kotlin.Any'`, 새 private 프로퍼티 미해석)도 마찬가지다.

**결정적 교차 검증:** 의심되는 구문만 떼어내 **실제 클래스패스로 컴파일**해 보라. 2차 세션에서
`try/finally 후 val 확정 할당`, `runCatching{}.onFailure{ e -> e.message }` 두 건을 이 방법으로 확인했다.
순수 JVM 테스트 대상 파일이라면 테스트 러너가 이미 실제 클래스패스로 컴파일하므로 그것이 더 강한 근거다.

### (3) Room 마이그레이션 하네스 — 저장소에 포함됨
```
python3 tools/verify_room_migration.py   # 최초 하네스 — 이후 버전별 스크립트가 하나씩 늘었다
```
의존성 없이 파이썬 내장 sqlite3만 사용. **AppDatabase.kt에서 실제 SQL을 추출해** 실제 SQLite로
실행한다. 하네스는 마이그레이션마다 하나씩이다(`ls tools/verify_room_migration*.py`로 센다) —
**새 마이그레이션은 `tools/verify_room_migration_<버전>.py`를 새로 만든다**(절차는
`docs/room_migration_verification.md` 1단계).

## 4. 이번 세션에서 새로 세운 규약 (다음 작업자가 반드시 알아야 함)

기존 7장 규약에 더해 2차 세션이 코드로 확립한 것들:

### 4-1. 불리언 열 규약 — `null`은 오직 '열 없음'만 뜻한다
`SheetSpec.parseSheetBoolean` / `sheetBooleanOrKeep`이 단일 소스다. **빈칸은 false(비움 의도)이며
절대 null이 되지 않는다.** 빈칸을 null로 접는 변형(`parseBooleanOrNull`)은 삭제했다 —
남겨 두면 다음 기여자가 다시 복사한다(실제로 [904]가 그렇게 생긴 결함이었다).
호출부는 `sheetBooleanOrKeep(colIndex >= 0, cell)` → `?: existing.x`(갱신) / `?: 엔티티기본값`(신규).

### 4-2. 참조 열 쌍 규약 — 유무는 이름 열이, 대상은 코드가 정한다
`ExcelRefColumns.refColumnIntent`가 단일 소스다. 편집 가능한 '이름' 열 + readOnly '코드' 열 쌍에서:
- 두 열 다 없음 → KEEP(F1-A) / 이름 열 있고 빈칸 → CLEAR(**남은 코드 셀은 읽지 않는다**) / 값 있음 → LOOKUP

적용처: 캐릭터 관계 '세력'/'세력코드', 이름 은행 '사용 캐릭터'/'사용캐릭터코드'.
이 규약이 없으면 "설정은 받고 해제는 무시하는" 비대칭이 생긴다.

### 4-3. 동명 참조는 범위로 좁히고, 안 되면 모호성을 선언한다
`FactionIndex.resolve`가 `resolveCharByNameNovel`과 동형이다. **후보가 여럿일 때만** 세계관으로 좁힌다
(하나면 힌트 없이 확정 — 무조건 skip은 조작 마찰 최소화 원칙에 역행).
좁혀지지 않으면 Ambiguous를 선언하고 세계관 목록 + 코드 열 안내를 낸다.
**모호를 '찾을 수 없음'으로 보고하지 말 것** — 사실과 다른 경고다.

### 4-4. DB id는 어떤 단계에서도 단독 근거가 아니다
`PortableFieldFilters`의 해석 사다리가 본보기다: 코드 → 코드 별칭 → 자연키(후보 1개면 채택,
다수면 범위로 좁히고, 그래도 다수면 **id가 후보 안에 있을 때만** 채택).
id는 이름이 이미 일치할 때의 타이브레이커로만 쓴다.

### 4-5. 예약 시트는 캐릭터 시트보다 먼저 이름을 선점한다
`ExcelExporter`에서 예약 시트명은 세계관 루프 **앞에서** `sanitizeSheetName`으로 확보해야 한다.
안 그러면 같은 이름의 세계관이 예약명을 빼앗는다. 이미지 시트가 세운 선례이며, 회귀 감사가 같은 결함을 잡았다.
→ **이 규약은 R-6(`assignSheetName` — `conventions.md`)으로 대체됐다.** 이제 호출 순서에
기대지 말 것 — 예약명 선점은 이름 배정기가 구조적으로 보장한다.

### 4-6. 복원할 수 없는 것은 지우지 않는다 — 스냅샷으로 때우지 말 것
회귀 감사가 잡은 가장 값진 교훈이다. "삭제하되 휴지통에 스냅샷을 남긴다"는 안전망은 두 이유로 무너졌다:

- 스냅샷 payload는 **DB id**(fieldDefinitionId·characterId·factionId·eventId)를 담는데, 같은 덮어쓰기가
  상위 엔티티를 지우면 그 id가 재발급(AUTOINCREMENT)되어 복원해도 아무것도 살아나지 않는다.
  그런데 경고는 "휴지통에 남겼습니다"라고 회수를 약속했다 — 사실과 다른 경고.
- 휴지통 한도(`TrashSnapshot.MAX_OPERATIONS = 30` — **항목 수가 아니라 삭제 '작업' 수다**, B-14/R-9)를 넘으면 커밋 직후 `pruneIfNeeded()`가
  **방금 만든 스냅샷과 사용자의 기존 휴지통을 함께** 지운다(보호되지 않은 이미지 파일까지).

올바른 형태는 기존 `shouldDelete(enabled, spec)`와 동형 — **삭제를 건너뛰고 사유·교정 경로를 안내**한다.
새 안전망 메커니즘을 만들기 전에 "이미 있는 가드로 표현할 수 있는가"를 먼저 물을 것.

## 7. 이 코드베이스의 왕복 규약 (수정 시 반드시 지킬 것)

- **F1-A**: 열이 헤더에 **없으면** 기존 DB 값 유지. 열이 있고 셀이 **빈칸**이면 "비움 의도"로 존중.
- **위치 폴백 금지**: `cols["X"] ?: 숫자`는 열 삭제 시 이웃 열을 오독한다. 선택 열은 `?: -1`.
  (1차 감사에서 이 패턴으로만 5건, 2차에서 추가로 6건이 나왔다 — 새 코드에 절대 넣지 말 것)
- **매칭 규약**: 코드(안정 식별자) 우선 → 자연키 폴백. DB id는 기기 이전·복원에서 재발급되므로 신뢰 불가.
  코드 열이 없는 시트는 '생성일' 같은 왕복 불변 속성을 안정 식별자로 승격한다(필드 템플릿·세력 소속 선례).
- **변수 제어**: 잘못된 입력을 조용히 버리지 않는다. 검증 → 경고 → **교정 경로 안내**.
  무음 데이터 유실은 그 자체로 결함이며, **사실과 다른 경고는 무음보다 나쁘다**.
- **덮어쓰기 대원칙**: 백업이 복원할 수 없는 것은 지우지 않는다(시트 존재 가드). 4-6 참조.
- **왕복 멱등성**: 무편집 왕복은 데이터를 바꾸지 않아야 한다. 재가져오기가 행을 늘리면 결함.
  **무편집 왕복에서 경고가 뜨는 것도 결함이다**(거짓 경고).
- **내보내기/가져오기 단일 소스**: 헤더 규칙·유효값·드롭다운을 양쪽에 따로 두면 반드시 드리프트한다.
  엔티티 companion(`SearchPreset.SORT_MODES`)에 두고 spec과 검증이 같은 상수를 보게 한다.
- **트랜잭션 밖 저장소**: DataStore/SharedPreferences는 DB 트랜잭션이 되돌리지 못한다.
  롤백 가능해야 하는 작업은 커밋 이후로 뺀다(`importAppSettings` 선례).

## 8. 검증 절차 (이 문서 작업분 기준)

> **'다음 세션 시작 방법'이 아니다** — 시작점은 `remaining_work` 5장이 소유한다
> (CLAUDE.md 문서 지도). 여기 있던 브랜치·커밋 대조 절차는 그 브랜치가 사라지고
> master에 커밋이 쌓여 **실행 불가능해졌으므로 지웠다.**

1. 검증 도구는 모두 `tools/`에 있다 — 3장의 환경 구축 절차대로 jar만 준비하면 된다.
2. 감사 원본 항목은 소진됐고, 5장의 별건 3개(N1~N3)도 처리 완료됐다.
   새 작업은 **`docs/remaining_work_2026-07.md` 4장의 백로그**부터 검토할 것.
3. 수정할 때마다 순수 JVM 테스트 · 차분 컴파일 · 리소스 점검을 돌리고,
   마이그레이션을 건드렸다면 하네스까지 돌릴 것(도구별 상세는 3장의 (1)~(4)).
4. **수정 후에는 반드시 자기 수정분을 재공격하라.** 2차 세션은 13건을 고친 뒤 회귀 감사에서
   자기 결함 7건(그중 high 1건)을 더 찾았다. 특히 **"안전망을 새로 만든" 코드를 의심할 것** —
   가장 심각했던 결함이 정확히 거기서 나왔다.
