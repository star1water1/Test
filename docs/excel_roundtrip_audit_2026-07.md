## 2. ⚠️ 사용자가 직접 해야 할 확인 (최우선)

**DB 버전이 41 → 42로 올라갔다.** 이 환경에서는 실기기 검증이 불가능하므로 배포 전 1회 확인이 필요하다.

1. 변경 전 커밋(`1b25432`)으로 빌드해 설치하고 캐릭터·관계·세력 소속 데이터를 몇 건 만든다.
2. **앱을 지우지 말고** 최신 빌드를 덮어 설치한다.
3. 앱을 켠다. 정상 기동하면 마이그레이션과 Room 스키마 검증을 모두 통과한 것이다.
4. 기존 데이터가 그대로인지, 엑셀로 내보냈을 때 관계 시트의 새 '코드' 열이 채워졌는지 확인한다.

실패 시 로그에 `Migration didn't properly handle` 또는 `Migration from 41 to 42` 예외가 남는다.
자세한 절차는 `docs/room_migration_verification.md` 참조.

> 참고: 이 앱은 `fallbackToDestructiveMigration()`을 쓰지 않으므로 **마이그레이션 실패가
> 데이터 삭제로 이어지지는 않는다.** 실패하면 앱이 기동하지 못할 뿐이며 되돌릴 수 있다.

## 3. 검증 도구 사용법 (새 세션에서 반드시 알아야 함)

### 환경 제약
- **Android/Gradle 빌드가 불가능하다.** `dl.google.com`이 네트워크 정책으로 차단되어 AGP를 받을 수 없다.
  `./gradlew`로 무엇을 하든 실패한다. 파이프로 연결된 명령의 종료 코드를 성공으로 오해하지 말 것.
- 따라서 아래 3가지로 검증한다.

### (1) 순수 JVM 단위 테스트 — 실제 실행됨
```
JARS_DIR=/path/to/jars tools/run_jvm_tests.sh
```
표준 kotlinc로 Android 비의존 소스만 컴파일하고 JUnitCore로 실행한다. **현재 66건 통과.**
필요한 jar 목록과 room 어노테이션 스텁 준비 방법은 스크립트 상단 주석에 적어 두었다.
(`androidx.room` 어노테이션은 스텁으로 대체한다 — 어노테이션은 매핑 로직 실행에 영향이 없다)

테스트 가능한 형태로 뽑아낸 순수 로직: `FieldValueSheetMapper`, `PortableFieldFilters`,
`EventFieldHeaders`, `ExcelHeaderAliases`, `SheetSpec`, `ExcelCellValue`.
**새 로직을 추가할 때 순수 함수로 분리하면 실제 실행 검증이 가능해진다** — 이 감사에서 가장 효과가 컸다.

### (2) 차분 컴파일 — 신규 오류만 골라냄
```
JARS_DIR=... tools/differential_compile.sh /tmp/base.txt   # git stash 상태에서 기준선
JARS_DIR=... tools/differential_compile.sh /tmp/cur.txt    # 작업본
```
전체 프로젝트를 표준 kotlinc로 컴파일하면 Android SDK가 없어 **기준선에서도 약 3.5만 줄의 오류**가 난다.
그래서 `git stash`로 기준선 오류 집합을 만들고 현재 상태와 비교해 **새로 생긴 오류 카테고리만** 본다.
줄 번호를 제거해 정규화한 뒤 `comm -13`으로 diff한다(정확한 명령은 스크립트 상단 주석 참조).

판정 기준: 같은 심볼이 **손대지 않은 파일에서도 기준선에 존재**하면 클래스패스 노이즈다.
이 방법으로 실제 컴파일 오류 1건(중복 인자 전달)을 잡아냈다 — 노이즈에 묻히지 않는다.

### (3) Room 마이그레이션 하네스 — 저장소에 포함됨
```
python3 tools/verify_room_migration.py
```
의존성 없이 파이썬 내장 sqlite3만 사용. **AppDatabase.kt에서 실제 SQL을 추출해** 실제 SQLite로
실행하고 35건을 검사한다. 이미 배포된 `MIGRATION_34_35`를 같은 하네스로 돌려 하네스 자체도 교차 검증한다.
새 마이그레이션을 추가하면 대상 버전·테이블 정의를 갱신할 것.

## 4. 남은 확정 항목 8건 (반증 통과 = 실제 결함)

우선순위 순. 각 항목의 상세 근거·시나리오·권고 수정안은 감사 원본에 있으나, 아래 요약만으로도 작업 가능하다.

### [27] (medium) 검색 프리셋 '정렬모드' 무검증 + 위치 폴백
`ExcelImportService.kt` `importSearchPresets`
- 한글로 '이름순'이라 적어도 경고 없이 저장되고, 적용 시엔 relevance로 동작해 사용자가 틀린 줄 모른다.
- 더 심각: '정렬모드' 열을 지우면 `?: 3` 폴백이 '기본값' 열을 읽어 sortMode가 "Y"/"N"이 된다.
- **수정**: 위치 폴백 제거(`?: -1`) + 목록 프리셋의 `validSortKinds`와 대칭으로 유효값 검증·경고.
  '기본값' 열도 동일.

### [36] (medium) 세력 이름 해석이 전 세계관 first-match
`ExcelImportService.kt` 세력 조회 (`allFactions.find { it.name == ... }`)
- 세계관 A·B에 동명 '기사단'이 있으면 B 캐릭터가 A 세력에 무경고로 소속된다. 그 소속으로 자동 관계까지 생성돼 오염이 번진다.
- **수정**: 캐릭터의 세계관으로 후보를 먼저 좁힌 뒤에만 모호성을 선언(`resolveCharByNameNovel` 선례와 동형).
  무조건 skip은 원칙 04(조작 마찰 최소화)에 역행하므로 피할 것.
- 주의: 안내 문구로 '세력코드' 열을 지목하려면, 그 열이 readOnly이고 사용 안내가 "코드 열은 수정하지 마세요"라고
  말하는 것과 모순되지 않게 함께 정리해야 한다.

### [37] (medium) 필드 템플릿 동명 붕괴
`ExcelImportService.kt` `importUserPresetTemplates` (`associateBy { it.name }`)
- DB는 동명 템플릿을 허용하는데 임포트가 이름으로 맵을 만들어 붕괴시킨다. 사용자의 편집이 어디에도 남지 않고
  "2건 갱신" 성공 보고만 뜬다.
- **수정 범위 주의**: 검색 프리셋·목록 프리셋은 **손대지 말 것**(name unique index가 이미 정체성 보장).
  `UserPresetTemplate` 하나만 코드 우선 → 자연키 폴백 규약으로 정렬한다.

### [44] (medium) 이미지 ZIP 실패·제외 미통보
`ImageZipHelper.kt`
- 이미지가 ZIP에 안 담겨도 사용자에게 알리지 않는다. 완전한 백업으로 믿고 원본 기기를 초기화하면 이미지가 사라진다.
- **수정**: 반환형을 승격해 실패 건수·표본 경로·참조되나 없는 건수를 내보내기 결과에 노출.

### [902] (medium) PortableFieldFilters가 세계관코드 완전일치만 인정
`PortableFieldFilters.kt` + `ExcelImportService.loadFieldFilterResolution`
- 기기 B에 같은 이름·다른 코드의 세계관이 있으면(이름 폴백으로 매칭됨) 프리셋 필터가 전량 폐기된다.
- **수정**: 프리셋에만 폴백을 다는 것은 방편식. `importUniverses`의 이름 폴백 분기에서
  `universeCodeAliases[파일코드] = 기존코드` 맵을 서비스 수준에 쌓고(기존 deferred 맵 패턴) 해석에 사용.

### [40] (low) 이미지 시트 basename last-wins
`ExcelImportService.kt` `importImageMeta`
- 같은 파일명 행이 2개면 뒤 행의 빈 태그가 앞 행의 태그를 통째로 지운다. 경고가 없다.
- **수정**: 해석된 path를 키로 seen 맵을 두고 다른 시트와 동일한 문구로 중복 경고(마지막 행 우선 유지).

### [904] (low) parseBooleanOrNull 규칙 분기
`ExcelImportService.kt` `importCharacterListPresets`
- 목록 프리셋에만 "빈칸=기존값 유지"를 도입해, 같은 이름·같은 드롭다운 열이 시트에 따라 반대로 동작한다.
  목록 프리셋에서는 '기본값'을 비워 해제할 수 없다.
- **수정**: 갱신은 F1-A(열 있음+빈칸=비움), 신규는 엔티티 기본값으로 분리해 규약을 하나로 통일.

### [905] (low) PortableFieldFilters 구버전 경로가 낡은 fieldId를 신뢰
`PortableFieldFilters.resolve`
- 안정 식별자가 없는 구버전 파일에서 id 존재 여부만 확인하고 유지한다. id가 재발급된 새 기기에서
  '성별' 이름표 아래 실제로는 '거주지'를 거르는 필터가 된다.
- **수정**: 존재검사 → 자연키(필드명) 합치 검증으로. 불일치는 즉시 폐기하지 말고 이름 후보로 재해석.

### [905] (low) 관계 시트 '세력' 열을 비워도 해제되지 않음
`ExcelImportService.kt` `importRelationships` (`factionId ?: existing.factionId`)
- 설정은 받고 해제는 무시하는 비대칭. 통계는 계속 자동 관계로 계수하고, 세력 삭제 시 함께 지워진다.
- **수정**: '세력'을 편집 가능한 참조 열로 승격(`세계관` 선례와 동형)하거나, readOnly를 유지하되
  해제 불가를 명시. **둘 중 하나를 통째로** 적용할 것.

## 7. 이 코드베이스의 왕복 규약 (수정 시 반드시 지킬 것)

- **F1-A**: 열이 헤더에 **없으면** 기존 DB 값 유지. 열이 있고 셀이 **빈칸**이면 "비움 의도"로 존중.
- **위치 폴백 금지**: `cols["X"] ?: 숫자`는 열 삭제 시 이웃 열을 오독한다. 선택 열은 `?: -1`.
  (이번 감사에서 이 패턴으로만 5건이 나왔다 — 새 코드에 절대 넣지 말 것)
- **매칭 규약**: 코드(안정 식별자) 우선 → 자연키 폴백. DB id는 기기 이전·복원에서 재발급되므로 신뢰 불가.
- **변수 제어**: 잘못된 입력을 조용히 버리지 않는다. 검증 → 경고 → **교정 경로 안내**.
  무음 데이터 유실은 그 자체로 결함이며, **사실과 다른 경고는 무음보다 나쁘다**.
- **덮어쓰기 대원칙**: 백업이 복원할 수 없는 것은 지우지 않는다(시트 존재 가드).
- **왕복 멱등성**: 무편집 왕복은 데이터를 바꾸지 않아야 한다. 재가져오기가 행을 늘리면 결함.
- **내보내기/가져오기 단일 소스**: 헤더 규칙을 양쪽에 따로 두면 반드시 드리프트한다.
  `EventFieldHeaders`·`ExcelHeaderAliases`가 그 사례(둘 다 이번에 드리프트로 인한 버그를 냈다).
