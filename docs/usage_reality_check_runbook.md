# 실사용 대조 런북 — 엑셀 파일 하나로 시작하는 세션

> **이 문서를 읽는 세션에게:** 사용자가 실사용 데이터(앱의 엑셀 내보내기 파일)를 저장소에
> 올려 두었을 것이다. 이 문서 하나로 끝까지 진행하도록 썼다.
>
> **이번 작업의 결과물은 `docs/usage_reality_check_2026-07.md` 한 문서다**(골격은 3장).
> 그 문서를 채우는 데 필요한 장을 **이 문서에 적힌 순서 그대로** 진행하고, 마지막 9장까지
> 채운 뒤 멈춘다. **10장 금지사항은 작업 내내 항상 적용된다.**
> 코드 수정은 이 문서에서 순위가 확정된 것만, 별도 작업으로 한다(10장 2번의 예외는 그대로).
>
> **장 순서 = 실행 순서다.** 4·5장(우회 흔적·기능 도달률)은 앱 코드를 한 줄도 쓰지 않으므로
> 검증 환경보다 **앞에** 놓았다. 환경이 막혀도 가장 값진 장은 확보된다.

## 0. 이 작업이 무엇이 **아닌지** 부터

기존 감사·색출 문서(`superficial_feature_audit_2026-07.md`, `remaining_work_2026-07.md`)는
**"있는데 안 되는 것"**을 찾았다. 코드를 읽으면 나오기 때문이다.

이 작업은 다르다. 실사용 데이터만이 보여주는 것은 둘이다:

| 부류 | 예 | 코드로 찾을 수 있나 |
|------|-----|--------------------|
| **되는데 안 쓰는 것** | 값 라이브러리 큐레이션(별칭·카테고리)이 전부 AUTO — 만들었지만 아무도 도달하지 못한 기능 | ❌ |
| **없어서 우회한 흔적** | TEXT 필드값 안에 `1장~3장: 주인공, 4장~: 조연` — 상태변화 기능이 그 용도에 안 맞아 손으로 우회한 자국 | ❌ |

그러므로 **결함을 고치러 들어가지 말 것.** 이번 산출물은 "무엇이 실제로 쓰이고,
무엇이 앱의 설계 의도와 어긋나 있는가"의 **대조표**이고, 그것이 다음 작업의 우선순위를 정한다.

`CLAUDE.md`의 개발 의도 4질문(받쳐주는 확장성 / 변수 제어 / 자율성 우선 / 엑셀 왕복 무결성)에
**추정이 아니라 수치로** 답하는 것이 최종 목표다.

## 1. 입력 확인

### 1-1. 파일 찾기

사용자가 올린 파일은 저장소 어딘가에 있다. 이름은 정해져 있지 않다.

```bash
find . -maxdepth 3 \( -name '*.xlsx' -o -name '*.ncworld' -o -name '*.zip' -o -name '*.db' \) \
  -not -path './.git/*' -not -path './build/*' | head
```

- **`.xlsx`** — 앱의 엑셀 내보내기. 이 런북의 주 대상이다.
- **`.ncworld` / `.zip`** — 월드패키지 또는 이미지 포함 백업. `ImportFileFormat`이 3분기로 판별한다(2-4 참조).
- **`.db`** — Room 데이터베이스. **5-3의 대조군으로 쓴다**(8장 — 원본 금지·사본만).
  B-9(마이그레이션 실검증)는 이번 범위 밖이며 별도 작업으로 넘긴다.

**후보가 0건일 때만 멈추고 사용자에게 묻는다.** 추측으로 만든 표본으로 이 작업을 하면
결론이 전부 허구가 된다 — 그것이 이 작업의 유일한 실패 방식이고, **이 작업의 유일한 정지
조건이다.**

후보가 복수면 묻지 말고 규칙으로 고른다:

1. `.xlsx` 중 **수정 시각이 가장 최근인 것**을 주 표본으로 삼는다
2. `.ncworld` / `.zip`은 2-4의 판별기 확인에만 쓴다
3. `.db`는 5-3 대조군 전용이다

고른 파일의 크기·수정 시각과 **탈락시킨 후보 수**를 산출물 §0에 적어 사용자가 나중에 뒤집을 수
있게 한다. **파일명 자체는 적지 않는다** — 세계관명·작품명이 들어 있을 수 있다. 문서에서는
"엑셀 내보내기 1건"으로 지칭한다.

### 1-2. 표본 메타 두 줄 확인 (여기서 물어야 한다)

파일을 받은 직후, **열기 전에** 두 가지만 묻는다. 9장까지 미루면 산출물을 다시 써야 한다.

- **Q0-a.** "이 파일을 내보낼 때 **항목 체크를 전부 켠 상태**였습니까? (예 / 아니오 / 기억 안 남 — 껐다면 어떤 항목)"
- **Q0-b.** "이 파일은 **전체 내보내기**입니까, 특정 세계관·작품만 내보낸 것입니까?"
- **Q0-c.** "이 데이터는 **다 채워 넣은 상태**입니까, 아직 **채워 나가는 중**입니까?
  (작업 중이라면 어느 갈래가 아직 손도 안 댄 쪽입니까)"

| 답 | 이후 처리 |
|----|----------|
| 셋 다 전체/예/완성 | 시트 부재를 (가)/(다)로만 좁혀 **확정 판정**으로 쓴다. 이 사용자에 대한 진술에 헤지를 붙이지 않는다 |
| 항목을 껐다 | 지목된 항목에 걸린 지표를 **관측 불가**로 표기하고, 그 지표로는 어떤 결론도 내리지 않는다 |
| 부분 내보내기 | 산출물 제목을 `표본: 부분 내보내기(범위 …)`로 바꾸고 5장의 '미도달' 판정을 전부 **'판별 불가'**로 내린다 |
| **채워 나가는 중** | **0건을 '안 쓴다'로 읽지 않는다.** 5장의 미도달 판정 중 **근거가 0건 카운트뿐인 것**을 전부 `⚠️ 미확정(표본 미성숙)`으로 내리고, 6장 백로그 재정렬에서 **하향 근거로 쓰지 않는다** |

**Q0-c가 없으면 이 작업은 조용히 틀린다.** 0건은 "쓰지 않는다"와 "아직 거기까지 안 갔다"를
구별하지 못하는데, 처방은 정반대다(전자는 제거·숨김, 후자는 **그대로 두고 기다린다**).
v1.2까지 이 질문이 없어서 1회차가 미도달 10건을 '확정'으로 올렸다가 사용자가 뒤늦게
"아직 채우는 중"이라고 알려 준 뒤 전부 되돌렸다.

> **단, 성숙도가 무너뜨리지 못하는 것이 있다.** 아래 셋은 표본이 미완이어도 그대로 선다 —
> 강등할 때 **함께 쓸어버리지 말 것**이다:
> ① **코드 결함**(있는 데이터로 앱이 틀린 값을 내는 것 — 오히려 데이터가 늘수록 커진다)
> ② **구조 측정**(타입↔값 정합성, 규모 스윕, 시트 판별 — 분모가 지금 있는 것이면 족하다)
> ③ **사용자가 직접 말한 사유**(9장의 답 — 카운트가 아니라 진술이 근거다)

**이 세 답은 9장의 질문 슬롯을 쓰지 않는다.** 그 슬롯은 미도달 *사유*를 묻는 데 쓴다.
**묻되 기다리지 않는다** — 답이 늦으면 `미확인`으로 두고 진행하되, 그 경우 5장 판정은 전부
미확정이 된다.

### 1-3. 절대 커밋하지 않는다

#### ① 이미 추적 중인지 먼저 본다

```bash
git ls-files | grep -Ei '\.(xlsx|xlsm|ncworld|zip|db|db-shm|db-wal)$'
git log --all --oneline --diff-filter=A -- '*.xlsx' '*.ncworld' '*.zip' '*.db'
```

둘 중 하나라도 결과가 나오면 **산출물 커밋을 보류하고 사용자에게 보고한다.** 이미 커밋된
데이터는 `.gitignore`로 되돌릴 수 없고, 이력 정리는 force-push가 필요한데 `CLAUDE.md`가
master force-push를 금지하므로 **세션이 단독으로 결정할 수 없다.** 분석은 계속해도 된다
(노출은 이미 발생했고 읽는 행위가 노출을 늘리지 않는다). 결정 전까지 커밋만 보류한다.

#### ② 확장자 목록을 훑지 말고 **손에 든 경로를 검사한다**

```bash
git check-ignore -v "<1-1에서 찾은 경로>"     # 종료코드 0이 아니면 그 자리에서 멈춘다
```

> **v1.0의 사고:** `.gitignore`의 규칙이 `/*.xlsx`처럼 **루트 앵커**였고, 1-1은
> `-maxdepth 3`으로 찾으라고 했다. `data/설정.xlsx`·`docs/x.db`는 **무시되지 않는데**
> 런북은 "이미 등재돼 있다"고 안심시켰다. 가려진 스니펫이 아니라 **원본 워크북 통째**가
> push되는 경로였다. v1.1에서 앵커를 제거했지만, **규칙을 믿지 말고 위 명령으로 확인하라.**

무시되지 않으면 `.gitignore`를 고친 뒤 **재확인**한다.

#### ③ 전량 스테이징 금지

**`git add -A` / `git add .` 를 쓰지 않는다.** 커밋 대상은 경로를 명시해 add하고
(`git add docs/usage_reality_check_2026-07.md tools/usage-probe/`), 커밋 직전
`git diff --cached --name-only`로 스테이지 목록이 그 둘뿐인지 확인한다. 그 외 파일이 하나라도
있으면 커밋하지 않는다. **경로를 명시해서만 add하면 이 절의 위반이 구조적으로 불가능해진다.**

#### ④ 산출물 표기 — 2층 규칙

산출물 문서는 커밋되어 origin(GitHub)으로 push된다. **세션 대화·터미널 출력·스크래치패드는
이 규칙의 대상이 아니다** — 사용자 본인의 데이터를 본인에게 보이는 것이고 어디에도 남지 않는다.
되돌릴 수 없는 채널(커밋되는 모든 것)에만, **아래 닫힌 목록에 열거된 토큰만** 통과시킨다.

**A층 — 원문 그대로 적는다 (닫힌 열거. 이 목록에 없으면 A층이 아니다):**

- 숫자와 자릿수 (선행 0 `007`, 과학표기 `1.2E+10` 포함)
- 표준 단위: `cm` `kg` `mm` `m` `살` `세` `년` `월` `일` `장` `화` `권` `막` `%`
- 구분자: `,` `~` `-` `→` `:` `/` `;` `|` 및 줄바꿈
- 괄호·따옴표, 공백 유무, 엑셀 중복 접미사 `(2)`
- 스키마 이름: 필드키·필드명·타입·spec 시트명·그룹명

**B층 — 치환한다 (A층에 열거되지 않은 모든 것):**

- 고유명사(캐릭터명·지명·세력명·**세계관명·작품명**·표본 파일명) → `OO`
- 설정 문구·서술문 → `<서술 N자>`
- **창작된 도량형·역법·연호 등 비표준 단위 → `<단위 N자>`.** 형식 토큰처럼 보여도 세계관
  설정이므로 A층이 아니다. 그 단위가 무엇인지는 9장에서 대화로 확인한다.

**길이 경계:**

- 원문 40자 이하 → 골격을 유지해 표기. 예: `1장~3장: 주인공, 4장~: 조연` → `1장~3장: OO, 4장~: OO (21자)`
- 40자 초과 → 골격을 재현하지 말고 토큰 요약만. 예: `<서술 210자 · 줄바꿈 4 · '→' 2 · 콤마 3>`

> **왜 일괄 치환이 아닌가:** v1.0은 "원문 값을 옮기지 않는다"를 전면 적용했다. 그런데 이 작업의
> 측정 대상 자체가 `"007"`·`1.2E+10`·`이름(2)`·값 안의 콤마 — **창작 내용 0%, 형식 100%**다.
> 형식을 가리면 측정이 성립하지 않고, 리포트를 읽는 사람(=데이터 소유자)이 발견을 검증할 수도
> 없다. 경계선은 "무엇을 말할 수 있나"가 아니라 **"무엇이 git 이력에 남나"**에 있다.

#### ⑤ 합성 데이터

회귀 테스트로 남길 값어치가 있으면 구조만 본뜬 **합성 데이터**를 새로 만들어 커밋한다.
**실파일에서 잘라내지 않는다**(행 삭제·열 삭제·값 일부 치환 모두 금지) — 코드로 새로 생성한다.
합성 데이터는 **A층 토큰을 원문 그대로 보존해야 한다** — 선행 0·과학표기·접미사·구분자를
재현하지 못하는 픽스처는 애초에 유효한 회귀 케이스가 아니다. 치환 대상은 B층뿐이다.

## 2. 환경과 파일 실체 확인

### 2-1. 검증 환경

Linux/WSL·Java·Gradle 라이브러리 준비와 작업별 `JARS_DIR` 설정은
[status.md 4장](status.md#4-재현-기준선)을 따른다. 명령·기본 경로·실행 시간의 사본을 이곳에 두지 않는다.

이 런북의 6·7장 하네스는 `run_jvm_tests.sh`가 컴파일한 `$JARS_DIR/out-tests`와 POI 의존성을
사용한다. 해당 하네스를 실행할 때는 현재 소스·의존성에 맞게 준비와 컴파일이 성공했는지 확인하고,
같은 결과가 유효하면 재사용한다. 다른 작업과 같은 `JARS_DIR`을 공유하거나 동시에 실행하지 않는다.

### 2-2. 기준선이 실패했을 때 — 무엇을 포기하고 무엇을 계속하나

**게이트가 가르는 것은 '무엇을 실행하나'가 아니라 '실패가 무엇을 포기시키나'다.**

| 상태 | 6장 · 7장 | 2-3 · 4장 · 5장 · 9장 |
|------|-----------|----------------------|
| 컴파일 실패 (러너가 `exit 1`) | **불가능** — `out-tests`가 없다. `측정: 불가(컴파일 실패)`로 표기 | **그대로 진행.** POI + kotlin-stdlib만 있으면 되고 앱 코드를 한 줄도 안 쓴다 |
| 컴파일 OK + **의존 테스트** red | 해당 장을 `기준선 red — 결론 보류`로 표기하고 어느 테스트가 red인지 적는다 | 그대로 진행 |
| 컴파일 OK + 그 외 테스트만 red | **진행한다.** 각주에만 남긴다 | 그대로 진행 |

**의존 테스트**란 6·7장이 결론으로 삼는 클래스를 덮는 것들이다. `$CP`는
`run_jvm_tests.sh` 33~38행과 동일하게 만든다(그 파일에서 다시 읽어라 — 여기 복사본을 두면 드리프트한다):

```bash
java -cp "$JARS_DIR/out-tests:$CP" org.junit.runner.JUnitCore \
  com.novelcharacter.app.excel.ExcelCellValueTest \
  com.novelcharacter.app.excel.MergedCellMapTest \
  com.novelcharacter.app.excel.SheetValueConventionsTest \
  com.novelcharacter.app.excel.ImportFileFormatTest \
  com.novelcharacter.app.util.FieldValueTokenizerTest \
  com.novelcharacter.app.util.FieldValueResolverTest \
  com.novelcharacter.app.util.ValueDistributionsTest \
  com.novelcharacter.app.util.NumericBinningTest \
  com.novelcharacter.app.util.StatsFieldPolicyTest \
  com.novelcharacter.app.stats.StatsConsistencyTest
```

`ImageFilterHelperTest`가 red인 것은 6장의 셀 값 해석이나 7장의 `StatsDataProvider` 시간
측정과 아무 관계가 없다. **무관한 red로 측정을 통째로 버리지 말 것.** 반대로
`ExcelCellValueTest`가 red인데 6장 결과를 결론으로 올리지도 말 것 — 그건 깨진 코드의 출력을
사실로 적는 일이다.

**러너 건수는 불변식이 아니라 스냅샷이다.** 10장 2번의 예외(합성 회귀 테스트 추가)나 1-3⑤를 따르면
건수는 달라진다. 차이는 각주에 적고 넘어가라.

**"아무것도 못 봤습니다"로 끝내지 마라.** 어느 층이든 4·5·9장은 완주한다. 기준선 실패는 정지
사유가 아니다 — 정지 조건은 1-1의 표본 부재 하나뿐이다.

**단, 게이트를 내리는 것이 기록 수위를 올리는 구실이 되어서는 안 된다.** 1-3④의 2층 규칙과
10장 금지사항은 그대로 지킨다.

### 2-3. 파일의 실체부터 본다 (해석 전에)

하네스를 만들어 **시트 목록과 행 수**부터 찍는다. 구조를 모른 채 분석 코드를 쓰면 그 코드가
틀렸는지 데이터가 특이한지 구분할 수 없다.

**하네스는 `tools/usage-probe/Probe.kt`에 만들고 커밋한다. 데이터는 커밋하지 않는다.**
조건 셋을 지키면 러너를 건드릴 일이 애초에 사라진다:

1. **파일 경로는 `args[0]`으로 받는다.** 코드에 박지 않는다.
2. **`run_jvm_tests.sh`의 `SOURCES`/`TESTS`에 넣지 않는다.** `tools/` 아래이므로 러너와
   Gradle 소스셋 어디에도 들어가지 않는다(선례: `tools/jvm-stubs/`).
   러너 목록을 고치면 기준선 건수가 흔들리고, **지난 세션이 원복을 빼먹어 러너를 깬 사고가 바로
   거기서 났다.**
3. **출력은 집계만.** 행 단위 덤프 금지(10장 6번).

```kotlin
// tools/usage-probe/Probe.kt — 이 파일은 커밋한다. 데이터는 커밋하지 않는다.
import org.apache.poi.xssf.usermodel.XSSFWorkbook
import java.io.File

fun main(args: Array<String>) {
    XSSFWorkbook(File(args[0])).use { wb ->
        for (i in 0 until wb.numberOfSheets) {
            val sh = wb.getSheetAt(i)
            val header = sh.getRow(sh.firstRowNum)?.map { it.toString() }
            println("[${sh.sheetName}] last=${sh.lastRowNum} physical=${sh.physicalNumberOfRows} header=$header")
        }
    }
}
```

> `last`와 `physical`을 **둘 다** 찍는 이유는 아래 '시트 부재의 해석 규칙' 참조 —
> 앱이 구멍 뚫린 시트를 만드는 경로가 있어 `lastRowNum`만으로는 행 수가 틀리게 읽힌다.

**실행 레시피** (러너가 만든 `out-tests`를 클래스패스로 재사용하므로 재컴파일이 없다):

```bash
J=<JARS_DIR>                      # 2-1에서 쓴 그 경로
CP=<run_jvm_tests.sh 33~38행과 동일하게 조립>
java -cp $J/kotlin-compiler-embeddable-2.0.21.jar:$J/kotlin-stdlib-2.0.21.jar:$J/annotations-13.0.jar:$J/kotlinx-coroutines-core-jvm.jar:$J/trove4j.jar \
  org.jetbrains.kotlin.cli.jvm.K2JVMCompiler -nowarn -no-stdlib \
  -cp "$J/out-tests:$CP" -d $J/out-probe tools/usage-probe/Probe.kt
java -Dstdout.encoding=UTF-8 -cp "$J/out-probe:$J/out-tests:$CP" ProbeKt "<파일경로>"
```

> ⚠️ **컴파일러 자신의 클래스패스에 `kotlinx-coroutines-core-jvm.jar`이 있어야 한다.**
> 빠지면 `NoClassDefFoundError: kotlinx/coroutines/CoroutineScope`로 컴파일이 **시작조차 못 한다**
> (kotlin-compiler-embeddable 2.0.21이 자기 부트스트랩에 쓴다). `run_jvm_tests.sh`의 `KOTLINC`
> 정의에는 처음부터 들어 있었는데 v1.1의 이 레시피에만 빠져 있었다 — v1.2에서 맞췄다.
>
> ⚠️ **`-Dstdout.encoding=UTF-8`을 빼지 마라.** 이 환경은 LANG이 비어 있어(POSIX) 한글 출력이
> 전부 `?`로 깨진다. 깨진 채로 2-4에 가면 정상 파일을 형식 이탈로 오판한다.

**이 하네스가 4·5·6장의 단일 통로다.** 워크북을 한 번만 열고 4장(값 내부 패턴)·5장(열 채움률·
시트 집계)·6장(셀 해석·병합·토크나이저)의 집계를 **한 번의 순회에서 함께** 뽑아 한 블록으로
출력한다. 산출물에서는 절을 나눠 적되 **측정은 나누지 않는다.** 7장의 스냅샷 조립기는 이 파일을
이어서 키운 것이다.

#### 시트 부재의 해석 규칙 (이하 모든 측정 장에 적용)

앱은 **데이터가 없는 시트를 만들지 않는다**(`ExcelExporter.kt` 각 export 함수 첫머리의
빈-데이터 조기반환 — **행 번호는 측정 시점 좌표라 적지 않는다.** 찾는 법:
`grep -n 'isEmpty()) return' excel/ExcelExporter.kt`. 주석 원문도 있다 —
`// 다른 시트와 동일 — 빈 시트는 만들지 않는다`).

따라서 **"비어 있는 시트"는 관측될 수 없다.** 판정은 시트 *부재*로 하되, 부재는 셋이 겹치므로
단독으로는 결론이 되지 않는다:

| 원인 | 내용 |
|------|------|
| **(가)** | 그 기능을 쓰지 않았다 → 미도달 |
| **(나)** | 내보내기 다이얼로그에서 그 항목 체크를 껐다 (`ExcelExporter`의 항목별 `if (options.*)` 분기) |
| **(다)** | 데이터는 있으나 **참조가 끊겨 무음 탈락**했다 (`exportStateChanges` — 원본이 비지 않았는데 캐릭터 참조 소실로 전량 탈락 가능) |

**파일 안의 공짜 판별기:** `exportAppSettings`에는 **빈 검사가 없다** — 옵션이 켜져
있으면 고정 행이 항상 쓰인다. 그러므로 `앱 설정` 시트가 **없으면** 사용자가 항목 체크를 껐다는
확정 증거이고, 그때는 다른 모든 시트의 부재를 (나)로 의심해야 한다. (있어도 다른 항목까지
보증하지는 않는다 — 1-2의 Q0-a와 교차 확인한다.)

**헤더행만 있는 시트를 외부 편집 흔적으로 읽지 말 것 — 앱 스스로 만든다.**
`exportRelationshipChanges`는 1130행 검사를 통과해 시트를 만든 뒤 1145행
`val rel = relMap[rc.relationshipId] ?: return@forEachIndexed`로 행을 건너뛰면서 인덱스는
`sheet.createRow(i + 1)`(1148행)에 고정한다 → **구멍 뚫린 시트**, 전부 고아면 **헤더만 남는 시트**.
따라서 헤더만 있는 시트와 `last + 1 ≠ physical`인 시트는 **(다) 참조 소실 후보로 별도 집계**한다.

### 2-4. 파일이 무엇인지 앱의 판별기로 확인

`ImportFileFormat`(순수 JVM, 러너 SOURCES에 있음)이 xlsx / 이미지 포함 ZIP / 월드패키지를
가른다. 사용자의 파일이 앱이 기대하는 형식으로 판별되는지 확인하라 —
여기서 어긋나면 그 자체가 첫 발견이다.

## 4. 측정 1 — 우회 흔적 ("없어서 손으로 한 것") · 산출물 §3

**이 장이 이 작업에서 가장 값지다.** 필드값 *안에* 구조가 들어 있으면, 그건 앱이 그 표현을
담지 못해 사용자가 우회한 자국이다. 앱 코드가 필요 없으므로 **환경이 막혀도 완주한다.**

### 4-1. 먼저 열어 본다 (정규식 이전)

4-2의 6패턴은 훑기의 목적지가 아니라 훑고 난 뒤의 체크리스트다. 먼저 `캐릭터 필드값` 시트의
값 전체를 훑어 아래 넷을 뽑는다:

1. **값 길이 분포** — 상위 20개 값을 필드명과 함께 읽는다. **읽기는 세션 안에서만.**
   산출물에는 필드명·길이·구조만 옮기고 1-3④를 적용한다.
2. **필드별 값 길이 중앙값 상위 5개 필드** — 긴 필드는 대개 '못 담아서 몰아넣은' 필드다.
3. **앱의 타입 선언과 값의 불일치 건수** — NUMBER인데 수치로 안 읽히는 값 / SELECT인데 옵션에
   없는 값 / DATE인데 날짜가 아닌 값. **이 수치는 산출물 §5 '변수 제어'의 유일한 정량 근거이므로
   그 절에 그대로 인용한다.**
4. **여러 필드에 반복 출현하는 동일 문자열** — 정규화되지 않은 수동 분류의 흔적.
   **문자열 자체는 옮기지 않는다.** `"값A: 3개 필드에 27회"`처럼 필드 수·출현 횟수만 적는다.

### 4-2. 알려진 6패턴 계수

| 패턴 | 정규식(예시) | 시사점 |
|------|-------------|--------|
| 값 안의 콤마 | `,` 포함 & 필드 타입이 TEXT & 표시 형식 미설정 | MULTI_TEXT/콤마 목록 설정이 발견되지 않음 (동시에 통계가 통값으로 세는 지점 — S-18) |
| 단위가 붙은 수치 | `^\d+\s*(cm\|kg\|살\|세\|년)` & 타입 NUMBER/TEXT | 타입 설계와 입력 습관의 괴리 → 통계가 조용히 실패 |
| 시계열 표기 | `\d+\s*(장\|화\|권\|막)\s*[~-]` 또는 `→` | **상태변화 기능이 있는데** 그 용도에 안 맞거나 미도달 |
| 괄호 별칭 | `^[^()]+\([^()]+\)$` (이름 필드) | 이명/별칭 설계와 실사용의 괴리 |
| 다른 캐릭터 이름 포함 | 값 안에 캐릭터 시트의 이름이 등장 | 관계 기능이 그 표현을 담지 못함 |
| 줄바꿈 다수 | `\n` 3개 이상 | 서술형 필드/여러 줄 표시 형식이 필요한데 미설정 |

**보고는 1-3④의 2층 규칙을 따른다.** 형식 토큰(A층)은 원문 그대로, 고유명사·서술(B층)만
치환한다. 예: `OO 필드 · 12건 · 형태: '178cm', '3장~5장: OO'`.
**단위를 통째로 `<단위>`로 덮지 마라** — 이 표의 처방은 cm/kg/살/년마다 갈린다.

**판정은 정규식 휴리스틱이므로 오탐이 섞인다.** 특히 괄호 별칭 `^[^()]+\([^()]+\)$`는 엑셀
중복 접미사 `이름(2)`(6장 참조)와 수량 표기 `천(2벌)`도 잡고, `1장~3장: OO, 4장~: OO` 같은
값은 `값 안의 콤마`와 `시계열 표기` 두 행에 **동시 계상**된다. 그러므로:

- 각 패턴 건수는 **오탐 후보를 분리해 적는다**: `12건(그중 접미사·수량 의심 3건)`
- 중복 계상된 건수는 표 하단에 `※ N건은 2개 패턴에 중복 계상` 명시
- 판정이 갈리는 값은 **9장에서 대화로 원문을 보여주고 사용자에게 확인한다**

## 5. 측정 2 — 기능 도달률 ("되는데 안 쓰는 것") · 산출물 §2

각 지표를 **분모와 함께** 적는다. "적다/많다"가 아니라 "50개 중 3개"라고 써야 판단이 된다.
이 장도 앱 코드가 필요 없다.

> 5-1·5-2의 지표는 전부 `필드 정의`·`필드 데이터` 두 시트에 의존하고, 그 둘은
> `options.fieldDefinitions` **하나로 함께** 가려진다(`ExcelExporter.kt:92`). 두 시트 중
> 하나라도 없으면 2-3의 '시트 부재의 해석 규칙'을 그대로 적용하고, 5-2의 "전부 AUTO면 큐레이션
> 기능 전체가 미도달"도 **미확정**으로 낮춘다.

### 5-1. 필드 설계

| 지표 | 어디서 | 무엇을 뜻하나 |
|------|--------|--------------|
| 타입 분포 | `필드 정의` 시트의 `타입` | TEXT 일변도면 타입 시스템(SELECT·GRADE·CALCULATED·BODY_SIZE)이 **발견되지 않은** 것 |
| `설정(JSON)`의 **키별 기본값 이탈** | 같은 시트의 `설정(JSON)` | 코드의 기본 설정 인스턴스를 직렬화해 **키 단위로** 비교한다(키 순서·공백 무시). 보고: `필드 N개 중 이탈 키가 1개 이상인 필드 M개 / 이탈 키 종류별 건수: 표시형식 a, 통계포함 b, 구간 c, 수식 d` |
| 세계관 간 같은 뜻 다른 `필드키` | `필드 정의` 시트 | 원칙 05의 "다른 작품 필드 불러오기"가 발견·사용되지 않는다는 증거 |
| 그룹·순서 사용 | `그룹`, `순서` | 정리·재배치 기능이 쓰이는가 |
| 사건 필드 존재 | `대상` = 사건 | 사건 커스텀 필드(B-10 계열)가 실제로 쓰이는가 |

> **`설정(JSON)` 판정 규칙:** M=0이면 **톱니 미발견**(처방: 진입점·발견성). M>0인데 이탈 키가
> 1~2종에 몰려 있으면 **톱니는 열지만 나머지는 안 만짐**(처방: 그 나머지 키들의 **기본값 설계**
> 개선). 이탈 키가 고르게 퍼져 있으면 **자율성 도달**이며, 그 경우에만 '설정 일관성'이 우선
> 과제가 된다. 비교 코드는 `tools/usage-probe/`에 합성 데이터 테스트와 함께 커밋해 재현 가능하게 둔다.

### 5-2. 값 라이브러리 (`필드 데이터` 시트)

| 지표 | 컬럼 | 뜻 |
|------|------|-----|
| `출처` 분포 | AUTO / MANUAL / IMPORT / AI | **전부 AUTO면 큐레이션 기능 전체가 미도달.** 그러면 별칭 접기(S-18)·카테고리 그룹핑의 실제 가치가 재평가된다 |
| 별칭/표시라벨/카테고리 채움률 | `별칭(콤마구분)`, `표시라벨`, `카테고리` | 세 기능 각각의 도달률 |
| `사용횟수` 0 + 큐레이션됨 | `사용횟수` | 만들어 놓고 안 쓰는 값 — 정리 기능이 필요한지의 근거 |
| `숨김` 사용 | `숨김` | 입력 제안 조절을 실제로 쓰는가 |

### 5-3. 기능별 사용 여부 (시트 존재/행수)

대상 시트 — **이 이름들은 `SheetSpec.kt`의 `sheetName =` 값이다. 반드시 그 파일에서 다시 읽어
대조하라.** 런북에 적힌 이름과 코드가 다르면 **코드가 정답**이다.

`세력` · `세력 소속` · `세력 관계` · `캐릭터 관계` · `관계 변화` ·
`캐릭터 상태변화` · `이름 은행` · `필드 템플릿` · `목록 프리셋` ·
`검색 프리셋` · `이미지` · `등급 체계`(U-1 — 존재 자체가 등급 체계 사용의 신호.
이 시트도 `options.fieldDefinitions`로 함께 가려진다, 5-1 참조)
(괄호로 달던 행 번호는 밀리므로 없앴다 — 이름의 정본은 `SheetSpec.kt`)

> **v1.0의 오기 3건을 바로잡았다:** `상태 변화` → **`캐릭터 상태변화`**, `사용자 템플릿` →
> **`필드 템플릿`**, `이미지 메타` → **`이미지`**. (`캐릭터 관계`는 v1.0에 없던 **추가**다.)
> 오기는 세션이 시트를 못 찾게 만들어 **`0건 — 미도달`이라는 허위 발견**을 낳는다.
>
> **저장소 전체 grep으로 확인하지 말 것** — `상태 변화`는 `ExportOptions.kt`의 UI 라벨과
> `ExcelImportService.kt`의 표시명으로 **실재하므로** grep 히트가 거짓 안심을 준다.
> 반드시 `SheetSpec.kt`의 `sheetName =` 에서 읽어라.

정확 일치로 못 찾으면 `isSuffixedVariantOf`(`SheetSpec.kt:205`)로 접미사 변형(`이름(2)`)을
함께 검사한 뒤에 0건으로 확정한다.

**판정 — 2-3의 '시트 부재의 해석 규칙'과 1-2의 답을 함께 적용한다:**

| 관측 | 표기 |
|------|------|
| 시트 N행 | `세력: 47건 — 활발` |
| 시트 없음 + Q0-a가 '예' + DB 0행 또는 DB 미상 | `세력: 시트 없음 · 0건 — 미도달(확정)` |
| 시트 없음 + Q0-a가 '아니오/기억 안 남' | `세력: 시트 없음 — 미도달(미확정: 내보내기 제외 가능)` |
| 시트 없음 + DB에 행 있음 | `세력: 시트 없음 / DB 47행 — 부분 내보내기(판정 제외)` → 전체 항목 재수집 요청 |
| 시트 있고 헤더만 / `last+1 ≠ physical` | `관계 변화: 헤더만 · 행 구멍 N개 — 참조 소실 의심(1145행)` — 미도달이 **아니다** |

**미확정·판별 불가 항목은 산출물 §6(백로그 재정렬)의 근거로 쓰지 않는다.** 근거 없는 재정렬은
다음 세션을 잘못 이끈다. §2에서는 `❌ 미도달`이 아니라 `⚠️`로 표기하고 9장 질문 목록 맨 위에 올린다.

**DB에 행이 있고 시트가 없는데 사용자가 "전부 체크하고 내보냈다"고 답한 경우에 한해**
내보내기 결함으로 신규 백로그를 세운다. 그 전에는 세우지 않는다.

> **주의:** 실제 시트 목록에는 **세계관 이름으로 동적 명명된 캐릭터 시트**가 섞여 있다
> (`SheetSpec.kt:399` — `sheetName = ""  // Sheet name is set dynamically`). 산출물에는 위 spec
> 고정 시트명만 적고, **워크북의 실제 시트명 목록(세계관명·작품명·`미분류 캐릭터` 포함)은 어떤
> 형태로도 옮기지 않는다**(1-3④ B층).

## 6. 측정 3 — 엑셀 왕복 무결성 (개발 의도 4번) · 산출물 §1

**질문: 내보낸 파일을 그대로 다시 들이면 무엇이 달라지는가?**

앱의 임포트 경로 중 **순수 JVM으로 실행 가능한 부분**을 그대로 태운다.
이 장부터는 `out-tests`가 필요하므로 2-2의 게이트가 적용된다.

| 검사 | 쓰는 코드 | 무엇을 보나 |
|------|----------|------------|
| 시트 정체 판별 | `headersMatchSpec`·`isSuffixedVariantOf` (`SheetSpec.kt:192, 205`) | 사용자 파일의 시트가 spec으로 정확히 잡히는가. 접미사 변형(`이름(2)`)이 있는가 |
| 셀 값 해석 | `ExcelCellValue` | 날짜로 자동 변환된 셀, 선행 0(`"007"`), 과학표기(`1.2E+10`)가 실제로 있는가 → **B-27** |
| 병합 셀 | `MergedCellMap` | 실제로 병합된 셀이 있는가 → **B-7** 산출물이 실제 데이터에서 작동하는가 |
| 다중값 구분 | `FieldValueTokenizer.splitForStats` | **값 안에 콤마가 든 값이 몇 건인가** → B-27 ②의 실측 |
| 헤더 별칭 | `ExcelHeaderAliases` | 사용자가 헤더를 바꿔 썼는가 |

> **`resolveSpecSheet`를 쓰려 하지 마라.** `ExcelImportService.kt:1596`의 **private** 함수이고
> 그 파일은 러너 SOURCES에 **없다**(SOURCES에 있는 건 `SheetSpec.kt`뿐이다). 하네스에서
> '정확 일치 → 헤더 검증 → 접미사 변형' 순서를 재현해 쓰고, 원본 판정과 갈릴 수 있는 지점
> (`looksLikeCharacterSheet` 미적용, 관대 매칭 범위 차이)을 산출물에 한 줄로 명시한다.
> **두 판정이 갈릴 여지가 보이면 그 차이 자체를 발견으로 기록한다.**

**보고 형식:** 각 항목을 `발생 0건` 또는 `N건 = 유형A a건 / 유형B b건 / 유형C c건`으로 적고,
**유형마다 대표 예 1개**를 싣는다. 유형이 몇 개든 각 1개씩이므로 총량은 저절로 제한된다.

**이 장의 검사 대상(`"007"`, `1.2E+10`, `이름(2)`, 값 안의 콤마)은 전부 A층이므로 원문 그대로
적는다**(1-3④). 형식을 가리면 측정 자체가 성립하지 않는다. 같은 값에 섞인 고유명사·서술만
B층으로 치환한다.

예: `값 안의 콤마 — 총 38건 = 목록형 31 / 문장부호형 5 / 천단위형 2.`
`대표: 'OO, OO, OO' · '그래서, OO는 <서술 12자>' · '1,000'`

**유형 분류가 곧 처방 분기다. "다수면 즉시 수리"는 유형별로 판단한다** — 목록형이 다수면
B-27 ↑, 문장부호형이 다수면 그것은 토크나이저가 **쪼개면 안 되는** 케이스이므로
**역방향 수리**(구분자 고지·옵트인)로 적는다.

0건인 항목은 그 사실 자체가 결론이다 — **백로그 우선순위를 내리는 근거**가 된다.

## 7. 측정 4 — 규모 실측 (추정을 사실로) · 산출물 §4

지금까지의 성능 판단은 전부 **추정**이다("캐릭터 300 × 필드 50이면 몇 초"). 실제로 잰다.

### 7-1. 최소 스냅샷 조립 (이번 세션 범위)

`StatsSnapshot`의 **6개 목록만** 채운다: `universes` · `novels` · `characters` ·
`fieldDefinitions` · `fieldValues`(캐릭터 시트 + `캐릭터 필드값` 시트) · `valueEntries`.
나머지 목록은 `emptyList()`로 두고 **산출물 §4에 `0건`이 아니라 `미조립`이라고 적는다**
(0건으로 적으면 그 자체가 허위 발견이다). `StatsDataProvider`는 순수 JVM에서 실행되므로
스냅샷만 만들면 돈다.

### 7-2. 시간 측정

`computeSummary` / `computeFieldInsights` / `computeFieldAnalysis` / `detectPatterns` /
`computeCrossNovelComparison` 각각 시간 측정. 함께 확인할 것:

- 값 종수가 많은 필드에서 **'기타 N종' 접기**가 실제로 어떻게 보이는가(S-17 산출물)
- 사용자 구간 설정이 있는 필드에서 **'구간 밖'**이 몇 건인가(B-40 산출물)
- CALCULATED 필드의 수식이 **실제로 평가되는가**, NaN이 몇 건인가(S-11·로드맵 5)
- 별칭이 실제로 접히는가(S-18 산출물)

### 7-3. 스케일 스윕 (1점 측정은 곡선을 못 그린다)

7-1의 스냅샷을 **구조 그대로 ×3 / ×10 / ×30으로 복제 증폭**한 합성 스냅샷을 만든다
(캐릭터 ID·값만 치환, 필드 정의와 값 종수 분포는 유지). 같은 계산을 각 배율에서 재고 표로 적는다.

곡선이 선형이면 받쳐주는 확장성은 확인된 것이고, 초선형이면 **어느 배율에서 무너지는지**가 곧
앱의 실제 상한이다. §5의 '최적화 가정은 맞았나/틀렸나'는 이 표로만 답할 수 있다.
합성 증폭은 원문 값을 쓰지 않으므로 1-3과 충돌하지 않으며, 오히려 1-3⑤가 권하는 '구조만 본뜬
합성 데이터'가 정확히 이것이다 — **`tools/usage-probe/`에 커밋해 다음 세션이 같은 스윕을
재현하게 한다.**

느리면 어디가 느린지까지 적는다(대개 `getFieldValues`의 config 재파싱 — 백로그 **B-42**의 실측 근거).

### 7-4. 후속 작업으로 넘기는 것 — `실사용 규모 실측 2단계`

`events` · `crossRefs` · `relationships` · `relationshipChanges` · `stateChanges` · `factions` ·
`factionMemberships` · `nameBank` · `eventField*` 조립 → `computeEventStats` ·
`computeRelationshipStats` · `computeFactionStats` · `computeRanking`.

> `computeRanking`은 `fieldDefIds`가 필요하다 — **값 종수가 가장 많은 필드 1개**를 넘긴다.
> 빈 목록을 넘기면 빈 결과가 즉시 돌아와 측정이 무의미해진다.

하네스가 `tools/usage-probe/`에 커밋돼 있으므로 이 후속 작업은 조립기만 이어 쓰면 된다.

## 8. DB 파일이 함께 있다면

### 8-1. 5-3의 대조군 (이번 범위 — 이것만 한다)

`.db`의 유일한 용도는 **시트 부재가 (가) 미도달인지 (나) 부분 내보내기인지 가르는 것**이다.
5-3 대상 시트에 대응하는 테이블의 **행 수만** 센다:

```bash
cp "<원본.db>" "$SCRATCH/probe.db"     # 반드시 사본. 원본은 열지 않는다
sqlite3 "$SCRATCH/probe.db" "SELECT COUNT(*) FROM <테이블>;"
```

- **`SELECT *` 결과를 문서·PR·커밋 어디에도 옮기지 않는다.** 행 수만.
- **사본은 저장소 밖(세션 스크래치패드)에 만든다.** 저장소 트리 안에는 어떤 이름으로도
  `.db`/`.db-shm`/`.db-wal`을 두지 않는다(1-3②가 2중 방어이지만 의존하지 않는다).
- `.db`가 없으면 5-3은 `판별 불가`로 남기고 9장으로 보낸다. 그것으로 충분하다.

### 8-2. B-9 마이그레이션 실검증 — **이번 범위 밖**

`.db`가 함께 올라와 있으면 **그 사실만 산출물 §0에 적고**
(예: `.db 동봉 — 실DB 마이그레이션 실검증 가능`) 별도 작업으로 넘긴다.
**이 세션에서 열지 않는다** — 엑셀 측정과 근거를 공유하지 않고, 예산이 남지 않은 시점에
시작하면 산출물이 미완으로 끝난다. 또한 `tools/verify_room_migration*.py`는 **합성 DB
전용이고 `--db` 인자가 없어** 실파일에 그대로 돌릴 수 없다 — 그 인자를 추가하는 것 자체가
별도 작업이다.

## 9. 데이터로 답이 **안 나오는 것** — 반드시 물어라 · 산출물 §7

데이터는 **"안 쓴다"는 사실**은 보여주지만 **이유**는 보여주지 않는다.
그런데 이유마다 처방이 정반대다:

| 이유 | 처방 |
|------|------|
| 있는 줄 몰랐다 | 발견성 개선(진입점·안내) |
| 필요 없다 | 기능 제거 또는 기본값에서 숨김 |
| 불편해서 안 쓴다 | 조작 개선(원칙 04) |
| **있는 건 알지만 내 표현을 못 담는다** | **기능 확장 — 그 표현형을 수용하도록. 제거·숨김 후보에서 제외** |
| **사실은 쓰고 있는데 이 파일에 안 담겼다(부분 내보내기)** | **도달률 판정 대상이 아님 — 표본 재수집** |

5장에서 미도달로 잡힌 기능에 대해 4장에서 **같은 표현 욕구의 우회 흔적**이 발견되면
(예: `캐릭터 상태변화` 시트 없음 + 값 안 시계열 표기 N건), 그 항목의 이유는 **데이터로 이미
확정된 4번째 행이다. 묻지 말고 그렇게 기록한다.**

> **이 두 행이 없으면** 5-3이 잡은 시트 부재가 "필요 없다 → 기능 제거"로 흘러,
> **손으로 우회할 만큼 필요했던 기능을 제거**하게 된다. 4장이 가장 값진 장인 이상
> 오분류의 대가가 가장 큰 지점이다.

**미도달로 판정된 기능의 이유를 사용자에게 묻는다.** 한 줄 답이면 충분하고, 그 한 줄이 백로그
순위를 뒤집는다. 지난 세션들에서 가장 값진 발견(휴지통 '유령 유실 예고')도 사용자 관찰 한 줄에서 나왔다.

**물을 때는 반드시 선택지를 준다.** "어떠셨어요"는 답하기 어렵다. 분량은 아래 순서로 정한다.

1. **묻지 않을 것을 먼저 뺀다.** (a) 위 표에 따라 데이터로 이유가 확정된 항목.
   (b) 어느 처방을 골라도 **다음 행동이 같은** 항목. (c) '기능'이 아닌 관측치
   (5-1·5-2에는 기능이 아닌 행이 섞여 있다 — 예: 그룹·순서 사용).
2. **남은 것의 순서는 오답의 대가 순.** **'기능 제거'가 후보로 오를 수 있는 항목**을 먼저 묻는다.
   되돌리기가 가장 어려운 처방이기 때문이다. 5-3의 `판별 불가` 항목이 그다음이다.
3. **한 번에 3~5개씩** 묻는다. **3~5는 한 턴의 질문 수이지 묻는 총량이 아니다.**
   남은 것은 다음 턴에 묻는다.
4. **묻되 기다리지 않는다.** 산출물 문서를 먼저 완성해 커밋하고, 질문은 §7에 `답: (미회신)`
   칸을 비운 채 남긴다. 세션은 거기서 종료한다. 답이 오면 다음 세션이 그 칸만 채우고 §6을
   갱신한다 — **답 대기가 산출물을 막아서는 안 된다.**
5. **끝내 답을 못 받은 항목은 임의로 조정하지 않는다.** §2의 `이유` 열에
   `이유 미상 — 조정 보류`라고 적는다.

**우회 흔적(4장)에는 위 선택지가 맞지 않는다.** 그쪽에는
**"앱 기능으로 하려다 안 된 것인가, 그런 기능이 있는 줄 몰랐던 것인가"**를 선택지로 준다.

> **질문은 대화에서 이뤄지며 커밋되지 않는다.** 우회 흔적을 물을 때는 해당 값을 **원문 그대로**
> 보여준다 — 상대가 데이터 소유자이고, 값을 가리면 무엇을 묻는지 알 수 없다. 치환된 채로
> "OO 필드에 시계열 표기가 12건 있는데"라고 물으면 사용자가 자기 파일을 다시 열어야 하고,
> 그것은 리포트가 스스로 조작 마찰(원칙 04)을 만드는 것이다.
> **4장의 오탐 확인과 비표준 단위 확인도 이 자리에서 원문으로 한다.**

## 10. 금지사항

1. **데이터를 커밋하지 않는다.** 원문 값(B층)을 **커밋·push되는 모든 표면**에 넣지 않는다 —
   산출물 문서, 커밋 메시지, PR 제목·본문, 테스트 픽스처, 저장소에 남는 스크립트, 새로 만드는
   파일명. 표기는 1-3④의 2층 규칙을 따른다(A층=형식 토큰은 원문 그대로).
   PR 본문에는 수치와 백로그 조정만 적는다(예: '우회 흔적 4패턴 · 총 N건, B-27 상향').
   **반대로 세션 대화·터미널 출력·스크래치패드에는 이 제한이 적용되지 않는다** —
   사용자 본인의 데이터를 본인에게 보이는 것이며 어디에도 남지 않는다.
   이 규칙이 강한 이유는 산출물이 push되고 master force-push가 금지되어 **되돌릴 수 없기
   때문이다.** 판단이 서지 않는 토큰은 문서에서 가리고 대화로 확인하라 — 나중에 덧붙이는 것은
   언제든 가능하지만 커밋을 되돌리는 것은 불가능하다.

2. **이 작업 중에 코드를 고치지 않는다.** 발견은 문서로 남기고, 수리는 순위가 정해진 뒤 별도로.
   - **예외 1(즉시 수리):** 파일을 읽다가 **크래시하는** 경로. 재현 케이스는 합성 데이터로
     만들어 테스트에 남긴다.
   - **예외 2(즉시 고지, 수리 아님):** **사용자 데이터가 아무 알림 없이 유실·왜곡되는** 경로를
     발견하면 — 코드는 건드리지 말되 (1) 그 자리에서 대화로 사용자에게 경고하고
     ("이 파일을 지금 임포트하면 N건이 사라집니다"), (2) 산출물 **§0-1 즉시 주의**에 올리고,
     (3) §6 재정렬안에서 무조건 최상위로 둔다.
     개발 의도 2번(변수 제어)이 이 런북에 걸어 둔 최소 요구다.
   - 여기서 말하는 '코드'는 `app/src`다. **런북 자신의 오기(시트명·심볼명·장 번호)는 발견 즉시
     고치고 문서 이력에 한 줄 남긴다** — 그것은 코드 수정이 아니다.

3. **다른 사용자로 일반화하지 않는다.** "창작자들은 …한다"는 이 표본으로 말할 수 없다.
   반면 **1-2에서 '전체 내보내기'로 확인된 경우, 이 사용자 본인에 대해서는 단정형으로 쓴다** —
   그 사람의 데이터를 전부 봤고, 리포트의 독자도 그 사람이다. 헤지된 결론은 다음 세션이 무시한다.
   '부분'으로 확인되면 5-3 판정을 전부 `판별 불가`로 내리고 그 범위에서만 말한다.

4. **임시 하네스를 러너 목록에 남기지 않는다** — 더 정확히는 **애초에 넣지 않는다.**
   하네스는 `tools/usage-probe/`에 두고 별도 kotlinc 호출로 컴파일한다(2-3 실행 레시피).
   러너의 `SOURCES`/`TESTS`를 건드리면 기준선 건수가 흔들리고, 원복 사고가 바로 그때 난다.
   `run_jvm_tests.sh`를 편집해야 할 일이 생기면 사본(`$SCRATCH/harness.sh`)을 고쳐 쓰고,
   작업 전후로 `git status --porcelain tools/`를 확인한다.

5. 측정값은 **분모와 함께.** "적다"는 판단이 아니라 인상이다.

6. **하네스는 집계만 출력한다.** 행 단위 덤프 금지. 예시가 필요하면 필드당 **최대 3건**을
   1-3④에 맞춰 출력한다. 원문 셀을 stdout에 대량으로 찍는 것은 세션 예산을 데이터 크기에
   비례해 태운다 — **뒤쪽 장에 도달하지 못하는 가장 흔한 경로다.**
   §3의 `판정식` 열과 §3-B의 서술형 기록에도 1번이 그대로 적용된다. 새로 발견한 패턴일수록
   기존 치환 형태가 없어 원문 인용의 유혹이 크다. **형태를 새로 정의해서 적을 것.**
