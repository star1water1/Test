# 실사용 대조 런북 — 엑셀 파일 하나로 시작하는 세션

> **이 문서를 읽는 세션에게:** 사용자가 실사용 데이터(앱의 엑셀 내보내기 파일)를 저장소에
> 올려 두었을 것이다. 이 문서 하나로 끝까지 진행하도록 썼다. 순서대로 따르되,
> **6장(산출물)까지가 이번 작업의 범위다** — 코드 수정은 그 문서에서 확정된 것만, 별도로 한다.

---

## 0. 이 작업이 무엇이 **아닌지** 부터

기존 감사·색출 문서(`superficial_feature_audit_2026-07.md`, `remaining_work_2026-07.md`)는
**"있는데 안 되는 것"**을 찾았다. 코드를 읽으면 나오기 때문이다.

이 작업은 다르다. 실사용 데이터만이 보여주는 것은 둘이다:

| 부류 | 예 | 코드로 찾을 수 있나 |
|------|-----|--------------------|
| **되는데 안 쓰는 것** | 값 라이브러리 큐레이션(별칭·카테고리)이 전부 AUTO — 만들었지만 아무도 도달하지 못한 기능 | ❌ |
| **없어서 우회한 흔적** | TEXT 필드값 안에 `1장~3장: 주인공, 4장~: 조연` — 상태변화 기능이 그 용도에 안 맞아 손으로 우회한 자국 | ❌ |

그러므로 **결함을 고치러 들어가지 말 것.** 이번 산출물은 "무엇이 실제로 쓰이고,
무엇이 앱의 설계 의도와 어긋나 있는가"의 **대조표**이고, 그것이 다음 작업의 우선순위를 정한다.

`CLAUDE.md`의 개발 의도 4질문(받쳐주는 확장성 / 변수 제어 / 자율성 우선 / 엑셀 왕복 무결성)에
**추정이 아니라 수치로** 답하는 것이 최종 목표다.

## 1. 입력 확인

### 1-1. 파일 찾기

사용자가 올린 파일은 저장소 어딘가에 있다. 이름은 정해져 있지 않다.

```bash
find . -maxdepth 3 \( -name '*.xlsx' -o -name '*.ncworld' -o -name '*.zip' -o -name '*.db' \) \
  -not -path './.git/*' -not -path './build/*' | head
```

- **`.xlsx`** — 앱의 엑셀 내보내기. 이 런북의 주 대상이다.
- **`.ncworld` / `.zip`** — 월드패키지 또는 이미지 포함 백업. `ImportFileFormat`이 3분기로 판별한다(2-3 참조).
- **`.db`** — Room 데이터베이스. 있으면 B-9(마이그레이션 실검증)까지 열린다. 8장 참조.

파일이 없으면 **거기서 멈추고 사용자에게 물어라.** 추측으로 만든 표본으로 이 작업을 하면
결론이 전부 허구가 된다(그것이 이 작업의 유일한 실패 방식이다).

### 1-2. 절대 커밋하지 않는다

`.gitignore`에 이미 실사용 데이터 확장자가 등재돼 있다(`/*.xlsx` 등). **확인하고**, 없으면 먼저 추가하라.
`git status`에 데이터 파일이 뜨면 그 상태로는 어떤 커밋도 하지 말 것.

산출물 문서에도 **원문 값을 그대로 옮기지 않는다.** 캐릭터 이름·설정 문구는 창작물이다.
필요하면 `"OO(캐릭터명)"`, `"값1"`처럼 치환하고, **구조·개수·패턴만** 적는다.
회귀 테스트로 남길 값어치가 있으면 **구조만 본뜬 합성 데이터**를 새로 만들어 커밋한다.

## 2. 환경 구축과 첫 관문

### 2-1. 검증 환경 (세션마다 사라진다)

```bash
JARS_DIR=<이 세션의 스크래치패드> tools/setup_jvm_env.sh
JARS_DIR=<같은 경로>            tools/run_jvm_tests.sh     # 기준선 재현 (현재 629건)
```

`setup_jvm_env.sh`가 jar 수집과 androidx 스텁 컴파일을 다 한다(막히기 쉬운 세 지점은
스크립트 주석에 적혀 있다). **손대기 전에 629건부터 재현할 것** — 재현되지 않으면
이후 모든 측정이 신뢰할 수 없다.

이 환경에는 **POI가 이미 들어 있다.** 즉 사용자의 엑셀 파일을 실제로 열어 돌릴 수 있다.

### 2-2. 파일의 실체부터 본다 (해석 전에)

임시 하네스를 만들어 **시트 목록과 행 수**부터 찍는다. 구조를 모른 채 분석 코드를 쓰면
그 코드가 틀렸는지 데이터가 특이한지 구분할 수 없다.

```kotlin
// 임시 — 커밋하지 않는다. tools/run_jvm_tests.sh의 TESTS에 넣었다면 반드시 원복할 것.
import org.apache.poi.xssf.usermodel.XSSFWorkbook
import java.io.File

fun main() {
    XSSFWorkbook(File("<파일경로>")).use { wb ->
        for (i in 0 until wb.numberOfSheets) {
            val sh = wb.getSheetAt(i)
            val header = sh.getRow(sh.firstRowNum)?.map { it.toString() }
            println("[${sh.sheetName}] rows=${sh.lastRowNum} header=$header")
        }
    }
}
```

> ⚠️ 러너의 `TESTS`/`SOURCES` 목록에 임시 파일을 넣었다면 **반드시 원복**하라.
> 지난 세션에 검증 에이전트가 이것을 빼먹어 러너 자체가 깨졌다.

### 2-3. 파일이 무엇인지 앱의 판별기로 확인

`ImportFileFormat`(순수 JVM, 러너 SOURCES에 있음)이 xlsx / 이미지 포함 ZIP / 월드패키지를
가른다. 사용자의 파일이 앱이 기대하는 형식으로 판별되는지 먼저 확인하라 —
여기서 어긋나면 그 자체가 첫 발견이다.

## 3. 측정 1 — 엑셀 왕복 무결성 (개발 의도 4번)

**질문: 내보낸 파일을 그대로 다시 들이면 무엇이 달라지는가?**

앱의 임포트 경로 중 **순수 JVM으로 실행 가능한 부분**을 그대로 태운다
(러너 SOURCES에 이미 있는 것들이다):

| 검사 | 쓰는 코드 | 무엇을 보나 |
|------|----------|------------|
| 시트 정체 판별 | `resolveSpecSheet`/`headersMatchSpec` (`SheetSpec.kt`) | 사용자 파일의 시트가 spec으로 정확히 잡히는가. 접미사 변형(`이름(2)`)이 있는가 |
| 셀 값 해석 | `ExcelCellValue` | 날짜로 자동 변환된 셀, 선행 0(`"007"`), 과학표기(`1.2E+10`)가 실제로 있는가 → **B-27** |
| 병합 셀 | `MergedCellMap` | 실제로 병합된 셀이 있는가 → **B-7** 산출물이 실제 데이터에서 작동하는가 |
| 다중값 구분 | `FieldValueTokenizer.splitForStats` | **값 안에 콤마가 든 값이 몇 건인가** → B-27 ②의 실측. 0건이면 우선순위 하락, 다수면 즉시 수리 |
| 헤더 별칭 | `ExcelHeaderAliases` | 사용자가 헤더를 바꿔 썼는가 |

**보고 형식:** 각 항목을 "발생 0건 / N건(예시 3개, 값은 치환)"으로.
0건인 항목은 그 사실 자체가 결론이다 — **백로그 우선순위를 내리는 근거**가 된다.

## 4. 측정 2 — 기능 도달률 ("되는데 안 쓰는 것")

각 지표를 **분모와 함께** 적는다. "적다/많다"가 아니라 "50개 중 3개"라고 써야 판단이 된다.

### 4-1. 필드 설계

| 지표 | 어디서 | 무엇을 뜻하나 |
|------|--------|--------------|
| 타입 분포 | `필드 정의` 시트의 `타입` | TEXT 일변도면 타입 시스템(SELECT·GRADE·CALCULATED·BODY_SIZE)이 **발견되지 않은** 것 |
| `설정(JSON)`이 기본값인 비율 | 같은 시트의 `설정(JSON)` | 통계 설정·표시 형식·구간·수식이 전부 여기 있다. **거의 기본값이면** 톱니/분석 설정이 실사용에 도달하지 못한 것 — 그러면 '설정 일관성'보다 **기본값 설계**가 중요해진다 |
| 세계관 간 같은 뜻 다른 `필드키` | `필드 정의` 시트 | 원칙 05의 "다른 작품 필드 불러오기"가 발견·사용되지 않는다는 증거 |
| 그룹·순서 사용 | `그룹`, `순서` | 정리·재배치 기능이 쓰이는가 |
| 사건 필드 존재 | `대상` = 사건 | 사건 커스텀 필드(B-10 계열)가 실제로 쓰이는가 |

### 4-2. 값 라이브러리 (`필드 데이터` 시트)

| 지표 | 컬럼 | 뜻 |
|------|------|-----|
| `출처` 분포 | AUTO / MANUAL / IMPORT / AI | **전부 AUTO면 큐레이션 기능 전체가 미도달.** 그러면 별칭 접기(S-18)·카테고리 그룹핑의 실제 가치가 재평가된다 |
| 별칭/표시라벨/카테고리 채움률 | `별칭(콤마구분)`, `표시라벨`, `카테고리` | 세 기능 각각의 도달률 |
| `사용횟수` 0 + 큐레이션됨 | `사용횟수` | 만들어 놓고 안 쓰는 값 — 정리 기능이 필요한지의 근거 |
| `숨김` 사용 | `숨김` | 입력 제안 조절을 실제로 쓰는가 |

### 4-3. 기능별 사용 여부 (시트 자체가 비었는지)

`세력`, `세력 소속`, `세력 관계`, `관계 변화`, `상태 변화`, `이름 은행`,
`검색 프리셋`, `목록 프리셋`, `사용자 템플릿`, `이미지 메타` —
**비어 있는 시트는 "구현했으나 실사용에 도달하지 못한 기능"이다.**

각각에 대해 한 줄로 적는다: `세력: 0건 — 미도달` / `상태 변화: 47건 — 활발`.

## 5. 측정 3 — 우회 흔적 ("없어서 손으로 한 것")

**이 장이 이 작업에서 가장 값지다.** 필드값 *안에* 구조가 들어 있으면, 그건 앱이 그 표현을
담지 못해 사용자가 우회한 자국이다. `캐릭터 필드값` 시트의 값 전체를 훑어 아래를 센다.

| 패턴 | 정규식(예시) | 시사점 |
|------|-------------|--------|
| 값 안의 콤마 | `,` 포함 & 필드 타입이 TEXT & 표시 형식 미설정 | MULTI_TEXT/콤마 목록 설정이 발견되지 않음 (동시에 통계가 통값으로 세는 지점 — S-18) |
| 단위가 붙은 수치 | `^\d+\s*(cm|kg|살|세|년)` & 타입 NUMBER/TEXT | 타입 설계와 입력 습관의 괴리 → 통계가 조용히 실패 |
| 시계열 표기 | `\d+\s*(장|화|권|막)\s*[~-]` 또는 `→` | **상태변화 기능이 있는데** 그 용도에 안 맞거나 미도달 |
| 괄호 별칭 | `^[^()]+\([^()]+\)$` (이름 필드) | 이명/별칭 설계와 실사용의 괴리 |
| 다른 캐릭터 이름 포함 | 값 안에 캐릭터 시트의 이름이 등장 | 관계 기능이 그 표현을 담지 못함 |
| 줄바꿈 다수 | `\n` 3개 이상 | 서술형 필드/여러 줄 표시 형식이 필요한데 미설정 |

**보고할 때 원문을 쓰지 말 것.** `"OO 필드 · 12건 · 형태: '<수치><단위>'"`처럼 **형태만** 적는다.

## 6. 측정 4 — 규모 실측 (추정을 사실로)

지금까지의 성능 판단은 전부 **추정**이다("캐릭터 300 × 필드 50이면 몇 초"). 실제로 잰다.

1. 엑셀에서 `StatsSnapshot`을 조립한다(캐릭터·필드 정의·필드값·사건·관계… 시트 → 모델 객체).
   `StatsDataProvider`는 순수 JVM에서 실행되므로 스냅샷만 만들면 전부 돌릴 수 있다.
2. `computeSummary` / `computeFieldInsights` / `computeFieldAnalysis` / `detectPatterns` /
   `computeCrossNovelComparison` / `computeRanking`을 각각 시간 측정.
3. 함께 확인할 것:
   - 값 종수가 많은 필드에서 **'기타 N종' 접기**가 실제로 어떻게 보이는가(S-17 산출물)
   - 사용자 구간 설정이 있는 필드에서 **'구간 밖'**이 몇 건인가(B-40 산출물)
   - CALCULATED 필드의 수식이 **실제로 평가되는가**, NaN이 몇 건인가(S-11·로드맵 5의 근거)
   - 별칭이 실제로 접히는가(S-18 산출물)

숫자를 그대로 적는다. 느리면 어디가 느린지까지(대개 `getFieldValues`의 config 재파싱 —
백로그 **B-42**의 실측 근거가 된다).

## 8. 데이터로 답이 **안 나오는 것** — 반드시 물어라

데이터는 **"안 쓴다"는 사실**은 보여주지만 **이유**는 보여주지 않는다.
그런데 이유마다 처방이 정반대다:

| 이유 | 처방 |
|------|------|
| 있는 줄 몰랐다 | 발견성 개선(진입점·안내) |
| 필요 없다 | 기능 제거 또는 기본값에서 숨김 |
| 불편해서 안 쓴다 | 조작 개선(원칙 04) |

**미도달로 판정된 기능마다 위 셋 중 무엇인지 사용자에게 묻는다.** 한 줄 답이면 충분하고,
그 한 줄이 백로그 순위를 뒤집는다. 지난 세션들에서 가장 값진 발견(휴지통 '유령 유실 예고')도
사용자 관찰 한 줄에서 나왔다.

물을 때는 **선택지를 주고 3~5개로 압축**한다. "어떠셨어요"는 답하기 어렵다.

## 9. DB 파일이 함께 있다면 (선택)

`.db`가 있으면 B-9(마이그레이션 실검증 부재 — 현재 CI의 가장 큰 구멍)를 실제로 닫을 수 있다.

```bash
python3 tools/verify_room_migration.py       # 41→42
python3 tools/verify_room_migration_43.py    # 42→43
```

두 하네스는 **합성 DB**로 검사한다. 사용자의 실제 DB가 있으면 같은 절차를 그 파일의 사본에
적용해 "실데이터에서도 마이그레이션이 통과하는가"를 확인할 수 있다.
**반드시 사본으로 하고, 원본은 건드리지 말 것.**

## 10. 금지사항

1. **데이터를 커밋하지 않는다.** 산출물 문서에 원문 값을 옮기지도 않는다.
2. **이 작업 중에 코드를 고치지 않는다.** 발견은 문서로 남기고, 수리는 순위가 정해진 뒤 별도로.
   (예외: 파일을 읽다가 **크래시하는** 경로를 발견하면 그것은 즉시 수리 대상이다 — 다만
   그때도 재현 케이스를 **합성 데이터로** 만들어 테스트에 남긴다.)
3. **표본은 하나다.** "사용자는 …한다"가 아니라 "이 표본에서는 …이다"라고 쓴다.
   한 사람의 데이터로 일반화하면 그 자체가 다음 세션을 잘못 이끈다.
4. **임시 하네스를 러너 목록에 남기지 않는다.**(2-2 경고 참조)
5. 측정값은 **분모와 함께.** "적다"는 판단이 아니라 인상이다.
