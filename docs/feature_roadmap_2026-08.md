## 1. 요청 ① — 전역 기본 필드 (B-119)

### 1-1. 무엇을 만드는가

**"모든 세계관의 모든 캐릭터가 기본으로 가지는 필드"를 사용자가 정의하는 기능.**
필드 생성 시 "전역 기본으로" 지정할 수 있고, 이미 있는 필드를 나중에 승격할 수도, 해제할 수도 있다.

### 1-2. 구조 — 참조가 아니라 **구체화(materialization)**다

두 갈래를 대조했다.

| 안 | 내용 | 판정 |
|---|---|---|
| 참조형 | 전역 필드를 세계관 밖에 두고 모든 읽기 경로가 `세계관 필드 ∪ 전역 필드`를 본다 | **기각.** 읽기 경로 전부(폼·통계·엑셀·값 라이브러리·월드패키지·검색·정렬)가 합집합을 알아야 한다. `FieldDefinitionDao`의 `entityType` 기본값 함정(R-29)과 같은 부류의 사각이 **경로 수만큼** 생기고, 하나만 빠져도 "전역 필드가 이 화면에서만 안 보인다"가 조용히 난다 — 원칙 02 위반(껍데기)의 가장 흔한 발생 경로다 |
| **구체화형 (채택)** | 전역 템플릿을 별도 표에 두고, 각 세계관에는 **보통 필드로 심는다**(복사 + 연결 표식). 기존 소비처는 아무것도 몰라도 된다 | **채택.** 이 저장소가 이미 같은 모양을 쓴다 — 세계관 등급 체계가 필드 config에 실효 표를 **물질화**하고(R-30), 다른 세계관 출신 필드는 참조를 **강등(demote)** 한다. 그 관행이 검증돼 있다 |

**저장:**

- 새 엔티티 `DefaultFieldTemplate` — `FieldDefinition`에서 `universeId`를 뺀 것 + `code`(안정 식별자, R-1).
  `entityType`을 그대로 갖는다(캐릭터 요청이 원문이지만 구조는 사건·작품에도 열어 둔다 — 원칙 01).
  마이그레이션은 표 추가뿐인 순수 추가다(버전 번호는 구현 시점의 다음 번호 — 선점하지 않는다).
- 세계관에 심긴 필드는 `config`에 `defaultField: <템플릿 code>` 한 키를 갖는다(연결 표식).
  **config 키라 필드 쪽 마이그레이션이 없다.**

**GRADE 템플릿의 등급 체계 참조는 갖지 못한다** — 등급 체계는 세계관 단위라 전역 템플릿이
가리킬 대상이 없다. 템플릿은 실효 표만 갖는다(강등된 형태 — `GradeSystemRef.demote`가 이미
다른 세계관 출신 복사에 쓰는 그 규칙이다). **같은 이유로 `duelGrade`(4장)도 갖지 못한다** —
대결 축 역시 세계관 단위이고, 축 code는 전역 유니크라 경계를 넘으면 남의 축에 정확히 붙는다
(4-2의 복사 경계 강등이 여기에도 적용된다).

### 1-3. 전파 규칙 — **기본 필드는 '존재'를 보장하는 것이지 '내용'을 강제하는 것이 아니다**

| 사건 | 처분 |
|---|---|
| 세계관 신설 | 템플릿 전부를 심는다. 프리셋을 함께 고르면 **기본 필드가 먼저** 심기고, 프리셋 병합(`PresetMerge`)이 같은 key를 중복으로 걸러낸다(기존 규칙 그대로) |
| 템플릿 신설 / 기존 필드의 승격 | 모든 세계관에 심는다. **같은 `(entityType, key)`가 이미 있으면 덮지 않고 연결만 건다**(그 세계관의 설정 존중 — 자율성 우선). 결과를 센다: *"새로 심음 N곳 · 기존 필드에 연결 M곳"* |
| 템플릿 편집 | **명시적 전파**다 — 자동으로 퍼뜨리지 않는다. 전파 미리보기가 세계관별 상태를 보인다: 템플릿과 같음(변경 없음) / 다름(**그 세계관에서 사용자가 고쳤다는 뜻** — 기본 해제된 체크박스로 두고 사용자가 고른 곳만 덮는다). 다름 판정은 `PresetMerge.configEquals`(이미 있는 canonical JSON 비교)를 그대로 쓴다. 타입이 바뀌는 전파는 세계관별 `checkTypeChangeImpact`를 미리보기에 싣는다. 덮이는 정의는 `snapshotFieldDefinitions`로 백업한다(B-89 병합이 이미 하는 그것) |
| 템플릿 삭제 / 승격 해제 | 심긴 필드는 **일반 필드로 강등만 한다**(연결 표식 제거). 값이 든 필드를 지우는 것은 사용자가 세계관에서 직접 지울 때뿐이다 — 어떤 경우에도 이 기능이 캐릭터 데이터를 지우지 않는다(개발 의도 2번) |
| 세계관에서 심긴 필드를 편집 | 배너 한 줄: *"이 필드는 기본 필드 '○○'와 연결되어 있습니다."* 그대로 저장하면 그 세계관만 달라진다(전파 미리보기가 '다름'으로 본다). **막지 않는다** |
| 세계관에서 심긴 필드를 삭제 | 허용(그 세계관의 자유). 템플릿은 남으므로 "다시 심기"가 기본 필드 관리 화면에 있다 |

### 1-4. UI

- **필드 편집 다이얼로그**(고급 탭)에 스위치 하나:
  - 라벨: `전역 기본 필드`
  - 목적문(R-25): *"켜면 이 필드가 모든 세계관에 기본으로 심어져, 어떤 세계관의 캐릭터에도 이 칸이 생깁니다."*
- **기본 필드 관리 화면** — 진입은 필드 관리 툴바 메뉴 + 설정. 템플릿 목록(이름·타입·대상 종류·
  *"세계관 N곳 연결 · M곳 다름"*) / 새로 만들기(FieldEditDialog 재사용, 등급 체계 참조 없음) /
  전파 / 다시 심기 / 해제.
- 필드 관리 목록의 심긴 필드 행에 작은 배지(예: `기본`).

### 1-5. 엑셀 왕복 · 월드패키지

- 새 시트 `기본 필드` — `필드 정의` 시트와 같은 열에서 `세계관`을 뺀 것 + `코드`.
  **가져오기 순서는 `기본 필드` → `필드 정의`**(정의가 값보다 앞이라는 기존 규약의 연장 —
  연결 표식이 가리킬 템플릿이 먼저 서야 한다).
- `필드 정의` 시트에 `기본필드코드` 열 하나 추가. 빈 칸 = 연결 없음(기존 "빈 칸 = 해제" 규약).
- 가져온 파일의 `기본필드코드`가 템플릿에 없으면 **강등하고 센다**(*"기본 필드 연결 N건을 찾지
  못해 일반 필드로 두었습니다"* — 거부가 아니라 수용·교정, 개발 의도 4번).
- **월드패키지는 바꾸지 않는다** — 세계관 단위 교환이라 심긴 필드가 이미 실려 있고, 받는 쪽에
  같은 템플릿이 없으면 위 강등 규칙이 그대로 적용된다.

### 1-6. 확장성 판정 (`scalability_performance` 7장 4단계)

1. **새 상한?** 없다. 템플릿 수는 사용자가 손으로 만드는 짧은 목록이다.
2. **비용 축?** 전파 한 번이 `세계관 수 × 템플릿 수`(목표 규모 270 × 수십 = 수천 행 upsert) —
   명시적 단추를 눌렀을 때만 돌고, B-89 병합이 이미 같은 크기의 트랜잭션을 돈다. 새 축이 아니다.
3. **스냅샷 목록?** 추가하지 않는다.
4. **엑셀?** 시트 하나(작다) + 열 하나. 가장 큰 시트가 되지 않는다.

### 1-7. 함께 얻는 것 (원칙 05)

기본 필드의 key는 **세계관을 넘어 안정**하다. 그래서 ⓐ 통계의 `(key, type)` 머지 카드가 전
세계관에서 자연히 한 장으로 모이고(성별 비율·나이대 분포의 전역 조감이 처음으로 정합해진다)
ⓑ B-116(대결 축 불러오기)의 필드 연결이 "없는 키" 없이 옮겨지며 ⓒ 3장의 프로필 트리오가
어느 세계관에서든 서게 된다.

### 1-8. 구현이 정한 것 — **설계가 말하지 않아 코드가 답한 셋** (2026.08.07)

구현하며 설계의 빈자리가 셋 드러났다. 셋 다 *"어느 쪽이든 말이 되는데 결과가 갈리는"* 부류가
아니라 **한쪽이 분명히 틀린** 것이라 묻지 않고 정했다(착수 규칙 3번).

**① 전파의 기본 선택 — 설계 1-3의 "다름은 기본 해제"만으로는 성립하지 않는다.**
그 표는 *다름 = "그 세계관에서 사용자가 고쳤다는 뜻"*이라 적었는데, **템플릿을 고친 직후에는
모든 세계관이 '다름'이다** — 아직 못 받았으니 당연히 다르다. 전부 기본 해제로 두면 흔한
조작(*"고쳤으니 전부 밀어라"*)이 세계관 수만큼의 체크를 요구하고(원칙 04 위반), 사용자는 곧
'모두 선택'만 누르게 되어 **정작 손대어 둔 세계관까지 함께 덮는다** — 설계가 막으려던 바로
그 결과다.

→ **직전 템플릿을 견주면 둘이 정확히 갈린다.** `DefaultFieldPlan.Divergence`가 셋이 된 이유다:

| 갈래 | 뜻 | 기본 |
|---|---|---|
| `SAME` | 템플릿과 같다 | 선택지를 주지 않는다(밀어도 달라질 게 없다) |
| `OUTDATED` | **직전 템플릿과 같다** = 손댄 적 없고 이번 편집을 못 받았다 | **켠다** |
| `DIVERGED` | 둘 다와 다르다 = 그 세계관에서 고쳤다 | 끈다 |

직전 템플릿을 알 수 없는 자리(관리 화면의 '전파' 단추)에서는 `OUTDATED`가 나오지 않아
아무것도 켜지 않는다 — **모르는 것을 안다고 하지 않는 쪽이 안전한 기본이다.**

**② 세계관을 만드는 길이 다섯인데 심기는 하나에만 붙였다.**
`UniverseRepository.insertUniverse`(빈 세계관·프리셋) **한 자리**에만 둔다. 부르는 쪽마다 적으면
다음에 생기는 길이 그것을 빠뜨리고, 그 고장은 *"이 세계관에만 기본 필드가 없다"*로 조용히 난다.
**나머지 셋(월드패키지·엑셀·휴지통 복원)은 일부러 부르지 않는다** — 그쪽은 자기 필드를 곧바로
넣으므로 미리 심으면 그 삽입이 `(universeId, entityType, key)` 유니크에 걸린다. 그 세계관들은
관리 화면의 **'다시 심기'**가 따라잡는다. 설계 1-4가 그 단추를 적어 둔 것이 여기서 값을 한다.
(설계 1-5의 *"월드패키지는 바꾸지 않는다"*는 그대로 지켜진다 — 형식도 경로도 무변경이다.)

**③ 프리셋이 기본 필드를 덮을 뻔했다.** 설계 1-3은 *"기본 필드가 먼저 심기고 `PresetMerge`가
같은 key를 중복으로 걸러낸다(기존 규칙 그대로)"*고 적었는데, **`applyPreset`은 `PresetMerge`를
쓰지 않고 있었다**(`insertAllFields` 직행). 그대로 두면 심긴 기본 필드와 같은 key의 프리셋
필드가 유니크에 걸려 **세계관 생성이 통째로 실패한다.** `PresetMerge.buildPlan` +
`defaultSelection()`으로 바꿨다 — 그 기본 선택이 정확히 *"새 것만 들이고 이미 있는 것은 손대지
않는다"*라, 존재는 보장하되 내용은 그 세계관의 것이 된다.

**함께 선 것 둘.** ⓐ **`FieldTypeCompatibility`** — 타입 변경 영향 판정이
`FieldEditDialog`의 private 함수였는데 전파 미리보기가 **같은 물음을 세계관마다** 던지게 됐다.
두 벌로 두면 *"미리보기가 괜찮다고 한 전파가 값을 지우는"* 모양이 되므로 한 자리로 뺐다(R-7).
ⓑ **`PresetMerge.configEquals`가 공개가 됐다** — 설계 1-3이 이름으로 지목한 단일 소스인데
private이었다. 둘째 구현이 서면 미리보기가 손대지 않은 필드를 "다름"으로 세어 덮어쓰기를 권한다.

**검사 둘이 실제로 잡았다.** `check_restore_preview_parity.sh`(R-33)가 `analyze*`의 손으로 짠
비교를 잡아 `read*Row`+`merge*` 쌍으로 고치게 했고, 마이그레이션 하네스의 추출 정규식이
`.trimIndent()`를 붙인 `execSQL`을 **조용히 건너뛰어** 문장 수 검사에서 걸렸다(붙이면 그 문장이
검사에서 빠진다 — 다른 마이그레이션이 전부 삼중따옴표를 곧바로 닫는 형태인 이유다).

## 2. 요청 ②·③ — AI에 이미지가 실린다 (B-120 · B-121)

두 요청은 **같은 기반(멀티모달 요청) 위의 소비처 둘**이다. 기반을 한 번만 만들기 위해 한 장으로
설계하되, 구현은 ②(기반+필드 추천) → ③(일괄 태깅)의 두 슬라이스로 가른다.

### 2-1. 공통 기반 — 멀티모달 요청 계층

**현행 사실:** `AiMessage(role, text)` — 이미지 칸이 없다. 세 직렬화기 전부 텍스트만 쓴다.
저장소 전체에 비전 요청 코드 0건. **그리고 문서·주석 두 자리가 "이미지를 모델에 보내지 않는다"를
약속하고 있다** — 이 기능이 들어가는 슬라이스는 그 문구(`image_folder_tag_ai` 1장,
`ImageFolderTagSuggester.kt:10`, 관련 도움말)를 반드시 함께 갱신한다.

**설계:**

- `AiMessage`에 `images: List<AiImage> = emptyList()` 추가. `AiImage(base64, mediaType)`.
  기본값이 있어 기존 호출부 5곳은 무변경이다.
- `AiProtocolCodec`이 프로토콜별로 직렬화한다 — ANTHROPIC은 content block 배열(`image` +
  `text`), OPENAI_COMPAT은 `image_url`(data URI) 파트, GEMINI는 `inline_data` 파트.
  **코덱은 순수 JVM이라 세 직렬화 모양을 하네스로 고정할 수 있다** — 프롬프트 문자열과 달리
  이 자리는 로컬 검증이 닿는다. 반드시 테스트를 함께 넣는다.
- **전송용 축소 유틸 `AiImagePreparer`** — 저장용 압축(`ImageImportHelper`)과 별개다(그쪽은
  로컬 용량 목적이고 8192px까지 허용한다). 전송용은 긴 변 1024px · JPEG 재인코딩을 기본으로
  하고, 상수는 한 곳에 둔다. *(1024는 제안값이다 — 실호출로 품질·비용을 재 본 뒤 확정한다.
  P-9의 관행: 근거 없는 숫자를 박지 않는다.)*
- **모델이 이미지를 거부하면**(400) — A-4의 관행 그대로: 이미지를 빼고 1회 재시도 →
  `imagesUnsupported`를 **학습**해 다음부터 묻지 않는다 → 결과에 한 줄 고지(*"이 모델이 이미지를
  받지 않아 글만 보냈습니다"*). **학습한 사실이므로 `hasLearnedFacts()`에 등재한다**(R-23 —
  B-108 ⑥이 지목한 바로 그 규칙).
- **비용 고지:** 기존 고지 다이얼로그에 줄 하나 — *"이미지 N장을 함께 보냅니다. 장당 대략
  250~1,600토큰이 더 듭니다(제공자마다 다릅니다)."* 이미지가 기기 밖으로 나간다는 사실도 같은
  자리에서 말한다(기존 약속을 뒤집는 지점이므로 침묵 금지).
- 파일이 없거나 읽을 수 없으면 **건너뛰고 센다**(*"이미지 2장을 읽지 못해 빼고 보냈습니다"* — R-14).

### 2-2. 소비처 A — 필드 추천·서술형 작성에 캐릭터 이미지 첨부 (요청 ②, B-120)

**어디에:** 짧은 값 추천(`CharacterFieldAiSuggester`)과 **서술형 작성**(`NarrativeFieldAiWriter`)
둘 다. 원문은 필드 추천을 말했지만 서술형(외모 묘사)이 이미지의 최대 수혜자이고, 두 경로는 이미
같은 컨텍스트 조립기를 쓴다 — 한쪽만 열면 반쪽이다(원칙 02).

**고르는 규칙(원문 그대로 + 한 걸음):**

| 옵션 | 동작 |
|---|---|
| 첨부 장수 | 0~10장. 0 = 안 보냄. 기본값은 AI 설정에 저장(`AiPromptSettings` — 적재량 슬라이더의 형제. 제안 기본값 1장) |
| **대표 이미지 반드시 포함** | 켜면 지정 대표(사다리 1칸)가 항상 첫 장이다. 지정 대표가 없으면 그 사실을 말하고 전부 랜덤으로 채운다(조용히 다른 그림을 '대표'라 부르지 않는다) |
| 나머지 | 그 캐릭터의 이미지 목록에서 랜덤(중복 없이). **직접 고르기 경로도 연다** — 썸네일 줄에서 체크해 갈아 끼우기(자율성 우선. 랜덤만 있으면 "하필 그 장"을 뺄 길이 없다) |
| 재추첨 | 고지 다이얼로그의 썸네일 줄에서 🎲 한 번 |

랜덤 대안으로 **태그 다양성 최대화**(태그가 겹치지 않는 장 우선)를 검토했다 — 태그 없는
이미지가 대부분인 실사용에서 근거가 서지 않아 v1은 랜덤 + 직접 고르기로 간다. 태깅(③)이
쌓이면 그때 다시 잰다(5-3장의 후속 확장 후보).

**응답 활용:** 시스템 프롬프트에 규칙 한 줄 — *"이미지에서 읽은 값이면 `reason`에 어느 이미지
몇 번째인지 적어라."* 검토 화면의 근거 줄이 그대로 보여 준다(새 UI 없음).

**A-3(보충 탭)의 뽑기 잠금 규칙이 그대로 적용된다** — 요청 중 대상이 바뀌면 A의 이미지로 받은
추천이 B 폼에 들어가는 사고는 기존 2겹(잠금 + `targetCharacterId` 대조)이 이미 막는다.

**계약 문서:** `docs/ai_integration.md`에 **A-7**(이미지 첨부)로 등재한다.

### 2-3. 소비처 B — 이미지 탭 일괄 AI 태깅 (요청 ③, B-121)

**현행 사실:** 기존 "AI 태그 제안"은 폴더 받아오기 흐름 전용이고 **폴더 이름만** 읽는다.
이미지 내용을 보는 태깅은 처음이다.

**흐름:**

1. 이미지 탭 다중선택 → 일괄 작업 시트에 **"AI 태그 제안"** 추가. (선택 없이 "태그 없는 이미지
   전체"를 고르는 지름길도 ~~필터에 이미 있는 무태그 필터로 잇는다~~ → **무태그 필터는 없었다.
   이 슬라이스가 만들었다** — 아래 2-6장 ①.)
2. 설정 시트: **한 번에 보낼 장수**(1~10, 기본 5 — 사용자 지정이 원문이다) · 요청 수 고지
   (*"이미지 23장을 5장씩 5번에 나눠 보냅니다"* — `AiPromptPolicy`의 기존 계산 관행) · 어휘
   요약 · 기조(기존 `imageTagPolicy` 600자 그대로).
3. 진행: **결정형 진행도**(R-26 — *"요청 3/5 · 이미지 15/23"*), 취소 가능. **끝난 배치의 제안은
   살린다**(B-108 ⓕ의 관행 — 완결된 몫은 버리지 않는다).
4. 검토: 이미지별 행(썸네일 + 제안 태그 칩, 칩 단위 체크) — 폴더 태그 검토 시트의 규칙을
   그대로 넓힌다(어휘 밖은 `새 태그` 표식, 기본 전부 체크). **적용은 기존 태그에 합친다**(덮지
   않는다 — D-4·D-7 그대로, `image_tags` 스키마 무변경). **수십 장 검토의 조작 셋**: 머리에
   [전체 해제 / 전체 선택] · **[새 태그만 보기]** 필터(기존 어휘 태그는 안심하고 일괄 승인하고
   새 태그만 훑는 것이 실제 검토 동선이다) · 이미지 행 접기(칩이 6개를 넘으면 "외 N개").

**오배정 방어 — 이 기능의 실제 위험은 비용이 아니라 "태그가 남의 이미지에 붙는 것"이다:**

- 한 요청의 이미지들은 **번호로 봉인**한다 — 프롬프트가 각 장을 `이미지 1`, `이미지 2`…로
  부르고, 응답은 `[{index, tags[]}]` JSON이어야 한다.
- 응답의 index가 요청 범위를 벗어나거나 겹치면 **그 배치를 통째로 실패로 접고 센다** —
  절반만 믿고 붙이는 것이 곧 오배정이다(R-1의 정신: *오배정은 생략보다 나쁘다*).
- 실패 배치는 "1장씩 다시 보내기" 재시도 경로를 준다(장수 1이면 index 사고가 원리적으로 없다).

**어휘 접기:** 응답 태그는 기존 태그와 **공백·대소문자 무시 일치**면 기존 표기로 접는다
(`matchOption`이 SELECT 값에 이미 쓰는 그 규칙). `물의정령`과 `물의 정령`이 두 태그로 갈리는
것을 막는다.

**어휘 조립은 단일 소스로 뺀다** — `buildVocabulary`(상위 120 태그 + `imageTagVocab` 필드 값 +
기조)는 폴더 제안기와 이 기능이 **같은 함수**를 써야 한다. 두 벌이 되면 같은 앱의 두 AI가 다른
어휘로 말한다.

### 2-5. 구현이 정한 것 — **설계가 말하지 않아 코드가 답한 셋** (2026.08.07 · B-120)

**① 청크마다 이미지를 다시 싣는가 — 설계에 없던 물음이고, 답하지 않으면 조용한 비대칭이 된다.**
짧은 값 추천은 대상 필드를 `chunkTargets`로 나눠 **여러 번 요청한다.** 설계 2-1은 요청 하나를
전제로 쓰여 이 자리를 말하지 않았다. 첫 요청에만 붙이면 뒤쪽 청크의 필드들은 **그림을 못 본 채**
답이 나오는데, 결과 화면에는 그 차이가 어디에도 드러나지 않는다 — 같은 실행 안에서 근거가
필드마다 다른 것이고, 사용자는 *"왜 이 필드만 이미지를 안 봤지"*를 물을 수조차 없다. 그래서
**전부에 싣고, 대신 고지가 연인원을 말한다**(`AiPromptPolicy.imageSendCount`). 설계 2-4가 스스로
*"요청 바이트가 이미지 장수에 선형"*이라 적고 *"요청 수 고지가 사전에 말한다"*고 한 것의 실행이다.
서술형은 후보 여러 개를 한 요청으로 받으므로 이 물음이 없다.

**② 시스템 프롬프트의 이미지 지시에 번호를 매길 수 없었다.** 설계는 *"규칙 한 줄"*이라 적었는데,
짧은 값 프롬프트의 규칙 16은 **근거 강도 하한이 조건부로 쓰는 자리**다(`confidenceFloorRule`).
거기에 이미지 규칙도 16을 매기면 **설정 조합에 따라 `16.`이 둘인 프롬프트**가 나간다 —
컴파일도 정적 검사도 통과하고 400도 나지 않으며, 모델이 규칙 하나를 흘리는 것으로만 드러난다.
창작도 지시가 이미 쓰던 `[라벨]` 블록 형태로 붙였다(새 문법이 아니다).
**서술형 쪽 지시는 한 줄이 더 붙는다** — *"'이미지 1'처럼 그림을 가리키는 말을 본문에 쓰지 마라."*
본문은 그 필드에 그대로 들어갈 작품 설정이지 작업 기록이 아니다(A-6의 등수 규칙과 같은 이유).
짧은 값은 반대로 **적으라고** 시킨다 — 거기서는 그 말이 본문이 아니라 `reason`에 들어가고,
검토 화면의 근거 줄이 그것을 그대로 보여 준다(설계가 *"새 UI 없음"*이라 적은 근거).

**③ 보완 재요청이 어느 그림으로 다시 묻는가.** 설계는 첫 요청만 말했다. 세 갈래가 있는데
둘은 틀렸다 — 다시 고르게 하면 사용자가 이미 정한 선택을 되풀이시키는 마찰이고(원칙 04),
비우면 **같은 검토 화면 안에서 근거가 조용히 바뀐다**(첫 답은 그림을 보고 나왔는데 보완 답은
아니다). 그래서 `AiSuggestRun.imagePaths`로 **첫 요청의 경로를 들고 있다가 그대로 다시 쓴다.**
base64가 아니라 **경로**를 드는 것이 함께 정한 것이다 — 그 객체는 유료 응답을 들고 회전을
넘기라고 만든 것이라 수 MB의 바이트를 얹으면 **그 자체가 비용**이고, 다시 읽는 편이 싸다.

**함께 선 것 둘:**
- **`util/AiImageAttach`(순수) ↔ `util/AiImagePreparer`(Android)를 갈랐다.** 설계 9-1은
  `AiImagePreparer` 하나만 적었지만, 그 안에 **고르기 규칙**(대표 우선·랜덤·직접 고르기)이
  함께 들어가면 비트맵에 묶여 **어느 것도 실행으로 검증할 수 없다.** 고르기는 세 화면이 같아야
  하는 규칙이라 순수로 내려 하네스를 걸었다(`AiImageAttachTest`).
- **프로브 두 자리를 명시적으로 뺐다**(`tools/probe_compile.sh`). `AiImagePreparer`는
  `android.graphics`에 묶여 원리적으로 해석되지 않고, `AiImageAttach`는 **순수인데
  `ai/AiPromptPolicy`를 참조한다** — 프로브가 `ai/**`를 통째로 빼므로 역시 못 본다.
  노이즈로 두면 **다음 세션이 base 대 cur를 비교할 때마다 무해함을 다시 알아내야 한다.**
  후자의 증명은 `run_jvm_tests.sh`가 대신하므로 손실이 없다(컴파일 + 실행 = 프로브보다 강하다).

**남긴 것 하나 — 1024px은 아직 재지 않았다.** 설계 2-1이 *"제안값이며 실호출로 품질·비용을 재
본 뒤 확정한다"*고 적었고, 이 세션은 실제 제공사 호출을 할 수 없어 그대로 뒀다. **근거 없는
숫자를 확정으로 적지 않는 것이 이 저장소의 관행이라**(P-9) 상수 주석에 미측정임을 남기고
백로그 **B-126**으로 등재했다.

### 2-6. 구현이 정한 것 — **설계가 말하지 않아 코드가 답한 넷** (2026.08.07 · B-121)

**① 설계가 이미 있다고 적은 '무태그 필터'는 없었다.** 2-3 1번이 지름길을 *"필터에 이미 있는
무태그 필터로 잇는다"*고 썼는데, `ImageFilterHelper`의 축은 `BaseFilter`(소유·상태) ·
`LinkFilter`(링크) · `tags`(어느 태그인가) · 검색어뿐이고 **'태그가 없는 것'은 어디에도
없었다**(`tags`가 비어 있다는 것은 *필터를 안 걸었다*는 뜻이지 *태그가 없다*가 아니다).
착수 규칙 2번의 *범위 안이면 고친다*에 걸려 만들었다 — `TagFilter { ANY, UNTAGGED }`를
**독립 축**으로 두고(`LinkFilter`가 세운 선례 그대로), 태그 필터 시트에 스위치를 붙였다.
**칩으로 담을 수 없어서 별도 축이다** — 없는 것에는 이름이 없다. 둘을 함께 걸면 결과가 비는데
그것은 AND의 정직한 답이라 특례를 두지 않고, 대신 조작에서 배타로 묶었다(켜면 칩이 잠긴다).
**이것이 없으면 이 기능의 실제 동선이 성립하지 않는다** — 수백 장에서 무태그를 눈으로 찾아
하나씩 고르는 것이 원칙 04가 금지하는 바로 그것이다.

**② 번호 봉인은 '실제로 실린 목록'을 가리켜야 한다 — 준비기가 짝을 잃고 있었다.**
설계는 번호로 봉인하라고만 적었는데, `AiImagePreparer.prepare`는 **이미지 목록과 '못 읽은
장수'**만 돌려준다(A-7이 그것만 필요했다). 그대로 쓰면 배치 가운데 한 장이 빠졌을 때
응답의 `이미지 3`이 원본 3번과 어긋나 **봉인해 놓고 봉인 대상을 흔든다.** 그래서
`prepareEach`(경로↔이미지 짝)를 더하고 seam을 짝으로 정의했다(`Loaded`).
**배울 것: 번호로 무언가를 봉인할 때는 그 번호가 세는 목록이 도중에 줄어들 수 있는지부터 볼 것.**

**③ 이미지를 못 싣는 모델의 답을 A-7과 반대로 처분한다.** A-4·A-7의 관행은 *거부당하면 빼고
재시도하고 고지한다*이고, `AiService`가 그것을 이미 해 준다 — **성공으로 돌아온다.**
곁들이인 A-7에서는 옳지만 여기서는 **그림이 근거의 전부**라, 그 성공을 그대로 쓰면 모델이
아무것도 안 보고 지어낸 태그가 검토 화면에 오른다. 그래서 `imagesOmitted`가 서면 배치를 접고
**남은 배치도 돌리지 않는다**(학습된 사실이라 뒤도 같고, 돌리면 돈만 쓴다).
**공용 계층의 '친절한 폴백'은 소비처마다 뜻이 다르다 — 얹는 쪽이 다시 판정해야 한다.**

**④ 잘린 응답을 번호 사고와 갈랐다.** 둘 다 파싱에 실패하지만 **처방이 다르다** — 번호 사고는
*1장씩 다시 보내기*이고 잘림은 *장수를 줄이거나 출력 상한을 올리기*다. 하나로 뭉뚱그리면
고지가 *"번호가 어긋났다"*는 틀린 사유를 말하고 사용자는 엉뚱한 곳을 고친다. 함께,
요청이 `effectiveMaxTokens()`를 싣게 했다 — 기본값 2048을 박아 두면 장수를 최대로 올린
사용자가 **설정을 올려도 계속 잘린다**(교집합 규칙상 요청값은 천장이지 바닥이 아니다).

**곁다리 — 상한 하나와 임계 하나가 함께 섰다.** 이미지당 태그 상한은 폴더(6)보다 큰 **8**이다:
폴더는 이름 한 줄이 근거의 전부지만 이미지는 인물·복장·배경·구도·분위기가 한 장에 함께 있어
분류축이 실제로 더 많다. 검토 행의 접기 임계는 **6**이고 **상한보다 작아야 한다** — 같게 두면
접기 코드가 영원히 안 도는 죽은 길이 된다(시험으로 잠갔다).

### 2-4. 확장성 판정 (두 소비처 공통)

1. **새 상한?** 둘 — 첨부 10장(②) · 배치 10장(③). 버려지는 것은 없다(사용자가 고른 만큼만
   나간다). 상수는 한 곳에 둔다.
2. **비용 축?** 새 축이다 — **요청 바이트/토큰이 이미지 장수에 선형**. 전송용 축소(2-1)가
   장당 크기를 묶고, 요청 수 고지가 사전에 말한다. 온디맨드 경로라 상시 비용은 0이다.
3. **스냅샷?** 건드리지 않는다.
4. **엑셀?** 없다. (첨부 장수 기본값 등 새 AI 설정은 **B-105 레지스트리가 서면 그쪽에 등재**한다.)

## 3. 요청 ④ — 대결창 프로필 필드 연동 + 화면 재설계 (B-122)

### 3-1. 연결이 셋이 된다 — 방향과 쓰임이 전부 다르다

| | 방향 | 대결 화면 | 예측에 쓰나 |
|---|---|---|---|
| 영향 필드 (기존) | 필드 → 대결 | 보인다 | **쓴다**(사전식) |
| 산출 필드 (기존) | 대결 → 필드 | 안 보인다 | 안 쓴다 |
| **프로필 필드 (신설)** | 표시 전용 | **보인다** | **안 쓴다** |

프로필 필드는 *"누구인지 알아보는"* 재료이지 *"누가 이길지 가르는"* 재료가 아니다 — 원문의
괄호(*"대결에 영향을 주는 필드와는 따로임"*)가 정확히 이 구별이다. 예측·어긋남 감지 어디에도
들어가지 않는다.

**저장: `DuelAxis.profileFieldKeys`** — `influenceFieldKeys`와 같은 모양의 열 하나(순수 추가
마이그레이션). 축 단위로 두는 이유: '강함' 축에서는 전투 관련을, '아름다움' 축에서는 외모 관련을
띄우고 싶은 것이 실사용이고, 저장·JSON·엑셀 규약(`DuelFieldLinks`)과 고르는 다이얼로그를
**그대로 재사용**한다(새 문법을 만들지 않는다). 엑셀 `대결 축` 시트에 `프로필필드` 열이 함께
는다(쉼표 이어쓰기 — `-` 접두 없음).

**산출 필드는 프로필로 골라도 표시에서 뺀다** — 물음과 답을 한 화면에 두지 않는다는 기존
원칙(설계 5장 ①·7-1)이 프로필 경로로 우회되면 안 된다. 고르는 다이얼로그가 그 항목을 비활성
+ 사유 표시로 막는다(R-24).

### 3-2. 필수 트리오 — 이름·성별·나이

| 줄 | 어디서 오나 |
|---|---|
| 이름 | `Character.displayName` — 항상 있다(종전에는 스크림에, 지금은 정보 패널 첫 줄에 뜬다) |
| 나이 | **AGE 시맨틱 역할** 필드의 **값** — 그 값이 곧 표준연도 기준 현재 나이다(`StandardYearSyncHelper`가 표준연도가 바뀔 때마다 다시 넣는다). ~~`TimeStateResolver`~~ **구현이 고쳤다 — 3-5 ⓪** |
| 성별 | **GENDER 시맨틱 역할 신설**(9번째)이 필요하다 — 지금 성별은 일반 SELECT 필드라 앱이 "어느 필드가 성별인지" 알 길이 없고, 라벨 문자열 추측은 R-20이 금지한다 |

GENDER 역할은 표식 전용이다(상태변화 동기화 없음 — AGE와 달리 규칙이 붙지 않는다). 이 역할은
대결 밖에서도 값을 한다 — 통계의 성별 비율, AI 컨텍스트의 성별 줄이 추측 없이 그 필드를 집는다
(원칙 05). **역할 필드가 그 세계관에 없으면 그 줄은 조용히 비우지 않고, 프로필 고르기
다이얼로그가 사유를 말한다**(*"성별 줄은 '성별' 역할을 지정한 필드에서 옵니다 — 이 세계관에는
아직 없습니다"* — R-17). 1장의 기본 필드로 성별·나이를 만들어 두면 전 세계관에서 트리오가 선다.

그림을 삼킨다. **카드를 '그림 위 글'에서 '그림 + 정보 패널'로 가른다.**

```
┌──────────────┐ ┌──────────────┐
│              │ │              │      위 55~65%: 이미지 (위 살리는 크롭 유지)
│    그림 A     │ │    그림 B     │
│              │ │              │
├──────────────┤ ├──────────────┤
│ 아리네        │ │ 벨            │  ← 이름 (한 줄 고정)
│ 여 · 17세     │ │ 여 · 21세     │  ← 필수 트리오 줄 (성별·나이)
│ 소속 달빛단    │ │ 소속 홍련회    │  ← 프로필 필드 (상한 4줄 + "외 N개")
│──────────────│ │──────────────│
│ 1 마력량  350 │ │ 1 마력량  280 │  ← 영향 필드 (순위 번호, 시각적으로 구분된 구역)
│ 2 속성    물  │ │ 2 속성    불  │
└──────────────┘ └──────────────┘
   [방금 그거 취소]  [비슷함]  [순위표]      ← 하단 바 — 가운데 빈 자리에 무승부(B-114)
```

정한 것:

- **카드 탭 = 그 캐릭터 승리** — 현행 유지(최소 조작). 프로필이 늘어도 탭 대상은 카드 전체다.
  실수는 기존 '방금 그거 취소'가 받는다.
- **영향 필드에 우열 강조를 하지 않는다** — 어느 쪽 값이 큰지 색·굵기로 표시하면 사전식 예측을
  화면이 대신 말하는 셈이라, 점수를 안 띄우는 것과 같은 이유로 금지다. 순위 번호와 값만 보인다.
- **프로필 상한 4줄 + "외 N개"**(R-14). 카드 탭과 겹치지 않는 작은 펼침(⌄)이 전체 프로필
  시트를 연다(러프하게 보고 → 필요하면 정밀히 — 이중 경로).
- **B-114(비슷함)를 이 재설계가 연다** — 하단 바 가운데가 원래 비어 있고, 저장 형식은 이미
  받는다. 같은 화면을 두 번 고치지 않는다.
- **k지선다(B-115) 대비를 골격에 미리 넣는다** — `duelArea`를 2장=가로, 3~4장=2×2 격자로
  바꿀 수 있게 짠다. 3장 이상에서는 정보 패널이 이름+트리오 줄로 접히고 펼침 시트가 나머지를
  진다. **B-115 자체는 이 슬라이스가 열지 않는다**(5-3 참조) — 다만 이 골격 덕에 그 슬라이스는
  격자 전환과 "묶음 취소" 문구만 남는다.
- **위아래(STACKED) 배치에서는 카드 안이 가로형이 된다** — 세로로 두 카드를 쌓으면 정보
  패널까지 세로로 이어 붙일 높이가 없다. 카드 안을 **이미지(좌 40%) + 정보 패널(우)** 가로
  배치로 전환하고, 접기 규칙(프로필 4줄 + "외 N개")은 그대로다. `applyViewOptions()`가 이미
  배치를 런타임에 갈아 끼우는 그 자리에서 함께 가른다.
- 보기 설정에 **프로필 표시 / 영향 필드 표시** 토글 추가(기존 배치·맞춤과 같은 자리,
  기본 둘 다 켬).
- 목적문(R-25), 프로필 고르기 다이얼로그: *"고른 필드의 값이 대결 카드에 함께 보입니다.
  승패 예측에는 쓰이지 않습니다."*

### 3-4. 확장성 판정

1. **새 상한?** 프로필 표시 4줄(표시 계층 상한 — R-19. 초과는 "외 N개"로 센다).
2. **비용 축?** 카드당 필드값 조회가 프로필 키 수만큼 — 영향 필드가 이미 같은 경로로 읽고,
   **트리오의 성별·나이도 그 한 질의에 얹힌다**(3-5 ⓪이 나이를 `TimeStateResolver`에서
   역할 필드 값으로 고친 것이 이 판정을 지키기 위해서다). 새 축 아님.
3. **스냅샷?** 없다.
4. **엑셀?** `대결 축` 시트 열 하나. **다만 그 열 하나가 규약을 하나 낳았다** — 열이 늘면
   그전 파일 전부가 *"그 열이 없는 파일"*이 되고, 없는 열을 빈 칸으로 읽으면 왕복이
   값을 지운다(R-36 · 3-5 ⑤).

### 3-5. 구현이 정한 것 — **설계 한 자리를 고쳤고 넷을 채웠다** (2026.08.07)

**고친 것이 하나 있다.** 「세션 착수 규칙」 2번대로 슬라이스 **안**이라 고친 뒤 착수했다.

**⓪ 나이의 출처 — `TimeStateResolver`가 아니라 AGE 역할 필드의 *값*이다.**
3-2 표는 나이를 *"AGE 시맨틱 역할 필드 + `TimeStateResolver`(표준연도 기준 현재 나이)"*로
적었는데, **그 두 자리가 같은 장 안에서 서로 어긋난다**: `TimeStateResolver.resolveStateAtYear`는
캐릭터마다 상태변화 목록을 읽어야 하므로 **참가자 수에 붙는 새 비용 축**인데, 바로 아래 3-4의
확장성 판정 2번은 *"새 축 아님"*이라고 적어 두었다. 목표 규모가 캐릭터 수백 명이고 대결은
판마다 다시 그리는 화면이라 이 축은 실제로 문다.

**요구는 그대로 지켜진다.** AGE 역할 필드의 값은 `StandardYearSyncHelper`가 표준연도가 바뀔
때마다 다시 계산해 넣는 값이라 *"연표와 같은 값"*이라는 요구를 그 자체로 만족하고, 어긋난
자리는 `ConsistencyChecker`가 이미 따로 짚는다. 그래서 카드는 **다른 필드값과 똑같이 한 번에
읽는다** — 프로필 키와 같은 질의를 타므로 비용이 정말로 늘지 않는다.

아래 넷은 **설계에 자리가 비어 있던 곳**이고, 판단 근거를 남긴다.

**① 빈 값의 처분이 두 구역에서 반대다.**
영향 필드는 값이 없어도 **줄이 남고**(`—`), 프로필은 **줄이 빠진다**. 반대인 것이 일부러다:
대결 화면에서 사용자가 하는 일이 *같은 줄끼리 견주는 것*이라 영향 구역은 두 카드의 자리가
맞아야 하고(한쪽에서 빈 줄을 빼면 그 아래가 통째로 어긋나 엉뚱한 줄끼리 마주 본다), 프로필은
견주는 재료가 아니라(3-1 표) 그 제약이 없어 **빈 줄이 상한 넷을 잡아먹지 않는 편이 낫다**.
하나로 통일하는 것이 자연스러워 보이는 자리라 `DuelCardInfoTest`가 양쪽을 함께 잠근다.

**② 겹치는 필드는 한 구역에만 뜬다.**
영향 필드로도 프로필로도 걸린 키, 그리고 트리오 역할 필드는 **프로필 구역에서 빠진다** —
이미 다른 구역에 있기 때문이다. **값이 사라지는 것이 아니라 자리가 하나**라 사유를 말하지
않는다. 반대로 **산출 필드가 프로필에 걸린 경우만은 말한다**(축 편집 창) — 그것은 사용자가
고른 것이 *어디에도 안 보이는* 유일한 경우다.

**③ 접힌 수는 전량 기준이다.**
*"외 N개"*는 `전량 − 카드에 올린 것`이라 **값이 빈 프로필도 세어진다.** 펼치면 그것이 비어
있음을 그대로 보여 주므로 거짓말이 아니고, 빼면 *"걸어 뒀는데 어디에도 없다"*가 된다.
같은 이유로 **막힌 산출 필드는 세지 않는다** — 그쪽은 펼쳐도 없다.

**④ k지선다 대비의 실체는 `duelArea`가 아니라 카드 한 벌이었다.**
3-3은 *"`duelArea`를 격자로 바꿀 수 있게 짠다"*고 적었는데, 실제로 B-115를 싸게 만드는 것은
**카드를 한 벌(`view_duel_card.xml`)로 두고 두 번 include하는 것**이었다. 그릇을 바꾸는 일은
어차피 그 슬라이스의 몫이고, 카드가 두 벌로 복제돼 있으면 셋째·넷째를 만드는 순간 네 벌이
된다. 배치를 가르는 자리도 `applyViewOptions` **하나**로 모아 뒀다(카드 안의 방향까지 거기서
갈린다 — 위아래 배치에서 카드 안이 가로가 되는 그 규칙이다).

**⑤ 엑셀 열을 더하다 규약 하나가 나왔다 — R-36.**
`프로필필드` 열을 더하는 순간 **그때까지 내보낸 모든 파일**이 *"그 열이 없는 파일"*이 되는데,
종전 읽기는 **없는 열과 빈 칸을 똑같이 `""`로** 읽었다 — 다시 들이는 것만으로 프로필 연결이
지워진다는 뜻이다. 같은 자리를 보니 형제 칸 둘(`영향필드`·`산출필드`)도 이미 같은 상태였고,
아무도 겪지 않은 것은 **그 열들이 시트와 함께 태어나 *"없는 파일"*이 아직 없었기 때문**일
뿐이었다. 셋을 함께 고쳤고 규약으로 올렸다(`conventions.md` R-36).

### 4-2. 필드 속성 — GRADE 필드에 얹는다

**자리: `FieldDefinition.config`의 새 키 `duelGrade`** — config 확장이라 **DB 마이그레이션이
없다.** 대상은 **GRADE 타입 필드**다(등급 라벨과 서열이 이미 있는 유일한 타입 — 등급 체계
참조·실효 표·엑셀 왕복이 전부 깔려 있다. SELECT까지 넓히는 것은 선택지에 서열이 없어 컷을
정의할 수 없으므로 기각).

```json
"duelGrade": {
  "axisCode": "<대결 축 code>",
  "cuts": [ {"label": "S", "topPercent": 5}, {"label": "A", "topPercent": 20}, ... ]
}
```

- `cuts`는 필드의 실효 등급 표(라벨) 위에 **누적 상위 %**를 얹는다 — *"상위 5%까지 S, 20%까지 A,
  …"*. 마지막 등급은 나머지 전부(컷 불필요). 검증: %가 **단조 비감소**(0% 구간 허용 — 4-4 ⓒ),
  라벨이 실효 표에 실재. **검증은 저장 시 1회가 아니라 반영 직전에도 다시 돈다**(그 사이에 실효
  표가 바뀔 수 있다 — 아래).
- **실효 등급 표가 바뀌면 cuts가 따라간다** — 등급 체계 전파(`GradeSystemRepository.propagate`)가
  개명 `renames`를 재정의에 적용하는 그 자리(`renameOverrides` 선례 — *"개명으로 재정의가 조용히
  증발하지 않게"*)에서 **cuts의 라벨도 함께 개명**한다. 라벨이 **삭제**되면 그 컷을 지우고 구간을
  다음 등급에 합친 뒤 필드 편집 섹션이 사유를 말한다. 반영 직전 재검증에 걸리면(유령 라벨 등)
  **반영을 차단하고 고칠 자리를 연다**(변수 제어 — 검증 → 알림 → 교정 경로).
- 축은 **code로** 가리킨다(R-1 — 프리셋의 `sortDuelAxisCode`와 같은 이유. 복원이 id를 재발급해도
  남의 축에 붙지 않는다). **단 축 code는 전역 유니크라 세계관 경계를 넘은 config 복사가 "못
  찾는" 것이 아니라 남의 세계관 축을 정확히 찾는다** — 그래서 둘을 겹쳐 막는다: ⓐ **복사 경계
  강등** — 필드 가져오기·프리셋 직렬화·기본 필드 템플릿(1-2)이 `GradeSystemRef.demote`를 부르는
  그 자리에서 `duelGrade` 키도 걷어낸다 ⓑ **소속 검사** — 읽는 쪽이 "축이 실재하고 **이 필드의
  세계관에 속하는가"까지 본다(강등이 한 경로라도 빠졌을 때의 이중 방어 — 오배정은 생략보다
  나쁘다). 축이 없거나 남의 것이면 **필드 편집 섹션과 반영 진입 양쪽**이 사유를 말한다.
- 이 속성을 켠 필드가 그 축의 **산출 필드가 아니면** 저장 시 산출 필드로 함께 등재할지 묻는다
  (연동을 두 곳에서 따로 관리하게 하지 않는다).
- 백분위 대상은 **점수가 있는 참가자뿐**이다 — 한 판도 안 친 캐릭터는 `DuelScoreIndex` 계약 2
  그대로 **값 없음**이고 등급을 받지 않는다(앵커 1500로 'C'를 지어내는 것이 정확히 그 계약이
  막는 병이다). **등수는 점수 보유자끼리 다시 매긴다** — `DuelScoreIndex.Entry.rank`는 순위표
  줄의 등수라 **무기록 참가자까지 센 수**이고, 그대로 나누면 분모(점수 보유 인원)를 넘어
  백분위가 100%를 넘는다(ⓔ AI 컨텍스트가 처음 밟았던 *"3명 중 4위"*와 같은 함정 —
  `DuelAiContext.rankWithinScored`가 이미 그 재매김을 하므로 **그 함수를 `DuelScoreIndex`로
  올려 공용화한다**). 백분위 = 재매긴 표준 경쟁 순위 ÷ 점수 보유 인원.

### 4-3. 값은 파생 표시가 아니라 **명시적 반영**으로 쓴다

두 갈래를 대조했다.

| 안 | 내용 | 판정 |
|---|---|---|
| 파생 표시 (R-16형) | CALCULATED처럼 저장 행 없이 읽을 때마다 계산 | **기각.** R-16의 짐("저장 값을 읽는 모든 경로가 그것을 알아야 한다")이 이미 수십 파일이고(B-55), 게다가 이 값은 **적합(축당 수십~수백 ms)**에서 나온다 — 목록·엑셀·통계가 필드값을 읽을 때마다 대결 적합이 따라붙는 구조는 B-117이 세운 "동시에 도는 축은 하나" 계약을 무너뜨린다 |
| **명시적 반영 (채택)** | 사용자가 단추를 눌러 미리보기를 보고 필드 값으로 **써 넣는다** | **채택.** 사용자 원문(*"이 대전의 결과가 이 필드로 이어진다"*)이 흐름을 말하고, 어긋남 감지(설계 7-3-1)가 이미 "언제 다시 반영할 때인가"를 짚어 주는 짝이다. 엑셀에도 보통 값으로 실려 왕복이 자명하다 |

**반영 흐름:**

1. 진입 둘 — 순위표의 산출 필드 고지 줄(*"순위와 '강함' 필드가 어긋난 자리가 12곳"*) 옆
   **[등급 반영]** + 필드 편집의 속성 섹션.
2. **미리보기가 전부 보인다**: 캐릭터 · 현재 값 → 새 등급 · 백분위. 값이 바뀌는 행만 기본 체크.
   **손으로 적어 둔 값을 덮는 행은 따로 묶어 보인다**(기본 체크 해제 — 자율성 우선).
   점수 없음(무기록) 캐릭터는 **건드리지 않고 센다**(*"12명은 아직 판이 없어 그대로 둡니다"*).
   **"손값"의 판별식** — 값 자체에는 출처가 없으므로 반영이 흔적을 남긴다: 반영 성공 시
   `duelGrade.lastApplied = {at, assignments(캐릭터코드→라벨)}`를 **같은 트랜잭션에서** config에
   쓴다(R-30의 정신 — 원본 쓰기와 파생 기록이 한 몸). 미리보기 분류는 셋이다 — **빈 칸**(기본
   체크) · **현재 값 = 직전 반영이 그 캐릭터에 쓴 라벨**(반영값 그대로 → 기본 체크 — 2차
   반영부터 전 행을 손으로 켜는 마찰을 없앤다) · **그 외**(손값 → 기본 해제). `lastApplied`는
   점수 보유자 몫만 담고, **크기를 세어 한도(R-10 예산 상수)를 넘으면 assignments를 생략하고
   그 사실을 미리보기가 말한다** — 그때 분류는 빈 칸/값 있음 둘로 정직하게 줄어든다.
3. 적용은 한 트랜잭션 + **기존 값 스냅샷**(일괄 편집 B-83과 같은 자리 — 휴지통에서 통째로
   되돌린다). 작업 이력(`OpResult.CAT_DUEL`)에 남는다 — B-113 ②(되돌리기 어려움)의 답이다.

**자동 반영은 두지 않는다** — 판 하나가 전원의 점수를 움직이는 시스템에서 자동 반영은 사용자
데이터가 소리 없이 계속 바뀐다는 뜻이다(변수 제어 위반). 어긋남 고지가 "반영할 때가 됐다"를
말하는 현행 설계가 이미 그 자리를 잘 지킨다.

### 4-4. 대안 조사 — 고정 %컷이 바닥이고, 경계 제안이 그 위에 얹힌다

| 후보 | 판정 |
|---|---|
| 고정 %컷 (사용자 원문) | **바닥으로 채택.** 결정적이고 설명 가능하다(*"상위 5%라서 S"*) — 화면이 그대로 말할 수 있는 문장이다. **컷 편집기는 사용자 제3안으로 확정됐다(Q2, 2026.08.07)** — 0~100% 막대 하나에 등급 구간을 놓고 **구분선을 끌어** 비율을 조정하는 **총량 고정 구간 슬라이더.** 합 100 제약이 손이 아니라 구조로 지켜지고, 숫자 정밀 입력을 병행한다(러프 드래그 / 정밀 조정 — 이중 경로). 초깃값은 균등 분할, [경계 제안]은 그 구분선을 옮겨 준다 |
| z-점수 구간 (평균±σ) | 기각 — 분포 가정이 창작 데이터에 근거 없고, 사용자에게 설명이 안 된다 |
| **자연 단절 제안 (Jenks류 1차원 군집)** | **컷 편집기의 보조로 채택.** [경계 제안] 단추가 현재 점수 분포에서 **±오차 겹침이 없는 큰 간격**을 찾아 %컷 초안을 채워 준다 — 겹침 조건이 핵심이다(오차 안의 간격은 표본 소음이라 제안하지 않는다. 기존 확신 기계를 그대로 쓴다). 사용자가 고쳐서 저장한다 — 자동이 아니라 제안이다(자율성 우선) |
| 불확실성 반영 배정 | 반영 미리보기에서 **경계에 걸친 캐릭터(±오차가 컷을 가로지름)에 표식** + *"판을 더 쌓으면 확실해집니다"*. 배정을 막지는 않는다(마찰 최소) |

**UI 정본 목업: `docs/mockups/duel_grade_ui_2026-08.html`** — 컷 슬라이더(9단 실사용 예시 ·
0% 구간 · 선택 경계 스테퍼)와 반영 미리보기(3분류 묶음 · 경계 배지)를 화면 그대로 담았다.
구현은 이 목업의 구조·비율을 따른다.

**슬라이더의 조작성 — 실사용이 9단이라는 사실을 설계가 받아야 한다.** 표본의 등급 체계는
F~SSS 아홉 칸이고, 360dp 폭에 아홉 구간이면 칸당 40dp가 안 돼 **드래그만으로는 1% 단위 조정이
불가능하다.** 그래서 셋을 정한다: ⓐ **구분선을 탭하면 선택**되고 선택된 구분선에 ± 스테퍼와
숫자 칸이 붙는다(드래그 = 러프, 스테퍼·숫자 = 정밀 — 이중 경로의 실체) ⓑ 구간이 좁아지면
**라벨·%를 막대 위아래로 교차 배치**해 겹침을 피하고, 그래도 못 그리는 폭(예: 2% 미만)은
라벨을 숨기되 선택 시 말풍선으로 보인다 ⓒ **0% 구간을 허용한다**(이 축에서 안 쓰는 등급 —
구분선 둘이 겹친 상태로 표현되고, 검증은 '단조 증가'가 아니라 '단조 비감소'다).

### 4-5. 함께 얻는 것 · 확장성 판정

등급이 **보통 필드 값**으로 실리므로 통계(분포·교차분석)·목록 카드·필터가 **공짜로** 그것을
분석한다(원칙 05 — 새 통계 코드 0줄). 4단계: ① **새 상한 하나 — `DuelGradeRef.MAX_CONFIG_CHARS`**(구현이 찾았다. 초안은 *"새 상한 없음"*이라 적었는데, 반영 흔적을 config에 남기기로 한 순간 크기가 인원에 비례하는 것이 생겼다. 넘치면 흔적만 버리고 약속은 지킨다 — 근거는 4-6장 ③, 등재는 `scalability_performance_2026-07.md` 4장) ② 반영 한 번 = 적합 한 번 + 값
쓰기 N행(명시적 조작, B-117과 같은 축) ③ 스냅샷 무변경 ④ 엑셀 무변경(보통 값으로 실린다).

### 4-6. 구현이 정한 것 — **설계가 말하지 않아 코드가 답한 셋** (2026.08.07)

설계와 어긋난 것은 없다. 아래는 **설계에 자리가 비어 있던 곳**이고, 판단 근거를 남긴다.

**① 라벨이 *늘어날* 때의 컷 — 설계는 개명과 삭제만 말했다.**
등급 체계는 필드와 따로 편집되므로 라벨이 늘 수도 있다. 그때 컷이 표와 어긋나면 반영이
막히는데, 사용자가 한 것은 등급 하나를 더한 것뿐이다. `DuelGradeAssign.reconcile`이
**기존 배정을 보존하는 방향**으로 맞춘다 — 새 등급은 **0% 구간**으로 들어오고(아무도 등급이
바뀌지 않는다), **맨 아래에 붙은 경우에만** 옛 마지막 등급이 100%를 받는다(그 등급이 갖고
있던 몫 그대로다. 이 한 자리 때문에 `reconcile`이 *옛* 라벨 차례를 함께 받는다 — 컷만 봐서는
"누가 마지막이었는가"를 알 수 없다).

**② `lastApplied` 흔적에 담는 범위 — "점수 보유자 몫만"의 해석.**
**배정 전체를 담는다**(체크된 것만이 아니다). 값이 이미 배정과 같은 캐릭터는 미리보기에
줄조차 서지 않는데, 그들을 빼면 **다음 반영이 직전에 자기가 쓴 값을 '손값'으로 읽어** 기본
체크를 풀어 버린다 — Q1이 없애려던 그 마찰이 되살아난다. 체크를 끈 캐릭터를 담아도 거짓이
되지 않는다: 분류는 흔적을 **현재 값과 대조**하므로 값이 그대로인 손값은 여전히 손값으로 갈린다.

**③ 흔적 한도의 근거 — 설계는 "R-10 예산 상수"라 적었다.**
실제로 이 자리를 묶는 것은 **엑셀 셀 상한(32,767자)**이다. config는 '필드 정의' 시트의 **셀
하나에 통째로** 실리고 내보내기가 넘치면 **자른다**(`ExcelExporter.setTextSafe`). 잘린 config는
JSON으로 깨져 돌아와 **등급 표도 재정의도 함께 잃는다** — 반영 흔적 하나 남기려다 필드를
통째로 부수는 셈이다. 그래서 `DuelGradeRef.MAX_CONFIG_CHARS`는 그 상한의 절반 아래로 잡고
(config에는 실효 표·재정의도 함께 산다), **두 상수의 관계를 `DuelGradeRefTest`가 잠근다.**
R-10과 어긋나는 것이 아니라 **더 좁은 상한이 먼저 걸린다**는 사실을 찾은 것이다.

### 4-7. 구현 뒤 사용자 보고로 고친 셋 (2026.08.07)

세 건 다 **B-113이 닫힌 뒤 실사용에서 나온 것**이고, 셋 다 *"자동 검증이 보이는 것을 못 본다"*는
「세션 착수 규칙」 4번의 실증이다 — 컴파일도 시험도 통과하는 자리들이다.

**① 켠 스위치가 말없이 되돌아갔다 (버그).** `applyDuelGradeConfig`는 축을 못 집으면
`keepStoredDuelGrade`로 빠지고, 그 필드에 원래 약속이 없었으면 **키를 쓰지 않는다.**
새 필드에서는 그것이 곧 *"켠 스위치가 저장되지 않는다"*이고, 다시 열면 꺼져 있다.
**화면은 사유를 말하고 있었다**(축 없음 줄) — 그래서 더 나빴다: 사유가 보이니 사용자는
*알려 주는 화면이 저장도 알아서 했겠거니* 하고 창을 닫는다.

> **켜짐을 config에 남기는 쪽으로 고치지 않았다.** `DuelGradeRef.fromConfig`는 축 code가 비면
> 통째로 없는 것으로 읽고, 그 판정에는 이유가 적혀 있다 — *축 없는 약속은 어느 순위를 나눌지
> 말하지 못해 실행할 수 없고, 반쯤 살아 있는 상태로 두면 화면이 그것을 켜진 것처럼 그린다.*
> 그 결정을 뒤집는 대신 **버리지 말고 막는다**로 갔다(변수 제어의 순서 그대로: 검증 → 알림 →
> **교정 경로**. 교정 경로가 아래 ②다). 창은 닫지 않는다(R-27).

**함께 고친 구조 하나:** 사유 판정이 화면(`refreshDuelGradeEditor`) 안에 인라인으로 있어
저장 쪽에서 같은 물음을 던질 방법이 없었다. `duelGradeProblem()` 하나로 뽑아 **두 자리가 같은
함수를 본다** — 두 벌로 두면 *화면은 괜찮다는데 저장이 막히는* 반대 방향의 어긋남이 생긴다.

**② 축이 없으면 나갔다 와야 했다 (마찰).** 사유 줄이 *"대결 탭에서 축을 먼저 만드세요"*로
내보냈는데, 그러면 하던 필드 편집을 접고 나갔다 와야 하고 적어 두던 것이 사라진다(원칙 04).
**[여기서 대결 축 만들기]**를 사유 줄 바로 아래에 세웠다 — **교정 경로는 문제를 말한 그 자리에
있어야 한다.** 묻는 것은 **이름뿐**이다(나머지는 전부 기본값이 있고, 필드 연결·순서는 대결
탭에서 정하는 것이 원래 동선이다 — 여기서 전부 물으면 축 편집 창이 두 벌이 되고 한쪽이 낡는다).
참가자 종류는 **캐릭터 고정**이다(이미지 축의 순위는 캐릭터 필드에 쓸 수 없다).

**③ [등급 반영]이 무엇을 하는 단추인지 알 수 없었다 (문구).** 두 자리(필드 편집·순위표) 모두
이름이 *'등급 반영'* 넉 자였다 — **무엇이 어디에 쓰이는지**가 없다. 위 슬라이더가 정하는 것은
*약속*이고 이 단추가 그 약속을 *값*으로 만드는데, 이름만으로는 그 구별이 서지 않는다.
`순위를 등급 값으로 반영`으로 바꾸고 **목적문 한 줄**을 두 자리에 붙였다(*"지금 순위대로
캐릭터들의 이 필드 값을 채웁니다. 무엇이 바뀌는지 먼저 보여 주고, 바뀌기 전 값은 휴지통에
남습니다"*) — 새 기능 체크리스트 7번이 요구하는 *"무엇이 어디서 어떻게"*다.

### 5-1. 최근 업데이트분 점검 (실속 검토 포함)

| 대표 이미지 사다리 | D9(2번 칸)는 ⓑ 슬라이스 몫으로 비어 있는 것이 맞다 — 이번 요청 ②의 "대표 반드시 포함"은 사다리 1칸(지정 대표)을 쓰므로 **빗장과 무관**하다 |
| AI 결손 회계·비용 제어 | 튼튼하다(불변식 `suggestions + missing = 대상 전체`, 상한 전부 고지형). 2장이 이 틀을 그대로 탄다 |
| 필드 편집 다이얼로그 | 스위치·섹션이 이미 20+ — 1·4장이 섹션을 둘 더 얹으므로 **고급 탭 안을 '입력·표시 / 통계 / AI / 연동' 접이식 4구획으로 재편**한다(6장). 기능 삭감 없음 — 접근 단계만 줄인다 |

### 5-2. 예정 기능과 신규 요청의 맞물림

| 대상 | 검토 결과 |
|---|---|
| **B-114 (무승부)** | **B-122(3장 재설계)가 흡수한다** — 같은 화면을 두 번 고치지 않는다는 그 행의 지침 그대로 |
| **B-115 (k지선다)** | 3장 골격이 격자 전환을 미리 받는다. **착수 시 적합도 함께 볼 것:** 지금 설계는 k지선다를 승자 대 각 패자의 k−1판으로 저장하는데, "k명 중 1등"의 원리 모형은 **Plackett–Luce**다 — `groupId`가 이미 묶음을 알므로 **저장 형식 무변경으로** 적합만 PL 항으로 바꿀 수 있고, MM 알고리즘(Hunter 2004)이 PL을 그대로 지원한다(현행 최적화기와 같은 계열). 판당 정보량이 정직해진다. 다만 대각 뉴턴의 전례대로 **실측이 먼저다** — 이득이 작으면 안 바꾼다 |
| **B-116 (축 불러오기)** | 1장의 기본 필드가 서면 필드 연결의 "없는 키" 문제가 구조적으로 준다(1-7). 순서 강제는 아니다 — 없는 키를 세어 알리는 처방은 그대로 유효하다 |
| **ⓑ·ⓒ (이미지 축 + 경로 재작성 빗장)** | 신규 7건 어느 것도 이 빗장을 건드리지 않는다(②③은 파일을 읽기만 하고 개명하지 않으며, ⑥⑦은 이미지와 무관하다). 대기열 위치만 뒤로 밀린다 — 소멸이 아니다 |
| **B-108 (제공자 자동 전환)** | 2장의 이미지 요청에도 그대로 적용될 설계다(확정 ⓕ의 "완결된 몫은 살린다"가 ③의 배치 단위 보존과 같은 규칙). 새 학습 사실 `imagesUnsupported`가 R-23 등재를 하나 늘린다 — **B-108 착수 세션이 그 목록을 갱신할 때 함께 볼 것** |
| **B-105 (엑셀 앱 설정 레지스트리)** | 2장의 새 AI 설정(첨부 장수 기본값 등)이 등재 대상 ⓐ 부류다 — 레지스트리가 서면 한 줄로 들어간다 |
| **`매칭` 표1 등재 슬라이스** | 이 문서의 제안 문구는 전부 '대결'·'판'·'짝'을 쓴다 — 새 부채를 만들지 않았다 |

## 7. 요청 ⑥ — AI 이름 추천 (B-123)

### 7-1. 기존 필드 추천 경로에 얹지 못한다 — 전용 시트다

이름은 커스텀 필드가 아니라 **엔티티 컬럼**(`name`·`firstName`·`lastName`·`anotherName`)이라
필드 추천의 대상식(`bulkTargetsOf` — `FieldDefinition` 기반) 밖이다. 서술형 작성이 전용
시트(`NarrativeWriteSheet`)를 가진 것과 같은 이유로 **이름 추천 시트**를 새로 연다.
진입은 편집 폼 **이름 줄의 ✨**(필드 ✨과 같은 문법 — 새 문법을 만들지 않는다).

### 7-2. "계속 피드백해서 소통" — 멀티턴 없이 라운드로 성립한다

현행 AI 계층은 단일 턴뿐이고 멀티턴은 향후 과제로 등재돼 있다. **그러나 이 요구에 멀티턴이
필요 없다** — 라운드마다 상태를 동봉하는 단일 턴으로 같은 대화가 성립하고, 그 문법은 이미
검증돼 있다(보완 재요청의 `userInstruction` + `rejectedValues` — 필드 추천 검토 화면이 쓰는
그것). 새로 만드는 것은 상태의 종류가 아니라 **크기**다:

| 라운드 요청에 실리는 것 | 뜻 |
|---|---|
| 다발 크기 N | *"한번에 많이"* — 기본 10, 1~30 |
| 유지 목록(♥ 표시한 이름) | *"이 결을 따르라"* |
| 거절 목록(✕ 표시한 이름) | *"이쪽은 피하라"* — `rejectedValues`·`REPEATED` 관행 그대로 |
| 자유 지시 | *"더 부드럽게"*, *"북부식으로"* — `userInstruction` 그대로 |
| 창작도 칩 | 기존 `CreativityChipRow` 재사용 |

화면은 후보 행 목록(이름 + 짧은 근거)이고 행마다 **♥ / ✕ / 적용** 셋이다. 적용은 폼 위젯에만
쓴다(AI 출력을 DB에 직접 기록하지 않는 기존 불변식). 라운드당 요청 1건을 미리 고지한다.

**UI 정본 목업: `docs/mockups/name_suggest_sheet_2026-08.html`** — 3구역 시트(♥ 선반 ·
최신 라운드 · 지난 라운드 접힘)와 피드백 줄, [은행에 담기]를 화면 그대로 담았다.

**라운드가 쌓이는 화면의 구성** — 세 라운드면 후보가 30개를 넘는다. 시트는 세 구역이다:
ⓐ 상단 고정 **♥ 선반**(유지한 이름 칩 — 어느 라운드 것이든 여기 모인다. 칩 탭 = 적용 후보로)
ⓑ **최신 라운드**(전개 상태 — 행 목록) ⓒ **지난 라운드**(라운드별로 접힘 — 머리글에
*"2라운드 · 10개 중 ♥2 ✕3"*). ✕ 표시는 어느 구역에서든 회색 처리로 남는다(사라지지 않는다 —
[은행에 담기]의 재료이고, 같은 이름이 다시 오는 것을 `REPEATED`로 거르는 근거다).

### 7-3. 컨텍스트 — 세계관의 결을 견본으로 싣는다

- 캐릭터 컨텍스트는 기존 조립기(`CharacterAiContextBuilder`) 재사용 — 태그·성별·종족·소속이
  이름의 결을 정한다.
- **같은 세계관의 기존 캐릭터 이름 견본**(상한 30 + 넘친 수 고지). 실사용 표본이 근거다 —
  세계관마다 이름 결이 뚜렷하고(0-1장) 견본 없이는 모델이 그 결을 알 길이 없다.
- **이름은행의 미사용 엔트리 견본**(상한 소량) — 이미 쌓아 둔 취향도 결의 일부다(8장 ⓒ와 연동).
- **모드 셋**: 전체 이름 / **성 고정 + 이름만**(가문명이 반복되는 실사용 — 프셀류트가에 새
  식구를 들일 때) / 이름 고정 + 성만. 적용 시 `name` 또는 `firstName`/`lastName` 칸에 맞게
  들어간다.
- **이명(`anotherName`) 모드**를 같은 시트에 스위치 하나로 연다 — 원문 밖이지만 같은 기계라
  여는 비용이 0에 가깝고, 실측 이명 채움 111/207이 수요를 말한다(칭호류 — *"시간의 용사"*).

### 7-4. "산출된 이름 데이터는 축적" — 세션 풀 → 이름은행

- 모든 라운드의 후보가 ♥/✕ 표식과 함께 **세션 풀**에 쌓인다(시트가 살아 있는 동안 — 회전
  생존은 기존 `runAiSuggest` 관행).
- **[은행에 담기]** — 중복을 걸러 이름은행에 넣는다: ⓐ 은행 기존 이름과 공백·대소문자 무시
  일치 제외 ⓑ 풀 안 중복 제외 ⓒ 이미 캐릭터가 쓰는 이름은 표식. ✕ 표시한 이름은 기본 체크
  해제로 두되 포함할 수 있다(이 캐릭터에게 아닌 이름이 다른 캐릭터에겐 맞을 수 있다).
  넣은 수·거른 수를 센다(R-14).
- 담을 때 **성별과 출처를 자동으로 채운다**(성별 = 모드/캐릭터 성별 · 출처 = `AI 추천`).
  실측에서 은행의 출처·메모가 전부 빈 칸인 것은 손으로 채울 이유가 없어서다 — 자동으로 채울
  수 있는 칸은 앱이 채워 준다.

### 7-5. 확장성 판정 · 순서

4단계: ① 새 상한 둘(다발 30 · 견본 30 — 둘 다 고지형) ② 비용은 라운드당 요청 1건(온디맨드,
새 축 아님) ③ 스냅샷 무변경 ④ 엑셀 무변경(은행 시트는 기존 그대로). **B-120(멀티모달)과
무관하다** — 텍스트 전용이라 언제든 열 수 있다. 은행 쪽 배선(중복 대조·담기)은 8장과 겹치므로
**B-124를 먼저 여는 편이 싸다**(강제는 아니다).

> 이 기능은 `ai_integration.md`가 후보 기능으로 적어 둔 *"이름은행 연동 이름 생성"*의 구현이다 —
> 계획으로만 있던 줄이 요청 ⑥으로 실체가 됐다. 계약은 **A-8**로 등재한다.

## 8. 요청 ⑦ — 이름은행 연계 개선 (B-124)

### 8-1. "따로 논다"의 실체 — 코드가 전수로 확인해 준다

착수 대조가 연계 부실을 16자리로 셌다(탐색 전수 — 대표만 든다):

| 없는 것 | 실상 |
|---|---|
| 편집 폼 ↔ 은행 | `ui/character/`에 은행 참조 **0건.** 이름 칸에서 은행을 열 길도, 은행이 제안할 길도 없다. **"미사용 이름 목록을 다른 화면에 주려던 API(`getAvailableNamesList`)가 소비처 없이 죽어 있다"** — 연계가 계획됐다 만 흔적이다 |
| 저장 시 자동 대조 | 손으로 만든 캐릭터가 은행의 이름을 그대로 써도 은행은 영원히 "미사용"이다 — 사용 표시가 켜지는 경로는 일괄 등록·엑셀·월드패키지·휴지통 복원 넷뿐. **실사용 표본이 그 결과다**(0-1장 — 겹침 3건, 링크 0) |
| 단건 "사용 처리" | `markAsUsed` API와 결과 문구까지 만들어져 있는데 **UI 진입점이 없다**(감사 문서가 이미 등재한 미배선) |
| "누가 쓰는가" 표시 | 목록 행은 "사용됨"만 찍고 `usedByCharacterId`를 읽지 않는다 — **연결이 화면에 나오는 곳은 엑셀 시트뿐이다** |
| AI | 프롬프트에 실리지도, AI가 넣지도 않는다(계획 줄만 있음 — 7장이 그 구현이다) |
| 통계 미사용 목록 | 표시만 하고 아무 행동도 걸 수 없다 |

휴지통 쪽 사용 링크 기계(B-3 — code 단독 relink · 빼앗기 금지)는 튼튼하다. **문제는 링크가
생기는 입구가 없다는 것**이다 — 기계는 있는데 아무도 태우지 않는다.

### 8-2. 설계 — 네 축

**ⓐ 편집 폼 ↔ 은행 (양방향).**
- 이름 줄에 **[은행]** 버튼 — 선택 시트: 미사용 우선 + 검색 + 성별 일치 우선 정렬(캐릭터의
  성별 필드 값 — GENDER 역할(Q4)이 서면 그것으로 집는다). 고르면 이름 칸에 들어가고 **저장
  시점에 사용 링크가 걸린다**(편집 취소 계약 준수 — 즉시 쓰지 않는다). 죽어 있던
  `getAvailableNamesList`가 드디어 소비처를 얻는다.
- 역방향 — 이름 칸 값이 은행에 없으면 **[지금 이름을 은행에 저장]**(시트 하단 한 줄).
- 같은 줄의 ✨은 7장의 이름 추천 시트를 연다(두 진입이 나란히 — 이미 있는 이름 창고와 새로
  만드는 기계).

**ⓑ 저장 시 자동 대조 (Q7).** 캐릭터 저장 경로(`CharacterSaveCoordinator`)가 이름을 은행과
대조해 — 일치하는 **미사용** 엔트리가 있으면 링크를 자동으로 걸고 결과에 한 줄 고지한다.
이름이 바뀌면 옛 링크는 미사용으로 풀린다. 대조 키는 은행의 자연키(이름+성별) 중 **이름**이고,
이미 남이 쓰는 엔트리는 빼앗지 않는다(B-3 규약 그대로). **기존 데이터의 뜻이 바뀌는 자리라
Q7로 묻는다** — 켜지는 순간 실사용 41건 중 3건이 '사용됨'으로 바뀐다(그것이 정확히 사용자가
원한 상태로 보이지만, 데이터 재해석은 확인 후 간다).

**ⓒ 은행 화면의 표시·행동.**
- 행에 **사용 캐릭터 이름**을 보이고 탭하면 그 캐릭터로 간다(역방향 이동 — 지금은 엑셀에만
  있는 정보를 화면으로).
- 롱클릭 옵션에 **[사용 처리]**(미배선 API에 UI를 단다 — 캐릭터 고르기)와 **[이 이름으로
  캐릭터 만들기]**(기존 일괄 등록 계획기의 단건판 — 새 기계 없음).
- **[AI로 이름 만들기]** — 7장의 시트를 캐릭터 없이 연다(세계관을 골라 그 결로 다발 생성 →
  은행에 담기). 은행이 소비 창고에서 **생성 도구**가 된다.
- 통계의 미사용 이름 목록에서 은행으로 이동(표시 전용이던 자리에 최소 행동 하나).
- 성별 입력의 고정 3옵션 스피너를 **자유 입력 + 제안**으로 연다(열린 구조 — 감사 문서 등재분).

**ⓓ 정리 부채 동반 수리.** 죽은 코드 4건(감사 문서 등재)은 이 슬라이스에서 처분한다 —
`getAvailableNamesList`·`markAsUsed`는 소비처가 생기고, `searchNames`·`insertAll`·
`getAllNameBankList`는 걷거나 쓰임을 단다. 일괄 등록의 성별 매핑 하드코딩(`"gender"` 키
고정)은 GENDER 역할(Q4)이 서면 역할로 집는다 — 사용자가 다른 key로 만든 성별 필드도 잡힌다.

### 8-3. v1 밖 — 등재만 하는 것

- **세계관 스코프(또는 태그·분류)** — 은행은 전역이고 스코프 칸이 없어, 세계관별 이름 결이
  한 목록에 섞이고 통계의 작품 필터가 미사용 이름을 통째로 숨긴다. **v1은 열지 않는다** —
  스코프 도입은 DB·필터·왕복·월드패키지를 함께 여는 되돌리기 어려운 축이고, 7장의 담기가
  **출처(origin)를 자동으로 채우기 시작하면**(세계관 이름을 적는다) 자유 텍스트 필터만으로
  충분한지가 실사용으로 판가름난다. 그 뒤에 재검토한다.
- **전역 검색 편입 · DB 검색(FTS)** — 검색 인프라(B-10)의 몫과 겹친다. 규모 미측정(×30에서
  1,230행)도 그쪽 축이다.

### 8-4. 확장성 판정

1. **새 상한?** 없다(선택 시트 목록은 기존 화면 상한 관행).
2. **비용 축?** 저장 시 대조 1회 — 이름 정확 일치 조회(색인 있는 작은 표). 새 축 아님.
3. **스냅샷?** 무변경(B-3 기계 그대로).
4. **엑셀?** 무변경 — '사용여부'·'사용 캐릭터' 열은 이미 있고, ⓑ가 채워 주기 시작할 뿐이다.
