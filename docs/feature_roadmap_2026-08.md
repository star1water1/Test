# 기능 로드맵 2026-08 — 신규 요청 5건 설계 · 기존 기능 개선 검토 · UI/UX 재구성

> **이 문서의 지위.** 사용자 요청(2026.08.06) 다섯 건과 함께 내려온 지시 — *"로드맵 검토하고 …
> 개선안 설계해. 그러고 난 뒤에 각각의 기능에 맞게 ui/ux 적극적으로 재구성하고 … 사용자가 이미
> 제안한 알고리즘이 있으면 그에 갇혀있지 말고 더 좋은 게 있는지 조사한 뒤 사용자에게 제안할 것.
> 이 세션에서 직접적인 코드 개발은 최소한으로 하고 기능 설계 및 업데이트 로드맵 구축, UI설계등의
> 문서작업을 위주로 진행할 것"* — 의 산출물이다. **이 세션은 코드를 한 줄도 바꾸지 않았다.**
>
> **신규 요청 다섯 건의 설계 정본은 이 문서다**(백로그 B-119~B-122와 B-113이 여기를 가리킨다).
> 대결 시스템 일반의 정본은 `docs/duel_system_design_2026-08.md`가 유지하며, 3·4장의 구현이
> 끝나면 그 결과는 그 문서의 새 장으로 옮겨 적고 이 문서의 해당 장은 포인터만 남긴다
> (같은 내용을 두 자리에 두지 않는다).
>
> **착수 세션은 9장(구현 순서)과 10장(판정 필요)부터 읽는다.** 10장이 비기 전에는
> 해당 슬라이스를 시작하지 않는다 — 세션 착수 규칙 3번(사용자 확정을 뒤집지 않는다)의 예방형이다.

## 0. 착수 대조 — 손대기 전에 확인한 것

「세션 착수 규칙」 1번대로 이번에 손댈 슬라이스(필드 시스템 · AI 연동 · 이미지 탭 · 대결)만 봤다.

| 본 것 | 결과 |
|---|---|
| 전역(모든 세계관 공통) 필드 개념이 코드에 있는가 | **없다.** 필드 유일성은 `(universeId, entityType, key)`이고, `universeId = 0`은 프리셋 미부착 상태일 뿐이며 **그 값으로 필드를 심는 것은 버그로 봉인돼 있다**(`remaining_work` 등재 + 검사 도구). 세계관 간 공유는 복사(B-89 병합)뿐이다 |
| AI에 이미지를 보내는 경로가 있는가 | **0건이다.** `AiMessage`는 `text: String` 하나이고, 세 프로토콜 직렬화기 전부 텍스트만 쓴다. `ImageFolderTagSuggester`는 **폴더 이름이라는 텍스트만** 읽으며, 문서와 코드 주석 양쪽이 *"이미지를 모델에 보내지 않는다"*를 명문으로 약속하고 있다(`image_folder_tag_ai` 1장 · `ImageFolderTagSuggester.kt:10`). **2장의 기능은 이 약속을 뒤집으므로 그 문구들을 함께 갱신해야 한다**(B-107 ②의 전례 — 예외를 만들면 그 예외를 화면이 말해야 한다) |
| 대결 화면의 선택지 구조 | **정확히 2택이다**(`DuelPlayFragment.pick(left)`). 하단 바는 좌 '방금 그거 취소' · 우 '순위표'이고 **가운데가 비어 있다**(B-114 무승부 버튼의 자리). 카드 정보는 이미지 위 스크림 한 줄(`이름` + 영향 필드 `\n` 연결 TextView 하나)에 몰려 있다 |
| B-113(산출 필드 반영)의 상태 | **살아 있는 판정 대기 유일 건.** 물음 ①(1500 눈금을 필드 값으로 어떻게 옮기나)에 **이번 요청 ⑤가 방향을 줬다** — 상위 %에 따른 등급. 물음 ②(덮어쓰기 보호)는 4장이 설계로 답한다 |
| 성별·나이가 시스템 필드인가 | **성별은 아니다** — 프리셋의 일반 SELECT 필드다. 시맨틱 역할 8종에 성별이 없다. 나이는 AGE 역할 + `TimeStateResolver`로 해석된다. 3장의 "이름·성별·나이 필수"는 이 사실 위에서 설계해야 한다 |
| 재현 기준선 | **밟지 않았다 — 이 세션은 코드 무변경이다**(사용자 지시). 구현 슬라이스가 `remaining_work` 5장 2번 절차로 밟는다 |

**용어:** 이 문서의 화면 문구 제안은 전부 '대결'·'판'·'짝'을 쓴다(`매칭` 금지 — 확정 23번 ↔ 2번).

**요청 원문(2026.08.06):**

> 1. 기본 필드 지정할 수 있게. 기본적으로 모든 캐릭터가 가지는 필드. 세계관 불문하고. 이건 필드
>    생성할때도 전역설정 할 수 있고 편집에서도 가능.
> 2. ai한테 필드 추천받을때 해당 캐릭터의 이미지도 한장(몇장인지는 선택할 수 있게, 최대
>    10장까지?) 보낼 수 있게 옵션 하기. 대표 이미지 반드시 포함 옵션도 있고 그 외엔 랜덤.
> 3. 이미지탭에서 이미지 (사용자 지정)장 씩 한꺼번에 ai한태 보내서 태깅할 수 있게 하기.
> 4. 대결창에 각 캐릭터 프로필 필드도 연동할 수 있게 하기. 기본으로 이름, 성별, 나이는 필수로
>    들어가게. 나머지는 사용자가 커스텀할 수 있게 하고 ui도 그에 맞춰서 재설계할것.(이건 대결에
>    영향을 주는 필드와는 따로임)
> 5. 대결 결과 필드를 좀더 잘 쓸 수 있도록 필드 속성? 아무튼 거기에서 대결 상위 몇퍼센트에 따라
>    등급 지정하는 속성옵션도 추가해줘.

## 1. 요청 ① — 전역 기본 필드 (B-119)

### 1-1. 무엇을 만드는가

**"모든 세계관의 모든 캐릭터가 기본으로 가지는 필드"를 사용자가 정의하는 기능.**
필드 생성 시 "전역 기본으로" 지정할 수 있고, 이미 있는 필드를 나중에 승격할 수도, 해제할 수도 있다.

### 1-2. 구조 — 참조가 아니라 **구체화(materialization)**다

두 갈래를 대조했다.

| 안 | 내용 | 판정 |
|---|---|---|
| 참조형 | 전역 필드를 세계관 밖에 두고 모든 읽기 경로가 `세계관 필드 ∪ 전역 필드`를 본다 | **기각.** 읽기 경로 전부(폼·통계·엑셀·값 라이브러리·월드패키지·검색·정렬)가 합집합을 알아야 한다. `FieldDefinitionDao`의 `entityType` 기본값 함정(R-29)과 같은 부류의 사각이 **경로 수만큼** 생기고, 하나만 빠져도 "전역 필드가 이 화면에서만 안 보인다"가 조용히 난다 — 원칙 02 위반(껍데기)의 가장 흔한 발생 경로다 |
| **구체화형 (채택)** | 전역 템플릿을 별도 표에 두고, 각 세계관에는 **보통 필드로 심는다**(복사 + 연결 표식). 기존 소비처는 아무것도 몰라도 된다 | **채택.** 이 저장소가 이미 같은 모양을 쓴다 — 세계관 등급 체계가 필드 config에 실효 표를 **물질화**하고(R-30), 다른 세계관 출신 필드는 참조를 **강등(demote)** 한다. 그 관행이 검증돼 있다 |

**저장:**

- 새 엔티티 `DefaultFieldTemplate` — `FieldDefinition`에서 `universeId`를 뺀 것 + `code`(안정 식별자, R-1).
  `entityType`을 그대로 갖는다(캐릭터 요청이 원문이지만 구조는 사건·작품에도 열어 둔다 — 원칙 01).
  마이그레이션은 표 추가뿐인 순수 추가다(버전 번호는 구현 시점의 다음 번호 — 선점하지 않는다).
- 세계관에 심긴 필드는 `config`에 `defaultField: <템플릿 code>` 한 키를 갖는다(연결 표식).
  **config 키라 필드 쪽 마이그레이션이 없다.**

**GRADE 템플릿의 등급 체계 참조는 갖지 못한다** — 등급 체계는 세계관 단위라 전역 템플릿이
가리킬 대상이 없다. 템플릿은 실효 표만 갖는다(강등된 형태 — `GradeSystemRef.demote`가 이미
다른 세계관 출신 복사에 쓰는 그 규칙이다).

### 1-3. 전파 규칙 — **기본 필드는 '존재'를 보장하는 것이지 '내용'을 강제하는 것이 아니다**

| 사건 | 처분 |
|---|---|
| 세계관 신설 | 템플릿 전부를 심는다. 프리셋을 함께 고르면 **기본 필드가 먼저** 심기고, 프리셋 병합(`PresetMerge`)이 같은 key를 중복으로 걸러낸다(기존 규칙 그대로) |
| 템플릿 신설 / 기존 필드의 승격 | 모든 세계관에 심는다. **같은 `(entityType, key)`가 이미 있으면 덮지 않고 연결만 건다**(그 세계관의 설정 존중 — 자율성 우선). 결과를 센다: *"새로 심음 N곳 · 기존 필드에 연결 M곳"* |
| 템플릿 편집 | **명시적 전파**다 — 자동으로 퍼뜨리지 않는다. 전파 미리보기가 세계관별 상태를 보인다: 템플릿과 같음(변경 없음) / 다름(**그 세계관에서 사용자가 고쳤다는 뜻** — 기본 해제된 체크박스로 두고 사용자가 고른 곳만 덮는다). 다름 판정은 `PresetMerge.configEquals`(이미 있는 canonical JSON 비교)를 그대로 쓴다. 타입이 바뀌는 전파는 세계관별 `checkTypeChangeImpact`를 미리보기에 싣는다. 덮이는 정의는 `snapshotFieldDefinitions`로 백업한다(B-89 병합이 이미 하는 그것) |
| 템플릿 삭제 / 승격 해제 | 심긴 필드는 **일반 필드로 강등만 한다**(연결 표식 제거). 값이 든 필드를 지우는 것은 사용자가 세계관에서 직접 지울 때뿐이다 — 어떤 경우에도 이 기능이 캐릭터 데이터를 지우지 않는다(개발 의도 2번) |
| 세계관에서 심긴 필드를 편집 | 배너 한 줄: *"이 필드는 기본 필드 '○○'와 연결되어 있습니다."* 그대로 저장하면 그 세계관만 달라진다(전파 미리보기가 '다름'으로 본다). **막지 않는다** |
| 세계관에서 심긴 필드를 삭제 | 허용(그 세계관의 자유). 템플릿은 남으므로 "다시 심기"가 기본 필드 관리 화면에 있다 |

### 1-4. UI

- **필드 편집 다이얼로그**(고급 탭)에 스위치 하나:
  - 라벨: `전역 기본 필드`
  - 목적문(R-25): *"켜면 이 필드가 모든 세계관에 기본으로 심어져, 어떤 세계관의 캐릭터에도 이 칸이 생깁니다."*
- **기본 필드 관리 화면** — 진입은 필드 관리 툴바 메뉴 + 설정. 템플릿 목록(이름·타입·대상 종류·
  *"세계관 N곳 연결 · M곳 다름"*) / 새로 만들기(FieldEditDialog 재사용, 등급 체계 참조 없음) /
  전파 / 다시 심기 / 해제.
- 필드 관리 목록의 심긴 필드 행에 작은 배지(예: `기본`).

### 1-5. 엑셀 왕복 · 월드패키지

- 새 시트 `기본 필드` — `필드 정의` 시트와 같은 열에서 `세계관`을 뺀 것 + `코드`.
  **가져오기 순서는 `기본 필드` → `필드 정의`**(정의가 값보다 앞이라는 기존 규약의 연장 —
  연결 표식이 가리킬 템플릿이 먼저 서야 한다).
- `필드 정의` 시트에 `기본필드코드` 열 하나 추가. 빈 칸 = 연결 없음(기존 "빈 칸 = 해제" 규약).
- 가져온 파일의 `기본필드코드`가 템플릿에 없으면 **강등하고 센다**(*"기본 필드 연결 N건을 찾지
  못해 일반 필드로 두었습니다"* — 거부가 아니라 수용·교정, 개발 의도 4번).
- **월드패키지는 바꾸지 않는다** — 세계관 단위 교환이라 심긴 필드가 이미 실려 있고, 받는 쪽에
  같은 템플릿이 없으면 위 강등 규칙이 그대로 적용된다.

### 1-6. 확장성 판정 (`scalability_performance` 7장 4단계)

1. **새 상한?** 없다. 템플릿 수는 사용자가 손으로 만드는 짧은 목록이다.
2. **비용 축?** 전파 한 번이 `세계관 수 × 템플릿 수`(목표 규모 270 × 수십 = 수천 행 upsert) —
   명시적 단추를 눌렀을 때만 돌고, B-89 병합이 이미 같은 크기의 트랜잭션을 돈다. 새 축이 아니다.
3. **스냅샷 목록?** 추가하지 않는다.
4. **엑셀?** 시트 하나(작다) + 열 하나. 가장 큰 시트가 되지 않는다.

### 1-7. 함께 얻는 것 (원칙 05)

기본 필드의 key는 **세계관을 넘어 안정**하다. 그래서 ⓐ 통계의 `(key, type)` 머지 카드가 전
세계관에서 자연히 한 장으로 모이고(성별 비율·나이대 분포의 전역 조감이 처음으로 정합해진다)
ⓑ B-116(대결 축 불러오기)의 필드 연결이 "없는 키" 없이 옮겨지며 ⓒ 3장의 프로필 트리오가
어느 세계관에서든 서게 된다.

## 2. 요청 ②·③ — AI에 이미지가 실린다 (B-120 · B-121)

두 요청은 **같은 기반(멀티모달 요청) 위의 소비처 둘**이다. 기반을 한 번만 만들기 위해 한 장으로
설계하되, 구현은 ②(기반+필드 추천) → ③(일괄 태깅)의 두 슬라이스로 가른다.

### 2-1. 공통 기반 — 멀티모달 요청 계층

**현행 사실:** `AiMessage(role, text)` — 이미지 칸이 없다. 세 직렬화기 전부 텍스트만 쓴다.
저장소 전체에 비전 요청 코드 0건. **그리고 문서·주석 두 자리가 "이미지를 모델에 보내지 않는다"를
약속하고 있다** — 이 기능이 들어가는 슬라이스는 그 문구(`image_folder_tag_ai` 1장,
`ImageFolderTagSuggester.kt:10`, 관련 도움말)를 반드시 함께 갱신한다.

**설계:**

- `AiMessage`에 `images: List<AiImage> = emptyList()` 추가. `AiImage(base64, mediaType)`.
  기본값이 있어 기존 호출부 5곳은 무변경이다.
- `AiProtocolCodec`이 프로토콜별로 직렬화한다 — ANTHROPIC은 content block 배열(`image` +
  `text`), OPENAI_COMPAT은 `image_url`(data URI) 파트, GEMINI는 `inline_data` 파트.
  **코덱은 순수 JVM이라 세 직렬화 모양을 하네스로 고정할 수 있다** — 프롬프트 문자열과 달리
  이 자리는 로컬 검증이 닿는다. 반드시 테스트를 함께 넣는다.
- **전송용 축소 유틸 `AiImagePreparer`** — 저장용 압축(`ImageImportHelper`)과 별개다(그쪽은
  로컬 용량 목적이고 8192px까지 허용한다). 전송용은 긴 변 1024px · JPEG 재인코딩을 기본으로
  하고, 상수는 한 곳에 둔다. *(1024는 제안값이다 — 실호출로 품질·비용을 재 본 뒤 확정한다.
  P-9의 관행: 근거 없는 숫자를 박지 않는다.)*
- **모델이 이미지를 거부하면**(400) — A-4의 관행 그대로: 이미지를 빼고 1회 재시도 →
  `imagesUnsupported`를 **학습**해 다음부터 묻지 않는다 → 결과에 한 줄 고지(*"이 모델이 이미지를
  받지 않아 글만 보냈습니다"*). **학습한 사실이므로 `hasLearnedFacts()`에 등재한다**(R-23 —
  B-108 ⑥이 지목한 바로 그 규칙).
- **비용 고지:** 기존 고지 다이얼로그에 줄 하나 — *"이미지 N장을 함께 보냅니다. 장당 대략
  250~1,600토큰이 더 듭니다(제공자마다 다릅니다)."* 이미지가 기기 밖으로 나간다는 사실도 같은
  자리에서 말한다(기존 약속을 뒤집는 지점이므로 침묵 금지).
- 파일이 없거나 읽을 수 없으면 **건너뛰고 센다**(*"이미지 2장을 읽지 못해 빼고 보냈습니다"* — R-14).

### 2-2. 소비처 A — 필드 추천·서술형 작성에 캐릭터 이미지 첨부 (요청 ②, B-120)

**어디에:** 짧은 값 추천(`CharacterFieldAiSuggester`)과 **서술형 작성**(`NarrativeFieldAiWriter`)
둘 다. 원문은 필드 추천을 말했지만 서술형(외모 묘사)이 이미지의 최대 수혜자이고, 두 경로는 이미
같은 컨텍스트 조립기를 쓴다 — 한쪽만 열면 반쪽이다(원칙 02).

**고르는 규칙(원문 그대로 + 한 걸음):**

| 옵션 | 동작 |
|---|---|
| 첨부 장수 | 0~10장. 0 = 안 보냄. 기본값은 AI 설정에 저장(`AiPromptSettings` — 적재량 슬라이더의 형제. 제안 기본값 1장) |
| **대표 이미지 반드시 포함** | 켜면 지정 대표(사다리 1칸)가 항상 첫 장이다. 지정 대표가 없으면 그 사실을 말하고 전부 랜덤으로 채운다(조용히 다른 그림을 '대표'라 부르지 않는다) |
| 나머지 | 그 캐릭터의 이미지 목록에서 랜덤(중복 없이). **직접 고르기 경로도 연다** — 썸네일 줄에서 체크해 갈아 끼우기(자율성 우선. 랜덤만 있으면 "하필 그 장"을 뺄 길이 없다) |
| 재추첨 | 고지 다이얼로그의 썸네일 줄에서 🎲 한 번 |

랜덤 대안으로 **태그 다양성 최대화**(태그가 겹치지 않는 장 우선)를 검토했다 — 태그 없는
이미지가 대부분인 실사용에서 근거가 서지 않아 v1은 랜덤 + 직접 고르기로 간다. 태깅(③)이
쌓이면 그때 다시 잰다(10장 ③).

**응답 활용:** 시스템 프롬프트에 규칙 한 줄 — *"이미지에서 읽은 값이면 `reason`에 어느 이미지
몇 번째인지 적어라."* 검토 화면의 근거 줄이 그대로 보여 준다(새 UI 없음).

**A-3(보충 탭)의 뽑기 잠금 규칙이 그대로 적용된다** — 요청 중 대상이 바뀌면 A의 이미지로 받은
추천이 B 폼에 들어가는 사고는 기존 2겹(잠금 + `targetCharacterId` 대조)이 이미 막는다.

**계약 문서:** `docs/ai_integration.md`에 **A-7**(이미지 첨부)로 등재한다.

### 2-3. 소비처 B — 이미지 탭 일괄 AI 태깅 (요청 ③, B-121)

**현행 사실:** 기존 "AI 태그 제안"은 폴더 받아오기 흐름 전용이고 **폴더 이름만** 읽는다.
이미지 내용을 보는 태깅은 처음이다.

**흐름:**

1. 이미지 탭 다중선택 → 일괄 작업 시트에 **"AI 태그 제안"** 추가. (선택 없이 "태그 없는 이미지
   전체"를 고르는 지름길도 필터에 이미 있는 무태그 필터로 잇는다.)
2. 설정 시트: **한 번에 보낼 장수**(1~10, 기본 5 — 사용자 지정이 원문이다) · 요청 수 고지
   (*"이미지 23장을 5장씩 5번에 나눠 보냅니다"* — `AiPromptPolicy`의 기존 계산 관행) · 어휘
   요약 · 기조(기존 `imageTagPolicy` 600자 그대로).
3. 진행: **결정형 진행도**(R-26 — *"요청 3/5 · 이미지 15/23"*), 취소 가능. **끝난 배치의 제안은
   살린다**(B-108 ⓕ의 관행 — 완결된 몫은 버리지 않는다).
4. 검토: 이미지별 행(썸네일 + 제안 태그 칩, 칩 단위 체크) — 폴더 태그 검토 시트의 규칙을
   그대로 넓힌다(어휘 밖은 `새 태그` 표식, 기본 전부 체크). **적용은 기존 태그에 합친다**(덮지
   않는다 — D-4·D-7 그대로, `image_tags` 스키마 무변경).

**오배정 방어 — 이 기능의 실제 위험은 비용이 아니라 "태그가 남의 이미지에 붙는 것"이다:**

- 한 요청의 이미지들은 **번호로 봉인**한다 — 프롬프트가 각 장을 `이미지 1`, `이미지 2`…로
  부르고, 응답은 `[{index, tags[]}]` JSON이어야 한다.
- 응답의 index가 요청 범위를 벗어나거나 겹치면 **그 배치를 통째로 실패로 접고 센다** —
  절반만 믿고 붙이는 것이 곧 오배정이다(R-1의 정신: *오배정은 생략보다 나쁘다*).
- 실패 배치는 "1장씩 다시 보내기" 재시도 경로를 준다(장수 1이면 index 사고가 원리적으로 없다).

**어휘 접기:** 응답 태그는 기존 태그와 **공백·대소문자 무시 일치**면 기존 표기로 접는다
(`matchOption`이 SELECT 값에 이미 쓰는 그 규칙). `물의정령`과 `물의 정령`이 두 태그로 갈리는
것을 막는다.

**어휘 조립은 단일 소스로 뺀다** — `buildVocabulary`(상위 120 태그 + `imageTagVocab` 필드 값 +
기조)는 폴더 제안기와 이 기능이 **같은 함수**를 써야 한다. 두 벌이 되면 같은 앱의 두 AI가 다른
어휘로 말한다.

### 2-4. 확장성 판정 (두 소비처 공통)

1. **새 상한?** 둘 — 첨부 10장(②) · 배치 10장(③). 버려지는 것은 없다(사용자가 고른 만큼만
   나간다). 상수는 한 곳에 둔다.
2. **비용 축?** 새 축이다 — **요청 바이트/토큰이 이미지 장수에 선형**. 전송용 축소(2-1)가
   장당 크기를 묶고, 요청 수 고지가 사전에 말한다. 온디맨드 경로라 상시 비용은 0이다.
3. **스냅샷?** 건드리지 않는다.
4. **엑셀?** 없다. (첨부 장수 기본값 등 새 AI 설정은 **B-105 레지스트리가 서면 그쪽에 등재**한다.)

## 3. 요청 ④ — 대결창 프로필 필드 연동 + 화면 재설계 (B-122)

### 3-1. 연결이 셋이 된다 — 방향과 쓰임이 전부 다르다

| | 방향 | 대결 화면 | 예측에 쓰나 |
|---|---|---|---|
| 영향 필드 (기존) | 필드 → 대결 | 보인다 | **쓴다**(사전식) |
| 산출 필드 (기존) | 대결 → 필드 | 안 보인다 | 안 쓴다 |
| **프로필 필드 (신설)** | 표시 전용 | **보인다** | **안 쓴다** |

프로필 필드는 *"누구인지 알아보는"* 재료이지 *"누가 이길지 가르는"* 재료가 아니다 — 원문의
괄호(*"대결에 영향을 주는 필드와는 따로임"*)가 정확히 이 구별이다. 예측·어긋남 감지 어디에도
들어가지 않는다.

**저장: `DuelAxis.profileFieldKeys`** — `influenceFieldKeys`와 같은 모양의 열 하나(순수 추가
마이그레이션). 축 단위로 두는 이유: '강함' 축에서는 전투 관련을, '아름다움' 축에서는 외모 관련을
띄우고 싶은 것이 실사용이고, 저장·JSON·엑셀 규약(`DuelFieldLinks`)과 고르는 다이얼로그를
**그대로 재사용**한다(새 문법을 만들지 않는다). 엑셀 `대결 축` 시트에 `프로필필드` 열이 함께
는다(쉼표 이어쓰기 — `-` 접두 없음).

**산출 필드는 프로필로 골라도 표시에서 뺀다** — 물음과 답을 한 화면에 두지 않는다는 기존
원칙(설계 5장 ①·7-1)이 프로필 경로로 우회되면 안 된다. 고르는 다이얼로그가 그 항목을 비활성
+ 사유 표시로 막는다(R-24).

### 3-2. 필수 트리오 — 이름·성별·나이

| 줄 | 어디서 오나 |
|---|---|
| 이름 | `Character.displayName` — 항상 있다(지금도 스크림에 뜬다) |
| 나이 | **AGE 시맨틱 역할** 필드 + `TimeStateResolver`(표준연도 기준 현재 나이 — 연표와 같은 값) |
| 성별 | **GENDER 시맨틱 역할 신설**(9번째)이 필요하다 — 지금 성별은 일반 SELECT 필드라 앱이 "어느 필드가 성별인지" 알 길이 없고, 라벨 문자열 추측은 R-20이 금지한다 |

GENDER 역할은 표식 전용이다(상태변화 동기화 없음 — AGE와 달리 규칙이 붙지 않는다). 이 역할은
대결 밖에서도 값을 한다 — 통계의 성별 비율, AI 컨텍스트의 성별 줄이 추측 없이 그 필드를 집는다
(원칙 05). **역할 필드가 그 세계관에 없으면 그 줄은 조용히 비우지 않고, 프로필 고르기
다이얼로그가 사유를 말한다**(*"성별 줄은 '성별' 역할을 지정한 필드에서 옵니다 — 이 세계관에는
아직 없습니다"* — R-17). 1장의 기본 필드로 성별·나이를 만들어 두면 전 세계관에서 트리오가 선다.

### 3-3. 화면 재설계 — 스크림 한 줄에서 정보 패널로

현행 카드는 이미지 위 스크림에 이름+영향 필드가 `\n`으로 포개진다 — 프로필까지 얹으면 글이
그림을 삼킨다. **카드를 '그림 위 글'에서 '그림 + 정보 패널'로 가른다.**
정본 목업: **`docs/mockups/duel_play_redesign_2026-08.html`** (2택 상태와 4지선다 상태를 함께 담았다).

```
┌──────────────┐ ┌──────────────┐
│              │ │              │      위 55~65%: 이미지 (위 살리는 크롭 유지)
│    그림 A     │ │    그림 B     │
│              │ │              │
├──────────────┤ ├──────────────┤
│ 아리네        │ │ 벨            │  ← 이름 (한 줄 고정)
│ 여 · 17세     │ │ 여 · 21세     │  ← 필수 트리오 줄 (성별·나이)
│ 소속 달빛단    │ │ 소속 홍련회    │  ← 프로필 필드 (상한 4줄 + "외 N개")
│──────────────│ │──────────────│
│ 1 마력량  350 │ │ 1 마력량  280 │  ← 영향 필드 (순위 번호, 시각적으로 구분된 구역)
│ 2 속성    물  │ │ 2 속성    불  │
└──────────────┘ └──────────────┘
   [방금 그거 취소]  [비슷함]  [순위표]      ← 하단 바 — 가운데 빈 자리에 무승부(B-114)
```

정한 것:

- **카드 탭 = 그 캐릭터 승리** — 현행 유지(최소 조작). 프로필이 늘어도 탭 대상은 카드 전체다.
  실수는 기존 '방금 그거 취소'가 받는다.
- **영향 필드에 우열 강조를 하지 않는다** — 어느 쪽 값이 큰지 색·굵기로 표시하면 사전식 예측을
  화면이 대신 말하는 셈이라, 점수를 안 띄우는 것과 같은 이유로 금지다. 순위 번호와 값만 보인다.
- **프로필 상한 4줄 + "외 N개"**(R-14). 카드 탭과 겹치지 않는 작은 펼침(⌄)이 전체 프로필
  시트를 연다(러프하게 보고 → 필요하면 정밀히 — 이중 경로).
- **B-114(비슷함)를 이 재설계가 연다** — 하단 바 가운데가 원래 비어 있고, 저장 형식은 이미
  받는다. 같은 화면을 두 번 고치지 않는다.
- **k지선다(B-115) 대비를 골격에 미리 넣는다** — `duelArea`를 2장=가로, 3~4장=2×2 격자로
  바꿀 수 있게 짠다. 3장 이상에서는 정보 패널이 이름+트리오 줄로 접히고 펼침 시트가 나머지를
  진다. **B-115 자체는 이 슬라이스가 열지 않는다**(5-3 참조) — 다만 이 골격 덕에 그 슬라이스는
  격자 전환과 "묶음 취소" 문구만 남는다.
- 보기 설정에 **프로필 표시 / 영향 필드 표시** 토글 추가(기존 배치·맞춤과 같은 자리,
  기본 둘 다 켬).
- 목적문(R-25), 프로필 고르기 다이얼로그: *"고른 필드의 값이 대결 카드에 함께 보입니다.
  승패 예측에는 쓰이지 않습니다."*

### 3-4. 확장성 판정

1. **새 상한?** 프로필 표시 4줄(표시 계층 상한 — R-19. 초과는 "외 N개"로 센다).
2. **비용 축?** 카드당 필드값 조회가 프로필 키 수만큼 — 영향 필드가 이미 같은 경로로 읽는다.
   새 축 아님.
3. **스냅샷?** 없다.
4. **엑셀?** `대결 축` 시트 열 하나.

## 4. 요청 ⑤ — 대결 등급 자동 산정 (B-113의 답)

### 4-1. 이것이 B-113을 닫는다

B-113의 물음 ①(*1500 눈금을 필드 값으로 어떻게 옮기나 — 1~100인가, 등급인가, 순위 숫자인가*)에
사용자가 답을 줬다: **상위 %에 따른 등급.** 물음 ②(덮어쓰기 보호)는 아래 4-3이 설계로 답한다.

### 4-2. 필드 속성 — GRADE 필드에 얹는다

**자리: `FieldDefinition.config`의 새 키 `duelGrade`** — config 확장이라 **DB 마이그레이션이
없다.** 대상은 **GRADE 타입 필드**다(등급 라벨과 서열이 이미 있는 유일한 타입 — 등급 체계
참조·실효 표·엑셀 왕복이 전부 깔려 있다. SELECT까지 넓히는 것은 선택지에 서열이 없어 컷을
정의할 수 없으므로 기각).

```json
"duelGrade": {
  "axisCode": "<대결 축 code>",
  "cuts": [ {"label": "S", "topPercent": 5}, {"label": "A", "topPercent": 20}, ... ]
}
```

- `cuts`는 필드의 실효 등급 표(라벨) 위에 **누적 상위 %**를 얹는다 — *"상위 5%까지 S, 20%까지 A,
  …"*. 마지막 등급은 나머지 전부(컷 불필요). 검증: %가 단조 증가, 라벨이 실효 표에 실재.
- 축은 **code로** 가리킨다(R-1 — 프리셋의 `sortDuelAxisCode`와 같은 이유. 복원이 id를 재발급해도
  남의 축에 붙지 않는다). 축을 찾지 못하면 그 사실을 말한다(조용한 무동작 금지).
- 이 속성을 켠 필드가 그 축의 **산출 필드가 아니면** 저장 시 산출 필드로 함께 등재할지 묻는다
  (연동을 두 곳에서 따로 관리하게 하지 않는다).
- 백분위 대상은 **점수가 있는 참가자뿐**이다 — 한 판도 안 친 캐릭터는 `DuelScoreIndex` 계약 2
  그대로 **값 없음**이고 등급을 받지 않는다(앵커 1500로 'C'를 지어내는 것이 정확히 그 계약이
  막는 병이다). 백분위 = 표준 경쟁 순위 ÷ 점수 보유 인원(등수 규칙도 기존 그대로).

### 4-3. 값은 파생 표시가 아니라 **명시적 반영**으로 쓴다

두 갈래를 대조했다.

| 안 | 내용 | 판정 |
|---|---|---|
| 파생 표시 (R-16형) | CALCULATED처럼 저장 행 없이 읽을 때마다 계산 | **기각.** R-16의 짐("저장 값을 읽는 모든 경로가 그것을 알아야 한다")이 이미 수십 파일이고(B-55), 게다가 이 값은 **적합(축당 수십~수백 ms)**에서 나온다 — 목록·엑셀·통계가 필드값을 읽을 때마다 대결 적합이 따라붙는 구조는 B-117이 세운 "동시에 도는 축은 하나" 계약을 무너뜨린다 |
| **명시적 반영 (채택)** | 사용자가 단추를 눌러 미리보기를 보고 필드 값으로 **써 넣는다** | **채택.** 사용자 원문(*"이 대전의 결과가 이 필드로 이어진다"*)이 흐름을 말하고, 어긋남 감지(설계 7-3-1)가 이미 "언제 다시 반영할 때인가"를 짚어 주는 짝이다. 엑셀에도 보통 값으로 실려 왕복이 자명하다 |

**반영 흐름:**

1. 진입 둘 — 순위표의 산출 필드 고지 줄(*"순위와 '강함' 필드가 어긋난 자리가 12곳"*) 옆
   **[등급 반영]** + 필드 편집의 속성 섹션.
2. **미리보기가 전부 보인다**: 캐릭터 · 현재 값 → 새 등급 · 백분위. 값이 바뀌는 행만 기본 체크.
   **손으로 적어 둔 값을 덮는 행은 따로 묶어 보인다**(기본 체크 해제 — 자율성 우선).
   점수 없음(무기록) 캐릭터는 **건드리지 않고 센다**(*"12명은 아직 판이 없어 그대로 둡니다"*).
3. 적용은 한 트랜잭션 + **기존 값 스냅샷**(일괄 편집 B-83과 같은 자리 — 휴지통에서 통째로
   되돌린다). 작업 이력(`OpResult.CAT_DUEL`)에 남는다 — B-113 ②(되돌리기 어려움)의 답이다.

**자동 반영은 두지 않는다** — 판 하나가 전원의 점수를 움직이는 시스템에서 자동 반영은 사용자
데이터가 소리 없이 계속 바뀐다는 뜻이다(변수 제어 위반). 어긋남 고지가 "반영할 때가 됐다"를
말하는 현행 설계가 이미 그 자리를 잘 지킨다.

### 4-4. 대안 조사 — 고정 %컷이 바닥이고, 경계 제안이 그 위에 얹힌다

| 후보 | 판정 |
|---|---|
| 고정 %컷 (사용자 원문) | **바닥으로 채택.** 결정적이고 설명 가능하다(*"상위 5%라서 S"*) — 화면이 그대로 말할 수 있는 문장이다 |
| z-점수 구간 (평균±σ) | 기각 — 분포 가정이 창작 데이터에 근거 없고, 사용자에게 설명이 안 된다 |
| **자연 단절 제안 (Jenks류 1차원 군집)** | **컷 편집기의 보조로 채택.** [경계 제안] 단추가 현재 점수 분포에서 **±오차 겹침이 없는 큰 간격**을 찾아 %컷 초안을 채워 준다 — 겹침 조건이 핵심이다(오차 안의 간격은 표본 소음이라 제안하지 않는다. 기존 확신 기계를 그대로 쓴다). 사용자가 고쳐서 저장한다 — 자동이 아니라 제안이다(자율성 우선) |
| 불확실성 반영 배정 | 반영 미리보기에서 **경계에 걸친 캐릭터(±오차가 컷을 가로지름)에 표식** + *"판을 더 쌓으면 확실해집니다"*. 배정을 막지는 않는다(마찰 최소) |

### 4-5. 함께 얻는 것 · 확장성 판정

등급이 **보통 필드 값**으로 실리므로 통계(분포·교차분석)·목록 카드·필터가 **공짜로** 그것을
분석한다(원칙 05 — 새 통계 코드 0줄). 4단계: ① 새 상한 없음 ② 반영 한 번 = 적합 한 번 + 값
쓰기 N행(명시적 조작, B-117과 같은 축) ③ 스냅샷 무변경 ④ 엑셀 무변경(보통 값으로 실린다).

### 5-2. 예정 기능과 신규 요청의 맞물림

| 대상 | 검토 결과 |
|---|---|
| **B-114 (무승부)** | **B-122(3장 재설계)가 흡수한다** — 같은 화면을 두 번 고치지 않는다는 그 행의 지침 그대로 |
| **B-115 (k지선다)** | 3장 골격이 격자 전환을 미리 받는다. **착수 시 적합도 함께 볼 것:** 지금 설계는 k지선다를 승자 대 각 패자의 k−1판으로 저장하는데, "k명 중 1등"의 원리 모형은 **Plackett–Luce**다 — `groupId`가 이미 묶음을 알므로 **저장 형식 무변경으로** 적합만 PL 항으로 바꿀 수 있고, MM 알고리즘(Hunter 2004)이 PL을 그대로 지원한다(현행 최적화기와 같은 계열). 판당 정보량이 정직해진다. 다만 대각 뉴턴의 전례대로 **실측이 먼저다** — 이득이 작으면 안 바꾼다 |
| **B-116 (축 불러오기)** | 1장의 기본 필드가 서면 필드 연결의 "없는 키" 문제가 구조적으로 준다(1-7). 순서 강제는 아니다 — 없는 키를 세어 알리는 처방은 그대로 유효하다 |
| **ⓑ·ⓒ (이미지 축 + 경로 재작성 빗장)** | 신규 5건 어느 것도 이 빗장을 건드리지 않는다(②③은 파일을 개명하지 않는다). 대기열 위치만 뒤로 밀린다 — 소멸이 아니다 |
| **B-108 (제공자 자동 전환)** | 2장의 이미지 요청에도 그대로 적용될 설계다(확정 ⓕ의 "완결된 몫은 살린다"가 ③의 배치 단위 보존과 같은 규칙). 새 학습 사실 `imagesUnsupported`가 R-23 등재를 하나 늘린다 — **B-108 착수 세션이 그 목록을 갱신할 때 함께 볼 것** |
| **B-105 (엑셀 앱 설정 레지스트리)** | 2장의 새 AI 설정(첨부 장수 기본값 등)이 등재 대상 ⓐ 부류다 — 레지스트리가 서면 한 줄로 들어간다 |
| **`매칭` 표1 등재 슬라이스** | 이 문서의 제안 문구는 전부 '대결'·'판'·'짝'을 쓴다 — 새 부채를 만들지 않았다 |

### 5-3. 후속 확장 후보 (등재는 사용자 확정 후)

- **이미지 내용 기반 캐릭터 자동 링크 제안** — ③의 태깅이 쌓이면 "이 이미지는 태그가 ○○와
