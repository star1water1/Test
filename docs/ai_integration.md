# AI 연동 아키텍처 (토대 MVP)

## 목적

사용자가 **본인 명의의 API 키(BYOK)** 를 등록해, 앱의 인앱 작업·관리를 AI가 보조하게 하는
기능의 **토대 계층**이다. 이 문서는 구조와 경계, 그리고 이후 기능이 얹히는 방법을 기록한다.

> 개발 의도와의 관계: "가능한 모든 AI"는 프리셋 나열이 아니라 **프로토콜 추상화**로 달성한다.
> OpenAI 호환 프로토콜 하나로 OpenAI·OpenRouter·Groq·DeepSeek는 물론 목록에 없는 서비스까지
> 커스텀 등록으로 수용된다(원칙 01 — 열린 구조). 클로드는 Anthropic 전용 프로토콜로,
> Gemini는 전용 프로토콜로 지원한다.

## 구조 (`com.novelcharacter.app.ai`)

```
[인앱 기능들: 필드 제안·설명 초안·정합성 해설·이름 생성·작업 보조 …(예정)]
        │  AiRequest(system, messages, maxTokens) 만 만들면 됨
        ▼
   AiService  ←──────── 단일 관문 (suspend complete / testConnection)
        │
        ├─ AiProviderStore   프로바이더 설정 CRUD + 활성 선택 (SharedPreferences, 수동 JSON)
        ├─ AiKeyStore        API 키 암호화 저장 (Android Keystore AES-256-GCM)
        └─ AiProtocolCodec   프로토콜별 요청 조립·응답/오류 해석 (순수 JVM, 단위 테스트 대상)
                │
                ├─ ANTHROPIC      POST {base}/v1/messages
                ├─ OPENAI_COMPAT  POST {base}(/v1)/chat/completions
                └─ GEMINI         POST {base}/v1beta/models/{model}:generateContent
```

- **UI**: `ui/settings/AiSettingsFragment` (설정 → AI 연동). 프리셋 선택 → 편집 다이얼로그
  (발급 가이드 + 콘솔 딥링크 + 연결 테스트 + 검증 저장) → 목록에서 활성 선택/편집/삭제.
- **프리셋**: `AiPresets` — 데이터 주도. 새 서비스 지원 = 항목 1개 추가. 생성된 설정은
  전 필드 편집 가능(프리셋은 읽기 전용이 아님).

## 보안 경계 (절대 규칙)

1. **API 키는 `AiKeyStore` 밖으로 저장되지 않는다.** 설정 JSON·로그·오류 메시지에 키를 넣지 말 것.
2. 키는 Android Keystore 마스터 키(AES-256-GCM)로 암호화되어 `ai_keys` prefs에 저장된다.
   식별용으로 끝 4자 힌트만 평문 보관.
3. **백업·엑셀 내보내기에 키가 포함될 경로가 없어야 한다.** 현재 인앱 백업은 DB→xlsx 방식이라
   prefs를 건드리지 않고, 매니페스트 `allowBackup=false`로 OS 백업도 차단됨. 향후 백업 범위를
   prefs로 확장할 일이 생기면 `ai_keys`·`ai_providers` 는 반드시 제외할 것.
4. 기기 이전 등으로 복호화가 불가하면 조용히 실패하지 않고 `NO_KEY` 로 표면화해
   재등록을 안내한다(변수 제어).
5. 커스텀 서버는 https만 허용(평문 HTTP 차단). 사설망 예외 허용은 향후 검토 항목.

## 오류 처리 계약 (변수 제어)

`AiService` 는 예외를 던지지 않고 `AiResult.Failure(kind, detail, httpCode)` 를 돌려준다.
호출측 UI는 **결과를 반드시 사용자에게 보여줄 것** — `AiErrorMessages.of(context, failure)` 가
분류별 안내문 + 교정 경로 + 제공사 원문을 만들어 준다. 조용히 버리는 것 금지.

자동 교정: OpenAI 신형 모델이 `max_tokens` 를 거부하면 `max_completion_tokens` 로 1회
자동 재시도한다(사용자는 모름). 붙여넣은 키의 앞뒤 공백·개행은 저장 시 자동 정리.

## 출력 토큰 상한 정책 (`AiTokenPolicy`)

**상한을 두지 않는 선택지는 없다** — Anthropic Messages API는 `max_tokens`가 **필수**다.
그래서 문제는 "둘 것인가"가 아니라 **"무엇을 근거로 둘 것인가"**이고, 근거는 세 축이다:

```
실제 요청값 = min( 그 기능이 요구한 값 , 사용자 슬라이더 설정 , 탐지된 모델 상한 )
```

- **사용자 설정** — 설정 → AI 연동 → 프로바이더 편집의 슬라이더(`maxOutputTokens`).
  미설정이면 `DEFAULT_REQUEST = 4096`으로 **종전과 동일하게** 동작한다(회귀 없음).
- **탐지된 모델 상한**(`detectedOutputLimit`) — **정적 표를 두지 않는다**(표는 새 모델마다 낡는다).
  두 경로로 학습한다:
  ① Gemini는 모델 목록 응답에 `outputTokenLimit`을 실어 준다 → `parseModelInfos`가 읽는다.
  ② Anthropic·OpenAI는 목록에 없지만 **상한 초과 400 오류가 실제 상한을 본문에 적어 준다**
     → `parseMaxTokensLimitFromError`가 읽어 1회 재시도하고, **그 재시도가 성공했을 때만** 기억한다.
     오판 방지: 요청값보다 작고 `FLOOR` 이상인 수만 후보이며, 상한 관련 문구가 없으면 학습하지 않는다.
     **성공 전에 기억하지 않는 것도 오판 방지의 일부다**(B-151 — 2026.08.07까지 이 자리만 무조건
     기억했다). 파서가 엉뚱한 수를 집으면 그 값이 굳고 `effective`가 **이후 모든 요청을 거기 맞춰
     깎는데**, 사용자가 슬라이더를 올려도 그 합성이 이긴다. 되돌릴 길은 R-23 초기화뿐인데 그것은
     모델이나 주소를 **바꿔야** 도는지라 값만 잘못 배운 경우에는 바꿀 것이 없다 — 증상은 잘린
     응답이나 `EMPTY_RESPONSE`로 나타나 원인을 짚기도 어렵다. **형제인 A-4 temperature와 A-7
     이미지가 처음부터 쓰던 형태**(`if (second is Success) remember…`)로 맞췄다: 재시도가 통해야 배운 것이다.
- 슬라이더의 **최대값이 곧 탐지된 상한**이라 자동 탐지와 수동 설정이 따로 놀지 않는다.
  Material Slider는 `(valueTo-valueFrom) % stepSize != 0`이면 죽으므로 `sliderMax`/`snapToStep`이
  항상 눈금에 맞춘 값을 준다(탐지값은 임의의 수일 수 있다).

**청킹은 상한에서 파생된다.** 종전 상수 `MAX_TARGETS_PER_REQUEST = 15`는 "4096 대비"라는
주석만 있어 상한이 바뀌면 근거를 잃었다. 이제 `targetsPerRequest(maxTokens)`가 계산하고
(4096 → 15로 기존과 일치), **비용 고지도 같은 값으로 계산해야 한다** — 상수로 고지하면
사용자가 상한을 올렸을 때 "요청 N건" 안내가 거짓이 된다.

**절단은 성공이 아니다.** `stop_reason=max_tokens` / `finish_reason=length` /
`finishReason=MAX_TOKENS`를 **텍스트가 있어도** 읽어 `AiResult.Success.truncated`로 표면화한다.
종전에는 이 신호를 빈 응답일 때만 읽어서, 잘린 응답이 Success로 흐르고 그 뒤 JSON 파싱이
실패해 **"형식 오류 — 다시 시도해 주세요"라는 오진**이 떴다. 재시도해도 결정적으로 같은
결과이므로 안내가 사용자를 헛수고로 보냈다. 이제 원인("출력 상한에 걸려 잘렸습니다")과
교정 경로("대상을 줄이거나 상한을 올리세요")를 말하고, 일부만 받은 경우 몇 개가 빠졌는지
수로 알린다(R-14).

## 프롬프트 적재량 설정 (`AiPromptSettings` / `AiPromptPolicy`)

일관성 참고 자료(기존 사용값 예시·문체 참고)는 결과를 기존 데이터에 붙여 주지만 **입력 토큰을
쓴다**. 그 교환비가 이득인지는 데이터 규모·모델·과금 방식마다 다르므로 개발자가 정하지 않고
사용자가 정한다(자율성 우선). 설정 → AI 연동 → **'AI 추천 일관성'** 카드 2개:

| 설정 | 범위(기본) | 효과 |
|---|---|---|
| 기존 값 예시 · 짧은 값 추천 | 0~24, 2단위 (12) | 필드마다 실을 기존 값 예시 개수 |
| 문체 참고 · 서술형 작성 | 0~3 (2) | 요청마다 실을 다른 캐릭터의 글 편수 |

- **저장 버튼 없음** — 슬라이더를 놓는 순간이 확정이다(원칙 04). 값 표시와 **토큰 비용 추정**이
  즉시 갱신되어, 늘렸을 때 무엇을 지불하는지 슬라이더를 움직이는 자리에서 보인다.
  0은 "0개"가 아니라 **"보내지 않음"**으로 표시한다 — 0은 수가 아니라 상태다.
- 범위·눈금·기본값의 단일 소스는 `AiPromptPolicy`다. 레이아웃과 저장소에 따로 적으면 눈금 밖
  값이 저장돼 Material Slider가 죽는다(출력 토큰 슬라이더에서 이미 겪은 문제).
- **설정이 끄는 것은 토큰이지 정확성이 아니다.** 기존 값 예시를 0으로 두어도 별칭 → canonical
  접기와 restricted 허용 검증은 그대로 동작하고, restricted 필드는 허용 목록이 곧 규칙이라
  0이어도 기본 개수만큼 싣는다(목록을 주지 않고 "목록 밖"이라 **표시**할 수는 없다 —
  B-79 이후 처분은 드롭이 아니라 표식이지만, 목록을 줘야 판정이 선다는 사실은 같다).
- 기본값은 종전 상수와 같아 **설정을 열지 않은 사용자의 동작은 바뀌지 않는다**(회귀 없음).

## 이후 기능이 얹히는 방법

새 AI 기능은 어시스턴트 provider처럼 **가산적으로** 추가한다:

1. `AiService(context)` 생성 → `hasUsableProvider()` 로 진입 가드(미설정 시 설정 화면 안내).
2. 캐릭터/작품 데이터를 프롬프트로 조립해 `AiRequest(system=…, userText=…)` 생성.
3. `val result = aiService.complete(request)` → `Success.text` 사용 / `Failure` 는
   `AiErrorMessages` 로 안내.
4. **AI 출력은 항상 사용자가 확인·수정 후 확정**하는 UI로 만들 것(러프 생성 → 정밀 조정,
   원칙 04). 데이터에 바로 쓰지 않는다.

구현된 기능:

- **필드 데이터 라이브러리 AI 정리** (`ai/FieldLibraryAiOrganizer` +
  `ui/fieldlibrary/AiOrganizeSheet`) — 유사값 병합·오탈자 교정·카테고리 제안. 첫 실데이터 AI
  기능으로서 공용 자산을 만들었다: `ai/AiJsonExtractor`(관대 JSON 추출), 청킹·환각 검증·부분 실패
  동반 반환 패턴, 체크리스트 검토→단일 통합 확인→선택 적용 UI 흐름 (docs/field_value_library.md).
- **캐릭터 필드 값 추천** (`ai/CharacterFieldAiSuggester` + `ui/character/AiFieldSuggestSheet`) —
  생일 포함 모든 편집 가능 필드의 값을 추천 이유와 함께 제안. 컨텍스트는 폼의 **라이브 입력값**
  (이름·이명·태그·메모·입력된 필드) + 이미지 태그·소속 세력·관계·**대결 우열**(아래 A-6)이며,
  절단·조회 실패 결손은 truncationNotes로 전부 고지한다(R-14). 대상은 요청당 15개로 청킹해 순차 실행 — 응답 절단
  없이 필드 수십 개를 받쳐주고, 실패·파싱 오류는 청크 단위로 격리해 성공분과 동반 반환한다
  (터미널 오류는 잔여 청크 중단). 검증은 SELECT/GRADE 옵션 일치·생일 달력 유효성·숫자 파싱·
  구조화 입력 형식(파트 수·구분자)으로 환각을 드롭하고 드롭 수를 표면화. 진입은 폼 인라인
  ✨ 버튼(필드별)과 폼 상단 버튼(전체, 빈 필드 기본·입력된 필드 포함 선택)의 이중 경로.
  실행은 `CharacterViewModel.runAiSuggest`(회전 생존 — 진행·결과가 화면 재생성을 넘어 복원)가
  수행하고, 적용은 `DynamicFieldFormBuilder.applyRandomValue`로 **폼 위젯에만** 기입 —
  영속화·`__birth` 동기화는 기존 저장 체인이 수행한다.

  **표기 기조(일관성) 연동** — 캐릭터 한 명의 정보만 주면 모델은 이 작품이 그 필드를 어떤
  표기·상세도로 써 왔는지 알 수 없어, 기존 값들과 어긋난 값을 만든다("흑발/은발"만 쓰는
  작품에 "짙은 밤하늘빛 흑청색"). 그래서 대상 필드마다 **값 라이브러리의 기존 사용값 예시**를
  프롬프트에 함께 싣는다. 값 전량을 보내면 토큰이 감당되지 않으므로 `selectUsageExamples`가
  **중복 없이 선별**한다: 앞 2/3은 빈도 상위(주류 기조), 나머지 1/3은 잔여 목록을 균등 간격으로
  훑어(분포의 폭) 채우고, 개수·값 길이·총 길이 상한을 건다(난수 없음 — 같은 데이터면 같은 예시).
  `usageCount`가 전부 0인 경우(라이브러리 화면 미방문)는 상위 구간 개념이 성립하지 않으므로
  목록 전체를 균등하게 훑는다 — 여기서 재계산하지 않는 이유는 재계산이 필드마다 값 전량
  스캔+쓰기라 읽기 경로가 짊어질 비용이 아니기 때문이다.
  캐릭터 전체를 훑지 않고 `field_value_entries`를 1쿼리 배치 조회하므로 비용은 캐릭터 수가
  아니라 값 종수에만 비례한다(받쳐주는 확장성). 조회 실패는 추천을 막지 않는다(용례 없이 진행).

  **값의 뜻도 함께 간다 (B-46, 2026.08.19)** — 사용자가 값 라이브러리에 써 둔
  `FieldValueEntry.description`을 `selectUsageDescriptions`가 실어 보낸다. 값 문자열만으로는
  '북부'가 *한랭한 변경*인지 *왕도의 북쪽 구역*인지 알 수 없어, 규칙 9(*"같은 뜻이면 기존 값을
  쓴다"*)와 규칙 10(*"이 목록에서만 고른다"*)이 **뜻을 모른 채 지켜야 하는 지시**였다.
  설계에서 갈라 둔 것이 둘이다. ⓐ **예산을 목록과 분리한다** — 값과 설명을 한 예산에서 자르면
  설명이 긴 필드일수록 허용 목록이 짧아져, restricted 필드에서 '목록 밖' 표시가 느는 새 결함이
  된다. 그래서 예시 선별은 손대지 않고 **이미 실리기로 정해진 값에만** 설명을 얹는다
  (필드당 총 예산은 필드 설명의 프롬프트 상한과 같은 수를 참조로 묶었다).
  ⓑ **프롬프트에서 목록과 섞지 않는다** — `기존 사용값: 북부, 남부` 뒤에 `값 뜻: 북부 = …`을
  별도 절로 붙인다. `북부(왕도 이북)`처럼 값에 섞으면 모델이 그 통짜 문자열을 값으로 되돌려
  주고, 그것은 목록에 없으니 '목록 밖'이 된다 — 사용자가 돈을 내고 손질을 산다.
  잘리거나 못 실은 설명은 `truncationNotes`로 고지한다(R-14).

  응답 쪽도 같은 카탈로그로 교정한다: **별칭 표기는 canonical로 접고**(모델이 '흑발'이라 답해도
  정규값이 '검은 머리'면 그쪽으로 — 통계·검색이 갈라지지 않게), 접기는 타입 검증보다 **먼저**
  수행해 SELECT 옵션의 별칭도 살린다. `inputMode=restricted` 필드는 저장 시 가드
  (`FieldValueRules.validateRestricted`)와 **같은 집합**으로 목록 밖 값을 가려내되,
  ~~드롭한다~~ → **정정(2026.08.03, B-79): 드롭하지 않고 '목록 밖'으로 표시해 후보로 낸다.**
  종전 서술은 "저장 시 가드와 같은 집합"이라 적으면서 **처분은 정반대**였다 —
  가드는 받아 주고 "추가하고 저장 / 입력 수정"을 묻는데 AI 경로만 버렸다(손으로는 넣을 수
  있는 값을 유료 응답에서만 버리는 비대칭). 이제 처분도 같다: 표시된 값을 채택하면
  **저장 가드가 그대로 그 질문을 한다**(새 경로를 만들지 않았다).
  단 라이브러리가 비어 있으면 표시하지 않는다(허용 목록을 준 적이 없으므로).
  허용 목록을 다 싣지 못한 restricted 필드는 truncationNotes로 고지하는데, 그것은 이제
  결손 고지가 아니라 **정확도 고지**다('목록 밖' 표시가 늘 수 있음 — R-14).
  `inputMode=free`(제안 끔) 필드는 용례도 접기도 하지 않는다 — 자율성은 AI 경로에서도 같은 뜻이다.

  **전량 응답 계약과 결손 회계** — 필드 열몇 개를 요청해도 서너 개만 돌아오던 문제의 원인은
  둘이었고, 둘 다 구조에 있었다(출력 토큰 상한이나 모델 성능이 아니다).

  ① *프롬프트가 생략을 허가했다.* 종전 규칙 6 "근거가 부족해 추천할 수 없는 필드는 응답에서
  생략한다"는 모델에게 빠뜨릴 재량을 준 지시였고, 캐릭터 한 명의 정보는 원래 성기므로 모델은
  대부분을 '근거 부족'으로 판정했다. 이제 계약을 뒤집어 **요청한 key 전부에 항목을 하나씩**
  내게 하고(프롬프트 머리·꼬리에 대상 개수를 명시), 정말 정할 수 없는 필드는 생략이 아니라
  `value:""` + 사유로 표기하게 한다. 확신이 낮은 추정도 내게 하되 근거를 밝히도록 한다 —
  채택 여부를 가리는 것은 모델이 아니라 검토 UI의 사용자다(자율성 우선).

  ② *빠진 필드가 어디에도 집계되지 않았다.* `droppedCount`는 모델이 값을 냈다가 검증에서
  떨어진 수만 셌고, **응답에 아예 안 들어온 필드**는 흔적이 없었다. 그래서 앱은 결손을 정상처럼
  보고했다(조용한 실패). 이제 `SuggestOutcome.missing`이 요청 대상 중 제안이 안 나온 전부를
  사유(`MissingCause`: 모델 미응답 / 모델 추천 불가 / 형식·옵션 불일치 / 허용 목록 밖 /
  현재 값과 동일 / 중복 / 응답 절단 / 해석 실패 / 요청 실패 / 미요청)와 함께 담는다 —
  `suggestions + missing = 요청 대상 전체`가 불변식이고, 결정적 실패로 **요청조차 안 한**
  잔여 청크까지 결손으로 남는다. UI는 "요청 N개 중 M개 수신"과 사유별 명세를 항상 띄우고,
  재요청으로 달라질 수 있는 사유만 골라 **못 받은 것만 다시 요청**하는 버튼을 준다
  (현재 값과 동일·모델이 사유를 밝힌 건은 제외 — 같은 답에 두 번 과금하지 않는다).

  또한 SELECT/GRADE 옵션 매칭은 정확 일치 실패 시 공백·대소문자를 무시한 일치까지 수용해
  표기 차이(`남 성`/`MALE`)로 유료 응답을 버리지 않는다. 반환값은 **언제나 옵션 원문**이라
  저장값이 옵션 목록 밖으로 새지 않는다.

  **근거 강도(confidence)와 받아올 범위** — 항목마다 모델이 스스로 강도를 매긴다
  (high 직접 근거 있음 / medium 무리 없는 추론 / low 기조·통념에 기댄 추측). 검토 화면은 값
  옆에 `[확실]`·`[추론]`·`[추측]`으로 띄우고, 어디까지 받을지는 설정 → AI 연동에서 정한다
  (`AiPromptSettings.minConfidence`, 기본값 **전부 받기**). 기본을 전부로 두는 이유: 최종 채택은
  어차피 검토 화면에서 항목별로 하므로 앱이 미리 걸러 봐야 선택지만 줄고, 넓게 받아 고르는 편이
  못 받은 것을 다시 요청하는 것보다 싸다. 하한은 프롬프트(모델이 애초에 안 만들게)와
  파싱(그래도 오면 `BELOW_CONFIDENCE`로 제외) **양쪽**에 건다 — 프롬프트만으로는 지킨다는
  보장이 없고, 파싱만으로는 버려질 값에 출력 토큰을 낸다. **강도 미표기(null)는 걸러 내지
  않는다**: 모른다는 이유로 버리면 모델이 생략한 것과 결과가 같다. 기본 선택도 강도를 본다 —
  빈 필드라도 `추측`은 체크가 꺼진 채 뜬다(전체선택 한 번에 얕은 값이 딸려 들어가지 않게).

  **검토 중 직접 수정과 2차 요청** — 제안을 '받거나 버리거나' 둘뿐이면 방향은 맞고 표현만
  아쉬운 제안이 버려진다. 그래서 행마다 `보완`을 두어 두 경로를 연다.
  ① *값 직접 수정* — 손으로 고친 값도 `normalizeChecked`로 **저장 시와 같은 규칙**을 통과해야
  한다(통과 못 한 값은 위젯이 조용히 무시하거나 저장에서 튕기므로, 고칠 수 있는 자리에서
  사유를 띄운다). 확정하면 `[직접 수정]` 표시가 붙고 체크가 켜진다.
  ② *지시를 달아 다시 요청* — `FieldSpec.userInstruction`("더 어둡게")과 `rejectedValues`(이미
  물린 값)를 프롬프트에 실어 **다른 방향**의 값을 받는다. 되풀이해 온 값은 `REPEATED`로
  제외한다(같은 답을 되받으면 과금만 두 번이다). 콕 집어 다시 묻는 요청이므로 근거 강도
  하한은 적용하지 않는다 — 구체적 요청이 일반 설정을 이긴다.
  재요청은 검토 화면을 갈아 끼우므로 **그 전에 지금 체크된 제안을 폼에 먼저 적용**한다
  (적용은 폼 위젯 기입일 뿐 저장이 아니라 되돌리기 쉽다). 이렇게 하지 않으면 한 필드를
  보완하려다 나머지 선택을 통째로 잃는다. '못 받은 N개만 다시 요청'도 같은 규칙을 따른다.

- **서술형 필드 작성** (`ai/NarrativeFieldAiWriter` + `ui/character/NarrativeWriteSheet`) —
  성격·배경·외모 같은 긴 TEXT 필드의 **초안 / 이어쓰기 / 다듬기 / 늘리기 / 줄이기**.
  짧은 값 추천기와 **경로를 나눈 이유**: 그쪽은 요청당 필드 여러 개를 묶고 근거를 한 문장으로
  받으며 컨텍스트 값을 300자로 자르는 *짧은 값 전용* 설계라, 산문을 끼워 넣으면 둘 다 망가진다.
  여기는 필드 하나 전용이고 출력 예산을 통째로 쓰며 원문 참고 상한도 따로 둔다(4000자).

  못 준다) 사용자가 고른 것만 폼 위젯에 기입한다 — **원문은 덮어쓰지 않는다.**
  이어쓰기는 적용 시점에 폼의 **라이브 원문**을 다시 읽어 그 뒤에 잇는다(검토 중 사용자가
  더 고쳤다면 그 편집이 우선이다).

  **문체 기조(일관성) 연동** — 짧은 값 경로의 '기존 사용값'에 대응하는 서술형판이다. 여기서
  어긋나는 것은 *값*이 아니라 **문체**(어투·시점·문장 길이·상세도)라, 값 목록으로는 전할 수
  없고 글로 전해야 한다. 그래서 **같은 필드에 다른 캐릭터가 쓴 글**을 소수 싣는다
  (`[문체 참고]` 절 + 시스템 규칙 6: 문체만 따르고 내용·인물은 가져오지 말 것).
  선별(`selectStyleSamples`)은 **길이 중앙값에 가장 가까운 글**을 고른다 — 가장 긴 글을 고르면
  모델이 그만큼 쓰려 해 분량·과금이 튀고, 가장 짧은 글을 고르면 성의 없는 결과가 나온다.
  너무 짧은 값(40자 미만)은 후보에서 빼고(메모 조각을 문체로 제시하면 거짓 신호가 된다),
  각 참고는 600자로 자른다. 동률은 값 문자열로 갈라 결정적이다(난수 없음).
  **자기 자신은 제외한다** — 원문은 이미 `[원문]` 절에 실리므로 참고로 또 넣으면 토큰만 쓰고
  후보가 원문 쪽으로 쏠린다.

  **경로 분기의 단일 소스는 필드 속성 `NarrativeMode`다**(`data/model/NarrativeMode.kt`,
  config 키 `narrativeMode`). 사용자가 필드 편집에서 **자동 / 서술형 / 짧은 값** 중 고른다.
  기본값 `AUTO`는 표시 형식이 '여러 줄'이면 서술형으로 본다 — 아무 설정 없이도 바로 동작해야
  하기 때문이다(원칙 04). `DisplayFormat.MULTILINE`을 그대로 쓰지 않은 이유는 그것이
  **표시 방식**이라서다: 거기에 AI 동작을 묶으면 표시를 바꿀 때 AI 동작이 딸려 바뀐다.
  한 줄로 보이지만 AI로 초안을 쓰고 싶은 필드, 여러 줄이지만 짧은 목록인 필드가 둘 다 실재한다.
  타입 계약을 산문이 만족할 수 없는 조합(SELECT의 옵션, NUMBER·BODY_SIZE의 형식,
  구조화 입력, 시맨틱 역할)은 애초에 성립하지 않으므로 설정 자체가 보이지 않는다.

## 구현됨 — P-A (`docs/ai_control_and_ui_density_2026-07.md`, 2026.07.28 구현)

아래 넷은 **구현 완료**됐다. 전체 설계·근거·기각한 대안·검증 항목은 위 문서에 있고,

### A-1. 필드별 AI 추천 대상 토글 (`data/model/FieldAiPolicy`)

`FieldDefinition.config`의 flat 키 `"aiSuggest"`(기본 `true`, 기본값은 저장하지 않음).
끄면 그 필드는 **일괄 추천 대상에서 빠지고 폼의 ✨ 버튼도 사라진다.** 🎲 랜덤과 값 라이브러리
AI 정리는 영향을 받지 않는다 — 그 둘은 *추천*이 아니다.

일괄 대상 산출은 새 순수 함수 **`CharacterFieldAiSuggester.bulkTargetsOf`** 하나로 모은다.
`AiFieldSuggestSheet`가 직접 필터를 조립하면 보충 탭(A-3)과 규칙이 갈린다.

```
대상 = 편집 가능 필드 ─ CALCULATED·미지 타입 ─ aiSuggest=false ─ NarrativeMode.isNarrative
```

> **여기서 현행 결함 하나가 함께 고쳐졌다.** 종전 `showForCharacter`는 `NarrativeMode`를 보지
> 않아 **서술형 TEXT 필드를 짧은 값 일괄 경로로 보냈다.** 경로를 나눈 이유("산문을 끼워 넣으면
> 둘 다 망가진다")가 인라인 ✨에서만 지켜지고 일괄에서는 지켜지지 않고 있었다.

제외분은 버리지 않고 **사유별 개수**로 비용 고지에 실린다(R-14) — 계산 필드 제외도 지금은
아무도 알려주지 않으므로 이 고지가 함께 메운다.

`entityType = event` 필드에는 **토글을 노출하지 않는다** — 사건 필드에는 AI 추천 경로 자체가
없어 아무 일도 하지 않는 스위치가 된다(R-24, 백로그 B-43).

### A-2. 필드 설명 (`data/model/FieldDescription`)

`config`의 `"description"` — **사용자가 쓰는, 이 필드가 무엇인지에 대한 설명.**
`FieldValueEntry.description`(값 하나의 설명)·P3 인앱 도움말(개발자 작성)과 **다른 것이며
합치지 않는다.** 표시 컴포넌트(`HelpDialog`)는 공유하되 아이콘을 나눈다 — `ⓘ` 사용자 설명 /
`?` 앱 도움말.

프롬프트에서는 대상 필드 줄에 ` / 설명: …`으로 실리고 시스템 규칙 14가 붙는다:

```
14. '설명'이 붙은 필드는 그 설명이 이 작품에서 그 필드가 뜻하는 바의 정의이자 제약이다.
    설명과 어긋나는 값을 내지 마라. 설명이 옵션·형식과 충돌하면 옵션·형식을 따르고,
    무엇이 충돌했는지 reason에 적어라.
```

- **세 경로 전부에 싣는다** — 짧은 값 추천 · 서술형 작성 · 값 라이브러리 AI 정리. 한 곳만
  실으면 같은 필드가 경로마다 다른 정의로 해석된다.
- **대상 필드에만** 싣는다(`[입력된 필드]` 컨텍스트에는 싣지 않는다 — 거기서는 값이 정보다).
- 저장 상한 1000자 / **프롬프트 상한 300자**. 요청당 15필드분이 실리므로 둘을 나눈다.
  초과분은 `truncationNotes`로 고지(R-14).
- **`AiPromptSettings`의 적재량 설정 대상이 아니다.** 기존 사용값 예시는 0으로 끌 수 있지만
  설명은 끌 수 없다 — *"설정이 끄는 것은 토큰이지 정확성이 아니다."* 예시는 일관성을 돕는
  힌트지만 설명은 값의 **계약**이다.
- 엑셀 `필드 정의` 시트에 전용 열 `AI추천`·`필드설명`을 판다. **파일 안에 같은 사실을 두 벌
  두지 않기 위해** 내보낼 때 `설정(JSON)` 셀에서 두 키를 제거한다. 가져오기는 3분기 병합 —
  열 있음 = 덮기 / 열 없음 + JSON 키 없음 = **기존 DB 값 보존**(`sheetBooleanOrKeep` 선례) /
  열 없음 + JSON 키 있음 = 그대로. **가운데 분기를 빠뜨리면 설명이 무통보로 사라진다.**

### A-3. 보충(랜덤) 탭 AI 추천

`AiFieldSuggestSheet`·`NarrativeWriteSheet`를 **그대로 재사용**한다. 랜덤 보충 탭은 이미
`DynamicFieldFormBuilder`·`CharacterViewModel`·`CharacterSaveCoordinator`를 편집 화면과 공유한다.

- **편집 모드에서만 노출.** AI 결과는 폼 위젯에만 기입되므로 미리보기 상태에는 적용할 곳이 없다.
- `buildAiContext()`를 **`CharacterAiContextBuilder`로 추출**해 두 화면이 공유한다. 복사하면
  두 화면의 컨텍스트가 갈린다.
- **이 탭에만 있는 위험:** 요청 도중 뽑기가 바뀌면 A를 근거로 받은 유료 추천이 B의 폼에 들어간다.
  → 예방(실행 중 뽑기 잠금) + 검출(`AiSuggestRun.targetCharacterId` 비교 후 불일치 시
  `[돌아가 적용] / [버리기]`)의 **2겹**. 편집 화면에서는 언제나 일치하므로 동작이 바뀌지 않는다.
- 완성도 검사 탭은 **작업 없음** — `보충 시작`이 `CharacterEditFragment(supplementMode)`로 가므로
  이미 AI에 도달한다. 목록 행에 "AI로 채우기"를 다는 안은 폼 없는 실행 = DB 직접 기록이라 기각.

### A-4. 창작도 (`ai/AiCreativity`, `AiRequest.temperature`)

> **창작도는 값의 후보 공간을 넓히지, 계약을 넓히지 않는다.**
> 필드 설명·SELECT/GRADE 옵션·형식(생일·구조화)·`restricted` 허용 목록은 어느 단계에서도
> 강제된다. ~~넷 다 응답 수신 후 코드가 검증하는 항목이라~~ → **정정(2026.08.01, 적대 검토
> F-6): 코드가 검증하는 것은 셋이다**(옵션 일치 · 형식 · 허용 목록 — `parseResponse`).
> **필드 설명의 '내용 준수'는 프롬프트 지시일 뿐 코드가 검증할 수 없다**(자연어 제약).
> 따라서 정확한 보증은 "**구조적으로 틀린 값**(옵션 밖·형식 이탈)은 저장 경로가
> 없다"까지이고, 설명 취지에 어긋나는 값의 마지막 방어는 사용자 확인 단계다. 비용이
> "드롭이 늘 수 있다"이지 "데이터가 망가진다"가 아니라는 결론은 그대로다.
>
> **정정(2026.08.03, B-79): 위 괄호에서 '목록 밖'을 뺐다.** `restricted` 허용 목록은
> 프롬프트에서는 여전히 강제되지만 **응답의 처분은 드롭이 아니다** — 목록 밖 값은
> '목록 밖' 표시가 붙은 후보로 나가고, 채택하면 저장 가드가 "추가하고 저장 / 입력 수정"을
> 묻는다. 그러므로 그 값에는 **저장 경로가 있다**(사용자가 그 질문에 답하면). 옵션·형식은
> 그대로 경로가 없다 — B-79가 연 것은 목록 하나뿐이다.

**2층으로 바꾼다.** 온도만 올리면 표현만 흔들리고, 지시만 바꾸면 무난한 답으로 수렴한다.

| 단계 | wire | temperature | 지시 |
|---|---|---|---|
| 정확 | `precise` | `0.1 × max` | 직접 도출되는 값만 |
| **균형**(기본) | `balanced` | **미전송** | 추가 규칙 없음 |
| 자유 | `free` | `0.85 × max` | 기존 사용값은 *표기 방식*의 참고이지 선택지의 울타리가 아니다 |
| 실험 | `bold` | `1.0 × max` | 뻔한 답을 피하라. 단 설명·옵션·형식은 그대로 |

```
프로토콜별 max: ANTHROPIC 1.0 / OPENAI_COMPAT 1.4 / GEMINI 1.4
```

- **기본값이 파라미터를 싣지 않는 이유:** 설정을 열지 않은 사용자의 동작이 바뀌면 안 된다
  (`AiTokenPolicy.DEFAULT_REQUEST`와 같은 태도 — 회귀 없음).
- **상한이 규격 최대(2.0)가 아닌 이유:** 이 기능들은 JSON 스키마 응답을 요구한다. 온도가 과하면
  형식이 무너져 유료 응답이 통째로 버려진다(`UNREADABLE`). 상한은 프로토콜 상한이 아니라
  **형식이 무너지지 않는 상한**이다.
- **프로토콜 차이를 숨기지 않는다** — Anthropic은 상한 1.0이라 `자유`와 `실험`의 샘플링 차이가
  작다. 그 사실을 선택지 아래 한 줄로 밝힌다.
- **모델이 temperature를 거부하면**(OpenAI 호환 추론 모델과 **Anthropic 최신 모델**의 400)
  `max_completion_tokens`와
  **같은 형태**로 자동 교정한다: 판정 → 파라미터 빼고 1회 재시도 → `temperatureUnsupported`로
  기억 → **결과에 한 줄 고지**("이 모델은 샘플링 조절을 지원하지 않아 지시 문구만 적용했습니다").
  고지를 빠뜨리면 사용자는 변화가 없는 이유를 영영 모른다. **두 교정은 연쇄된다** — 추론
  모델은 파라미터 이름과 temperature를 둘 다 거부하므로, 이름 교정 재시도가 temperature
  거부로 떨어지면 이어서 빼고 한 번 더 시도한다(성공하면 둘 다 기억되어 다음부터는 1회 호출).
  > **판정의 거부 표현 목록은 관찰로만 늘린다 — 짐작으로 넓히지 않는다** (B-160, 2026.08.08
  > 사용자 보고). 이 목록은 OpenAI 호환의 낱말 넷(`unsupported`·`not supported`·
  > `does not support`·`not allowed`)으로 출발했는데, **Anthropic이 `deprecated`라는 다섯째
  > 낱말로 거부하면서 판정이 false를 냈다.** 그러면 위 교정이 **통째로 안 돌고** 400이 그대로
  > 사용자에게 나가는데, 하필 일반 400 문구가 *"모델명과 서버 주소를 확인해 주세요"*라
  > **멀쩡한 곳을 고치라고 시킨다**(그 문구 자체는 B-161로 등재만 했다).
  > **이것은 저장소가 이미 이름 붙인 부류의 셋째다** — *"손으로 적은 목록은 그것이 불완전할 때
  > 아무 말도 하지 않는다"*(B-145·B-158). 이번 것은 목록이 **문자열 매칭**이라 더 조용하다:
  > 컴파일도 정적 검사도 시험도 초록이고, 증상은 실기기에서 400으로만 난다.
  > **넓히지 않는 쪽도 규약이다** — 오탐 하나면 `temperatureUnsupported`가 잘못 학습되어
  > 그 모델에서 창작도가 영영 죽고, 사용자는 이유를 볼 수 없다. 새 표현을 **만나면** 더한다.
- **근거 강도와 충돌한다.** `실험` × `minConfidence=확실`은 대부분 `BELOW_CONFIDENCE`로 빠져
  돈만 나간다. 선택 시점에 경고 + **그 자리에서 하한을 바꾸는** 링크를 준다.
- 값 라이브러리 AI 정리에는 **적용하지 않는다** — 그것은 창작이 아니라 정리이고, 무작위성이
  유사값 병합·오탈자 교정에서는 해가 된다.
- 값은 **하나다**(`AiPromptSettings.creativity`). 설정 화면 / 실행 다이얼로그 / 재요청 다이얼로그 /
  서술형 시트 어디서 바꾸든 같은 값을 바꾼다. "이번 요청만"과 "기본값"을 나누면 화면마다 다른
  값이 살아 있어 일일이 열어봐야 알게 된다(원칙 04 위반).

### 함께 고친 것 (A-0)

- **R-23 — 학습한 사실은 학습 대상이 바뀌면 함께 버린다.** 종전 `AiSettingsFragment.readConfig`는
  모델·주소를 바꿔도 `detectedOutputLimit`을 그대로 넘겼다(4k 모델에서 배운 상한이 128k
  모델로 갈아탄 뒤에도 남아 요청값을 조용히 깎았다). `temperatureUnsupported`가 같은 성격의
  값을 하나 더 만들었기 때문에 **둘을 같은 규칙으로** 고쳤다 — 모델·baseUrl 변경 시 전부 `null`,
  초기화 사실을 저장 시 한 줄로 고지. 등재 판정의 단일 소스는 `AiProviderConfig.hasLearnedFacts()`.
  **학습값은 등재할 자리가 셋이다**(B-132가 실증했다): `hasLearnedFacts()` · `readConfig`의 초기화 ·
  **`AiProviderCodec`의 직렬화**. `imagesUnsupported`는 앞의 둘까지만 배선되고 코덱에만 빠져 있었고,
  저장소가 Context 의존이라 **어떤 로컬 검증도 그 누락을 보지 못했다** — 그래서 코덱을 순수 계층으로
  갈라 왕복 전체를 시험이 잠그게 했다. 지금은 *"설정에 선언된 모든 필드가 JSON에 실린다"*를 선언에서
  읽어 확인하므로, **새 학습값을 더하고 코덱을 잊으면 그 자리에서 실패한다.**

- **B-150 — 실패는 어느 프로바이더에서 났는지를 들고 온다.** `AiResult.Failure.provider`(`AiProviderRef`)를
  **`AiService`가 관문에서 새긴다.** 표식이 없는 실패는 `NO_PROVIDER` 하나뿐이고, 그 사실이
  *"어디선가 새기는 것을 빠뜨렸다"*의 판별 기준이 된다. 호출부(8곳)가 넘기게 하지 않은 이유가 이것이다 —
  빠뜨린 자리는 **종전과 글자 그대로 같은 문구**를 내므로 고쳤다고 믿는 채로 안 고쳐진다.
  문구 조립은 `AiErrorText.compose`가 단일 소스이고 **프로바이더 줄이 맨 앞에 선다**(뒤로 밀면
  길이가 들쭉날쭉한 제공사 원문에 가려 사실상 안 보인다).

### A-6. 대결 우열을 프롬프트에 싣는다 (`util/DuelAiContext`, 2026.08.05 · B-104 소비처 ⓔ)

설계 정본은 `docs/duel_system_design_2026-08.md` **10장**이다. 조립 규칙의 단일 소스는
`util/DuelAiContext`이고, **짧은 값 경로와 서술형 경로가 그 하나를 함께 쓴다.**

- **왜 다른 섹션과 성격이 다른가:** 태그·메모·필드값은 사용자가 *적은* 것이지만 대결 우열은
  **어느 칸에도 적혀 있지 않다.** 둘씩 비교해 고른 것이 쌓여 생긴 서수 데이터라, 이 줄이
  없으면 모델은 사용자가 이미 정해 둔 우열을 모른 채 값을 지어낸다.
- **줄의 모양:** `대결 우열(사용자가 둘씩 비교해 쌓은 순위): 강함: 12명 중 3위 · 1523 ±37 (12판)`.
  절 이름의 괄호가 본체다 — 출처를 밝히지 않으면 모델이 이 수를 필드값처럼 읽는다.
  등수를 먼저 적는 것은 BT 점수의 눈금이 축마다 달라 **1523 자체에는 뜻이 없기** 때문이고,
  `±`를 붙이는 것은 세 판 친 1520과 백 판 친 1520이 같은 수가 아니기 때문이다(설계 9-4-1).
- **점수는 순위표의 그 수이고 등수는 다시 매긴다.** `DuelRepository.scoresOf`를 타므로 순위표·
  목록 정렬·통계와 같은 진입점에서 나온다. 등수만 예외인 이유는 설계 9-3이 통계 순위 탭에
  세운 것과 같다 — **여기서는 한 판도 안 친 참가자가 빠지므로 등수도 함께 다시 매겨야 한다**
  (그러지 않으면 앵커 1500이 표 한가운데 끼어 *"3명 중 4위"*가 나온다).
- **한 판도 안 친 축은 싣지 않고, 적합조차 하지 않는다.** 앞은 `DuelScoreIndex` 계약 2이고
  (앵커 1500을 실으면 모델이 그것을 *측정된 실력*으로 읽는다), 뒤는 그 계약에서 따라오는
  비용 절감이다 — 결과가 어차피 같으므로 판 수 COUNT로 걸러 적합을 건너뛴다.
- **상한은 축 20개**(`DuelAiContext.MAX_AXES`)이고 넘치면 **판이 가장 적은 축**부터 빠진다
  (판 수가 곧 그 줄을 믿을 근거의 양이다). 뺀 수는 truncationNotes로 고지한다(R-14).
- **시스템 프롬프트가 함께 간다** — 짧은 값 규칙 15번(*그 서열과 어긋나는 값을 내지 마라*),
  서술형 규칙 8번(같은 것 + *등수를 글에 숫자로 적지 마라* — 작업 기록이지 작품 설정이 아니다).
  줄만 싣고 지시가 없으면 모델은 참고 정보로 흘려보낸다.
- **미저장 신규(-1)는 건너뛴다** — 판은 캐릭터 코드로 쌓이므로 애초에 참가자가 아니다.
  이미지 축도 제외한다(참가자가 이미지 경로라 캐릭터 코드로 집을 수 없다).

### A-7. 캐릭터 이미지를 프롬프트에 싣는다 (`AiMessage.images`, 2026.08.07 · B-120)

설계 정본은 `docs/feature_roadmap_2026-08.md` **2-1·2-2**다. 조립 규칙의 단일 소스는 셋으로
갈려 있다 — **고르기** `util/AiImageAttach`(순수) · **전송용 축소** `util/AiImagePreparer`
(Android) · **직렬화** `AiProtocolCodec`(순수). 짧은 값 경로와 서술형 경로가 그 셋을 함께 쓴다.

> **이것은 기존 약속을 뒤집는 지점이다.** 종전에는 앱의 어떤 AI도 이미지를 보내지 않았고
> 두 자리가 그 사실을 문서로 약속하고 있었다(`image_folder_tag_ai` 1장 ·
> `ImageFolderTagSuggester` 주석). 둘 다 **이 슬라이스에서 함께 고쳤다** — 그 기능들 자신은
> 여전히 폴더 이름만 읽으므로 문장을 지운 것이 아니라 **범위를 그 기능으로 좁혔다.**
> 사용자에게도 침묵하지 않는다: 첨부 고지가 *"이미지는 AI 제공사 서버로 전송됩니다"*를
> 요청 직전에 말한다.

- **무엇을 보내는가:** 그 캐릭터의 이미지에서 고른 0~10장
  (`AiPromptPolicy.ATTACH_IMAGES_MAX`). 기본 **1장**은 사용자 확정이다(로드맵 Q3) —
  비용이 붙는 기본값은 보수적으로 두고 올리는 것을 사용자 선택으로 남긴다.
- **고르는 규칙(`AiImageAttach`):** ① '대표 반드시 포함'이 켜져 있고 **지정 대표가 목록에
  있으면**(사다리 1칸 = `PINNED`) 그것이 첫 장이다 ② 지정이 없거나 목록에서 사라졌으면
  **그 사실을 고지하고** 전부 무작위로 채운다 — 조용히 다른 그림을 '대표'라 부르지 않는다
  ③ 나머지는 시드 무작위(중복 없이) ④ **썸네일을 탭해 직접 고르면 그것이 전부다** —
  랜덤도 대표 강제도 끼어들지 않는다(자율성 우선. 랜덤만 있으면 "하필 그 장"을 뺄 길이 없다).
  🎲가 시드를 갈아 규칙으로 되돌린다.
- **전송용 축소(`AiImagePreparer`):** 긴 변 `SEND_LONG_EDGE_PX`(현재 1024) 이하로 줄이고
  JPEG로 재인코딩한다. 저장용 압축(`ImageImportHelper`, 8192px까지)과 **별개다** — 그쪽은
  기기 용량이 목적이고 이쪽은 요청 바이트가 곧 돈이다.
  **1024는 아직 실호출로 재지 않은 제안값이다**(설계 2-1이 그렇게 적었고, 이 저장소는
  근거 없는 숫자를 박지 않는다 — P-9). 확정은 실사용 측정 뒤이며 백로그 **B-126**이다.
- **직렬화(`AiProtocolCodec`):** ANTHROPIC은 `content` 배열의 `image`(base64 source) 블록,
  OPENAI_COMPAT은 `image_url`의 `data:` URI, GEMINI는 `inline_data` 파트.
  **세 프로토콜 모두 이미지를 텍스트 앞에 둔다** — 프롬프트가 "순서대로 실려 있다"고 말하고
  몇 번째인지 적으라고 시키므로, 그 번호가 모델이 본 순서와 같아야 한다.
  **이미지가 없으면 요청은 글자 그대로 종전과 같다**(`content`가 문자열로 남는다) —
  배열로 바꾸면 이미지를 안 쓰는 기존 경로 전부가 새 형식으로 나간다. `AiImageRequestTest`가
  그 사실을 잠근다. 원격 URL은 쓰지 않는다: 앱의 이미지는 기기 안 파일이라 모델이 가져갈
  주소가 없고, 만들려면 어딘가에 올려야 하는데 그것은 **보안 경계를 넘는다**.
- **모델이 이미지를 거부하면**(400) — A-4의 관행 그대로다: 판정
  (`isImagesUnsupportedError` — 낱말과 거부 표현이 **함께** 있어야 참) → 이미지를 빼고 1회
  재시도 → `imagesUnsupported`로 **기억** → **결과에 한 줄 고지**(*"이 모델이 이미지를 받지
  않아 글만 보냈습니다"*). 고지를 빠뜨리면 사용자는 그림을 붙였는데 결과가 달라지지 않는
  이유를 영영 모른 채 첨부만 계속 켜 둔다. **학습값이므로 `hasLearnedFacts()`에 등재했고**
  R-23을 그대로 탄다 — 비전 지원은 같은 프로토콜 안에서도 모델마다 갈리므로, 안 받던
  모델에서 배운 사실을 받는 모델에 물려주면 첨부가 영영 조용히 빠진다.
  > ✅ **위 "기억"은 이제 참이다 — `B-132` 처리 완료** (2026.08.07). 종전에는
  > `AiProviderStore.toJson`/`fromJson`만 이 키를 쓰지도 읽지도 않아 학습이 저장되지 않았고,
  > **`strippedUpfront` 경로와 그것에 기댄 사전 고지 세 자리가 전부 dead code**였다.
  > 직렬화는 `AiProviderCodec`으로 갈라 나왔고 `AiProviderCodecTest`가 왕복을 잠근다.
  >
  > **그 경로가 살아나자 잠자던 결함이 깨어났다 — `B-139`** (2026.08.08 처리 완료. 아래 항).
  > 죽은 경로를 살리면 **그 경로가 하던 말이 참인지도 함께 봐야 한다**는 것이 이 자리의 교훈이다
  > (같은 부류를 B-135→B-137이 하루 전에 겪었다).
- **비용 고지는 연인원을 말한다.** 짧은 값 추천은 대상 필드를 청킹해 **요청마다 같은 그림을
  다시 싣는다** — 첫 요청에만 붙이면 뒤쪽 필드는 그림을 못 본 채 답이 나오고 그 차이가
  사용자에게 보이지 않는다(조용한 비대칭 금지). 그래서 붙이는 쪽을 택하고
  `AiPromptPolicy.imageSendCount(장수, 요청 수)`가 고지의 단일 소스다(R-4). 서술형은 후보
  여러 개를 한 요청으로 받으므로 연인원이 장수 그대로다.
- **읽지 못한 파일은 건너뛰고 센다**(R-14) — 앱 밖에서 파일이 지워졌거나 폴더 왕복이 경로를
  바꾼 자리라 **사전 확인이 원리적으로 불가능하다.** 사후 고지가 유일한 경로다.
- **앱 저장소 밖의 파일은 싣지 않는다 — 그리고 그것은 "못 읽음"과 다른 사유다**
  (B-141, 2026.08.08 · **R-39**). 준비기는 **기기의 바이트를 제3자 서버로 올리는 유일한
  경로**인데, 저장 이미지를 읽는 다른 자리가 전부 두는 filesDir 가드가 여기에만 없었다.
  입력은 믿을 수 없다: `imagePaths`는 엑셀 '이미지' 열 편집으로 들어오고
  (`remapImagePaths`가 표에 없는 경로를 **원본 그대로 유지**한다) DB 적재 경로 둘은
  `validateInternalPaths` 없이 화면에 싣는다. 같은 경로를 **첨부 줄 썸네일은 플레이스홀더로
  그리는데 준비기만 읽어 올렸다** — 사용자가 화면에서 볼 수 없는 파일이 그 화면의 요청으로
  나갔다.
  판정은 `util/ImagePathMatch.isInside`(순수)가 들고 `filesDir`는 **필수 인자**다
  (`Context`를 들면 가드가 *기억해서 부르는 것*이 되고 넷째 소비처에서 조용히 빠진다 —
  B-139와 같은 판단). **막힌 장수는 `blocked`로 갈라 센다**: 못 읽은 것과 처방이 달라
  뭉뚱그리면 멀쩡히 있는 파일을 두고 *"읽지 못했습니다"*라고 말하게 된다.
  `tools/check_ai_send_guard.sh`가 가드의 삭제·기본값·뿌리 누락을 막고
  (**호출 자리는 훑어서 찾는다** — 손으로 적은 목록은 불완전할 때 침묵한다),
  `ImagePathMatchTest`가 판정 자체를 잰다(경계 문자·`..` 이탈·심볼릭 링크·실패 처분).
  설계 정본은 `docs/feature_roadmap_2026-08.md` **2-9장**.
- **시스템 프롬프트가 함께 간다** — 짧은 값은 *"그림에서 읽은 값이면 reason에 몇 번째
  이미지인지 밝혀라"*(검토 화면의 근거 줄이 그대로 보여 주므로 새 UI가 없다), 서술형은 같은
  것 + *"'이미지 1'처럼 그림을 가리키는 말을 본문에 쓰지 마라"*(본문은 그 필드에 그대로 들어갈
  작품 설정이지 작업 기록이 아니다 — A-6의 등수 규칙과 같은 이유).
  **번호를 매기지 않고 `[이미지]` 블록으로 붙인다** — 규칙 16을 근거 강도가 조건부로 쓰는
  자리라, 여기에 또 번호를 매기면 설정 조합에 따라 `16.`이 둘이 된다.
- **그 지시는 이미지와 한 몸으로 다닌다 — 그림을 빼면 지시도 빠진다** (B-139, 2026.08.08).
  `AiRequest.imageSystemRule`이 `system`과 **갈려 있고**, 프로토콜 계층은 `system`이 아니라
  `effectiveSystem()`을 싣는다(그 함수가 `hasImages()`로 판정한다).
  **이어 붙여 두면 안 되는 이유:** 이미지가 빠지는 경로가 둘인데(④ 거부 재시도 ·
  `strippedUpfront`) 붙여 두면 그 둘이 **각자 문자열을 도로 걷어내야 하고**, 실제로 둘 다
  빠뜨려 *"이미지 N장이 순서대로 함께 실려 있다"*가 그림 없이 나갔다 — 모델은 없는 그림을
  근거로 삼아 **날조된 출처**를 낼 수 있고, `strippedUpfront`는 학습된 뒤 **매 요청** 어긋난다.
  갈라 두면 빠뜨릴 자리 자체가 없다. `tools/check_ai_image_rule.sh`가 두 부활(코덱이
  `request.system`을 직접 읽는 것 · 지시를 `buildSystemPrompt`에 도로 이어 붙이는 것)을
  기계로 막고, `AiImageRequestTest`가 세 프로토콜의 결과를 잰다.
  > **왜 검사와 시험을 둘 다 두는가:** 시험은 *지금 있는* 세 프로토콜만 재므로 넷째가
  > `request.system`으로 들어오면 아무 말도 하지 않고, 검사는 모양만 보므로 이름을 바꾼
  > 부활을 놓친다. 실수의 방향이 **빼는 쪽**이라 어느 쪽이 뚫려도 모델이 속지는 않는다.
- **A-3의 뽑기 잠금이 그대로 적용된다** — 요청 중 대상이 바뀌어도 기존 2겹(잠금 +
  `targetCharacterId` 대조)이 막는다. **보완 재요청은 첫 요청과 같은 그림을 다시 쓴다**
  (`AiSuggestRun.imagePaths`) — 다시 고르게 하면 마찰이고, 비우면 같은 검토 화면 안에서
  근거가 조용히 바뀐다. base64가 아니라 **경로**를 들고 있는 이유: 회전을 넘기는 객체라
  수 MB를 얹으면 그 자체가 비용이다(다시 읽는 편이 싸다).

### A-9. 이미지 내용을 보고 일괄 태깅한다 (`ai/ImageBatchTagSuggester`, 2026.08.07 · B-121)

설계 정본은 `docs/feature_roadmap_2026-08.md` **2-3**이고, A-7의 멀티모달 기반 위에 선다
(그래서 순서 강제였다). **A-7과 갈리는 지점은 이미지가 곁들이가 아니라 근거의 전부라는 것**이며,
아래 계약 셋이 전부 그 한 줄에서 나온다.

- **번호 봉인이 이 기능의 본체다.** 한 요청에 여러 장을 실으므로 응답의 태그가 **남의
  이미지에 붙을 수 있다.** 프롬프트가 각 장을 `이미지 1`…로 부르고 응답은 `{"images":
  [{"index":1,"tags":[…]}]}`이어야 한다. 번호가 범위를 벗어나거나 겹치면 **그 배치를 통째로
  접는다** — 절반만 믿고 붙이는 것이 곧 오배정이고, *오배정은 생략보다 나쁘다*(R-1).
  접힌 배치는 검토 시트의 **'1장씩 다시 보내기'**로 되받는다(장수 1이면 번호 사고가
  원리적으로 없다).
- **번호가 가리키는 목록은 '실제로 실린' 목록이다.** 읽지 못한 파일은 배치에서 빠지므로,
  전송 준비기가 **경로와 짝지어** 돌려주지 않으면 가운데 한 장이 빠졌을 때 3번이 원본
  3번과 어긋난다 — 봉인해 놓고 봉인 대상을 흔드는 셈이다. 그래서 `AiImagePreparer`에
  `prepareEach`(짝 유지)를 두고 이 경로만 그것을 쓴다. A-7의 `prepare`(장수만 셈)는
  그대로 남는다 — 그쪽은 순서가 근거 문구의 편의일 뿐이라 요구가 다르다.
- **이미지를 못 싣는 모델의 답은 버린다.** A-7은 거부당하면 글만 보내 재시도하고 그것이
  옳다(그림이 곁들이라 글만으로도 답이 선다). **여기서는 아니다** — 그림을 보지 않고 나온
  태그는 지어낸 것이다. `imagesOmitted`가 서면 그 배치를 접고 **남은 배치도 돌리지 않는다**
  (학습된 사실이라 뒤에도 같은 일이 나고, 돌리면 돈만 쓴다). 고지가 그 사실을 말한다.
- **잘린 응답은 번호 사고와 갈라 센다**(`RESPONSE_TRUNCATED`). 둘 다 파싱에 실패하지만
  **처방이 다르다** — 이쪽은 장수를 줄이거나 출력 상한을 올리는 것이다. 뭉뚱그리면 고지가
  틀린 곳을 고치라고 시킨다. 요청은 `effectiveMaxTokens()`를 실어 사용자가 올려 둔 상한을
  그대로 쓴다.
- **어휘는 A-7이 아니라 폴더 제안기와 공유한다** — `ai/ImageTagVocabulary`가 단일 소스다
  (B-121에서 `ImageFolderTagSuggester`의 companion에서 옮겨 왔다). 두 벌이 되면 같은 앱의
  두 AI가 다른 어휘로 말한다. **응답 태그는 공백·대소문자를 무시해 기존 표기로 접는다**
  (`matchOption` — SELECT 값에 이미 쓰는 그 규칙). `물의정령`과 `물의 정령`이 두 태그로
  갈리면 필터도 통계도 둘로 쪼개진다. *(폴더 제안기 쪽은 아직 정확 일치다 — 백로그 **B-127**.)*
- **적용은 합친다**(덮지 않는다). 기존 태그·`image_tags` 스키마 무변경.
  AI 출력은 검토 시트를 통과해야만 들어간다.
- **진입은 이미지 탭 다중선택 → 일괄 작업**이고, 쓸 수 있는 프로바이더가 없으면 **줄 자체가
  보이지 않는다**(R-24). 실행 전 고지가 요청 수·장수·*"이미지는 AI 제공사 서버로 전송됩니다"*를
  말하고, 진행은 결정형(R-26)에 취소가 붙는다 — **취소해도 끝난 배치의 제안은 살린다.**
- **실행·결과·취소·진행도가 전부 ViewModel에 있다**(R-38 · B-136, 2026.08.08 보강).
  이 문서는 A-6에서 이미 AI 실행을 *"회전 생존"*으로 적어 두었는데(`CharacterViewModel.runAiSuggest`),
  **A-9의 첫 구현은 그것을 따르지 않았다** — 실행이 `viewLifecycleOwner.lifecycleScope`에 있어
  **회전 한 번이 결제 중인 요청을 끊었고**, 결과는 Fragment의 지역 변수에만 살아 되살아난
  검토 시트가 빈 껍데기였다. 이제 `ImageManagerViewModel.runImageTagSuggest`가 실행을 들고
  `aiTagResult`가 응답을 든다. 소비(clear)는 **검토 시트의 액션 시점**이다.
  **선행 기능(폴더 이름 태깅)도 같은 모양이라 함께 세웠다**(`runFolderTagSuggest`/`folderTagResult`) —
  한 시트만의 이탈이 아니라 **검토 시트 부류가 통째로 빠져 있었다.**
- **'1장씩 다시 보내기'는 앞 실행의 성공분 위에 얹는다 — 갈아치우지 않는다**(B-140).
  종전에는 시트를 **먼저 닫고** 재실행해, 25장을 5요청에 돌려 1요청만 접히면 **20장분 제안이
  소멸**하고 되받으려면 이미 성공한 4요청을 다시 결제해야 했다. 위 줄이 선언한
  *"끝난 배치의 제안은 살린다"*가 **화면 계층에서 뒤집혀 있던 자리다.** 합치는 규칙은
  `ImageBatchTagSuggester.mergeRetry`가 들고, **다시 물을 값어치는 그 배치에 실렸던 장수로
  잰다**(`retryablePaths` — 1장이 실렸던 배치를 1장으로 다시 보내는 것은 같은 요청을 한 번 더
  결제하는 것이다). **집계는 축을 갈라 합친다**: 응답이 만든 드롭은 더하되 **어휘 절단·못 읽은
  파일은 큰 쪽을 든다** — 같은 프롬프트를 두 번 실은 것이라 더하면 고지가 부풀어 거짓말이 된다.

### A-8. 이름을 지어 라운드로 다듬는다 (`ai/CharacterNameAiSuggester`, 2026.08.09 · B-123)

설계 정본은 `docs/feature_roadmap_2026-08.md` **7장**(구현이 정한 것은 7-6, 확장성 재판정은 7-7).
**A-9와 갈리는 지점은 대상이 필드도 이미지도 아니라 엔티티 컬럼이라는 것**이다 —
`name`·`firstName`·`lastName`·`anotherName`은 `FieldDefinition`이 아니라서 짧은 값 추천의
대상식(`bulkTargetsOf`) 밖이고, 그래서 서술형(A-0 계열)처럼 **전용 경로**다.

- **멀티턴 없이 대화가 성립한다.** 이 문서가 한계로 적어 둔 *단일 턴만 지원*은 그대로인데,
  이 기능은 그것을 **필요로 하지 않는다**: 라운드마다 유지(♥)·회피(✕)·자유 지시·창작도를
  **요청에 동봉**한다. 문법은 보완 재요청(`userInstruction`+`rejectedValues`)이 이미 검증한
  그것이고, 새로 만든 것은 종류가 아니라 **크기**다. **요청은 라운드당 1건**이다 — 다발
  크기(1~30, 기본 10)로 나누지 않는다. 나누면 과금이 배로 늘고 *"후보끼리 겹치지 마라"*를
  줄 수 없어 같은 이름이 여러 요청에서 돌아온다.
- **회피 목록에는 상한이 있고 뒤에서 자른다**(최근 60). 그 목록은 라운드마다 자라 그대로
  실으면 입력이 후보 본문보다 커진다. **앞에서 자르면 막 거절한 이름이 회피에서 빠져** 바로
  다음 라운드에 되돌아온다 — 코드는 멀쩡해 보이고 증상은 *"AI가 말을 안 듣는다"*다.
  잘라낸 수는 고지한다(R-14).
- **컨텍스트는 기존 조립기를 그대로 쓴다**(`CharacterAiContextBuilder`) — 태그·성별·소속·
  종족이 이름의 결을 정한다. **대결 우열(A-6)은 싣지 않는다**: 이름의 결과 무관하고 토큰만
  쓴다. 여기에 **같은 세계관 기존 이름 견본**(상한 30)과 **은행 미사용 견본**(상한 12)을
  더하며, **둘 다 등간격 표집**이다 — 앞에서 자르면 먼저 만든 캐릭터들만 실려 뒤로 가며 바꾼
  표기 관행이 통째로 빠진다. 난수를 쓰지 않으므로 같은 데이터가 같은 프롬프트를 낸다.
- **응답은 `{"names":[{"name":…,"why":…}]}`이고 형식 이탈은 거부가 아니라 정리해 수용한다**
  (감싼 따옴표·번호 접두·문자열만 준 배열). 버리는 것은 셋뿐이고 전부 개수로 고지한다 —
  빈 이름 · 응답 안 중복 · 요청 개수 초과. **되풀이는 드롭과 갈라 센다**(R-17): 형식 이탈은
  다시 요청하면 되지만 되풀이는 *지시를 더 주라*는 뜻이라 처방이 다르다.
- **AI 출력은 DB에 직접 쓰지 않는다**(기존 불변식). [적용]은 **모드가 정한 폼 칸**에만
  넣고(전체 이름 → `name` · 성 고정 → `firstName` · 이름 고정 → `lastName` · 이명 →
  `anotherName`에 **덧붙임**), 이름은행에는 사용자가 [은행에 담기]를 눌러야 들어간다.
- **같음의 판정은 `util/NameBankMatch` 하나다**(B-124가 세운 것) — 되풀이도 은행 중복도 그
  함수다. 여기서 규칙을 새로 적으면 *담을 때는 새 이름인데 저장 때는 중복인* 상태가 나고,
  그 어긋남은 화면 어디에도 보이지 않는다.
- **담기는 은행 중복과 풀 안 표기 중복만 거른다**(개수 고지). **이미 캐릭터가 쓰는 이름은
  표식이지 거름이 아니다** — 목업 주석이 반대로 적혀 있었고 설계 정본을 따랐다. 성별과
  출처(`AI 추천`)는 자동으로 채운다: 실측에서 은행의 출처가 전부 빈 칸인 것은 손으로 채울
  이유가 없어서다.
- **유료 응답과 실행은 시트의 ViewModel이 든다**(R-38). 진입이 둘이라(편집 폼 ✨ · 은행
  [AI로 이름 만들기]) 호스트 ViewModel에 두면 **같은 엔진이 두 벌**이 된다. 회전에 넘는 것은
  후보·표식·실행이고, 호스트가 다시 붙일 것은 **콜백 하나**(적용)다. 검토 상태(펼침)는 시트가
  `onSaveInstanceState`로 지킨다. **시트를 닫으면 세션 풀도 끝난다** — 설계가 그렇게 정했고
  (7-4), 남길 것은 담은 이름이며 그것은 DB에 있다.
- **`tools/check_ai_review_retention.sh`가 이 시트도 본다**(B-123에서 항목 신설) — 회전
  보존 · 실행 엔진이 뷰 밖 · 호스트 재배선 셋을 기계가 지킨다.

## 구현됨 — B-108. 프로바이더 자동 전환 (2026.08.09)

사용자 요청(2026.08.03): *"사용중에 사용량 한도 걸리면 자동으로 다른 api로 전환해서
이어나가도록 하게. 그리고 그 전환 우선순위도 지정할 수 있게."*
판정 원문은 `docs/judgment_confirmations_2026-08.md` **7-1**(2026.08.04 사용자 확정 6건).

**새로 만든 것은 '전환'이 아니라 '언제·어디로·무엇을 알리며'다.** 바탕은 이미 서 있었다 —
`AiProviderConfig`가 목록이고 프로토콜이 추상화돼 있어 갈아 끼우는 것 자체는 값 교체이며,
오류 갈래도 `RATE_LIMITED`·`QUOTA_EXCEEDED`로 이미 갈려 있었다.

### 계층

| 자리 | 무엇 |
|---|---|
| `ai/AiProviderFallback` (신설, **순수**) | 순서·방아쇠·쿨다운·고지 문구의 **단일 소스**. JVM 시험 대상 |
| `ai/AiService.completeWithFallback` | 그 판정을 실행만 한다 (관문 하나) |
| `ai/AiProviderConfig.priority` · `.cooldownUntilMillis` | 저장되는 두 칸. 직렬화는 `AiProviderCodec` |
| `ui/settings/AiSettingsFragment` | 끌어 놓기로 우선순위 · 쿨다운 상태 표시 |

**전환을 관문에 둔 것이 이 구현의 요점이다.** 인앱 기능 여섯이 각자 폴백을 짜면 여섯 벌이 되고
**한 벌만 빠뜨려도 그 기능에서만 조용히 종전처럼 죽는다**(B-150이 실패 표식에서 겪은 그 부류).

### 확정 6건이 코드에서 어디에 있는가

- **ⓐ 방아쇠는 한도 둘뿐** — `dispositionOf`. 429는 `RETRY_SAME` → 재시도까지 실패하면 `SWITCH`,
  크레딧 소진은 곧바로 `SWITCH`, 나머지는 전부 `STOP`.
  > **429가 결국 전환하는 것이 확정과 어긋나지 않는 이유.** 확정 ⓐ가 경계한 것은
  > *"일시적 혼잡에 키를 갈아치우고 **돌아오지 않는다**"*이고, 처방이 재시도였다. 여기서는
  > 재시도가 **먼저** 서고(그래서 혼잡에 곧바로 바뀌지 않는다), 밀린 키는 **10분 뒤 돌아온다**
  > (ⓔ의 쿨다운). 반대로 429가 끝내 전환하지 않으면 멀쩡한 둘째 키를 두고 사용자가 실패를
  > 받는데, 그것이 이 요청이 없애 달라고 한 바로 그 상황이다. ⓔ가 *"**한도로** 밀린 제공자"*에
  > 쿨다운을 건 것도 이 읽기에서만 뜻이 산다.
- **ⓑ 고지 한 줄** — `AiResult.Success.provider`·`.switchedFrom`을 **관문이 새기고**(`withProvider`·
  `withSwitchedFrom`), 문구는 `switchNote` 하나다. 호출부 여섯은 `switchNoteOf(result)` 한 줄을
  자기 고지 채널에 얹는다. **그 등재를 `tools/check_ai_switch_notice.sh`가 기계로 본다.**
- **ⓒ 우선순위는 전역 하나** — `AiProviderConfig.priority`(작을수록 먼저). 설정 화면에서
  끌어 놓아 정하고(원칙 04 — 숫자를 직접 적게 하지 않는다), 저장은 손을 뗀 순간 한 번이다.
- **ⓓ 키 없는 프로바이더 건너뜀** — `order`가 순회 전에 거른다.
- **ⓔ 최대 3곳 + 10분 쿨다운** — `MAX_PROVIDERS_PER_REQUEST` · `COOLDOWN_MILLIS`.
- **ⓕ 필드 단위로 가른다** — **새 장치 없이 성립한다.** 청킹 호출부(`CharacterFieldAiSuggester`
  등)는 이미 청크마다 결과를 누적하고 터미널 오류에서만 멈추는데, 전환이 관문 안에 있으므로
  `QUOTA_EXCEEDED`는 **모든 프로바이더가 소진된 뒤에야** 호출부에 닿는다. 그래서 다 나온 필드는
  그대로 살고 덜 나온 청크만 새 프로바이더로 이어진다. 쿨다운이 그 뒤 청크를 새 프로바이더로
  곧장 보낸다(밀린 곳이 맨 뒤로 가므로).

### 이 구현이 정한 것 넷 — 확정이 말하지 않은 자리

1. **활성이 언제나 맨 앞이다.** 우선순위는 *전환할 때 어디로 가는가*의 순서이지 활성을 고르는
   규칙이 아니다. 그래서 **아무것도 실패하지 않는 평소에는 종전과 글자 그대로 같은 곳이
   답한다** — 회귀가 새 기능이 아니라 **옛 기능**에 나는 자리라 시험이 못 박는다.
2. **쿨다운은 빼는 것이 아니라 미루는 것이다.** 빼면 전부 한도일 때 두드릴 곳이 없어
   *"프로바이더가 없습니다"*가 나가는데 **등록된 키는 멀쩡히 있다** — 거짓말을 하는 실패이고
   교정 경로도 틀린 곳을 가리킨다.
3. **`INVALID_KEY`는 전환하지 않는다.** *"그 키로는 영영 안 되는 것"*이라는 점에서 크레딧
   소진과 닮아 한 갈래로 묶고 싶어지지만, 묶으면 **틀린 키가 둘째 프로바이더의 성공으로 덮여
   사용자가 영영 고치지 않는다.** 확정이 방아쇠로 든 것도 한도 둘뿐이다.
4. **명시 지정(`complete(request, config)`)은 전환하지 않는다.** 그 인자는 *"이것으로 해 보라"*는
   뜻이라(연결 테스트가 저장 전 설정을 넘기는 자리) 다른 곳의 성공으로 답하면 검사가 거짓이 된다.

### 마이그레이션이 없다

프로바이더 설정은 Room이 아니라 SharedPreferences + `AiProviderCodec`이고, 새 칸 둘은
**구버전 JSON에 없으면 `priority=0` · 쿨다운 없음**으로 읽힌다. 전부 0이면 정렬이 `createdAt`으로
떨어져 **옛 목록 순서 그대로**다(시험이 잠근다).

### R-23과의 관계

`cooldownUntilMillis`는 **학습한 사실**이라 `hasLearnedFacts()`에 등재했고, 모델·주소가 바뀌면
`readConfig`가 함께 버린다. 남겨 두면 모델을 바꿔 놓고도 옛 쿨다운 때문에 그 프로바이더가 계속
뒤로 밀리는데, **화면에 표시가 없는 미룸이라 원인을 짚을 길이 없다.**
반면 `priority`는 **사용자가 정한 값**이라 R-23 대상이 아니다 — 모델을 바꿨다고 사용자가 정한
순서를 지우면 그것이야말로 조용한 유실이다.

> **벽시계 주의.** 쿨다운은 저장된 시각이라 사용자가 시계를 뒤로 돌리면 *"10분"*이 며칠이 된다.
> `isCoolingDown`이 **상한을 넘는 잔여를 만료로** 본다 — 설정 어디에도 쿨다운을 되돌리는 길이
> 없으므로, 굳으면 원인도 교정 경로도 없는 침묵이 된다.

## 한계·향후 과제

- 단일 턴 요청만 지원(멀티턴 대화·스트리밍은 필요 기능이 생길 때 `AiProtocolCodec` 확장).
  **스트리밍 부재는 서술형 생성의 선행 과제다** — 긴 글은 응답까지 무피드백 대기가 길어진다.
- 사용량(토큰) 집계는 **회당 표시만** 있다(실행 결과에 입력·출력 토큰). 기간 누적 집계는 없음.
- 필드 **정의** 생성(어떤 필드를 둘지)에는 AI가 없다 — 수동 생성과 고정 프리셋(`PresetTemplates`)뿐.
  "도구를 만들 수 있는 도구"라는 앱 정체성의 정중앙이라 가치가 크다.
- SELECT/GRADE **옵션 목록 생성**도 없다. 값 라이브러리 AI는 *있는 값 정리*만 한다.
- **사건 필드에는 AI 경로가 없다** — 추천기가 캐릭터 컨텍스트 전용이다. 그래서 A-1의 토글도
  사건 필드에서는 감춘다(R-24). 사건용 컨텍스트(사건명·연도·관련 캐릭터·작품)를 정의하면
  토글이 함께 열린다 (백로그 B-43).
- **서술형 필드의 일괄 초안이 없다** — A-1이 서술형을 짧은 값 일괄에서 빼므로, 서술형만 모아
  도는 경로가 비어 있다. 필드 하나가 출력 예산을 통째로 쓰므로 **비용 고지 설계부터** 하고
  착수할 것 (백로그 B-45).
- 로컬 LLM(http) 미지원 — https 전용. 필요 시 network security config로 사설망 예외 검토.
- 모델 추천 목록은 시점 고정 — 필드가 자유 입력이므로 기능은 깨지지 않음. 프리셋 갱신은
  `AiPresets` 수정만으로 완료.
