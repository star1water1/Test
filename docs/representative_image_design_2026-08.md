# 캐릭터 대표 이미지 (B-103) — 설계

> **확정된 뼈대는 사용자 판정이다**(`docs/judgment_confirmations_2026-08.md` 1장 1번):
> **ㄱ1** 파일 기준 저장 · **ㄴ3** 화면 진입마다 랜덤 · **ㄷ1** 삭제 시 알리고 랜덤 복귀 ·
> **ㄹ1** 엑셀에 실음. 이 문서는 그 넷을 **어떻게 만들지**를 정한다 —
> 확정 문서가 스스로 적어 둔 대로 *"확정은 무엇을 할지가 정해졌다는 뜻이지
> 어떻게 만들지가 정해졌다는 뜻이 아니다"*.
>
> **사용자 요청 원문은 둘이었다**(2026.08.02): ① 다가오는 생일 배너의 사진도 랜덤화
> ② 캐릭터마다 대표 이미지를 고정 — **랜덤보다 우선해서** 뜬다.
>
> **착수 순서상 이것이 B-104(대결)보다 먼저다**(확정 문서 4장) — 대결이 쌓는 이미지 축
> 승자가 대표의 **기본값 후보**이므로, 대표가 먼저 서야 얹을 자리가 생긴다(D9).

진입마다 랜덤 시작. **B-103 등재가 알고 있던 것은 이 중 넷뿐이다.**

### 1-2. 등재가 몰랐던 것 셋 — "전제는 늘 틀린다"의 이 문서 판

1. **`ImageIndexPrefs`가 등재에 없다.** 캐릭터 목록은 **이미 랜덤이고, 이미 "화면 진입마다"다.**
   따라서 사용자가 고른 **ㄴ3은 새 동작이 아니라 나머지 여덟 종류를 목록에 맞추는 것**이다.
2. **상세 화면도 이미 진입마다 랜덤이다**(시작 위치). 등재는 상세를 "그 함수를 쓰게 할 곳"으로만 적었다.
3. **`RankingAdapter`가 등재 목록에 없다.** 세는 법(`ui` 하위 `firstImagePath`·`imagePaths` grep)이
   실제로는 `RankingEntry.imagePaths`라는 **한 겹 우회**를 못 잡는다 — 순위 카드는 스냅샷 필드를 거친다.

> **그리고 이 랜덤은 한 번 죽은 적이 있다.** 세션 로그 **1-12**(사용자 실기기 보고, 2026.07.28):
> 성능 수리 **P2-1**이 *"방출마다 clearAll = 전 목록 재랜덤 + O(N) 쓰기"*를 없애면서
> **재추첨 호출부가 통째로 사라져** "최초 1회 추첨 후 영구 고정"이 됐다. 지금 살아 있는 것은
> `observeData()` 진입부의 1회 재추첨이다.
> **이 설계는 바로 그 자리를 다시 손댄다 — 회귀 위험이 가장 큰 지점이고,
> 그때의 제약(같은 화면 안에서 이미지가 튀지 않을 것 · 방출마다 O(N) prefs 쓰기 금지)은
> 이 설계도 그대로 지켜야 한다.**

### 1-3. `imagePaths`를 다시 쓰는 자리 — 여섯 갈래, 열여섯 지점

ㄱ1(파일 기준 저장)이 실제로 요구하는 것은 칸 하나가 아니라 **이 목록 전수**다.

| 갈래 | 지점 | 경로에 무슨 일이 일어나는가 |
|---|---|---|
| 이미지 관리 | `ImageManagerViewModel:361`(삭제) `:601`(이동·개명) `:699`(이동 되돌리기) `:914`(되살리기) `:1018`(정리) | 사라짐 / 바뀜 / 바뀜 / 새로 붙음 / 사라짐 |
| 폴더 왕복 | `OrganizeFolderService:401·430`(편입) `:422·467`(제외) | 붙음 / 사라짐 — **폴더 왕복은 경로를 바꾼다는 것이 이미 확인된 사실이다** |
| 엑셀 가져오기 | `ExcelImportService:3277`(갱신) `:3296`(신규) — 재매핑은 `:293 remapImagePaths` | 다른 기기의 경로가 이 기기 경로로 **재매핑** |
| 월드패키지 | `WorldPackageImporter:362` — 재매핑은 `:226 restoreImagePaths` | ZIP 엔트리가 새 경로로 풀림 |
| 폼 저장 | `CharacterSaveCoordinator:99~113` | **목록 전체 교체** |

| 휴지통 | 스냅샷 `TrashRepository:730` · 복원 `:1600`(`data.character.copy(...)`) | payload에 실려 함께 오간다 |

> **`CharacterSaveCoordinator`가 이 목록에서 가장 위험하다.** 이 함수는 기존 엔티티를
> `copy()`하지 않고 **폼 스냅샷으로 `Character`를 새로 조립한다**(`:99`). 새 칸을 여기에
> 적지 않으면 **캐릭터를 한 번 저장할 때마다 대표가 조용히 지워진다.**
> **같은 병이 이 저장소에서 이미 한 번 났다** — `partSlots`가 저장할 때마다 지워지던 것
> (세션 로그 **1-ar**). 값·해석·소비가 다 있는데 아무도 밟지 않던 경로였다.

### 1-4. 곁가지 사실

- `Character`(`data/model/Character.kt`)에는 `imagePaths` 하나뿐 — 모드도 포인터도 없다. DB `version = 46`.
- `Universe`/`Novel`에는 `imageMode` + `imageCharacterId`(+`imageNovelId`)가 있고,
  화면 문구는 이미 **"대표 이미지 설정"**(`image_mode_label`)이라는 말을 쓴다 → **용어를 새로 짓지 않는다.**
- 캐릭터 이미지 순서를 바꾸는 화면은 **없다**(`CharacterImageStripController`: 탭=뷰어, 롱프레스=삭제).
  등재가 인덱스 방식의 약점으로 든 "순서 편집에 밀린다"는 **아직 일어나지 않은 위험**이고,
  실제로 일어난 위험은 **경로가 바뀌는 것**이다(1-3의 여섯 갈래 중 넷).
- `runCatching { File(p).canonicalPath }.getOrNull() ?: p`가 **여덟 곳에 복붙**돼 있다
  (`ImageOwnershipGuard`·`CharacterImageAutoLinker`·`StorageAnalyzer`·`OrganizeFolderService`·
  `ImageManagerViewModel` 등). 경로 대조의 단일 소스가 없다.

## 3. 결정 (D1~D9)

### D1. 저장 — 칸 하나. **모드 칸은 두지 않는다**

```kotlin
// data/model/Character.kt
val representativeImagePath: String = ""   // 빈 문자열 = 지정 없음(랜덤)
```

- **왜 `Universe.imageMode` 선례를 따르지 않는가.** 세계관·작품은 이미지의 **출처가 여럿**이라
  (자기 이미지 / 캐릭터 / 작품) 모드가 필요하다. 캐릭터의 이미지 출처는 **자기 것 하나뿐**이고
  선택지는 *고정했나 / 안 했나*뿐이다. 칸을 둘로 나누면 `mode=select`인데 포인터가 빈 상태가
  **표현 가능해지고**, 그 순간 두 칸이 서로를 부정한다(R-29가 경계하는 "잘못된 정답" 부류).
- 마이그레이션 **46→47**: `ALTER TABLE characters ADD COLUMN representativeImagePath TEXT NOT NULL DEFAULT ''`.
  하네스 `tools/verify_room_migration_47.py`를 함께 만든다(46판과 동형).
- **읽을 때는 `String?`로 받는다**(R-2) — 휴지통 payload·월드패키지는 Gson이 Unsafe로 객체를
  만들므로 **구버전 데이터에는 non-null 선언에도 null이 주입된다.** D2의 함수가 null과 빈 문자열을
  같게 다루면 그것으로 끝난다. `CharacterSnapshotPayloadTest`에 구버전 payload 사례를 더한다.

### D2. 판정 단일 소스 — `CharacterRepresentativeImage` (util, 순수)

```kotlin
object CharacterRepresentativeImage {
    enum class Source { PINNED, RANDOM, NONE }
    data class Pick(
        val path: String?,        // 표시할 경로 (없으면 null)
        val source: Source,
        val pinnedMissing: Boolean // 지정은 있는데 목록에 없다 — ㄷ1의 사후 고지 신호
    )
    fun pick(imagePathsJson: String?, representativePath: String?, seed: Long, characterId: Long): Pick
}
```

**사다리**
1. 지정한 대표가 **그 캐릭터의 목록 안에 있으면** 그것 (`PINNED`)
2. *(비어 있는 칸 — B-104가 채운다. D9)*
3. 시드 랜덤 (`RANDOM`)
4. 목록이 비었으면 없음 (`NONE`)

- **대조는 정규화 경로로 한다.** `ImagePathMatch.canonical(p)`를 util에 세우고 새 코드가 그것만 쓴다
  (1-4의 여덟 곳 복붙을 이 슬라이스에서 전부 걷어내지는 않는다 — 범위 밖이므로 **백로그 등재**. 5장).
- 순수 함수이므로 **순수 JVM 테스트 대상**이다(아키텍처 4장: 판단 로직은 `util`로 내린다).

### D3. 랜덤 주기 — **시드 하나 = 화면 진입 한 번.** 맵도 prefs도 쓰지 않는다

```
index = floorMod(mix(seed, characterId), paths.size)
```

| 요구 | 이 방식이 어떻게 만족하는가 |
|---|---|
| 화면 진입마다 다른 이미지 (ㄴ3) | 진입 때 새 시드를 뽑는다 |
| 같은 화면 안에서는 고정 | 시드가 같으면 결과가 같다 — 스크롤 재바인드·검색·필터·정렬·저장에 **튀지 않는다** |
| P2-1 제약 (O(N) 쓰기 금지) | **쓰기가 0이다.** 지금은 진입마다 prefs 전량 읽기(`loadAll`) + bind마다 쓰기가 있다 |
| 스테일 인덱스 위험 | 상태를 저장하지 않으므로 **없다** |

- **시드는 화면이 소유한다**(`onViewCreated`에서 1회 생성해 어댑터에 넘긴다).
  전역 싱글턴을 두지 않는 이유: 두 화면이 동시에 살아 있을 때 한쪽의 진입이 **다른 쪽 그림을 바꾼다.**
- **`ImageIndexPrefs`의 캐릭터 몫은 사라진다.** 작품·세계관 몫은 이 슬라이스 밖이라 **그대로 둔다**
  (백로그 등재 — 5장).
- **"화면 진입"의 정의:** 그 화면의 **뷰 생성**(`onViewCreated`). 회전 복원도 새 진입이다 —
  1-12의 수리가 이미 그 단위를 쓰고 있고, 사용자에게도 *"나갔다 들어오면 바뀐다"*가 설명 가능한 유일한 선이다.

### D4. 표시 자리 아홉 종류를 전부 D2로 바꾼다

| 자리 | 시드 소유자 | 바뀌는 것 |
|---|---|---|
| 캐릭터 목록 | `CharacterListFragment` | 인덱스 prefs → D2. 고정된 캐릭터는 언제나 그 장 |
| 생일 배너 | `HomeDashboardFragment` | `paths[0]` → D2. **사용자 요청 ①이 여기서 이뤄진다** |
| 상세 ViewPager | `CharacterDetailFragment` | 랜덤 시작 위치 → **대표가 있으면 대표에서 시작**, 없으면 랜덤(현행 유지) |
| 순위 카드 | 통계 화면 | `firstOrNull` → D2 (`RankingEntry`에 포인터 동승 — D8) |
| 통계 드릴다운 ×2 | 통계 화면 | 같음 |
| 어시스턴트 ×7 | 각 화면 | `firstImagePath()` → D2 |
| 중복 다이얼로그 | 그 다이얼로그 | 같음 |
| 세계관·작품 카드 연동 ×4 | 각 목록 | **연동 캐릭터의 대표를 존중한다** — 지금은 무조건 랜덤 |
| `CharacterDetailFragment:1055` | 그 화면 | 같음 |

> **`CharacterImageLoader.firstImagePath()`는 지운다.** 남겨 두면 다음 사람이 그것을 부르고,
> 그 화면만 다시 0번을 보여 준다 — 등재가 *"모으지 않으면 손댄 화면에서만 듣는다"*고 적은 그대로다.

### D5. 쓰기 정합 — 1-3의 열여섯 지점, 처분은 셋뿐

| 무슨 일이 일어나는가 | 대표를 어떻게 하는가 | 해당 지점 |
|---|---|---|
| 경로가 **바뀐다** | **따라서 고쳐 쓴다** | 이동·개명·되돌리기 · 폴더 왕복 편입 · 엑셀 재매핑 · 월드패키지 복원 |
| 경로가 **사라진다** | **비운다 + 고지**(ㄷ1) | 삭제 · 정리 · 폴더 왕복 제외 |
| 목록이 **통째로 바뀐다** | 대표가 새 목록에 없으면 비운다 + 고지 | 폼 저장(`CharacterSaveCoordinator`) |

- **전부 `imagePaths` 쓰기와 같은 트랜잭션에서 한다.** 빠뜨려도 오류는 나지 않고,
  포인터만 조용히 어긋난다 — **R-30이 등급 체계에서 배운 것과 같은 모양**이다
  (*"물질화는 원본 편집 경로의 목록을 함께 관리하는 일이다"*).
- **구현 세션은 이것을 규약으로 승격한다(제안 R-32):**
  *"목록을 가리키는 포인터는 그 목록을 고치는 모든 경로가 함께 고친다."*
  승격 시 갱신할 곳 셋 — `conventions.md` 원문 · 아키텍처 6장 색인 · 세션 로그 근거.

> 삭제하시겠습니까?

(둘 이상이면 `캐릭터 %1$d명의 대표 이미지입니다`.) 편집 화면 스트립의 롱프레스 삭제도 같은 문장을 쓴다.

**ⓑ 사후 — 앱 밖 삭제·폴더 왕복·복원 (사전 고지가 불가능한 자리)**

D2가 `pinnedMissing`을 내면 **상세 화면에 인라인 고지**를 띄우고 **그 자리에서 고칠 경로**를 준다
(변수 제어: 검증 → 알림 → 바로잡을 경로).

> 대표로 지정한 이미지를 찾을 수 없어 랜덤 표시로 돌아갔습니다. 다른 이미지를 대표로 지정할 수 있습니다.

- **포인터를 조용히 지우지 않는다.** 사용자가 정한 것이고, **폴더 왕복은 파일을 되돌려 놓을 수 있다** —
  잠깐 안 보인다고 지우면 되돌아왔을 때 지정이 사라져 있다.
- 앱 **안**의 삭제는 파일이 영구히 사라지는 것을 아는 자리이므로 ⓐ에서 **비운다**(D5).

### D7. 지정 조작 — ☆ 한 번 (원칙 04)

| 자리 | 조작 | 왜 여기인가 |
|---|---|---|
| 상세 화면 이미지 위 ☆ | 탭 = 지금 보고 있는 그 장을 대표로. 다시 탭 = 해제 | 큰 그림을 보면서 고르는 자리다. **1탭** |
| 편집 스트립 썸네일 코너 ☆ | 같음 | 롱프레스(=삭제)와 탭(=뷰어)을 **건드리지 않는다** — 기존 제스처를 뺏지 않는다 |

- 대표인 장에는 ☆가 채워진 상태로 남아 **목록에서도 어느 것이 대표인지 보인다**
  (원칙 04: 일일이 확인하지 않으면 존재를 알 수 없는 데이터가 있어서는 안 된다).
- 새 설정 스위치가 아니므로 R-25 목적문 의무 대상은 아니다. 대신 **도움말 한 줄**을 상세 화면 `?`에 넣는다:
  *"대표로 지정한 이미지는 목록·배너·통계에서 언제나 그 장이 보입니다. 지정하지 않으면 화면에 들어올 때마다 무작위로 한 장이 보입니다."*

### D8. 엑셀·월드패키지 왕복 (ㄹ1)

**캐릭터 시트에 `대표이미지` 열 하나**(`이미지경로` 바로 뒤. `SheetSpec:469` 다음).
`CHARACTER_FIXED_HEADERS`(`SheetSpec:65`)와 `ExcelHeaderAliases`(`:32` 근처)에 함께 등재한다 —
**등재하지 않으면 커스텀 필드 열로 오인된다.**

- **내보내기:** 그 행의 이미지 중 **파일명**. 같은 행 안에서 파일명이 겹치면 **전체 경로**로 떨어진다.
  (`이미지경로`가 내부 경로 원문을 싣는 것과 달리, 이 열은 사람이 읽고 고칠 수 있어야 값어치가 있다.)
- **가져오기 사다리** — 거부가 아니라 수용·교정(개발 의도 4번):
  1. 그 행의 경로와 **정확히 일치**
  2. **재매핑된** 경로와 일치(`remapImagePath` 재사용 — 다른 기기에서 온 파일)
  3. 그 행 안에서 **유일한 파일명**
  4. **1부터 세는 번호**("2" → 두 번째 이미지)
  5. 그래도 못 찾으면 **경고 등재 + 기존 값 유지** — 버리지 않는다
- **빈 칸 = 해제**(앱의 기존 왕복 규약과 같다).
- 파일명 겹침 처리는 **이미 있는 판단을 따른다** — `ImageMetaRowResolver`가 "이미지" 시트에서
  같은 문제를 같은 방식으로 다룬다(겹치면 파일명만으로 확정하지 않고 알린다).
- **월드패키지:** `Character` 엔티티를 통째로 직렬화하므로 자동으로 실린다. 셋만 손댄다 —
  ① `WorldPackageContents`의 `allPresent(...)` 캐릭터 행에 추가(R-2)
  ② `WorldPackageImporter:362`에서 `imagePaths`와 **같은 재매핑**
  ③ **`CURRENT_SCHEMA_VERSION`은 올리지 않는다** — 4·5 두 번의 상향은 전부 **새 엔트리 파일 추가**였고,
  필드 추가로 올리면 구버전 앱이 **패키지 전체를 거부한다**(`schemaVersion > CURRENT` 검사).
  잃는 것이 "대표 한 칸"에서 "패키지 전체"로 커진다.
- **통계 스냅샷:** `RankingEntry`(`StatsDataProvider:508·3195`)와 드릴다운 스냅샷이
  `imagePaths`를 이미 나르므로 포인터도 **같이 나른다**(캐릭터당 짧은 문자열 하나. 순회 계산은 늘지 않는다).

### D9. B-104(대결)를 위해 비워 두는 칸

D2 사다리의 **①과 ③ 사이**가 그 자리다. 대결이 이미지 축 승자를 내면 **기본값 후보**로 ②에 들어간다.

- **호출부는 바뀌지 않는다** — D2 함수 하나만 고치면 아홉 종류가 동시에 따라온다. 이것이 ⓐ를 먼저 하는 이유다.
- **직접 고정이 이긴다**는 것은 B-104 행이 이미 확정한 사실이다(*"단 직접 고정이 이긴다"*).
- **지금 인자를 미리 만들지 않는다** — 쓰지 않는 인자는 방편식이다. 자리와 규칙만 여기 적어 둔다.

6. **의도 부합** — 아래 4단계 + 4질문. ✅

## 6. 적대 자기 검토 — 예상 반론과 답

| 반론 | 답 |
|---|---|
| **진입마다 바뀌면 "내 캐릭터 카드"를 눈으로 못 찾는다** | 그래서 대표 고정이 있고 **그것이 이 항목의 본체다.** 랜덤은 지정하지 않은 캐릭터의 기본값일 뿐이며, 그 동작은 지금도 그렇다(1-1) |
| **경로 저장은 파일이 움직이면 깨진다** (등재가 든 위험) | D5가 열여섯 지점을 전수로 든다. 앱이 모르게 깨지는 유일한 길은 **앱 밖에서 파일을 옮기는 것**이고, 그때는 `imagePaths` 자체가 이미 깨져 있다 — **대표만의 약점이 아니다.** 그 경우는 `pinnedMissing` → D6ⓑ가 받는다 |
| **인덱스가 더 싸지 않은가** | 인덱스는 **지금 있는 방식**이고 이미 스테일 위험을 안고 있다(`idx % paths.size`로 가려 둔 상태다 — 이미지가 줄면 **다른 그림을 가리킨다**). 사용자 확정(ㄱ1)이기도 하다 |
| **시드 방식은 진짜 랜덤이 아니다** | 필요한 성질은 "진입마다 다르고, 진입 안에서는 같다"이다. 균등성은 시드·id 혼합 품질이 정하며 **순수 테스트로 분포를 고정한다**(같은 시드에서 캐릭터마다 독립적일 것) |
| **☆가 이미지 탭 제스처를 가린다** | 코너에 두고 크기·터치 영역을 규격으로 정한다. 이미 `imageCountBadge`가 같은 자리에 겹쳐 있다. **자동 검증이 못 보는 축이므로 실기기 확인 항목이다**(착수 규칙 4번) |
| **엑셀 파일명 기준은 겹치면 틀린다** | 겹치면 내보내기가 **전체 경로로 떨어지고**, 가져오기는 "그 행 안에서 유일할 때만" 파일명을 쓴다. 못 찾으면 버리지 않고 **경고 + 기존 값 유지** |
| **대표를 "이미지" 시트(라이브러리 meta)에 두면 안 되나** | 안 된다. 그 시트는 **파일 단위 전역**이고 대표는 **(캐릭터, 이미지) 관계**다. 한 파일을 두 캐릭터가 쓰면 표현할 자리가 없다 |
| **휴지통에서 되살리면 대표가 사라지지 않나** | payload가 엔티티 통째이고 복원이 `copy()`라 함께 돌아온다(`TrashRepository:1600`). 구버전 payload는 D1의 `String?` 취급이 받는다(R-2) |
| **`ImageIndexPrefs`를 캐릭터에서만 걷어내면 절반만 정리된 것 아닌가** | 그렇다. 작품·세계관 몫은 **이 슬라이스 밖**이라 백로그에 올린다(착수 규칙 2번: 밖이면 등재만 하고 진행) |

5. 폴더 왕복으로 이미지를 내보냈다 되받은 뒤 대표가 유지되는가
6. 엑셀 내보내기 → `대표이미지` 열을 다른 이름으로 고쳐 가져오기 → 경고가 뜨고 기존 값이 남는가
7. 상세 ☆ 토글이 이미지 탭·스와이프를 방해하지 않는가

## 8. P-3 — **확정 (2026.08.03, 사용자 확정 "같은 주기")**

확정 문서 3장의 **P-3**: *"ㄴ3(화면 진입마다 랜덤)이 목록에서도 매번 바뀌는가."*

**답:** **같은 주기를 쓴다 — 화면 진입 1회 재추첨, 그 화면 안에서는 고정.**
목록·배너·상세가 **한 규칙**을 쓴다. **이로써 이 설계를 막는 판정은 남아 있지 않다.**

근거 셋:
1. **목록은 이미 그렇게 동작한다**(1-1·1-2). 사용자가 고른 ㄴ3과 현행 목록 동작이 **이미 일치한다.**
2. 매 바인드마다 다시 뽑으면 **스크롤할 때 그림이 깜빡인다** — 등재 자신이 ③에서 그것을 경계했다.
3. 방출마다 다시 뽑는 것은 **P2-1이 성능 때문에 없앤 바로 그 동작**이다(세션 로그 1-12).

→ **사용자가 이 답을 확정했다**(2026.08.03). 확정 문서 3장의 P-3은 해소됐고,
**D3이 그대로 선다** — 시드 하나 = 화면 진입 한 번.

> **묻는 방식이 답을 만들었다.** 선택지 셋을 나열만 하지 않고 **현행 동작을 실측해 함께 냈다** —
> *"캐릭터 목록은 이미 그렇게 돌고 있습니다"*가 근거의 첫 줄이었다. 확정 문서 3장이
> 이 방식을 파생 판정을 묻는 본보기로 등재했다.
