# 사건 필드 — 추천에서 고르기 (설계)

> **상태: 초안 — 내장 세트 내용과 도움말 본문은 사용자 판정 대기.**
> 방향 둘은 확정됐다(2026.08.01 사용자): **자동으로 심지 않고 추천만** · **이번에는 사건 축만
> 켜되 구조는 축 중립**. B-62를 해소할 설계이며, 착수는 이 문서 7장 절차를 따른다.

## 2. 진단 — 셋이 겹쳐 있다

- **① 의미** — '사건 필드'가 무엇이고 만들면 어디에 나타나는지 아는 자리가 안내문 한 줄뿐이다.
- **② 경우의 수** — 무엇을 만들 수 있는지 단서가 0이고, 버튼은 **빈 캔버스**를 연다.
  사용자 회신(2026.08.01): *"'사건 필드'만 딱 보고는 뇌정지가 온다."*
- **③ 재고** — 항상 0개에서 출발한다. 캐릭터는 프리셋에서 수십 개를 **받는데** 사건은 손으로 만든다.

**③이 근본이다.** 실사용의 90:0은 취향이 아니라 이 경사의 결과다(B-62의 진단 그대로).
그래서 **①만 고치면 안 된다** — 읽고 나서도 작업량이 그대로라 도움말은 구색이 된다.

## 3. 결정

### D1. 추천은 '고르는 것'이지 심는 것이 아니다 (확정)

새 세계관에 사건 필드를 **자동으로 심지 않는다.** 모든 새 세계관이 받는 기본값은 자율성
침해이고(개발 의도 3), 되돌리기 어렵다. 추천은 **보여 주고 고르게** 한다.

### D2. 추천 목록의 출처 — 새 저장 구조를 만들지 않는다 (확정)

> **추천 목록 = 내장 프리셋의 사건 필드 ∪ 사용자의 다른 세계관 사건 필드**

- 코드 상수 목록은 **쓰지 않는다.** 닫힌 프리셋이라 원칙 01 정면 위반이고 사용자가 못 고친다.
- 내장 프리셋에 넣으면 **이미 추가·편집·삭제가 되고** 엑셀·월드패키지로 오간다.
- 다른 세계관 몫은 '필드 가져오기'가 이미 하는 일이다(P5가 종류 구분까지 고쳤다) — 원칙 05.
- 두 출처는 **합집합**이라 서로 충돌하지 않는다. 같은 `key`가 겹치면 **세계관 쪽을 우선**해
  보여 준다(내 데이터가 내장값보다 나를 잘 안다).

### D3. 각 추천 항목은 이름·타입만이 아니라 **설명과 값까지** 들고 온다 (확정)

`config`의 `description`(ⓘ)과 선택지·등급표를 함께 싣는다. "추천값까지 안내"의 실체가 이것이고,
도착한 뒤 무엇을 적어야 하는지를 **그 자리에서** 말한다.

### D4. 두 경로를 준다 — 러프 / 정밀 (확정, 원칙 03)

- **러프:** 목록에서 여러 개 체크 → **한 번에 생성**.
- **정밀:** 항목 하나를 골라 **채워진 채로 필드 편집 창을 연다** → 다듬어 저장.

### D5. 구조는 축 중립으로, 배선은 사건만 (확정)

고르는 화면은 `entityType`을 인자로 받는다. **캐릭터 축에는 이번에 켜지 않는다** — 근거는
6장 반론 3. 나중에 켜는 비용은 배선 한 줄이다.

### D6. 도움말 주제 신설 (H15 — 본문 승인 후 등재)

`?`로 여는 '사건 필드' 주제. `HelpDialog.Topic`이 **"새 주제는 본문 승인 후에만 등재한다"**를
규칙으로 갖고 있으므로 초안은 `text_style_guide_2026-07.md` **9-2**에 먼저 쓴다(H14 선례).

### D7. 선행 조건 둘 — 안 고치면 그대로 구색이 된다

- **B-68**: 사건 편집만 '값 사전 등록'을 안 받는다. D3의 값이 **조용히 사라진다.**
  고치는 자리는 `EventEditDialogFragment`의 결과 수신부이며, B-68이 남긴 판정
  (인터페이스 3구현을 고칠 것인가 / 다이얼로그가 직접 심을 것인가)을 먼저 답한다.
- **프리필 인자 분리**: 지금 `newInstance`에 `field`를 넘기면 편집 모드가 되어 제목이 틀리고
  `stagedInitialValues`가 채워지지 않는다(1장 실측). **'미리 채우되 생성 모드'** 인자가 필요하다.

## 4. 화면

**사건 편집 창 맨 아래, 현행 셋 사이에 하나가 는다.**

```
사건 필드
이 세계관에는 사건 필드가 없습니다. 추가하면 사건 편집 폼과 연표 카드,
통계 교차분석에 함께 나타납니다.                                    [?]
   [ 추천에서 고르기 ]   [ 사건 필드 추가 ]
```

- `?`는 D6의 도움말(H15).
- **추천이 먼저다** — 빈 캔버스보다 고르는 쪽이 값싸다. 필드가 이미 있어도 둘 다 남긴다
  (하나 더 필요할 수 있다 — 현행 주석이 이미 그 이유로 버튼을 항상 남긴다).
- 고르는 화면은 체크 목록 + 각 항목에 **이름 · 타입 · 설명 한 줄**. 이미 있는 `key`는
  **비활성 + 사유**(조용히 빼지 않는다 — 변수 제어).

## 5. 새 기능 체크리스트 판정 (CLAUDE.md 7항목)

① **확장성** — 추천은 프리셋이므로 사용자가 편집·추가·삭제할 수 있다. 닫힌 목록이 아니다.
② **실질성** — 재고 0을 실제로 없앤다. 도움말만으로는 작업량이 안 주는데 D4가 그것을 줄인다.
③ **완결성** — 새 저장 구조 0. **선행 조건 둘(D7)을 함께 처리한다** — 안 하면 값이 사라지는
방편식이 된다. ④ **연결성** — 프리셋·필드 가져오기·값 라이브러리·ⓘ 설명 넷을 그대로 쓴다.
⑤ **조작성** — 빈 캔버스 → 체크 한 번. ⑥ **의도 부합**(`scalability` 7장 4단계): **새 상한
없음** / 비용 축 = 사건 필드 수(현재 0, 목표 규모에서도 캐릭터 필드값의 4% 미만 — 1-q-3 실측)
/ **스냅샷 무관** / **엑셀 왕복 무변경**(필드 정의 시트가 이미 `대상` 열로 사건을 싣는다).
⑦ **텍스트** — H15 본문 승인 후 등재, 추천 항목의 설명도 스타일 가이드를 따른다.

## 6. 적대 자기 검토

**반론 1. "추천 목록도 결국 누가 정한 고정 목록 아닌가?"**
→ 출처가 **프리셋**이라 사용자가 고치고 지우고 늘릴 수 있다. 코드 상수였다면 맞는 반론이다.
그래서 D2가 상수 목록을 명시적으로 금지한다.

**반론 2. "도움말(H15)만 넣으면 싸게 끝나지 않나?"**
→ 그러면 ③(재고 0)이 그대로다. 읽고 나서도 빈 캔버스가 기다린다. **이 설계에서 도움말은
보조이지 본체가 아니다.**

**반론 3. "캐릭터 축에도 같이 넣는 게 짝 아닌가?"**
→ 아니다. ① 두 축의 문제가 정반대다 — 사건은 재고 0, 캐릭터는 **90개인데 채움률 21.7%**다.
캐릭터에서 그 UI가 하는 말은 "필드를 더 만드세요"이고, 그건 방향이 반대다.
② 캐릭터의 실제 결함은 추천 부재가 아니라 **프리셋이 기존 세계관에 못 붙는 것**이다
(`applyPreset`이 세계관을 새로 만든다 → **B-89**). 추천을 캐릭터에 붙이면 그 결함을 **우회**하는
세 번째 경로가 생기고, 셋이 같은 일을 조금씩 다르게 하다 갈린다.
③ **R-16을 근거로 쓸 수 없다** — 원문은 계산 필드 규약이고, 취지는 "고를 수 있는데 조용히
안 되는 자리를 만들지 마라"다. 사건에만 추천을 넣어도 캐릭터 쪽에 그런 자리는 안 생긴다.
→ 그래서 D5(구조는 축 중립, 배선은 사건만). 켜는 비용을 0으로 남겨 둔다.

**반론 4. "이미 있는 `key`를 또 고르면?"**
→ 비활성 + 사유 표시. 조용히 빼면 "왜 없지"가 되고, 그냥 두면 중복 생성이 실패한다
(`SQLiteConstraintException` — 현행 `createEventField`가 이미 그 갈래를 갖고 있다).

**반론 5. "작품을 안 고르면 추천도 못 보나?"**
→ 못 본다. 세계관을 모르면 어디에 만들지 모르기 때문이고, 현행 버튼과 같은 규칙이다.
다만 **그 사실을 말해야 한다** — 지금은 섹션이 통째로 숨는다(B-31 부류). 문구는 H15와 함께 정한다.

## 7. 착수 절차

1. `remaining_work` 5장 규칙대로 기준선 재현 후 시작. **DB 스키마 무변경 · 엑셀 왕복 무변경** —
   마이그레이션 하네스 불요, 차분 컴파일은 필수(다이얼로그 신설 + 사건 편집 배선).
2. 순서: **① B-68 해소(판정 먼저)** → ② 프리필 인자 분리 → ③ 내장 프리셋에 사건 필드 등재
   (8장 승인본) → ④ 추천 목록 조립(프리셋 ∪ 타 세계관, `key` 중복 처리) → ⑤ 고르는 화면
   (축 중립 인자) → ⑥ 사건 편집 배선 + `?`(H15) → ⑦ 문구·목적문 → ⑧ 실기기 확인 절 신설(3장).
3. 백로그 갱신: **B-62 해소 표시**, B-68 처리 기록, B-89·B-90 상태 확인.

## 8. 내장 세트 초안 — **판정 대기**

작품 성격을 아는 쪽은 사용자이므로 **이 표가 승인 대상**이다. 여섯을 넘기지 않았다 —
추천이 길면 그것대로 또 뇌정지이고, 늘리는 것은 언제든 되지만 기본이 많으면 지우는 일이 는다.

| 이름 | 타입 | 값·설정 | 설명(ⓘ에 실린다) |
|---|---|---|---|
| 회차 | NUMBER | — | 이 사건이 몇 화·몇 장에 나오는가. 집필·연재 단위로 사건을 묶을 때 씁니다 |
| 장소 | TEXT | 값 라이브러리 연동 | 사건이 벌어지는 곳. 값이 쌓이면 장소별 분포를 볼 수 있습니다 |
| 시점 인물 | TEXT | — | 이 사건을 누구의 시점으로 서술하는가 |
| 이야기 단계 | SELECT | 도입 / 전개 / 절정 / 결말 | 전체 흐름에서 이 사건이 놓인 자리 |
| 중요도 | GRADE | C 0.5 · B 1 · A 2 · S 3 | 줄일 수 없는 사건인지 곁가지인지 |
| 공개 상태 | SELECT | 공개 / 복선 / 비공개 | 독자가 지금 이 사건을 아는가 |

**함께 정할 것 둘**
- **프리셋별로 다르게 할 것인가** — 별님대모험 ↔ 천칭의 마법사. 추천 목록이 **합집합**이므로
  다르게 두어도 충돌하지 않는다(둘 다 보인다). 권고는 **공통 코어 여섯을 양쪽에 같게** 두고,
  색깔이 필요해지면 그때 한쪽에만 더하는 것이다.
- **'중요도'를 등급으로 둘 것인가** — U-1(세계관 등급 체계)이 들어와 있어 등급 체계를
  참조하게 할 수도 있다. 다만 프리셋이 체계까지 만들지는 않으므로(복사 경계 강등, R-30)
  **독자 표로 두는 것**을 권고한다.
