# AI 창작 입력·검토 개선 실행 계획

기준: `origin/master` 398c6be61b1f3d0313072f06e6f1984102f6bdd9 (2026-09-08).
요구사항: 사용자가 제공한 「AI 창작 UX 및 음성 입력 개선」. 이 문서는 이번 구현의 계획과 검증 범위이며 기존 제품·규약 정본을 대체하지 않는다.

## 조사 결과와 설계 기준

- Android/Kotlin, ViewBinding, Fragment와 AndroidViewModel, Room v58. 도메인 저장 형식 변경은 필요 없다.
- 캐릭터 필드 추천·사건 추천은 `CharacterFieldAiSuggester`의 청킹·검증·결손 처리를 공유한다. 직접 수정도 `normalizeChecked`를 사용해야 한다. 적용은 기존 폼과 저장 가드(제한 라이브러리·별칭·생일·구조화·시스템 연동)를 통과한다.
- `AiFieldSuggestSheet`에 직접 수정은 있으나 보완 창 안에 숨었다. 재요청은 다른 선택분을 먼저 폼에 적용하고 기존 결과를 지워, 검토와 적용을 섞는다. 선택·수정 상태를 유지하는 부분 병합으로 바꾼다.
- `CharacterAiContextBuilder`는 저장 DB만이 아니라 **현재 폼 입력**도 읽는다. 이를 확정 DB라고 잘못 표시하지 않는다. 기존 정보와 새 브리핑은 별도 자료 블록으로 전달한다.
- 서술형 단건은 160자 미리보기를 눌러 바로 적용하며, 일괄도 짧은 미리보기만 제공한다. 전체 후보와 직접 수정 내용을 ViewModel이 들도록 한다.
- 이름 추천에는 라운드·유지·회피·자유 지시가 이미 있다. 음성 컴포넌트는 이를 대체하지 않는 별도 자연어 입력 경계다.
- `AiService`는 텍스트 생성 관문이다. STT는 음성 파일·시간·인식 기능 지원 여부가 달라 별도 전사 서비스로 두고 `AiKeyStore`의 키 암호화 원칙을 재사용한다.

## 공통 불변식

1. AI/STT 응답은 검토 자료다. 명시적으로 고른 값만 폼에 적용하고 DB 저장은 기존 저장 흐름이 맡는다.
2. 직접 수정은 무료이며 같은 결과에서 다른 선택·수정값을 보존한다. AI 보완은 요청 수를 미리 알리고 대상만 보낸다. 실패하면 이전 후보가 남는다.
3. 원문 근거는 실제 브리핑의 정확한 부분 문자열만 인정한다. AI 메모는 검증·confidence의 근거가 아니며 사용자가 명시적으로 합칠 수 있다.
4. DB 메모·필드·산문은 data/context다. 내용 안의 명령문을 시스템 지시로 승격하지 않는다. 부정·추측·범위·정도·자기 정정의 흔적을 전사 단계에서 임의로 다시 쓰지 않는다.
5. 결과·수정·선택·진행 상태는 뷰 밖에서 유지한다. 회전 중 새 호출을 시작하지 않으며, 실패·취소·누락을 고지한다. 받은 응답과 검토 상태는 기기의 백업 제외 영역에 체크포인트로 보관한다. 복구 시 유료 요청을 자동 재실행하지 않는다.
6. 음성 전송은 사용자가 고른 서비스로만 한다. 키는 암호화 저장소 외에 저장하지 않는다. 음성 임시 파일은 앱 전용 영역에서만 읽고 수명·삭제를 관리한다.

## STT 방식 조사 (2026-09-08 공식 문서)

- [OpenAI file transcription](https://developers.openai.com/api/docs/guides/speech-to-text): 전사 전용 API, m4a 등 파일 입력, 25 MB 제한, 고유명사 prompt 지원. 최신 문서에는 `gpt-transcribe` 및 keywords/languages 지원이 있으며 기존 `gpt-4o-transcribe`도 prompt를 지원한다. 모델·URL은 사용자가 선택/편집할 수 있게 하고 지원 차이를 명시한다.
- [Groq speech to text](https://console.groq.com/docs/speech-to-text): OpenAI 호환 파일 전사, Whisper 모델과 용어 prompt(224 tokens). 한 프로토콜을 공유하되 문자 수를 토큰 수라고 주장하지 않는다. 전사 모델 설정과 힌트 예산을 따로 둔다.
- [Google Chirp 3](https://docs.cloud.google.com/speech-to-text/docs/models/chirp-3): 고유명사 adaptation이 유용하지만 Cloud project/region/인증 체계가 기존 BYOK보다 복잡하다. 현재 앱에서 우선 연결할 방식은 파일 전사 호환 API다. 한국어/조어 실측 없이 품질 순위를 단정하지 않는다.
- [Android SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer), [RecognizerIntent](https://developer.android.com/reference/android/speech/RecognizerIntent): API 31+ 온디바이스 가용성 확인, API 33+ biasing strings. 일반 기본 인식은 원격 서버를 사용할 수 있으므로 이를 오프라인으로 표시하지 않는다. 기기 지원 여부가 다른 온디바이스 경로는 선택적 보조 경로다.

문맥 어휘는 현재 이름/이명→관련 인물·세력→현재 필드/관련 라이브러리 순으로 고르고 제한과 제외 수를 표시한다. 이름 은행·DB 전체를 무차별로 전송하지 않는다. 원문은 항상 보존하고 교정은 정확한 후보와 연결된 제안으로 보여 준다. 통문장 재작성용 LLM 후처리는 사용하지 않는다.

- Android SDK / JDK 17 / Gradle 8.11.1에서 `assembleDebug` 성공. 정적 검사와 스키마 하네스의 최종 판정은 Linux PR CI에서 확인한다.
- 실제 마이크·권한 UI·온디바이스 가용성·유료 전사 품질은 기기와 API 키가 없어 미확인이다. 테스트의 permission/rotation 항목은 순수 상태와 ViewModel 배선 검증이며 실제 화면 회전 계측 통과를 뜻하지 않는다.

## 실제 보존 범위와 운영 제약

ViewModel은 화면 회전 동안 진행 중 요청을 유지한다. 받은 캐릭터/사건 추천과 단건/일괄 서술형, 첫 AI 원본·미완성 편집·선택·보완 지시·전사 원문/수정본은 `noBackupFilesDir/creative-reviews`에 보관한다. 같은 대상의 AI 버튼 또는 같은 입력의 마이크를 다시 누르면 공급자 설정 확인이나 새 요청보다 먼저 복구한다. 신규 미저장 대상의 AI 결과 검토는 기존 편집 드래프트처럼 -1 슬롯 하나를 사용하며 요청 당시 이름과 원문을 표시한다. 신규 캐릭터의 Creator Brief와 그 음성 입력은 아래 안정화 M1의 독립 식별자를 사용한다. 다른 대상의 서술형 결과는 적용하지 못한다.

`ReviewJournal`은 버전/소유자/체크섬을 검사하고 파일 동기화 후 원자적으로 교체한다. 다른 편집 창의 최신 기록은 이전 리비전으로 덮어쓰거나 지울 수 없다. 손상·지원하지 않는 버전·저장 실패는 고지하고 원본 파일을 남기며 새 유료 요청을 시작하지 않는다. 저장 형식을 바꾸는 후속 변경은 버전과 호환 경로도 함께 바꿔야 한다. 창의 닫기/뒤로 가기는 보관이고, 적용 성공 또는 명시적 버리기는 해당 검토 및 관련 보완 입력/전사 기록을 정리한다. API 키와 녹음 바이트는 이 기록에 넣지 않으며 Excel/자동 백업 대상도 아니다. 앱 삭제·데이터 삭제 시 기록은 사라진다.

짧은 필드 추천은 청크마다, 일괄 서술형은 필드 응답마다 다음 요청 전에 저장한다. 서술형 일괄은 아직 보내지 않은 ID만 선택해 이어 요청하며 성공한 후보·수정·선택을 그대로 둔다. 전송 직전 별도 상태를 기록하므로 요청 도중 종료된 필드는 미요청과 구분하고 사용량 확인 후 사용자가 재요청하도록 한다. 앱 강제 종료/편집 화면의 ViewModel 종료는 진행 중 통신을 끊을 수 있으며 **서버에서 생성했지만 앱이 받지 못한 응답의 복구는 보장하지 않는다**. 복구 자체는 네트워크를 호출하지 않는다.

파일 전사 녹음은 안정화 M2의 백업 제외 전용 저장소에서 복구한다. 앱 시작·화면 종료·전사 성공만으로 삭제하지 않는다. 구버전 캐시 파일도 내용을 확인한 전용 복사본을 만든 뒤 보존하며, 원래 대상을 추측해 연결하지 않는다.

외부 전사는 HTTPS 파일 전사만 사용하고 제공자 자동 전환·리디렉션·자동 재시도를 하지 않는다. 요청 후 네트워크가 끊기면 서버의 과금 여부는 앱이 확정할 수 없으므로 재시도 전에 이를 알린다. 외부 전사용 녹음은 아래 안정화 M3의 20 MB 전송 예산 기반 최대 약 40분을 사용한다. 전사 실패·취소·앱 종료 뒤에도 보관 파일을 명시적으로 재전사할 수 있으며, 결과를 확인해 입력에 추가하거나 직접 버린 뒤 원본을 정리한다. 삭제 실패는 완료된 처리 기록을 남기고 다음 복구 목록에서 정리를 재시도한다.

설정의 `speech_config`는 Excel 앱 설정으로 왕복한다. 키는 기존 별도 동의 규칙을 유지하고, 음성 파일·전사·기기 사용량은 설정 행에 넣지 않는다.

## 실사용 안정화 M1 — 입력·음성 식별과 중복 전달 방지

PR #402 이후 실기기 요구사항의 첫 구현 단위다. 위 최초 구현 M1–M7과 번호 체계가 다르다.

- 전사 세션마다 ID를 부여한다. 최종 입력, 수신한 세션 ID, 전사 원문과 당시 최종 수정본을 같은 journal payload에 원자적으로 저장한 뒤 음성 창의 기록을 정리한다. 저장 후 정리 전 종료·정리 실패·중복 전달에도 같은 세션은 한 번만 추가된다. 내용이 같은 별도 녹음은 각각 추가되며, 사용자가 이후 Brief를 지워도 옛 세션이 다시 삽입되지 않는다.
- 구버전 입력 payload의 새 속성은 nullable로 읽는다. 구버전 전사에는 전달 전에 ID를 저장한다. 전달 시 입력과 음성 양쪽의 기존 revision/lease를 확인해 다른 편집 창의 최신 수정을 이전 창이 소비하거나 덮어쓰지 못한다.
- 새 캐릭터 편집 화면의 Creator Brief는 `briefing:draft:<UUID>`를 사용한다. 선택은 `SavedStateHandle`로 회전·시스템 상태 복원을 잇고, 입력/전사는 journal에 보관한다. 새 편집 화면은 새 구상으로 시작한다. “다른 구상·보관한 전사 열기”에서 이전 구상의 내용을 확인하고 명시적으로 이어 사용할 수 있다. 옛 `briefing:-1`도 삭제하거나 새 캐릭터에 자동 연결하지 않는다. 글이 아직 없는 구상도 먼저 기록해 보관한 전사를 찾을 수 있게 한다.
- 캐릭터 폼 드래프트·Room·Excel 형식은 바꾸지 않는다. 새 Brief 식별자를 폼 전체의 식별자로 주장하지 않는다. AI 검토 세션의 신규 대상 귀속과 늦은 AI 보완 응답 제어는 안정화 M5에서 다룬다.
- 보관한 원문·최종본의 긴 비교 UI는 안정화 M7 범위다. 녹음 바이트 수명은 아래 M2에서 바꾸며, background/화면 잠금 안전성(M3)은 후속 범위다.

자동 검증은 `CreativeInputStateTest`의 순수 상태·실제 journal 왕복과 `CreativeInputDeliveryTest`의 Android ViewModel/slot 연결로 나눈다. 후자는 실제 프로세스를 죽이지 않고 저장 경계에서 객체를 재생성하는 계측 시험이며, 마이크·유료 API·실기기 종료 시험을 대신하지 않는다. PR CI의 Android API 26 계측 실행에 포함된다.

기기에서는 새 구상 A/B 분리, 이전 버전 구상의 명시적 복구, 회전·프로세스 종료 후 같은 구상 선택, 전사 추가 연타와 추가 직후 종료, 서로 다른 두 녹음 연속 추가를 확인한다. 원문과 최종본 중 최종본만 Brief에 들어가야 한다.

## 실사용 안정화 M2 — pending audio 보존·재전사

M1의 세션 식별과 수신 기록을 재사용한다. 녹음 바이트는 `noBackupFilesDir/pending-voice/audio`, 메타데이터는 같은 영역의 `records` journal에 보관한다. 새 메타데이터 형식은 version 1이며, 녹음 ID·입력 소유자·상태·시작 시각·종료된 음성의 길이·크기·SHA-256·전사 시도 ID·제공자/모델 참조·받은 전사 checkpoint를 가진다. 키는 넣지 않는다. 경로는 검증한 UUID에서 계산하고 심볼릭 링크·상위 경로를 거부한다.

- 녹음 생성 전에 소유자 메타데이터를 저장한다. 정상 종료 뒤 audio track과 duration을 확인하고 파일 동기화·체크섬을 기록한다. 재전사 전 크기·체크섬을 확인한다. RECORDING/INTERRUPTED 파일도 지우지 않고 복구 목록에 표시하지만, 단순히 파일이 존재한다고 재생 가능한 것으로 판정하지 않는다.
- 전송 전 TRANSCRIBING과 새 attempt ID를 기록한다. 실패·취소·provider 변경 재시도는 같은 파일을 유지한다. OkHttp 취소는 기존 AiService와 같은 enqueue/cancellation 방식으로 연결한다. 복구는 자동 마이크 시작·자동 요청을 하지 않는다.
- 성공 응답과 사용자 수정은 기존 voice slot에 남기며 audio도 유지한다. 재전사가 실패하면 앞의 원문·수정본이 남는다. 입력의 영속 수신 확인 또는 명시적 버리기 후 RELEASED를 먼저 기록하고 파일→메타데이터 순서로 정리한다. 정리 실패·종료 뒤 RELEASED 파일을 다시 전사하지 않는다.
- 메인 화면의 “보관한 녹음”에서 원래 입력과 녹음·전사를 연다. 입력에 추가해도 도메인 DB 저장은 하지 않는다. 대상 없는 파일·불완전 복사·손상 메타데이터도 숨기거나 나이만으로 지우지 않는다. 읽을 수 있는 대상 미상 파일은 사용자가 선택한 경우 새 독립 구상으로 복구한다. 구버전 캐시의 원본은 전용 복사본과 SHA-256이 일치한 뒤에만 제거한다.
- 실제 녹음 중 무통지 kill로 손상된 m4a의 유효 prefix 보장, microphone FGS, 화면 잠금/전화/route 안전성, 한도 개선은 M3 범위다. 현재 M2는 정상 종료된 파일의 수명과 복구를 개선한다. 온디바이스 SpeechRecognizer에는 앱 소유 audio 파일이 없으므로 이 파일 복구 계약을 적용했다고 주장하지 않는다.

자동 시험: `PendingAudioStoreTest`는 실제 파일 왕복·실패·stale revision·경로·orphan·release/cleanup 순서를 검사한다. `PendingAudioDeliveryTest`는 실제 Android ViewModel과 저장소에 가짜 전사 서비스를 연결해 실패 종류·취소·재생성·provider 변경·확인 후 정리를 검사한다. `PendingAudioContainerTest`는 플랫폼 AAC encoder/muxer로 합성 음성을 만들어 파일 보존과 audio track/duration을 검사한다. 실제 마이크 녹음·강제 종료·실기기 decode 품질은 별도 확인이 필요하다.

## 실사용 안정화 M3 — 서비스 녹음과 중단 복구

외부 전사용 녹음은 `VoiceRecordingService`가 소유한다. 보이는 화면에서 사용자가 시작하고 마이크 권한이 있을 때만 microphone foreground service를 시작한다. 알림·화면의 중지는 같은 세션 ID를 확인한다. 홈·회전·편집 화면 소멸은 서비스를 종료하지 않는다. 알림 중지, 복구, 서비스 재시작은 전사 요청을 만들지 않는다. START_NOT_STICKY와 프로세스 내 시작 예약으로 재시작/재전달에 의한 자동 마이크 시작을 막는다. 알림이 차단되어 있으면 시작 화면에서 중지 경로가 앱의 보관 목록임을 고지한다.

- M2의 journal/UUID/lease/release를 재사용한다. 구버전 m4a·수신 영수증은 유지하며 Room·Excel·custom AI prompt는 바꾸지 않는다. nullable `captureFormat/checkpointBytes/interruption`만 추가한다.
- `PcmCapture`는 16 kHz mono PCM16 LE를 전용 원본에 기록한다. 오디오 약 1초마다 fd.sync → journal checkpoint 순서로 저장한다. 화면과 알림의 길이는 타이머가 아니라 실제 PCM 프레임에서 계산한다. 파일에 아직 쓰지 못한 마이크 버퍼·전원 차단 직전 구간까지 보장하지 않는다.
- 정상 종료는 CAPTURED, 확인한 인터럽트는 INTERRUPTED이다. 무통지 kill은 RECORDING과 마지막 checkpoint가 남는다. 복구는 파일에 남은 완전한 2바이트 프레임 전체를 변환하며, checkpoint 이후의 완전한 구간도 포함한다. 불완전한 마지막 1바이트까지 PCM 원본에서 삭제하지 않는다.
- `PcmEncoding`은 명시적 전사 때만 IO 스레드에서 AAC/m4a를 만든다. encoding 임시 파일 → 실제 media duration 검사 → 원자적 교체 → M2 READY 기록 순서다. 원본 PCM은 입력의 영속 수신 또는 명시적 버리기 전까지 남는다. 변환 실패·취소·journal 충돌 시 파일을 지우지 않는다. 취소 중 IO가 아직 끝나지 않았으면 onCleared도 lease를 먼저 풀지 않는다.
- 사용자 중지·서비스 종료·AudioRecord 오류·5초간 프레임 미수신·통화/음소거·API 29+ client silencing에서 저장 가능한 prefix를 보관한다. route 변경만으로 실패시키지 않는다. 무음 샘플을 곧바로 오류로 판단하지 않는다. 전화·Bluetooth·OEM 배터리 정책의 실제 영향은 기기 확인 대상이다.
- 기존 20 MB 전송 한도와 AAC 64 kbps, 컨테이너 여유 0.8 MB로 최대 40분을 계산한다. 3분 전부터 남은 시간을 보여 주고 한도에서 보관 종료한다. 저장 공간도 변환 예상 용량을 남기기 전에 경고·종료한다. PCM 분당 약 1.9 MB와 별도 m4a 약 0.5 MB가 필요하다. 실제 변환 결과는 전송 직전 다시 크기를 검사한다. 사용자 제공자의 더 작은 한도·과금·timeout은 이 앱의 고정 한도만으로 보장할 수 없다. 유료 청킹·자동 이어 녹음은 하지 않는다.

**온디바이스 축은 미완료다.** 기존 API 31+ SpeechRecognizer 모드를 숨기거나 클라우드로 자동 전환하지 않는다. 화면 이탈·발화 종료 후 녹음 중 표시를 멈추며 결과 대기를 별도로 표시한다. 지연 안내 뒤에도 늦은 결과를 기다리고, 사용자가 직접 버리기로 취소할 수 있다. 임의 timeout으로 결과를 버리지 않는다. 그러나 이 인식기가 앱 소유 원본을 제공하는 것은 아니다. API 33의 EXTRA_AUDIO_SOURCE는 인식기 구현이 지원하지 않으면 무시하고 마이크를 열 수 있으므로, 미확인 경로를 파일 전사·process death 복구로 표시하지 않는다. API 31/33+ 실제 기기의 지원 판정과 제품 경로가 정해져야 이 축을 닫을 수 있다. 경고 문구만으로 M3 전체가 완료됐다고 간주하지 않는다.

자동 검증은 `PcmCaptureTest`의 미종료 prefix·저장 충돌·정리 순서, `PcmRecoveryTest`의 실제 AAC 인코딩/디코딩과 처음·중간·끝 주파수, `VoiceRecordingServiceTest`의 실제 Android 서비스/AudioRecord·ViewModel 소멸/재접속·서비스 종료·권한 거부·무지시 재시작을 포함한다. M1/M2 계측도 계속 실행한다. CI의 API 26은 최소 호환성, API 35는 target SDK의 서비스 제약을 검사한다. 에뮬레이터의 녹음 성공은 실제 마이크의 품질이나 화면 잠금·Bluetooth 통과를 뜻하지 않는다.

M3의 남은 실기기 gate:
대상은 사용자 회신 기준 갤럭시 노트20·Android 13(API 33)이며 온디바이스 인식 미지원이다. 이 기기에서는 외부 전사용 녹음과 미지원 고지·자동 전환 없음이 확인 대상이다. CI에도 API 33을 포함하되 실제 삼성 기기 검증을 대신하지 않는다.

1. 5–10분, 20분 이상, 37–40분 경고/종료를 녹음하고 앞·중간·끝의 실제 음성 및 decoded 길이 비교. 알림 허용/거부, 낮은 저장 공간도 포함한다.
2. 홈·화면 잠금·앱 전환·회전·편집 화면 종료·알림 중지에서 동일 ID와 캡처 길이 확인.
3. 정상 stop 후 kill, 녹음 중 무통지 kill, force-stop, 시스템 서비스 중지를 각각 실행하고 재실행 후 유효 음성 구간과 중단 고지 확인. 자동 마이크/유료 요청은 0건이어야 한다.
4. 전화 수신/통화, 마이크 경쟁/개인정보 토글, Bluetooth 연결/해제와 배터리 절약 정책에서 마지막 유효 발화를 비교.
5. API 31/33+ 온디바이스 지원과 파일 입력 계약을 확인한다. 지원 불명인 상태를 장시간 복구 성공으로 분류하지 않는다.

설계 근거: [Android microphone FGS 유형과 시작 전제](https://developer.android.com/develop/background-work/services/fgs/service-types), [마이크 공유와 silencing callback](https://developer.android.com/media/platform/sharing-audio-input), [RecognizerIntent의 오디오 입력 계약](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE).

## 기기에서 이어 확인할 시나리오

1. AI 연동 제공자를 등록하고 음성 설정에서 전사 모델 선택. 첫 캐릭터 추천과 단건/일괄 서술형에서 브리핑 없이 실행한 결과를 기존 흐름과 비교한다.
2. 마이크 권한 거부 후 직접 입력, 재허용, 영구 거부 시 앱 권한 설정 진입. 녹음 중 홈 이동·닫기·회전에서 마이크 해제와 이어 검토를 확인한다.
3. “귀족은 아니다. 키는 165~170 정도. 흑발, 아니 은발 후보로 생각 중”을 전사하고 원문 보존·교정 제안 선택·입력에 추가를 확인한다. 동명이인·조어·숫자·조사도 포함한다.
4. 전사 중 회전·창 닫기와 재열기, 네트워크 실패·401·429·지원 안 하는 모델, 같은 버튼 연타에서 중복 요청과 비용 고지를 확인한다.
5. 추천 두 항목을 수정·체크 해제한 뒤 다른 항목 하나/선택 묶음만 AI 보완. 일부 실패 후 기존 결과·체크·미완성 편집이 남는지 확인한다.
6. SELECT·GRADE·라이브러리 제한·별칭·생일·구조화 값의 직접 수정에서 기존 검증이 작동하는지, 저장 뒤 __birth와 의미 필드 동기화를 확인한다.
7. 작은 화면·큰 글꼴로 서술형 전체 글과 원문/후보를 비교하고 직접 수정·AI 보완·회전·선택 적용을 확인한다. 이어쓰기는 현재 폼 원문 뒤에 붙어야 한다.
8. 사건 편집에서도 같은 검토·수정·보완·적용 실패 복구를 확인한다. 다른 사건의 결과는 적용할 수 없어야 한다.
9. 음성 설정 Excel 내보내기/가져오기를 실제 파일로 수행하고, 키/녹음/전사/사용량이 `speech_config`에 실리지 않는지 확인한다.

10. 캐릭터/사건/단건·일괄 서술형 결과와 체크·편집을 만든 뒤 창을 닫고 편집 화면을 나갔다가 다시 연다. 앱을 강제 종료한 뒤에도 같은 대상의 AI 버튼에서 받은 결과와 수정본이 복원되며 새 요청이 나가지 않아야 한다.
11. 일괄 서술형 두 번째 응답 후 취소하고, 남은 항목 일부만 이어 요청한다. 성공한 앞 항목이 재요청되지 않고 후보·편집·체크가 유지되는지 확인한다. 요청 중 앱을 종료하면 진행 중이던 항목은 과금 가능성이 있는 중단 항목으로, 나머지는 미요청으로 표시되어야 한다.
12. 전사 결과를 수정한 뒤 앱 종료/재진입, 입력에 추가 직후 종료를 각각 확인한다. 같은 입력에서 원문과 수정본이 살아 있고 전사/추가가 자동 반복되지 않아야 한다. 검토 버리기는 해당 보완 입력/전사만 지우고 다른 검토를 남겨야 한다.
