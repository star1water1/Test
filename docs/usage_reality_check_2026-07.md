## 0. 표본 개요

**측정: 완료**

세계관 **9개** / 작품 **17개** / 캐릭터 **214명** / 커스텀 필드 **90개**(캐릭터 90, 사건 **0**) /

  = 그 세계관에 커스텀 필드 정의가 하나도 없다.
- 시트 구멍(`last+1 ≠ physical`)·헤더만 있는 시트 **0건** → (다) 참조 소실 후보 없음.

*내보내기 항목 체크: **전부 켬**(§7 Q0-a 회신). `앱 설정` 시트 존재(런북 2-3의 공짜 판별기)와도
일치한다.*
*표본 범위: **전체 내보내기**(§7 Q0-b 회신).*
→ 따라서 **시트 부재의 원인 (나)(항목 끔)와 (다)(참조 소실, 구멍 0건)가 모두 배제**되고, 남는 것은
(가) 그 기능을 쓰지 않았다 뿐이다. 아래 §2의 `❌ 미도달`은 전부 **확정**이며, 런북 10-3에 따라
**이 사용자 본인에 대해서는 단정형으로** 쓴다(다른 사용자로 일반화하지 않는다).

### 1-B. 값 라이브러리 `사용횟수`의 66% 오차 — 수확 축과 집계 축의 비대칭

**측정: 완료 · 코드 실독으로 원인 확정**

| 관측(실파일) | 값 |
|---|---|
| 라이브러리 엔트리 | 482 |
| `사용횟수 = 0` | **318 (66.0%)** |
| ├ 그 값이 **현재 캐릭터 필드값에 실재** | **318** |
| ├ 상태변화에만 실재 | 0 |
| └ 어디에도 없음(정상적인 과거 잔재) | **0** |
| `사용횟수 > 0`인데 현재 값에 없음 | 0 |
| 필드 34개 분포 | 전부 0 = **15** · 전부 비0 = **7** · **섞임 = 12** |

**원인 — 수확은 7경로, 집계는 5경로이고 겹치지 않는다.**

- 수확(`harvestUniverses`)은 **캐릭터 저장마다** 돈다(`CharacterRepository.kt:408`), 그리고
  월드패키지 임포트·휴지통 복원 2경로·엑셀 임포트·앱 최초 백필에서도 돈다.
  새 엔트리는 `FieldValueEntry(fieldDefinitionId, value)`로 삽입되므로 **`usageCount`는 기본값 0**이다.
- 집계(`recountUsage`)는 **앱 1회 백필**(`NovelCharacterApp.kt:133`, `field_library_seeded`
  플래그로 1회만) · **엑셀 임포트**(`ExcelImportService.kt:585`) · **그 필드의 라이브러리 목록
  화면 진입**(`FieldValueListFragment.kt:101`) · 값 이름변경/병합/AI 정리에서만 돈다.
- 즉 **일상 경로(캐릭터 저장)에는 집계가 없다.** 백필 이후 입력한 값은 전부 0으로 남고,
  사용자가 그 필드의 라이브러리 화면을 열 때까지 0을 유지한다.
- **'섞임 12필드'가 이 진단의 결정적 증거다.** 필드 단위로 한 번 집계된 뒤 값이 더 늘어난
  필드에서만 나올 수 있는 분포다(전부-0 15 = 한 번도 집계 안 됨, 전부-비0 7 = 집계 후 추가 없음).

**영향 — `usageCount`를 갱신 없이 읽는 경로:**

| 경로 | 무엇이 틀리나 | 심각도 |
|------|--------------|--------|
| `FieldLibraryHomeFragment.kt:183` ← `loadFieldRows` → `repo.entryCounts()`(생 DB) | 라이브러리 **첫 화면**이 필드마다 '미사용 N'을 표시 — 이 사용자에게는 **미사용 318**로 뜨지만 실제는 **0** | **높음** — 정리를 권하는 수치가 정반대 |
| `StatsMainFragment.kt:88` | 통계 화면의 라이브러리 요약도 같은 합계를 그대로 더한다 | 높음 |
| 캐릭터 편집 자동완성 (`FieldValueEntryDao` `ORDER BY usageCount DESC`, `CharacterViewModel.kt:1058`) | '많이 쓴 값 먼저'가 **66%가 0인 상태로 정렬** — 매일 쓰는 경로에서 제안 순서가 사실상 무작위 | **높음**(원칙 02) |
| `CharacterFieldAiSuggester.kt:542` (`usable.none { it.usageCount > 0 }`) | 예시 적재량 분기가 잘못 걸린다 | 중간 |
| `pruneUncuratedUnused` / `countPrunable` (`FieldValueListFragment.kt:231·241`) | **화면 진입 시 `refreshUsage`가 먼저 돌아 교정된 뒤 실행**되므로 실제 삭제는 안전하다 | 낮음 — **유실 경로 아님** |

**따라서 이것은 데이터 유실이 아니라 표시·정렬 왜곡이다.** 규약 **R-16**("계산 필드는 저장 행이
없다 — 저장 값을 읽는 모든 경로가 그것을 알아야 한다")과 같은 형태의 결함이다:
**쓰는 축과 세는 축을 따로 늘렸다.**

> **초안의 가설 하나는 사용자 회신으로 기각됐다.** 초안은 이 결함이 §2의 큐레이션 도달률 0%의
> 유력한 선행 원인이라고 적었다("첫 화면이 '미사용 318'이라고 말하면 큐레이션할 마음이 들지
> 않는다"). §7 Q2의 답은 **"그런 기능이 있는 줄 몰랐다"** — 사용자는 그 화면까지 가지 않았다.
> 두 문제는 **독립**이다. U-0은 그 자체로 고쳐야 하고, 큐레이션 미도달의 처방은 **발견성**이다.
> 다만 U-0을 먼저 고치지 않으면, 발견성을 고쳐 사용자가 처음 들어간 순간 **"482개 중 318개
> 미사용"이라는 틀린 첫인상**을 받게 된다 — 순서는 여전히 U-0이 먼저다.

### 3-B. 표에 없던 패턴 / 판별 불가

1. **값 길이 분포(4-1①)** — 상위 20개 값은 **전부 콤마 나열형**이고 서술문이 하나도 없다.
   최장 79자(`시그니쳐 요소`, 콤마 12개). 40자 초과 값은 **2건**뿐. → **서술형 몰아넣기 우회는 없다.**
   이 사용자는 값을 **짧은 토큰의 나열**로 쓴다.
2. **필드별 값 길이 중앙값 상위 5(4-1②)** — `시그니쳐 요소` 35자(n=13) · `퍼스널 컬러` 12자(n=14) ·
   `경지` 9자(n=1) · `외모 특징` 9자(n=1) · `좋아하는 것` 9자(n=2). 상위 2개는 둘 다 MULTI_TEXT이므로
   **'못 담아서 몰아넣은 필드'가 아니라 원래 다중값 필드**다. → 해당 없음.
3. **타입 선언과 값의 불일치(4-1③)** — NUMBER인데 수치 아님 **0/1,217** · SELECT인데 옵션 밖
   **0/1,217** · GRADE 이상 **0** · BODY_SIZE 파트 분리 실패 **0**. → **불일치 0건**(§5 '변수 제어'의 정량 근거).
4. **여러 필드에 반복 출현하는 동일 값(4-1④)** — 20종. 상위는 전부 **등급 문자와 숫자**:
   `'S'` 6필드 33회 · `'B'` 6필드 28회 · `'A'` 6필드 15회 · `'C'` 7필드 11회 · `'0'` 3필드 54회 ·

   다만 등급 문자가 **6~7개 필드에 걸쳐 반복**되므로, 세계관 단위 '등급 체계' 공유 개념이 있으면
   중복 정의가 줄어든다 → **신규 후보 U-1**.
5. **새 패턴: 역법(창작 달력)의 압도적 사용** — 사건 137건 중 **136건(99.3%)**이 `역법` 열을 채운다.

## 5. 개발 의도 4질문의 실측 답

- **받쳐주는 확장성** — **확인됨.** §4 스윕에서 ×30까지 선형 이하. 이 사용자의 실규모(214명)에서
  통계 5계산 합계 **65ms**. 백로그 **B-42**(config JSON 재파싱)가 예고한 "캐릭터 300 × 필드 50이면
  JSON 파싱 수십만 회"는 사실이지만, 그 비용이 **실사용 규모의 30배에서도 임계로 드러나지 않는다.**
- **변수 제어** — **양면.** 잘못된 입력 쪽은 완벽하다: 타입 선언과 값의 불일치 **0/1,217**(§3-B ③),
  참조 이름의 콤마 파손 조건 **0건**(§1). 반면 **앱이 스스로 만든 수치가 66% 틀려 있고**(§1-B)
  그것을 두 화면이 그대로 표시한다 — 변수 제어의 실패는 사용자 입력이 아니라 **앱의 자체 집계**에 있다.
- **자율성 우선** — **도달.** 필드 **48/90(53.3%)**이 설정 키를 갖고 **13종에 분산**(런북 5-1의
  '고르게 퍼짐' 기준). 순서 재배치 87/90, 그룹 13종, 관계 유형 15종 — 톱니를 실제로 만진다.
  반대로 **값 라이브러리 큐레이션만 0%**로 홀로 떨어져 있는데, 그 사유는 자율성 부족이 아니라
  **발견성**이다(§7 Q2 "있는 줄 몰랐다"). 톱니를 이만큼 만지는 사용자가 그 화면만 못 찾았다는 것은
  **기능의 문제가 아니라 진입점의 문제**라는 뜻이다 → U-5.
- **엑셀 왕복 무결성** — **표본으로는 답할 수 없다. 초안의 결론을 철회한다.**
  이 파일은 전 셀이 앱이 쓴 그대로다: 병합 0 · 날짜 자동변환 0 · 0패딩 서식 0 · 헤더 변경 0 ·
  참조 이름의 콤마 0. 초안은 여기서 "이 사용자는 왕복하지 않는다"고 적었다.
  **§7 Q1의 답은 '자주 왕복한다'다 — 그 결론은 틀렸다.**
  올바른 해석은 **표본 선택의 한계**다: 이 파일은 **외부 편집 이전의 갓 내보낸 산출물**이므로,
  왕복에서 무엇이 깨지는지 물어볼 수 있는 표본이 애초에 아니다. 0건은 "안전하다"가 아니라
  **"측정하지 않았다"**로 읽어야 한다.
  실제로 부하를 받는 항목은 **과학표기 699건**(전부 epoch millis) 하나이고 B-7의 평문 십진
  변환이 그것을 받아 낸다 — 이것만은 표본으로 확인됐다.
  → **필요한 것: 외부 편집기로 고친 뒤 저장한 파일 1건.** 런북 1-1의 정지 조건("표본 부재")이
  B-27·B-38 갈래에 한해 지금 성립한다.

| **U-6** 외부 편집 표본 재수집 | 없음(신규) | Q1='자주 왕복'인데 표본은 편집 전 파일 | **선행 과제.** B-27 갈래 판정에 필요 |

*판별 불가 항목(`.db` 동봉 없음 → B-9)은 조정 근거로 쓰지 않았다. `이미지`는 Q0-a 회신으로 확정됐다.*
