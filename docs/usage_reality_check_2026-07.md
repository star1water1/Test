**그래서 이 문서는 근거의 종류를 나눠 읽어야 한다:**

| **사용자가 직접 말한 사유** — §7의 답 | **없음.** 카운트가 아니라 진술이 근거다 | 사건 필드·큐레이션·상태변화 |
| **0건 카운트뿐** — 시트 부재, 채움률 0% | **결정적.** '안 쓴다'로 읽을 수 없다 | 아래 ⚠️ 표시 행 전부 |

### 1-B. 값 라이브러리 `사용횟수`의 66% 오차 — 수확 축과 집계 축의 비대칭

**측정: 완료 · 코드 실독으로 원인 확정**

| 관측(실파일) | 값 |
|---|---|
| 라이브러리 엔트리 | 482 |
| `사용횟수 = 0` | **318 (66.0%)** |
| ├ 그 값이 **현재 캐릭터 필드값에 실재** | **318** |
| ├ 상태변화에만 실재 | 0 |
| └ 어디에도 없음(정상적인 과거 잔재) | **0** |
| `사용횟수 > 0`인데 현재 값에 없음 | 0 |
| 필드 34개 분포 | 전부 0 = **15** · 전부 비0 = **7** · **섞임 = 12** |

**원인 — 수확은 7경로, 집계는 5경로이고 겹치지 않는다.**

- 수확(`harvestUniverses`)은 **캐릭터 저장마다** 돈다(`CharacterRepository.kt:408`), 그리고
  월드패키지 임포트·휴지통 복원 2경로·엑셀 임포트·앱 최초 백필에서도 돈다.
  새 엔트리는 `FieldValueEntry(fieldDefinitionId, value)`로 삽입되므로 **`usageCount`는 기본값 0**이다.
- 집계(`recountUsage`)는 **앱 1회 백필**(`NovelCharacterApp.kt:133`, `field_library_seeded`
  플래그로 1회만) · **엑셀 임포트**(`ExcelImportService.kt:585`) · **그 필드의 라이브러리 목록
  화면 진입**(`FieldValueListFragment.kt:101`) · 값 이름변경/병합/AI 정리에서만 돈다.
- 즉 **일상 경로(캐릭터 저장)에는 집계가 없다.** 백필 이후 입력한 값은 전부 0으로 남고,
  사용자가 그 필드의 라이브러리 화면을 열 때까지 0을 유지한다.
- **'섞임 12필드'가 이 진단의 결정적 증거다.** 필드 단위로 한 번 집계된 뒤 값이 더 늘어난
  필드에서만 나올 수 있는 분포다(전부-0 15 = 한 번도 집계 안 됨, 전부-비0 7 = 집계 후 추가 없음).

**영향 — `usageCount`를 갱신 없이 읽는 경로:**

| 경로 | 무엇이 틀리나 | 심각도 |
|------|--------------|--------|
| `FieldLibraryHomeFragment.kt:183` ← `loadFieldRows` → `repo.entryCounts()`(생 DB) | 라이브러리 **첫 화면**이 필드마다 '미사용 N'을 표시 — 이 사용자에게는 **미사용 318**로 뜨지만 실제는 **0** | **높음** — 정리를 권하는 수치가 정반대 |
| `StatsMainFragment.kt:88` | 통계 화면의 라이브러리 요약도 같은 합계를 그대로 더한다 | 높음 |
| 캐릭터 편집 자동완성 (`FieldValueEntryDao` `ORDER BY usageCount DESC`, `CharacterViewModel.kt:1058`) | '많이 쓴 값 먼저'가 **66%가 0인 상태로 정렬** — 매일 쓰는 경로에서 제안 순서가 사실상 무작위 | **높음**(원칙 02) |
| `CharacterFieldAiSuggester.kt:542` (`usable.none { it.usageCount > 0 }`) | 예시 적재량 분기가 잘못 걸린다 | 중간 |
| `pruneUncuratedUnused` / `countPrunable` (`FieldValueListFragment.kt:231·241`) | v1.2는 "진입 시 갱신이 먼저 도니 안전하다"고 적었으나 **순서 보장이 없다**(§1-C ②) — 진입 직후 즉시 정리를 누르면 낡은 0을 읽어 사용 중 엔트리를 지운다 | 낮음 — 삭제 대상이 큐레이션 흔적 없는 AUTO뿐이고 다음 수확이 되살린다. **다만 '안전'은 경합에 기댄 것이다** |

**따라서 이것은 데이터 유실이 아니라 표시·정렬 왜곡이다.** 규약 **R-16**("계산 필드는 저장 행이
없다 — 저장 값을 읽는 모든 경로가 그것을 알아야 한다")과 같은 형태의 결함이다:
**쓰는 축과 세는 축을 따로 늘렸다.**

> **초안의 가설 하나는 사용자 회신으로 기각됐다.** 초안은 이 결함이 §2의 큐레이션 도달률 0%의
> 유력한 선행 원인이라고 적었다("첫 화면이 '미사용 318'이라고 말하면 큐레이션할 마음이 들지
> 않는다"). §7 Q2의 답은 **"그런 기능이 있는 줄 몰랐다"** — 사용자는 그 화면까지 가지 않았다.
> 두 문제는 **독립**이다. U-0은 그 자체로 고쳐야 하고, 큐레이션 미도달의 처방은 **발견성**이다.
> 다만 U-0을 먼저 고치지 않으면, 발견성을 고쳐 사용자가 처음 들어간 순간 **"482개 중 318개
> 미사용"이라는 틀린 첫인상**을 받게 된다 — 순서는 여전히 U-0이 먼저다.

## 5. 개발 의도 4질문의 실측 답

- **받쳐주는 확장성** — **확인됨.** §4 스윕에서 ×30까지 선형 이하. 이 사용자의 실규모(214명)에서
  통계 5계산 합계 **65ms**. 백로그 **B-42**(config JSON 재파싱)가 예고한 "캐릭터 300 × 필드 50이면
  JSON 파싱 수십만 회"는 사실이지만, 그 비용이 **실사용 규모의 30배에서도 임계로 드러나지 않는다.**
  **표본이 아직 채워지는 중이라는 사실이 이 답을 약화시키지 않고 오히려 이 답을 필요하게 만든다** —
  질문이 "지금 빠른가"가 아니라 "다 채워도 버티는가"이기 때문이다. ×30은 그 질문에 대한 답이다.
- **변수 제어** — **양면.** 잘못된 입력 쪽은 완벽하다: 타입 선언과 값의 불일치 **0/1,217**(§3-B ③),
  참조 이름의 콤마 파손 조건 **0건**(§1). 반면 **앱이 스스로 만든 수치가 66% 틀려 있고**(§1-B)
  그것을 두 화면이 그대로 표시한다 — 변수 제어의 실패는 사용자 입력이 아니라 **앱의 자체 집계**에 있다.
- **자율성 우선** — **도달.** 필드 **48/90(53.3%)**이 설정 키를 갖고 **13종에 분산**(런북 5-1의
  '고르게 퍼짐' 기준). 순서 재배치 87/90, 그룹 13종, 관계 유형 15종 — 톱니를 실제로 만진다.
  반대로 **값 라이브러리 큐레이션만 0%**로 홀로 떨어져 있는데, 그 사유는 자율성 부족이 아니라
  **발견성**이다(§7 Q2 "있는 줄 몰랐다"). 톱니를 이만큼 만지는 사용자가 그 화면만 못 찾았다는 것은
  **기능의 문제가 아니라 진입점의 문제**라는 뜻이다 → U-5.
- **엑셀 왕복 무결성** — **표본으로는 답할 수 없다. 초안의 결론을 철회한다.**
  이 파일은 전 셀이 앱이 쓴 그대로다: 병합 0 · 날짜 자동변환 0 · 0패딩 서식 0 · 헤더 변경 0 ·
  참조 이름의 콤마 0. 초안은 여기서 "이 사용자는 왕복하지 않는다"고 적었다.
  **§7 Q1의 답은 '자주 왕복한다'다 — 그 결론은 틀렸다.**
  올바른 해석은 **표본 선택의 한계**다: 이 파일은 **외부 편집 이전의 갓 내보낸 산출물**이므로,
  왕복에서 무엇이 깨지는지 물어볼 수 있는 표본이 애초에 아니다. 0건은 "안전하다"가 아니라
  **"측정하지 않았다"**로 읽어야 한다.
  실제로 부하를 받는 항목은 **과학표기 699건**(전부 epoch millis) 하나이고 B-7의 평문 십진
  변환이 그것을 받아 낸다 — 이것만은 표본으로 확인됐다.
  → **필요한 것: 외부 편집기로 고친 뒤 저장한 파일 1건.** 런북 1-1의 정지 조건("표본 부재")이
  B-27·B-38 갈래에 한해 지금 성립한다.

| **열을 새로 추가**해서 필드를 만든다 | 매칭 실패 시 **TEXT 필드로 자동 생성** + `'컬럼 X → TEXT 필드로 자동 생성됨'` 경고 | `buildColumnFieldMap:4924~4947` |
| **열 순서를 바꾸거나 열을 지운다** | 헤더 **이름**으로 매칭하므로 순서 무관. 열이 없으면 기존 값 **유지**, 열이 있고 빈칸이면 **비움 의도**(F1-A) | `buildColumnFieldMap` · `sheetBooleanOrKeep` |
| **행을 새로 추가**한다(코드 빈칸) | 신규 생성 + `newCodesGenerated` 집계 | `:2648` |
| **코드를 잘못 고친다** | 이름으로 폴백 + **"의도한 새 캐릭터라면 코드를 비우세요"**, 이름도 없으면 "오타·삭제 여부를 확인하세요" | `:2598~2602` |
| **드롭다운 아래로 행을 더 넣는다** | 유효성 검사가 데이터 끝 **+100행**까지 미리 깔려 있다 — 실파일 확인: 43행 시트 → `I2:I144`, 137행 시트 → `E2:E238` | `DROPDOWN_EXTRA_ROWS=100` |
| readOnly 열 식별 | 회색 스타일이 적용돼 시각적으로 구분된다 | `applyReadOnlyColumn:408` |
| 전각 쉼표·대소문자·병합 셀·선행 0·과학표기 | 전부 관대 수용 또는 원문 보존 | `toHalfWidth` · `MergedCellMap` · `ExcelCellValue` |

**즉 '엑셀에서 편집해서 되돌리기'라는 축 자체는 이미 상당히 튼튼하다.** 아래는 그 위에 남은 구멍이다.

### 8-2. 결함 — 고칠 것

**E-1. 캐릭터 시트의 CALCULATED 열에 입력하면 무통보로 사라진다.** (→ U-10)

계산 필드를 저장하지 않는 것은 옳다(파생값). 문제는 **고지의 형제 불일치**다:

| 경로 | CALCULATED 열에 값이 있을 때 | |
|---|---|---|
| `캐릭터 필드값` 시트 (`:2445`) | `"'X'은(는) 계산 필드라 저장하지 않습니다"` 경고 | ✅ |
| `사건 연표` 시트 (`:3020`) | `"사건 시트의 'X' 열은 계산 필드라 저장하지 않습니다"` 경고 | ✅ |
| **캐릭터 시트** (`:2700`) | `if (field.type == "CALCULATED") continue` — **아무 말 없음** | ❌ |

**캐릭터 시트가 엑셀 작업자의 주 작업면인데 거기만 조용하다.** 이 사용자에게 실재하는 문제다 —
CALCULATED 2개 × 43행 = **86칸에 값이 채워져 있고**(§1-C ④), 엑셀에서 그 숫자를 고쳐 넣으면
경고 한 줄 없이 폐기된다. 변수 제어("조용히 버리지 않는다") 위반이고, 수리는 형제 문구를
그대로 가져오는 기계적 작업이다.

**E-2. 행을 복사해 새 캐릭터를 만들면 경고는 뜨지만 해결 방법을 안 알려준다.** (→ U-11)

엑셀에서 비슷한 캐릭터를 만드는 가장 자연스러운 방법은 **행 복사**인데, 복사된 행은 `코드`를
그대로 물고 온다. 앱은 이것을 감지해 경고한다 —
`"캐릭터 행 N: 행 M 과 같은 항목('이름')을 다시 덮어씀"`(`:2670~2673`).

그런데 **형제 경고 3개는 전부 교정 방법을 말해 준다**("코드를 비우세요" / "오타·삭제 여부를
확인하세요" / "헤더를 '이름(필드키)' 형식으로 바꾸세요"). 이 경고만 무엇을 하라는 말이 없다.
사용자는 "덮어썼다"는 사실만 듣고 **왜 두 번째 캐릭터가 안 생겼는지 모른다.**
필요한 것은 한 줄이다 — `코드 열을 비우면 새 캐릭터로 들어옵니다`.
`remaining_work` §5의 교훈("문구는 형제를 데리고 다닌다")이 정확히 걸리는 자리다.

### 8-3. 마찰 — 설계 선택이지만 엑셀 우선에 불리한 것

**E-3. 캐릭터가 세계관별 시트 10장으로 쪼개져 있고 열 구성도 다르다.**
이 파일은 캐릭터 시트가 10장(49 · 38 · 42 · 13열 등)이다. 엑셀의 최대 강점인
**전체 정렬·필터·피벗**을 214명 전체에 걸 수 없다. 손으로 합치면 그 시트는 다시 못 넣는다
(세계관별 필드 열이 다르므로 구조적으로 불가피한 면이 있다).
→ 처방 후보: **읽기 전용 '전체 캐릭터' 시트**를 하나 더 내보내기(공통 열 + 세계관·작품).
가져오기는 그 시트를 무시하면 되므로 왕복 규약을 건드리지 않는다.

**E-4. 엑셀에서 행을 지워도 기본값으로는 삭제되지 않는다.**
`DeleteOptions`는 9개 필드가 **전부 기본 false**다. 안전한 기본값이지만, 엑셀 작업자의
자연스러운 기대("지웠으니 없어지겠지")와 반대다. 옵션은 `엑셀에 없는 항목 삭제` 문구 하나로만
노출된다 → 최소한 **가져오기 요약에 "엑셀에 없던 항목 N건은 그대로 두었습니다"** 한 줄이
있으면 기대 어긋남이 그 자리에서 해소된다.

**E-5. `사용횟수` 열은 내보내지지만 읽히지 않고, 게다가 66%가 틀리다.**
파생 캐시이므로 안 읽는 것은 설계상 맞다. 문제는 **엑셀 작업자가 그 숫자를 보고 판단한다**는
점이다 — U-0 때문에 이 파일의 사용횟수는 482개 중 **318개가 0으로 잘못 표시**돼 있다(§1-B).
엑셀에서 라이브러리를 정리하려는 사람에게 **틀린 안내판**이 된다. U-0을 고치면 함께 해소된다.

### 8-4. 기회 — 이 사용자에게 특히 값싼 수

**E-6. 큐레이션은 엑셀에서 대량 편집이 가능하고, 임포트가 실제로 반영한다.** (→ U-5의 최단 경로)

`필드 데이터` 시트의 **표시라벨 · 별칭(콤마구분) · 카테고리** 열은 읽기 전용이 아니고,
임포트가 그대로 반영한다(`ExcelImportService:2137~2235`).
그런데 이 사용자의 파일에는 **482행 × 3열이 전부 빈칸**이고, 사유는 §7 Q2 —
**"그런 기능이 있는 줄 몰랐다"**.

엑셀에서 주로 작업하는 사람에게 482개 값의 별칭·카테고리를 다는 일은 **앱 화면을 482번 여는
것보다 비교할 수 없이 빠르다.** 즉 U-5(발견성)의 처방은 앱 화면 개선만이 아니다 —
**`사용 안내` 시트(현재 107행)에 "이 시트의 표시라벨·별칭·카테고리를 채워 다시 가져오면
값 정리가 반영됩니다" 한 줄**을 넣는 것이 가장 값싼 수이고, 이 사용자의 작업 방식에 정확히 맞는다.
