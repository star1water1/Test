## 1. 이 설계가 서 있는 근거와, 서지 않는 것

**서는 것 — 코드를 직접 읽어 확인한 사실만 근거로 삼았다.**

- 필드 설정의 저장소는 `FieldDefinition.config`(JSON 문자열)다 — **스키마 변경 없이** 키를 더할 수
  있다(`NarrativeMode`·`FieldValueLibraryConfig` 선례). Room 마이그레이션이 필요 없다.
- 짧은 값 추천의 대상 산출은 `AiFieldSuggestSheet.showForCharacter` → `fieldSpecOf` 한 경로다.
- 보충(랜덤) 탭은 이미 `DynamicFieldFormBuilder`·`CharacterViewModel`·`CharacterSaveCoordinator`를
  편집 화면과 **공유**한다(`RandomSupplementFragment:88~92`) — AI 경로 재사용의 전제가 이미 서 있다.
- `AiRequest`에 `temperature`가 **없다**. 세 프로토콜 어디에도 샘플링 파라미터를 싣지 않는다.
- 캐릭터 목록의 상단은 툴바 + 검색/비교 행 + 칩 행 **3행**이고, 툴바는 탭 루트(`novelId == -1`)와
  푸시 목적지(작품별 목록) **양쪽**에서 쓰인다 — 통째로 지울 수 없다.

**서지 않는 것 — 다음은 추정이므로 착수 시 실측한다.**

- 상단바 절감 실수치(dp). 기기·폰트 배율에 따라 다르므로 "3행 → 2행"이라는 **구조**만 못 박고
  수치는 목표로 두지 않는다.
- 필드 설명을 실었을 때의 실제 입력 토큰 증가. 8장의 추정치는 고지용이지 계약이 아니다.
- 창작도 각 단계가 실제로 만드는 값의 다양성. 모델마다 다르므로 **문구로 약속하지 않는다.**

## 2. A-0 — 착수 전 부수 수리 (선행 조건)

A-1이 필드 목록 행에 스위치를 넣기 때문에 **먼저 정리해야 하는 두 가지**다. 둘 다 지금도
틀려 있지만 A-1 없이는 드러나지 않던 것이라 여기 묶는다.

### 2-1. 필드 관리 목록의 드래그가 롱프레스와 롱클릭에 동시에 물려 있다

`FieldManageFragment:119` 의 `ItemTouchHelper`는 `isLongPressDragEnabled()`를 끄지 않았고,
`FieldDefinitionAdapter`는 `item_field_definition.xml`의 `dragHandle`을 `startDrag`에 배선하지
않았다. 그래서 **드래그 핸들은 장식이고**, 롱프레스는 옵션 다이얼로그(`onLongClick`)와 드래그
시작이 함께 걸려 있다.

**이 앱의 나머지 4곳은 전부 반대로 되어 있다** — 세계관(`UniverseListFragment:164`)·
작품(`NovelListFragment:158`)·캐릭터(`CharacterListFragment:182`)·연표(`TimelineFragment:306`)가
모두 `isLongPressDragEnabled() = false` + 핸들 `startDrag` 배선이다. 필드 관리만 규약 밖이다.

**수리:** 나머지 4곳과 같은 형태로 통일한다. `FieldDefinitionAdapter`에 `onStartDrag` 훅을 추가해
`dragHandle.setOnTouchListener`에서 `itemTouchHelper.startDrag(holder)`를 부르고,
`isLongPressDragEnabled()`를 `false`로 둔다.

> 이것을 A-1보다 먼저 하는 이유: 행에 스위치를 얹으면 **한 행에 탭·롱탭·드래그·스위치 4개**가
> 경쟁한다. 지금 상태로 스위치를 넣으면 "순서를 바꾸려다 AI 토글이 꺼지는" 오조작이 난다.

### 2-2. 모델을 바꿔도 앞 모델에서 학습한 사실이 남는다

`AiSettingsFragment.readConfig:568`은 `detectedOutputLimit = detectedLimit`으로 **모델명이
바뀌어도 학습값을 그대로 넘긴다.** 출력 상한이 4k인 모델에서 배운 값이 128k 모델로 갈아탄 뒤에도
남아 슬라이더 상한과 실제 요청값을 조용히 깎는다(`AiTokenPolicy.effective`가 `min`을 취한다).

A-4가 같은 성격의 학습값(`temperatureUnsupported`)을 하나 더 만들기 때문에, 규칙을 지금 세운다.

> #### R-23. 학습한 사실은 학습 대상이 바뀌면 함께 버린다
>
> `detectedOutputLimit`·`temperatureUnsupported`처럼 **오류 응답에서 배운 값**은 그 모델에
> 한정된 사실이다. `AiProviderConfig.model`이 바뀌면 같은 저장 시점에 전부 `null`로 되돌린다.
> 되돌린 뒤 첫 요청이 다시 배우면 되므로 손실이 없고, 남겨 두면 사용자가 **원인을 볼 수 없는
> 제약**을 계속 받는다. baseUrl 변경도 같다(같은 모델명이 다른 서버에서 다른 상한을 가진다).

**수리:** `readConfig`에서 `model`·`baseUrl`이 `base`와 다르면 학습값 전부를 `null`로 둔다.
사용자에게는 저장 시 한 줄로 고지한다 — "모델이 바뀌어 이 모델에 대해 학습한 상한을
초기화했습니다(다음 요청에서 다시 감지)". 조용히 바꾸지 않는다(변수 제어).

## 3. A-1 — 필드별 AI 추천 대상 토글

### 3-1. 저장 형태

`FieldDefinition.config` JSON에 **flat 키 하나**를 둔다. 새 순수 오브젝트
`data/model/FieldAiPolicy.kt`가 단일 소스다.

```
키:    "aiSuggest": false     // 기본값(true)은 저장하지 않는다
읽기:  FieldAiPolicy.isSuggestEnabled(config): Boolean   // 키 없음 = true
쓰기:  FieldAiPolicy.applyToConfig(existing, enabled)    // true면 키를 제거
```

기본값을 저장하지 않는 것은 `NarrativeMode.applyToConfig`·`FieldValueLibraryConfig.applyToConfig`와
같은 관행이다. **기존 필드 전부가 config를 건드리지 않고도 켜진 상태로 시작한다 — 회귀 없음.**

### 3-2. 왜 2단(on/off)인가 — 3단을 기각한 이유

`NarrativeMode`(auto/narrative/short)나 `inputMode`(suggest/free/restricted)처럼 3단으로 갈
수도 있었다. 후보였던 3번째 상태는 **"수동만"**(일괄에서는 빼되 ✨ 버튼은 남김)이다.

**기각.** 그 상태는 이미 **필드 성격으로 자동 성립**한다 — 서술형 필드는 구조적으로 짧은 값
일괄 경로에 들어갈 수 없고(3-4), ✨는 서술형 경로로 간다. 사용자가 손으로 지정할 이유가 없는
상태를 선택지로 만들면 설정만 늘고 결과는 같다. 요청도 "간단하게 토글로"였다.

### 3-3. OFF의 의미 — 정확히 무엇이 달라지는가

| 경로 | OFF일 때 |
|---|---|
| 일괄 추천(`showForCharacter`) 대상 | **제외.** 제외 개수·사유를 비용 고지에 명시 |
| 폼 인라인 ✨ 버튼(`createAiButtonOrNull`) | **숨김** |
| 서술형 작성(`NarrativeWriteSheet`) | **숨김**(✨이 진입점이므로 함께 사라진다) |
| 🎲 랜덤 값 생성 | **영향 없음** — 랜덤은 AI가 아니다 |
| 값 라이브러리 AI 정리(`FieldLibraryAiOrganizer`) | **영향 없음** — 그것은 *있는 값 정리*이지 추천이 아니다 |
| 통계·검색·엑셀 | **영향 없음** |

**✨을 숨기는 것이 맞는 이유:** 이 토글의 목적이 "이 필드는 AI가 건드리지 않는다"이기 때문이다.
버튼만 남기면 토글은 일괄 필터에 불과해지고, 사용자가 요청한 "AI한테 추천 받을 수 있게 할 건지"와
어긋난다. 대신 **사라진 것을 모르게 두지 않는다** — 3-5의 고지가 짝이다.

> **폼에서 ✨이 없는 필드의 사유는 어디서 보이는가.** 폼의 필드 행 자체에는 아무 표시도
> 남기지 않는다(꺼진 필드마다 회색 아이콘을 두면 "끈 것"이 "고장 난 것"처럼 보인다).
> 사유를 보는 자리는 둘이다 — **필드 관리 목록**(스위치가 켜짐/꺼짐을 한눈에 조감한다)과
> **일괄 추천 비용 고지**(3-5의 "AI 추천 꺼짐 N개 [제외 목록 보기]"). 사용자가 "왜 안 뜨지"를
> 물을 실제 시점은 일괄을 돌릴 때이고, 그 자리에 사유와 필드명이 있다. 폼에 상시 표지를 두는
> 것은 이 앱이 금지하는 "존재를 알 수 없는 데이터"가 아니라 **끄기로 한 결정의 결과**다.

### 3-4. 일괄 추천 대상의 재정의 (요청 1의 "일괄 추천도 다르게 작동")

현행 `showForCharacter`의 대상은 `fieldDefinitions.mapNotNull { fieldSpecOf(it, …) }`이다.
여기엔 **지금 코드에 있는 결함 하나**가 포함돼 있다.

> **현행 결함 — 일괄 추천이 서술형 필드를 짧은 값 경로로 보낸다.**
> `fieldSpecOf`는 CALCULATED와 미지 타입만 거른다. `NarrativeMode.isNarrative`는 **보지 않는다.**
> 그래서 성격·배경 같은 서술형 TEXT 필드가 일괄 요청에 섞여 들어가고, 모델은 "근거 한 문장"
> 형식에 맞춰 산문 자리에 한 줄짜리 값을 낸다. `docs/ai_integration.md`가 경로를 나눈 이유
> ("산문을 끼워 넣으면 둘 다 망가진다")가 **인라인 ✨에서만 지켜지고 일괄에서는 지켜지지 않는다.**
> 이 저장소가 반복해서 겪은 "한 경로만 고쳐지고 나머지에 조용한 실패가 남는" 형태다.

새 대상 규칙 — **단일 소스는 새 순수 함수 `CharacterFieldAiSuggester.bulkTargetsOf(fields, values)`**다.
`AiFieldSuggestSheet`가 직접 필터를 조립하지 않는다(A-3이 같은 함수를 쓰기 위해서다).

```
대상 = 편집 가능 필드
      ─ CALCULATED·미지 타입      → 사유 UNSUPPORTED_TYPE
      ─ aiSuggest = false         → 사유 AI_DISABLED
      ─ NarrativeMode.isNarrative → 사유 NARRATIVE_PATH
      (그 뒤 '빈 필드만'/'입력된 필드 포함' 기존 선택 적용)
```

제외분은 버리지 않고 **사유별 개수**로 들고 나온다(`BulkTargets(targets, excluded: Map<Cause,List<name>>)`).

### 3-5. 고지 — 사라진 것을 개수로 남긴다 (R-14의 적용)

비용 고지 다이얼로그에 대상 수 아래 한 줄을 더한다.

```
필드 12개를 요청 1건으로 추천받습니다.
제외: AI 추천 꺼짐 3개 · 서술형 2개 · 계산 필드 1개          [제외 목록 보기]
```

- `[제외 목록 보기]`는 사유별 필드명을 펼친다. 상한을 넘으면 "외 N개"로 접되 **총 수는 밝힌다.**
- **계산 필드 제외는 지금도 일어나지만 아무도 알려주지 않았다** — 이 고지가 그것도 함께 메운다.
- 서술형 줄에는 "필드별 ✨에서 초안·이어쓰기로 작성합니다"를 병기한다. 제외가 곧 기능 부재로
  읽히지 않게 한다(변수 제어 — 교정 경로를 함께 준다).

### 3-6. 설정 지점 — 두 자리, 같은 소스

| 자리 | 형태 | 이유 |
|---|---|---|
| **필드 관리 목록 행** | 행 끝의 `MaterialSwitch` — 1탭 즉시 반영, 저장 버튼 없음 | 요청 그대로(원칙 04). 목록에서 켜짐/꺼짐이 **한눈에 조감**된다 |
| **필드 편집 다이얼로그** | `AI` 섹션의 스위치 | 다른 필드 설정이 전부 여기 있다. 여기에 없으면 필드를 만드는 흐름에서 존재를 모른다 |

두 자리는 같은 `applyToConfig`를 쓴다. 목록 스위치는 `viewModel.updateField(field.copy(config=…))`를
부르고, `FieldDiffCallback.areContentsTheSame`이 data class 전체 비교라 config 변경이 그대로
리바인드된다(추가 작업 없음).

**행 레이아웃:** `dragHandle`(시작) … 텍스트(가중치 1) … `switchAiSuggest`(끝). A-0-1로 드래그가
핸들 전용이 되므로 스위치와 경쟁하지 않는다.

### 3-7. 사건 필드에서는 토글을 노출하지 않는다

`entityType == ENTITY_EVENT` 필드에는 **AI 추천 경로 자체가 없다**(추천기는 캐릭터 컨텍스트를
받는다). 그런 필드에 스위치를 두면 아무 일도 하지 않는 스위치가 된다 — 이 저장소가 색출해 온
"구색만 갖춘 기능"의 정의 그대로다.

> #### R-24. 성립하지 않는 조합의 설정은 보이지 않는다
>
> `NarrativeMode.isEligibleType`이 SELECT·NUMBER 등에서 설정을 감추는 것과 같은 규칙이다.
> **설정을 무시하는 것이 아니라 애초에 성립하지 않는 조합이고, 그 사실은 설정이 보이지 않는
> 것으로 드러난다.** 나중에 그 조합이 성립하게 되면(사건 필드 AI 경로가 생기면) 설정이 함께
> 열린다 — 그때까지 백로그에 남긴다(11장).

**필드 설명(A-2)은 사건 필드에도 노출한다** — 그쪽은 AI와 무관하게 인앱에서 값을 갖는다.

## 4. A-2 — 필드 설명 (인앱 확인 + AI 전달)

### 4-1. 무엇이며, 무엇이 아닌가

**필드 설명 = 사용자가 쓰는, 이 필드가 무엇인지에 대한 설명.** 예: `마나친화 — 이 세계의
마나를 몸에 받아들이는 정도. 0~100 수치이며, 60 이상은 마법사 계열만 나온다.`

혼동하기 쉬운 이웃이 셋 있다. **전부 다른 것이며 합치지 않는다.**

| 이웃 | 무엇 | 왜 다른가 |
|---|---|---|
| `FieldValueEntry.description` | **값 하나**의 설명(값 라이브러리) | 대상이 필드가 아니라 값이다 |
| P3 인앱 도움말(`helpKey`) | **앱 기능**의 설명(개발자 작성, `strings.xml`) | 출처가 사용자가 아니다. 번역·검색 대상이다 |
| `TextInputLayout.helperText` | 입력 힌트 | 항상 보여야 하는 한 줄. 설명은 길고, 눌러야 보인다 |

### 4-2. 저장 형태

```
키:    "description": "…"    // 빈 문자열이면 키를 제거
읽기:  FieldDescription.fromConfig(config): String
쓰기:  FieldDescription.applyToConfig(existing, text)
상한:  FieldDescription.MAX_CHARS = 1000   // 저장 상한(입력창에 카운터)
```

`config` 키 `"description"`은 현재 어떤 경로도 쓰지 않는다(전수 grep 확인). 충돌 없음.

### 4-3. 어디서 보이는가

| 화면 | 형태 | 차수 |
|---|---|---|
| 필드 관리 목록 행 | 설명이 있으면 `ⓘ` 아이콘 표시 → 탭하면 다이얼로그 | **1차** |
| 필드 편집 다이얼로그 | 여러 줄 입력창(`AI` 섹션 위, `설명` 섹션) | **1차** |
| 캐릭터 편집 폼 / 보충 편집 폼 | 필드 행의 인라인 `ⓘ` 버튼(🎲·✨과 같은 문법) | **1차** — 입력하는 자리에서 가장 값지다 |
| 캐릭터 상세 / 보충 미리보기(`DynamicFieldRenderer`) | 필드명 옆 `ⓘ` | **2차**(11장 백로그) |

- **설명이 없는 필드에는 아이콘을 만들지 않는다.** 눌러도 빈 다이얼로그가 뜨는 버튼은 구색이다.
- 인라인 버튼이 셋(🎲 ✨ ⓘ)까지 늘어나므로 `addInputRow`의 가로 배치 폭을 확인할 것 —
  좁은 화면에서 입력창이 뭉개지면 `ⓘ`를 필드 **라벨 옆**으로 옮긴다(9장 검증 항목).

**표시 컴포넌트는 P3의 `HelpDialog`와 공유한다.** 진입만 둘로 나눈다:

```
HelpDialog.showHelp(fragment, helpKey)        // 앱 도움말 — 개발자 작성, strings.xml  (P3)
HelpDialog.showFieldNote(fragment, field)     // 필드 설명 — 사용자 작성, config       (P-A)
```

> **P3의 착수 게이트를 깨지 않는다.** P3가 금지한 것은 *도움말 본문을 승인 없이 쓰는 것*이지
> 다이얼로그 컴포넌트가 아니다. P-A는 껍데기(제목+본문+선택적 예시 블록)만 만들고 본문을 쓰지
> 않는다. P3는 그 위에 `helpKey` 규약과 본문을 얹는다. **같은 화면에 둘 다 필요하면 아이콘을
> 나눈다 — `ⓘ` = 사용자가 쓴 설명, `?` = 앱 도움말.**

### 4-4. AI에게 어떻게 전달되는가

`FieldSpec`에 `description: String`을 더하고, `fieldSpecOf`가 채운다. 프롬프트의 대상 줄에 붙는다.

```
- key: mana_affinity / 이름: 마나친화 / 타입: 숫자 / 범위: 0~100
  / 설명: 이 세계의 마나를 몸에 받아들이는 정도. 60 이상은 마법사 계열만 나온다.
  / 기존 사용값(총 18종 중 12개 예시): 12, 25, 33, …
```

시스템 프롬프트에 규칙을 하나 더한다(현행 13개 뒤).

```
14. '설명'이 붙은 필드는 그 설명이 이 작품에서 그 필드가 뜻하는 바의 정의이자 제약이다.
    설명과 어긋나는 값을 내지 마라. 설명이 옵션·형식과 충돌하면 옵션·형식을 따르고,
    무엇이 충돌했는지 reason에 적어라.
```

**적용 범위 — 세 경로 전부.** 짧은 값 추천(`CharacterFieldAiSuggester`)·서술형 작성
(`NarrativeFieldAiWriter`)·값 라이브러리 AI 정리(`FieldLibraryAiOrganizer`)가 모두 같은 필드를
다루므로, 한 곳만 싣게 두면 같은 필드가 경로마다 다른 정의로 해석된다.

**상한과 고지:**

- 프롬프트에 싣는 길이 상한 `MAX_DESCRIPTION_PROMPT_CHARS = 300`. 초과분은 잘라 싣고
  `truncationNotes`로 고지한다(R-14). 저장 상한(1000)과 프롬프트 상한(300)이 다른 이유는
  **인앱 설명은 길어도 되지만 요청마다 15필드분이 실리기 때문**이다(대략 15 × 300자 ≈ 2~3천 토큰).
- **대상 필드에만 싣는다.** `[입력된 필드]` 절의 컨텍스트 필드에는 설명을 싣지 않는다 —
  거기서는 값 자체가 정보이고, 설명은 "무엇을 만들지"의 지시라서 대상에만 의미가 있다.

**설명은 프롬프트 적재량 설정(`AiPromptSettings`)의 대상이 아니다.**
기존 사용값 예시·문체 참고는 0으로 끌 수 있지만 설명은 끌 수 없다. 근거는 `ai_integration.md`가
이미 세운 문장 그대로다 — **"설정이 끄는 것은 토큰이지 정확성이 아니다."** 예시는 일관성을 돕는
*힌트*지만 설명은 값의 *계약*이다. 계약을 토큰 절약으로 떼면 그 필드의 추천은 그냥 틀린 답이 된다.

### 4-5. 엑셀 왕복 (개발 의도 4번 — 엑셀 왕복 무결성)

`필드 정의` 시트에 **전용 열 둘**을 더한다.

```
… 타입 | 설정(JSON) | 그룹 | 순서 | 필수여부 | AI추천 | 필드설명 | 세계관코드 | 대상
                                              └ Y/N ┘  └ 자유문 ┘
```

**왜 JSON 셀에 두지 않고 열을 파는가:** 이 사용자는 엑셀 우선 작업자다
(`docs/usage_reality_check_2026-07.md`). 설명은 **사람이 쓰는 산문**인데 JSON 문자열 안에서만
편집 가능하면(따옴표 이스케이프·한 셀에 뭉친 설정 전체) 사실상 앱에서만 쓸 수 있다.
전용 열이면 214행에 채워 넣고 한 번에 들일 수 있다.

**파일 안에 같은 사실을 두 벌 두지 않는다** — 내보낼 때 `설정(JSON)` 셀에서는 `aiSuggest`와
`description` 두 키를 **제거**하고 전용 열에만 싣는다. 두 벌이면 어느 쪽이 진짜인지 물어야 하고,
그 질문에 좋은 답이 없다.

**가져오기 병합 규칙 (여기를 틀리면 설명이 통째로 날아간다):**

```
merged = 셀의 설정(JSON)
① 'AI추천' 열이 있으면      → 그 값으로 aiSuggest 를 덮는다
   열이 없고 JSON에도 키가 없으면 → 기존 DB 값을 다시 얹는다   ← 빠뜨리면 무통보 유실
   열이 없고 JSON에 키가 있으면   → 그대로 둔다(구버전 파일)
② '필드설명' 열도 같은 3분기
```

`필수여부`가 이미 쓰는 `sheetBooleanOrKeep`(열 없음 = 기존 유지)과 **같은 문법**이다.
새 필드(기존 DB 행 없음)는 열·키가 모두 없으면 기본값이다.

- 설명이 셀 규격(32,767자)을 넘길 일은 저장 상한 1000자 때문에 없다. `setTextSafe`가 그대로 방어한다.
- `사용 안내` 시트에 한 줄 더한다 — "`필드 정의` 시트의 **AI추천·필드설명** 열을 채워 다시
  가져오면 AI 추천 동작에 반영됩니다."(P4의 U-12c와 같은 성격의 발견성 조치)

**월드패키지(`.ncworld`)는 손댈 것이 없다.** `WorldPackageExporter:118`은 `FieldDefinition`
객체를 Gson으로 통째 직렬화하므로 `config`의 새 키가 자동으로 왕복한다.
**두 내보내기 경로의 규칙이 달라도 되는 이유**가 여기에 있다 — 월드패키지는 *객체*를 나르고
엑셀은 *사람이 고칠 표*를 나른다. 엑셀에만 열을 파는 것은 규칙의 분기가 아니라 매체의 차이다.
(단 착수 시 확인할 것: 엑셀 내보내기에서 JSON 셀의 키를 제거하는 코드가 **DB의 config를 건드리지
않고 사본에만 적용**되는지. 원본을 고치면 월드패키지 쪽이 함께 비어 버린다.)

## 5. A-3 — 보충 탭 AI 추천

### 5-1. 두 탭 중 어디에 붙는가

보충 화면은 내부 탭 둘이다.

| 탭 | 현재 AI 도달 경로 | 이번 작업 |
|---|---|---|
| **완성도 검사** | `보충 시작` → `CharacterEditFragment(supplementMode)` → **이미 AI 추천이 있다** | **없음.** 이미 도달한다는 사실을 화면에 알리는 것으로 충분 |
| **랜덤 보충** | 없음 | **이번 작업의 전부** |

완성도 검사 목록의 각 행에 "AI로 채우기"를 다는 안은 **기각**한다. 폼 없이 실행하면 결과를 적용할
위젯이 없어 DB 직접 기록이 되고, 그것은 `ai_integration.md`의 절대 규칙("AI 출력은 어떤 경우에도
자동 적용·DB 직접 기록되지 않는다")을 깬다.

**AI가 메울 수 있는 미흡 항목은 하나뿐이라는 사실도 밝힌다** — `SupplementIssue` 중
`INCOMPLETE_FIELDS`만 값 추천으로 해소되고, 이미지 없음·관계 없음·작품 미배정·사건 없음·세력 없음은
AI 추천의 대상이 아니다. 비용 고지에 이 한 줄을 넣어 기대치를 맞춘다(변수 제어).

### 5-2. 편집 모드에서만 노출한다

랜덤 보충 탭은 미리보기(PREVIEW) ↔ 인라인 편집(EDIT) 두 상태다. **AI 진입은 EDIT에서만** 보인다.

- 근거: AI 결과는 **폼 위젯에만 기입**되고 영속화는 사용자의 저장이다. PREVIEW에는 기입할 폼이 없다.
- 마찰 검토: 편집 스위치는 접힘과 무관하게 **상시 노출**이므로(design_intent 규칙 4) EDIT까지 1탭이다.
- 기각한 대안: PREVIEW에서 AI 버튼을 누르면 자동으로 EDIT로 들어가며 다이얼로그를 여는 안.
  1탭을 아끼는 대신 **상태 전환과 유료 요청이 한 번에 일어나** 되돌릴 자리가 모호해진다.

배치: 편집 컨테이너 안, `dynamicFormContainer` 바로 위에 `btnAiSuggest`(편집 화면과 같은 위치·같은
문자열). 필드별 ✨은 `formBuilder.aiSuggestHandler`를 설정하면 **자동으로** 붙는다.

### 5-3. 컨텍스트 조립기를 공유한다 (중복 금지)

`CharacterEditFragment.buildAiContext()`(:624)는 이름·이명·태그·메모를 폼 위젯에서, 이미지 태그·
소속·관계를 VM 로더에서 읽어 `CharacterAiContext`를 만든다. 보충 탭의 편집 폼은 **같은 id의 위젯**
(`editName`·`editLastName`·`editFirstName`·`editAnotherName`·`editTags`·`editMemo`)과 같은
`imageStrip`·같은 `CharacterViewModel`을 가진다.

그대로 복사하면 두 화면이 갈린다 — 이 저장소가 반복해서 겪은 실패 형태다. **`ui/character/
CharacterAiContextBuilder`로 추출**하고 두 화면이 `Host` 인터페이스만 구현한다.

```kotlin
interface Host {
    fun rawName(): String; fun firstName(): String; fun lastName(): String
    fun aliasesRaw(): String; fun tagsRaw(): String; fun memo(): String
    fun imagePaths(): List<String>
    fun characterId(): Long          // -1이면 소속·관계 조회를 건너뛴다
    fun formBuilder(): DynamicFieldFormBuilder
}
suspend fun build(host: Host, viewModel: CharacterViewModel): CharacterAiContext
```

`loadFailures` 고지(이미지 태그·소속·관계 조회 실패)도 함께 옮겨 두 화면이 같은 결손 보고를 한다.

### 5-4. 뽑기와 AI 실행이 겹치는 경우 — 이 탭에만 있는 위험

편집 화면은 캐릭터가 하나로 고정이지만 **랜덤 보충 탭은 요청 도중에 캐릭터가 바뀔 수 있다**
(다시 뽑기 ◀ ▶, 필터 변경, 캐릭터 삭제). 지금 구조 그대로 얹으면 A를 근거로 받은 유료 추천이
B의 폼에 기입된다 — 무통보 오염이다.

**두 겹으로 막는다.**

1. **예방** — 실행 중(`aiSuggestRunning == true`)에는 뽑기 이동·모드 변경을 막는다.
   기존 `guardedPickAction`에 조건을 더하고, 막힐 때는 조용히 삼키지 않고 "AI 추천을 받는
   중입니다"를 띄운다.
2. **검출** — `CharacterViewModel.AiSuggestRun`에 `targetCharacterId`를 더한다. 결과를 표시하기
   전에 지금 화면의 캐릭터와 비교해 다르면 **적용 대신 선택지를 준다**:
   `[○○(으)로 돌아가 적용] / [버리기]`.
   예방만으로 부족한 이유는 프로세스 재생성·회전·탭 전환처럼 예방이 닿지 않는 경로가 있고,
   유료 응답을 조용히 버리는 것도 조용히 오적용하는 것도 둘 다 안 되기 때문이다.

`targetCharacterId`는 편집 화면에서는 언제나 일치하므로 그쪽 동작은 바뀌지 않는다.

### 5-5. 미저장 편집 가드와의 관계

- AI 적용은 `applyRandomValue` 경로라 `onFieldChanged` → `markDirty()`가 걸린다.
  **적용 직후 `hasUnsavedChanges == true`가 되는지 실기기에서 확인할 것**(9장).
- 적용은 저장이 아니다. 사용자가 저장하지 않고 다시 뽑으면 기존 미저장 가드가 그대로 뜬다 —
  새 경로를 만들지 않는다.
- 자동저장 옵트인 상태에서 AI 적용 후 다시 뽑기를 누르면 **검토 없이 저장된다.** 이것은 기존
  자동저장 계약대로이므로 바꾸지 않되, AI 적용 결과 토스트에 "저장을 눌러야 반영됩니다"
  문구가 자동저장 상태에서 거짓이 되지 않도록 문구를 상태에 맞춘다.

## 6. A-4 — 창작도 (Creativity)

### 6-1. 무엇을 넓히고, 무엇을 넓히지 않는가 (요청 3의 단서)

> **창작도는 값의 후보 공간을 넓히지, 계약을 넓히지 않는다.**

| 넓힌다 | 넓히지 않는다 (창작도와 무관하게 항상 강제) |
|---|---|
| 값의 다양성·의외성 | **필드 설명**(A-2)의 내용 |
| 기존 사용값 밖으로 나갈 자유 | SELECT·GRADE **옵션** 목록 |
| 서술형의 문체·전개 폭 | 생일 `MM-DD`·구조화 입력 등 **형식** |
| | `inputMode = restricted`의 **허용 목록** |
| | 캐릭터 정보와의 **모순 금지** |

오른쪽 열은 전부 **응답을 받은 뒤 코드가 검증**하는 항목이다(`parseResponse`의 옵션 일치·달력
유효성·구조화 파트 수·`isAllowedByLibrary`). 그래서 창작도를 최대로 올려도 **잘못된 값이 저장되는
경로는 생기지 않는다** — 어긋난 값은 `MissingCause.INVALID`/`RESTRICTED`로 사유와 함께 제외된다.
창작도를 올리는 비용은 "드롭이 늘어날 수 있다"이지 "데이터가 망가진다"가 아니다.

### 6-2. 2층 구조 — 샘플링과 지시

온도만 올리면 표현이 흔들릴 뿐 **무엇을 후보로 삼을지**는 바뀌지 않고, 지시만 바꾸면 모델이
여전히 가장 무난한 답으로 수렴한다. 그래서 둘 다 바꾼다.

**① 샘플링** — `AiRequest`에 `temperature: Double?`을 더한다(`null`이면 **파라미터를 싣지 않는다**).
프로토콜별 직렬화는 `AiProtocolCodec`이 전담한다(`messages`/`chat.completions`/`generationConfig`).

**② 지시** — 단계별 규칙 문구를 시스템 프롬프트 꼬리에 붙인다(`confidenceFloorRule`과 같은 문법).

### 6-3. 단계 정의 — 4단, 기본은 무회귀

`ai/AiCreativity.kt`(순수, 단위 테스트 대상):

| 단계 | wire | temperature | 지시 요지 |
|---|---|---|---|
| **정확** | `precise` | `0.1 × max` | 캐릭터 정보와 기존 사용값에서 직접 도출되는 값만. 새 표기를 만들지 마라 |
| **균형**(기본) | `balanced` | **미전송** | 현행 프롬프트 그대로 — 추가 규칙 없음 |
| **자유** | `free` | `0.85 × max` | 기존 사용값은 *표기 방식*의 참고이지 선택지의 울타리가 아니다. 표기 스타일(길이·상세도)은 따르되 값 자체는 새로워도 된다 |
| **실험** | `bold` | `1.0 × max` | 뻔한 답을 피하고 서로 다른 방향을 시도하라. 단 설명·옵션·형식은 그대로 지킨다 |

```
프로토콜별 max:  ANTHROPIC 1.0 / OPENAI_COMPAT 1.4 / GEMINI 1.4
```

- **기본값 `균형`은 temperature를 아예 싣지 않는다** → 프로바이더 기본값 그대로 = **현행과
  완전히 동일**. 설정을 열지 않은 사용자의 동작은 바뀌지 않는다(회귀 없음). 이 저장소가
  `AiTokenPolicy.DEFAULT_REQUEST`에서 지킨 것과 같은 태도다.
- **OpenAI·Gemini의 상한을 규격 최대(2.0)가 아니라 1.4로 잡는 이유:** 이 기능들은 JSON 스키마
  응답을 요구한다. 온도가 과하면 **형식이 무너져 유료 응답이 통째로 버려진다**(`UNREADABLE`).
  상한은 프로토콜 상한이 아니라 **형식이 무너지지 않는 상한**이다.

### 6-4. 프로토콜 상한이 다르다는 사실을 숨기지 않는다

Anthropic은 온도 상한이 1.0이라 **`자유`와 `실험`의 샘플링이 같다**(0.85 vs 1.0으로 좁다).
차이는 지시 문구에서만 난다. 이것을 감추면 "올려도 똑같다"는 불신이 생긴다.

**선택지 아래 한 줄로 밝힌다** — "현재 프로바이더는 온도 상한이 1.0이라 *실험*과 *자유*의 차이가
작습니다. 차이는 지시 문구에서 납니다." 활성 프로바이더의 프로토콜에 따라 문구가 바뀐다.

### 6-5. 모델이 temperature를 거부하는 경우 (자동 교정)

OpenAI 호환의 일부 추론 모델은 `temperature`를 거부하고 400을 돌려준다.
`max_tokens` → `max_completion_tokens` 자동 재시도와 **같은 형태**로 처리한다.

```
① AiProtocolCodec.isTemperatureUnsupportedError(code, detail) 로 판정
② temperature 를 뺀 요청으로 1회 재시도
③ 성공하면 AiProviderConfig.temperatureUnsupported = true 로 기억 (다음부터 안 싣는다)
④ 결과 고지에 한 줄 — "이 모델은 창작도의 샘플링 조절을 지원하지 않아 지시 문구만 적용했습니다"
```

④를 빠뜨리면 사용자는 창작도를 올렸는데 아무 변화가 없는 이유를 영영 모른다(조용한 실패).
③의 기억은 **R-23**에 따라 모델·주소가 바뀌면 함께 버린다.

### 6-6. 다른 설정과의 충돌 — 미리 막는다

**근거 강도(`minConfidence`)와의 충돌.** 창작도를 올리면 모델은 근거가 얕은 값을 더 낸다.
사용자가 `minConfidence`를 `확실`로 올려 둔 상태에서 창작도를 `실험`으로 올리면 **낸 값의
대부분이 `BELOW_CONFIDENCE`로 제외되어 돈만 나가고 결과가 없다.**

→ 창작도 선택 UI에서 `자유`·`실험`을 고르고 `minConfidence != null`이면 **그 자리에서** 경고한다:
"근거 강도 하한이 '확실'로 설정돼 있어 창작도를 올려도 대부분 제외됩니다. [강도 하한 낮추기]"
링크는 설정 화면이 아니라 **그 값을 바로 바꾸는 다이얼로그**여야 한다(원칙 04).

**표기 기조(기존 사용값)와의 충돌.** 시스템 규칙 9는 "같은 뜻이면 기존 값을 그대로 쓴다"인데
창작도 `자유` 이상은 이것과 정면으로 부딪친다. 규칙을 **덮어쓰지 말고 좁힌다** —
`자유` 이상에서는 규칙 9의 적용 범위를 *표기 방식(길이·상세도·어투)*으로 한정하는 문장을
꼬리 규칙에 넣는다. `restricted` 필드의 규칙 10은 **어느 단계에서도 완화하지 않는다**(허용
목록은 취향이 아니라 계약이다).

### 6-7. 적용 범위

| 경로 | 창작도 적용 | 이유 |
|---|---|---|
| 짧은 값 추천 | **적용** | 요청의 본체 |
| 서술형 작성 | **적용** | 창작 폭이 가장 크게 체감되는 자리 |
| 값 라이브러리 AI 정리 | **미적용** | 그것은 창작이 아니라 *정리*다. 무작위성이 유사값 병합·오탈자 교정에서는 해가 된다 |
| 연결 테스트 | 미적용 | 검증 요청이다 |

### 6-8. 어디에 두는가 — "접근하기 쉽고 방해되지 않는 위치"

**값은 하나다.** 어디서 바꾸든 같은 설정(`AiPromptSettings.creativity`)을 바꾼다.
"이번 요청만"과 "기본값"을 나누는 안은 기각한다 — 화면마다 다른 값이 살아 있으면 사용자가
일일이 열어봐야 지금 무엇으로 요청되는지 알 수 있고, 그것이 원칙 04가 금지한 상태다.

| 자리 | 형태 | 성격 |
|---|---|---|
| 설정 → AI 연동 | `AI 추천 일관성` 카드 아래 **창작도 카드** — 4택 라디오 + 단계 설명 + 6-4 고지 | 기본 자리(발견성) |
| **추천 실행 다이얼로그**(비용 고지) | 대상 수 아래 **칩 한 줄** | 실행 직전 1탭 |
| **검토 화면의 `보완` → 다시 요청** | 지시 입력창 위 **같은 칩 한 줄** | 가장 값진 자리 — "이 값은 뻔하다 → 올려서 다시"가 1탭이 된다 |
| 서술형 작성 시트 | 후보 생성 버튼 옆 **같은 칩 한 줄** | |

칩 한 줄(높이 ~32dp)이라 기존 다이얼로그 레이아웃을 밀지 않는다. 별도 진입점·별도 화면을
만들지 않는 것이 "다른 기능 사용에 방해되지 않는 위치"에 대한 답이다.

## 7. N-1 — 캐릭터 탭 상단 밀도와 ⋮ 통합

### 7-1. 현행

```
① MaterialToolbar (?attr/actionBarSize)   제목 "캐릭터" + [보충 라벨버튼] [일괄편집] [⋮ 순서변경]
② compareLayout                            [검색 ────────] [컨트롤] [비교] ([취소])
③ filterSortBar                            [프리셋 칩][정렬 칩][필터 칩]   ← 조건부
```

제목 `캐릭터`는 하단 내비게이션이 이미 말하고 있고, ①이 통째로 한 행을 쓴다.

### 7-2. 설계 — 3행을 2행으로

```
① 액션 행     [검색 ──────────────] [컨트롤] [⋮]
② filterSortBar (조건부, 현행 유지)
```

- **툴바는 지우지 않고 조건부로 감춘다.** 이 프래그먼트는 탭 루트(`novelId == -1`)뿐 아니라
  **작품별 캐릭터 목록으로 푸시되기도 한다**(`CharacterListFragment:108` 이 뒤로가기 아이콘을
  단다). 푸시 상태에서는 툴바가 뒤로가기와 작품명을 보여줘야 하므로 **살아 있어야 한다.**
  → 탭 루트에서만 `toolbar.visibility = GONE`.
- **⋮ 하나에 넷을 모은다:** `보충` · `비교` · `일괄 편집` · `순서 변경`.
  액션 행의 `ImageButton`(`ic_more_vert`)에 `PopupMenu`를 붙인다 — 일괄 편집 바
  (`btnBatchOverflow`)가 이미 쓰는 문법이라 새 패턴이 아니다.
- **메뉴 호스트는 하나다.** 액션 행은 **두 상태 모두에서** 보이므로, 툴바가 보이는 푸시
  상태에서도 툴바는 **네비게이션 아이콘 + 제목만** 갖고 메뉴는 갖지 않는다
  (`toolbar.inflateMenu` 호출 제거). 두 곳에 메뉴를 두면 같은 항목의 가시성 게이팅
  (보충은 탭 루트에서만)이 두 벌이 되어 반드시 갈린다.
- **`character_menu.xml`과 `action_supplement.xml`은 삭제한다.** 항목이 `PopupMenu`로 옮겨가면
  둘 다 참조가 없어진다. 남겨 두면 다음 사람이 "여기를 고치면 되겠다"고 읽는 죽은 리소스가 된다
  (S-10 스트리밍 리더가 같은 형태로 방치돼 있다).

### 7-3. 규칙 2와 충돌한다 — 규칙을 고친다

`docs/design_intent_2026-07.md` 규칙 2와 `character_menu.xml` 주석은 **정반대**를 말한다:

> "보충은 `always` 고정 — overflow로 밀리면 진입이 숨은 2탭으로 회귀한다."

그 규칙이 지키려던 것은 **보충의 발견성**이지 툴바의 자리가 아니다. 그리고 이번 변경은
발견성을 다른 표면으로 옮겨 **더 늘린다**:

| | 변경 전 | 변경 후 |
|---|---|---|
| 홈 대시보드 | 없음 | **도구 타일 `보충`**(N-2) — 앱 첫 화면에서 0탭 가시 |
| 캐릭터 탭 | 툴바 라벨 버튼(1탭) | ⋮ 안(2탭) |

앱을 열면 가장 먼저 보이는 화면에 상시 노출되는 진입점이 새로 생기므로 **총 발견성은 올라간다.**
규칙 2의 근거가 무너지는 것이 아니라 **다른 수단으로 충족**된다. 규칙 본문을 그렇게 고친다(10장).

> **덧붙일 규칙:** *진입점을 덜 눈에 띄는 자리로 옮길 때는, 옮기기 전에 더 눈에 띄는 자리에
> 대체 진입점을 먼저 만든다.* 그래서 0장이 **N-2 → N-1** 순서를 강제한다.

### 7-4. 비교 모드는 전용 바를 갖는다

지금은 `btnCompare`가 진입 버튼이면서 선택 수 표시(`compare_button_text`)와 실행을 겸하고,
옆의 `btnCancelCompare`가 취소다. 진입이 ⋮로 들어가면 **모드 중의 상태·실행·취소가 갈 곳이 없다.**

→ 일괄 편집 모드와 **같은 문법**으로 `compareBar`를 둔다(`batchEditBar`와 형제):
`[✕ 취소] 선택 2/N  ……  [비교하기]`. 모드 진입 시 액션 행을 감추고 이 바를 띄운다.
새 패턴이 아니라 이미 있는 패턴의 재사용이며, "모드에 들어와 있다"는 사실이 화면에 상주한다.

### 7-5. 하지 않는 것

- **검색창을 아이콘으로 접지 않는다.** 검색은 이 화면의 주 조작이고, 접으면 1탭이 늘면서
  절감은 0이다(행 수가 그대로다).
- **filterSortBar를 합치지 않는다.** 칩 행은 이미 조건부(칩이 없으면 GONE)이고, 활성 필터를
  상시 보이게 하는 것이 규칙 3의 취지다.

## 8. N-2 — 홈 도구에 보충 + 하단 영역 밀도

### 8-1. 홈 도구 타일 `보충`

`fragment_home_dashboard.xml`의 ⑤ 도구 섹션에 `cardSupplement`를 **첫 타일**로 넣는다
(연표 → 이름 은행 → 이미지 → 엑셀 앞).

- 계층 배정(규칙 1): ⑤ 저빈도 도구. ④ 바로가기가 아닌 이유는 **생성 진입이 아니라 이동**이기 때문.
  도구 안에서 첫째인 이유는 넷 중 유일하게 "지금 뭘 손봐야 하는가"에 답하는 작업 진입이라서다.
- 스타일: `Widget.App.Card.Tonal` + `ic_supplement` + `@string/tab_supplement`(규칙 2의 이동 타일).
- 이동: `supplementFragment`는 전역 목적지라 인자 없이 id로 이동한다(`imageManagerFragment`와 동일).
  보충의 세계관·작품 필터는 자기 prefs(`supplement_ui_state`)에서 복원되므로 넘길 인자가 없다.

### 8-2. 하단 내비게이션 밀도

`Widget.Material3.BottomNavigationView`는 위 12dp·아래 16dp 패딩으로 80dp급이다.
5개 항목이라 항목당 폭도 좁다.

```xml
<style name="Widget.App.BottomNavigation" parent="Widget.Material3.BottomNavigationView">
    <item name="itemPaddingTop">6dp</item>       <!-- 12dp → 6dp -->
    <item name="itemPaddingBottom">8dp</item>    <!-- 16dp → 8dp -->
    <!-- labelVisibilityMode=labeled 유지 -->
</style>
```

- **라벨을 끄지 않는다.** `labelVisibilityMode="selected"`로 바꾸면 12dp쯤 더 줄지만, 규칙 2의
  "오독 여지가 있는 진입점은 아이콘 단독 금지"에 정면으로 걸린다. 밀도를 위해 발견성을 파는 거래는
  이 앱의 결이 아니다.
- **스크롤 시 숨김(`HideBottomViewOnScrollBehavior`)도 채택하지 않는다.** 목록을 조금만 움직여도
  탭이 사라져 "존재를 알 수 없는" 상태를 만든다(원칙 04).
- 절감폭은 기기·폰트 배율에 따라 다르므로 **수치를 약속하지 않는다.** 실기기에서 재고, 항목 라벨이
  두 줄로 접히면 되돌린다(9장 검증 항목).

### 8-3. FAB이 마지막 항목을 가린다

`characterRecyclerView`는 `padding=4dp`로 부모 바닥까지 차 있고 `fabAddCharacter`가 그 위에 뜬다.
스크롤을 끝까지 내려도 **마지막 카드가 FAB에 가린다.** 하단 영역 최적화의 실질은 여기다.

→ `paddingBottom = 88dp` + `clipToPadding="false"`. 목록 화면 전반에 같은 문제가 있는지는
착수 시 훑는다(같은 형태면 같은 수리 — 방편식 패치 금지).

## 9. 검증 규약

`remaining_work_2026-07.md` §5-6·§5-7과 `repair_plan_2026-07.md` 8장 그대로.

1. **순수 JVM 테스트** — 기준선 수는 적지 않는다(이 문서 안에서만 677·745 두 값이 돌아다녔다). **실행 결과를 믿는다** — 기준선은 `remaining_work_2026-07.md` 5장이 든다.
   `JARS_DIR=<스크래치패드> tools/run_jvm_tests.sh`. **테스트를 추가하면 러너 목록도 갱신할 것**
   (PR #88이 이것을 빼먹어 master의 하네스가 컴파일조차 안 됐다).
2. **차분 컴파일** — 건너뛰지 말 것. 이번 작업은 Fragment·Adapter·레이아웃 비중이 커서
   순수 하네스가 통과해도 실빌드가 깨질 수 있다.
3. **리소스 점검** — A-1~A-4·N-1~N-2가 전부 `strings.xml`을 건드린다. 레이아웃 id ↔ 바인딩 교차 확인.
4. **마이그레이션 하네스 — 불필요.** 이번 설계에 **스키마 변경이 없다**(전부 `config` JSON 키와
   prefs). 이것이 A-1·A-2를 값싸게 만드는 이유다.
5. **자기 재공격** — 각 단계 종료 시. 특히 **"안전망을 새로 만든" 코드를 의심할 것** —
   이번에는 5-4의 캐릭터 불일치 검출과 6-5의 temperature 자동 재시도가 정확히 그 성격이다.

### 실기기에서만 확인되는 것 (사용자 확인 항목) → **`remaining_work` 3-23장으로 이관**

> **실기기 확인의 단일 목록은 `remaining_work` 3장이다**(CLAUDE.md 문서 지도).
> 아래 10건은 그 목록 밖에 있어 사용자가 순회할 때 나타나지 않았다 — 옮겼다.
> 아래는 이관 전 원문이다.

1. 필드 관리에서 드래그 핸들로만 순서가 바뀌고, 롱프레스는 옵션 다이얼로그만 뜬다.
2. 목록 스위치를 끄면 그 필드의 ✨이 사라지고, 일괄 고지에 "AI 추천 꺼짐 1개"가 뜬다.
3. 필드 설명을 넣고 엑셀 내보내기 → 셀에서 편집 → 들이기 → 설명이 바뀐다.
   **`필드설명` 열을 지우고 들이면 기존 설명이 남는다**(무통보 유실 없음).
4. 보충(랜덤) 탭 편집 모드에서 AI 추천 → 적용 → 저장 버튼이 활성화된다.
5. 보충 탭에서 AI 실행 중 다시 뽑기를 누르면 막히고 사유가 뜬다.
6. 창작도를 `실험`으로 올리면 — ① 근거 강도 하한이 걸려 있을 때 **그 자리에서 경고**가 뜨고
   ② Anthropic 프로바이더에서는 "상한 1.0이라 자유와 차이가 작다"는 고지가 뜬다.
   (요청 본문에 `temperature`가 실제로 실리는지는 순수 테스트가 본다 — 기기에서 볼 수 없다.)
7. 캐릭터 탭 상단이 2행이고, ⋮에 보충·비교·일괄 편집·순서 변경이 있다. 작품별 목록으로 들어가면
   툴바(뒤로가기 + 작품명)가 **다시 나타나고, 그 툴바에는 메뉴가 없다**(⋮는 액션 행에 그대로).
8. 비교를 켜면 전용 바(취소 · 선택 수 · 비교하기)가 뜨고, 끄면 액션 행이 돌아온다.
9. 홈 도구의 `보충` 타일로 보충 화면에 도달한다.
10. 목록 맨 아래 카드가 FAB에 가리지 않는다. 하단 탭 라벨이 두 줄로 접히지 않는다.

## 12. 최종 검토 — 이 설계를 다시 공격해 고친 것

초안을 5개 렌즈(회귀 / 조용한 실패 / 규모 / 규약 충돌 / 기존 문서와의 모순)로 다시 읽어 고친 것들이다.
**아래는 전부 초안에서 틀렸던 것이고, 본문은 이미 고쳐진 상태다.**

1. **[회귀] 창작도 기본값이 현행 동작을 바꿀 뻔했다.** 초안은 `균형 = 0.35 × max`를 보냈다.
   그러면 설정을 한 번도 열지 않은 사용자의 출력이 조용히 보수적으로 바뀐다. → `균형`은
   **파라미터를 싣지 않는다**로 정정(6-3). 이 저장소가 `DEFAULT_REQUEST = 4096`에서 지킨 태도와 같다.
2. **[조용한 실패] 툴바를 지우려 했다.** 초안은 캐릭터 탭 툴바를 제거해 한 행을 벌려 했는데,
   같은 프래그먼트가 **작품별 목록으로 푸시될 때 뒤로가기를 그 툴바에 단다**(`:108`).
   지웠으면 그 화면에서 나갈 길이 사라졌다. → 탭 루트에서만 `GONE`(7-2).
3. **[규약 충돌] 진입점을 옮기면서 발견성 근거를 그냥 버릴 뻔했다.** `character_menu.xml`의
   `always` 고정에는 명시적 사유 주석이 있었다. 무시하고 옮기면 같은 실수를 반복하게 된다.
   → 규칙의 *근거*를 다른 표면(홈 타일)으로 충족시키고 **순서를 강제**(N-2 → N-1), 규칙 본문을
   개정하는 것으로 정리(7-3, 10장).
4. **[조용한 실패] 엑셀 병합에서 설명이 통째로 날아갈 뻔했다.** `설정(JSON)` 셀에서 두 키를
   제거하기로 해 놓고 가져오기 병합을 "열이 있으면 덮는다"로만 적었다. **열을 지운 파일**을
   들이면 셀에도 없고 열에도 없어 설명이 사라진다. → 4-5의 3분기 규칙(열 없음 + 키 없음 =
   **기존 DB 값 보존**)을 명시하고 `sheetBooleanOrKeep` 선례에 붙였다.
5. **[규모] 보충 탭에서 유료 응답이 남의 캐릭터에 붙을 수 있었다.** 편집 화면 코드를 그대로
   재사용한다는 판단은 맞았지만, 편집 화면에는 없는 전제("캐릭터가 요청 도중 바뀔 수 있다")를
   놓쳤다. → 예방(실행 중 뽑기 잠금) + 검출(`targetCharacterId` 비교)의 2겹(5-4).
   *예방만 두면 회전·프로세스 재생성 경로가 남고, 검출만 두면 흔한 경로에서 매번 사용자를
   귀찮게 한다.*
6. **[규약 충돌] 새 학습값이 옛 결함을 복제할 뻔했다.** `temperatureUnsupported`를 config에
   기억하기로 정한 순간, 이미 같은 성격인 `detectedOutputLimit`이 **모델 변경 시 초기화되지
   않는다**는 사실이 드러났다. 새 값만 올바르게 만들면 규칙이 갈린다. → **R-23**을 세우고
   기존 값까지 함께 고치는 것을 A-0에 넣었다(2-2).
7. **[조용한 실패] 행에 스위치를 그냥 얹을 뻔했다.** 필드 관리만 드래그가 롱프레스에 걸려
   있고 핸들이 장식이라는 사실(나머지 4곳과 다름)을 확인하고 A-0-1을 선행 조건으로 올렸다(2-1).
8. **[기존 문서와의 모순] 필드 설명과 P3 도움말이 같은 `?`를 두고 부딪쳤다.** 둘은 출처가
   다르다(사용자 / 개발자). → 컴포넌트는 공유하고 **아이콘을 나눈다**(`ⓘ` / `?`), P3의 착수
   게이트는 건드리지 않는다(4-3).
9. **[규모] 필드 설명이 프롬프트를 삼킬 뻔했다.** 저장 상한만 두고 프롬프트 상한을 두지 않았다.
   요청당 15필드면 저장 상한 그대로 실릴 때 수천 토큰이다. → 저장 1000자 / 프롬프트 300자로
   분리하고 초과를 `truncationNotes`로 고지(4-4).
10. **[조용한 실패] 일괄 추천에서 서술형이 빠지는 것을 사용자가 모를 뻔했다.** 결함을 고치는
    것까지는 맞았지만, 고친 결과가 "성격·배경이 일괄에서 안 나온다"로 체감된다. → 제외 사유
    줄에 "필드별 ✨에서 작성합니다"를 병기(3-5)하고 후속을 B-45로 등재.
11. **[규모] 창작도와 근거 강도가 서로를 무력화하는 조합이 있었다.** `실험` × `확실`은 돈만
    나가고 결과가 없다. → 선택 시점에 경고 + 그 자리에서 하한을 바꾸는 링크(6-6).
12. **[기존 문서와의 모순] 하단바를 아이콘만 남겨 줄이려 했다.** 규칙 2의 "아이콘 단독 금지"에
    정면으로 걸린다. → 라벨 유지 + 패딩 압축으로 정정하고, 실질 이득은 FAB 여백(8-3)에서
    가져오는 것으로 바꿨다.

### 문서를 다 쓴 뒤 한 번 더 훑어 고친 것 (교차 문서 검토)

13. **[조용한 실패] 메뉴 호스트가 둘이 될 뻔했다.** 툴바를 조건부로 감추기로 하면서 메뉴는
    그대로 툴바에 두면, 탭 루트에서는 `PopupMenu`가·푸시 상태에서는 툴바 메뉴가 같은 항목을
    갖게 된다. **보충의 "탭 루트에서만 노출" 게이팅이 두 벌**이 되고, 두 벌이 된 게이팅은
    반드시 갈린다. → 툴바에서 `inflateMenu`를 걷어 내고 액션 행의 ⋮ 하나만 남긴다(7-2).
    함께: 참조가 사라지는 `character_menu.xml`·`action_supplement.xml`을 **삭제**한다 —
    남은 죽은 리소스는 다음 사람을 잘못된 자리로 부른다(S-10이 그 형태다).
14. **[규모] 두 내보내기 경로의 규칙이 갈리는 줄 알았다.** 엑셀에서 JSON 셀의 두 키를
    제거하기로 했는데, 월드패키지(`.ncworld`)도 필드 정의를 내보낸다. 확인해 보니
    `WorldPackageExporter`는 `FieldDefinition` **객체를 통째 직렬화**하므로 새 키가 자동으로
    왕복한다 — 손댈 것이 없다. 다만 **엑셀 쪽에서 키를 제거할 때 DB의 config가 아니라 사본을
    고쳐야 한다**는 조건이 새로 생겼다(원본을 고치면 월드패키지가 함께 빈다). 4-5에 명시.
15. **[원칙 04] 꺼진 필드의 사유를 볼 자리가 없었다.** 초안은 "✨을 숨긴다"만 적고, 설명이
    없는 필드에서는 폼에 아무 흔적도 남지 않는다는 사실을 다루지 않았다. 폼에 회색 아이콘을
    두는 안은 **"끈 것"을 "고장 난 것"으로 보이게 해서** 기각하고, 사유를 보는 자리를 두 곳
    (필드 관리 목록의 스위치 조감 · 일괄 고지의 사유별 목록)으로 명시했다(3-3).
16. **[검증] 기기에서 볼 수 없는 것을 사용자 확인 목록에 넣었다.** "요청 본문에 `temperature`가
    없는지"는 앱 화면으로 확인할 수 없다. → 그 항목은 순수 테스트로 옮기고, 사용자 확인은
    **화면에 실제로 뜨는 것**(근거 강도 경고 · 프로토콜 상한 고지 · 비교 전용 바)으로 교체(9장).
