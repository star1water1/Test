### ✅ 이번 판이 낸 것 (2026.08.21) — **사용자 보고: 이미지탭 AI 태그 제안 크래시 → 부류 전체 수리**

**크래시 로그 한 장에서 열었다.** `PromptTokens`의 자리표 정규식 셋이 **닫는 중괄호를
이스케이프하지 않아** 기기에서 정규식 컴파일 자체가 거절됐다.

| | |
|---|---|
| 무엇이 | `TOKEN` · `TOKEN_SHAPED` · `PADDED_TOKEN` — 셋 다 날 `}`를 들고 있었다 |
| **왜 안 잡혔나** | **데스크톱 JVM은 홀로 선 `}`를 글자로 읽어 준다.** 안드로이드의 `java.util.regex`는 ICU 엔진이라 **문법 오류로 거절한다**(`U_REGEX_RULE_SYNTAX`). 문자 클래스도 같다 — ICU는 UnicodeSet 문법이라 `[^{}]`의 `{}`가 **문자열 원소**가 된다. **JVM 시험·CI가 전부 초록인 채 기기에서만 죽었다** |
| 왜 크게 터졌나 | `object`의 초기화식이라 하나만 거절돼도 `<clinit>`이 통째로 터진다 — 자리표를 쓰는 **모든** AI 경로가 `ExceptionInInitializerError`로 함께 넘어갔다 |
| 고친 것 | 중괄호를 **여닫이 모두** 이스케이프하고 클래스 안도 `[^\{\}]`로. **값은 안 바뀐다 — 표기만 바꿨다**(R-37과 같은 판단) |
| 그물 | `PromptTokensTest`가 **리플렉션으로 그 오브젝트의 정규식을 전수로 훑어** 날 중괄호를 잡는다(손으로 적은 목록을 두지 않았다 — 낡는다). **되돌리면 빨간불인 것을 확인했다** |

**앱 전체를 실제 ICU 엔진에 태워 확인했다** — 정적으로 읽히는 정규식 **35개 + 보간 3개, 거절 0**.
이 셋 말고는 없다.

#### 그다음 — **사용자 지시로 부류 전체를 훑었다** (*"있는대로 싸그리 잡아 수정하자. 방편식이 아니라 제대로"*)

크래시 하나가 아니라 **부류**를 잡았다: *데스크톱 JVM에서는 초록인데 기기에서만 다르게 도는 것.*

**두 엔진을 실제로 세워 놓고 쟀다** — ICU 74(`libicui18n`)와 OpenJDK 21에 같은 (패턴, 입력)을
먹여 결과를 대조하는 하네스를 만들고, **BMP 전 코드포인트 63,488자**로 약칭의 집합을 떴다.
짐작이 아니라 실측이다.

| 약칭 | 데스크톱 JVM | 안드로이드(ICU) |
|---|---:|---:|
| `\d` | `[0-9]` 10자 | 유니코드 `Nd` **370자** |
| `\s` | ASCII 6자 | 유니코드 공백 **25자** |
| `\w` | 63자 | **50,802자** |
| `\p{Nd}` · `\p{L}` · `\p{Zs}` · `[0-9]` | — | **같다** (그래서 이걸 쓴다) |

**앱 정규식 38개 중 20개가 갈리고 있었다.** 프로브(입력을 찔러 보는 방식)로는 14개만 보였고,
**정적 판정으로 바꾸니 20개**였다 — 프로브 운에 기대는 방식의 한계를 그 자리에서 실증했다.

| 심각도 | 무엇을 고쳤나 |
|---|---|
| 조용한왜곡 | **`normalizeNumber`가 기기에서 전각 숫자 `１２３`을 "정규화된 수"로 돌려주고 있었다** — `toDoubleOrNull()`이 거부하는 글자를 NUMBER 필드에 실어 보내는 자리였고, 그 함수의 계약은 *"실패 시 null"*이었다. 데스크톱에서는 null이라 **시험이 옳은 동작만 보고 있었다** |
| 조용한왜곡 | **대결 수치 비교가 섞인 표기(`12３`)에서 기기만 `UNKNOWN`으로 빠졌다** — JVM은 `12`를 읽어 비교하는데 ICU는 `12３` 전체를 물고 파싱에 실패한다 |
| 미검증 | **엑셀 헤더 정규화·값 분리·이름 대조 11곳**이 NBSP·전각 공백을 기기에서만 공백으로 쳤다 — **기기 쪽이 옳은 동작이라 그대로 두고**, 데스크톱이 기기를 따라오도록 25자를 명시적으로 못박았다(시험이 이제 실제 동작을 본다) |
| 미검증 | **파일명 정리**가 기기에서만 모든 유니코드 글자를 남겼다 — 기기 동작을 보존하되 ZWJ·RTL 오버라이드 같은 **파일명에 들어가면 곤란한 것**은 빠지는 집합으로 못박았다 |

**단일 소스로 모았다** — `util/RegexCharClasses.kt`. 덤으로 `[-/\s]+`가 **세 벌**로 적혀
있던 것(`FieldValueSorter`·`BodyMeasurements`·`StatsDataProvider`)이 한 자리가 됐다.
`BodyMeasurements`의 KDoc은 *"현행 인라인 파서와 같은 구분자를 쓴다"*고 적고 있었는데,
그것을 잇는 것이 없었다.

**검사를 세웠다** — `tools/check_regex_engine_parity.sh` + **규약 R-69**.
**검사 동결 규칙의 문턱을 넘겼기 때문이다**: 같은 부류의 앱 결함이 두 번 났다
(`B-250` 2026.08.17 `java.awt` · 이번 정규식 둘). 탐지기 자기 시험 16표본이 붙어 있고,
**주석 인용·코틀린 보간·`\p{}`·`\Q\E`는 일부러 안 본다** — 거짓 양성이 검사를 죽인다.

**확인:** 조립된 최종 패턴 14개가 **63,515개 입력에서 두 엔진 동일** ·
순수 JVM 시험 **3,589건 통과** · 검사 **52종 전부 통과** · 프로브 컴파일이 수리 전후
**동일**(538 기준선, 내가 손댄 파일 오류 0) · **이 판 전체를 되돌리면 새 검사가 32건을 잡는다**

뺀 채 잰 수였다 — 콜드 검토에서 스스로 잡아 정정한다.*

#### 그다음 — **여섯 축으로 부류 전체를 감사했다** (적대 반증 통과 37건)

*없는 클래스 · minSdk 초과 API · 로케일/문자셋 · 컬렉션/수치 · 안드로이드 런타임 규칙 · 하네스 사각.*
중복을 접으면 24개 자리다. 이 판이 닫은 것:

| 심각도 | 무엇을 고쳤나 |
|---|---|
| 크래시 | **엑셀 내보내기가 기기 전용 `Error`에 프로세스째 죽었다** — `catch (e: Exception)`이 `NoClassDefFoundError`·`OutOfMemoryError`를 통과시키고, 그 `launch`에 `CoroutineExceptionHandler`가 없어 밖으로 샜다. 설계가 준비해 둔 실패 고지도 이력도 하나도 안 남은 채였다. `Throwable`로 넓히고 스코프에 처리기를 붙였으며, **메모리 부족은 "다시 시도하세요"가 아니라 줄일 수 있는 축을 말한다**(R-17) |
| 조용한왜곡 | **자동 백업의 실패 고지 기구 전체가 `catch (e: Exception)` 안에만 있었다** — B-250이 실제로 낸 `Error`는 그것을 통과해 `recordFailure`·알림·이력이 셋 다 안 돌았고, **설정 화면은 직전 성공 시각을 그대로 보여 줬다.** 사용자는 없는 백업을 있다고 믿는다 |
| 조용한왜곡 | **`org.json`이 구현 둘이다** — JSON `null`에 참조 구현은 `""`, 기기(libcore)는 **`"null"`**. 모델이 `"tags":["실내",null]`을 주면 **기기에서만 `null`이라는 이름의 태그**가 붙었다. `optString` **91곳 전부**를 `util/JsonText.kt`의 `stringOr`로 돌렸다 — 앱이 쓴 config도 예외가 아니다(엑셀로 나갔다 사람이 고쳐 돌아온다) |
| 조용한왜곡 | **로케일이 값을 바꾸던 자리 열둘** — 🎲 랜덤 NUMBER가 `72,4`로 저장돼 **앱이 자기 파서가 못 읽는 값을 자기 필드에 썼고**, 엑셀 **가져오기**의 날짜가 저장값을 아랍-인도 숫자로 굳혔으며, `Calendar.getInstance()`가 태국 로케일에서 **불기 2567**을 돌려줘 `year == 1900` 판정이 성립할 수 없었고, 구간 라벨(분포의 **맵 키**)의 자릿수 판정이 항상 실패했다. **크래시 로그는 쓰고 되파싱하는 서식이 둘 다 기본 로케일이라 로케일을 바꾸면 앱이 자기 로그를 못 읽었다** — 파일은 로케일보다 오래 산다 |

**검사와 규약을 세웠다** — `tools/check_platform_api_parity.sh` + **R-70**(R-69의 형제).
축 넷이고 ③④는 `ui/` 밖만 본다(R-22가 이미 *"보이기만 하는 문구는 기본 로케일"*로 갈랐다).
자기 시험 17표본 · **되돌리면 108건을 잡는다.**

**확인:** 순수 JVM 시험 **3,595건 통과** · 검사 **53종 전부 통과** · 프로브 기준선 **동일**(538).

**이어서 닫은 것 — 기기 런타임 규칙과 거짓 서술:**
· **거짓 서술 정정** — 로드맵 S7이 *"스트리밍이 두 경로의 기본이다"*라고 적어 왔는데, 기기에는 `java.awt`가 없어 **언제나 DOM으로 돈다.** S7이 없앴다고 적힌 *파일 크기 비례 메모리*는 **기기에서 아직 서 있다.** 문서와 코드 주석을 실측에 맞췄다(폴백 자체는 건전하다 — 남은 것은 그 대가이고 실기기 몫이다).
· **취소가 안 보이던 자리 다섯** — 진행도 다이얼로그의 취소를 **메인이 쓰고 IO가 읽는데 평범한 `var`**였다(happens-before 없음). 같은 저장소의 `TaskProgressDialog.Handle.isCancelled`는 이미 `@Volatile`인데 이 다섯이 그것을 비휘발성 지역변수로 복제했다. `AtomicBoolean`으로. **같은 꼴 셋은 같은 코루틴 안 지역 누적이라 결함이 아니어서 안 건드렸다.**
· **AI 관문이 디스패처를 안 지키던 자리** — `AiService.complete`의 앞머리(SharedPreferences 해독 + AndroidKeyStore **바인더 왕복**)가 `withContext` 밖이라 호출자의 디스패처에서 돌았고, AI 진입점 다수가 그것을 `Dispatchers.Main.immediate`에서 부른다. KDoc의 *"어디서든 부르면 된다"*가 **네트워크에만** 참이었다.
· **썸네일 디코드가 바인딩에서 돌던 자리** — `decodeThumbnail`은 KDoc이 *"IO에서 호출할 것"*을 계약으로 적어 뒀는데, 그것을 쓰는 파일 스물하나 중 **`DuplicateCharacterDialog` 하나만** 어겼다(코루틴 임포트조차 없었다). 형제 여섯의 패턴을 그대로 옮겼다(재활용 시 취소 포함).
· **위젯 셋의 이름이 API 26~30에서 안 보이던 것** — 이름을 API 31 전용 `android:description`에만 싣고 `<receiver>`의 `android:label`이 없어 셋 다 앱 이름으로 보였다.
· **위젯 갱신에 시간 상한이 없던 것** — `goAsync()` 안에서 캐릭터 표 전량을 올리는데 형제 위젯만 `withTimeoutOrNull`이 있었다.
· **콜드 스타트가 메인에서 하던 디스크+키스토어** — 산출은 `Log.w` 한 줄뿐이라 바로 위 `appScope.launch(Dispatchers.IO)`로 옮겼다.

**안 건드린 것 하나 — `AiSettingsFragment`의 저장 핸들러(cosmetic).** `setValidatedPositiveButton`이
다이얼로그를 닫을지 **동기로 반환**해야 해서, 비동기로 바꾸려면 저장 플로우 자체를 재설계해야 한다.
심각도에 비해 위험이 크고 **로컬 컴파일 검증이 안 되는 계층**이라 남긴다.

⚠️ **이 마지막 묶음은 전부 `ui/`·`widget/`·최상위·`backup/`이라 로컬 프로브 범위 밖이다 —
컴파일 증명은 CI(master 대상 PR)뿐이다.**

**남은 증명:** `ui/assistant/AssistantProviders.kt`·`ui/field/FieldViewModel.kt` 둘은
`ui/**`라 프로브 범위 밖이다(import 한 줄 + 토큰 하나 치환) — **그 둘의 컴파일 증명은 CI뿐이다.**

**판정 둘은 사용자가 이 판에 맡겼다** (*"뭐든 앱의 설계 원칙과 최고퍼포먼스를 기준으로

- ⓐ **관계도의 세력 칩** → **바꾸지 않고 둘 다 연다.** 강조 하나뿐인 것은 ⑴ **접힘을 못

  고지가 안내하는 *"필터로 좁히면 접힌 인물도 볼 수 있습니다"*에 세력으로 가는 길이 없었다)
  ⑵ **성능을 못 준다**(좁히면 O(n²) 배치가 실제로 싸진다). **기본은 종전대로 강조**이고
  '좁히기' 칩으로 고른다(개발 의도 3 — 기능의 쓸모는 사용자가 가린다). 좁힘은 **상한보다
  앞**이고, 빠른 경로(슬라이더)도 같은 좁힘을 지나며, 빈 화면이 **원인을 바로 지목한다**.
  판정은 `util/GraphFactionNarrow`로 내려 시험이 잠근다 — 이 화면은 로컬 검사가 하나도
  닿지 않는 자리다.
- ⓑ **캐시 비우기 범위** → **맞춘다.** 걸려 있던 것(*"돌고 있는 전송의 임시 파일을
  앗아갈 수 있다"*)은 판정을 세워 풀었다: 이미 있는 `phase` 대입을 세터로 흘려
  `ActiveTransfers`가 *"지금 전송이 도는가"*를 들고, 도는 것이 있으면 **아예 시작하지
  않는다**(사유를 말한다 — R-17). **함께 닫은 결함 셋** — 비우기가 **저장을 기다리는
  내보내기를 지웠다**(재시도 창이 약속한 그 파일. 형제인 회전 정리는 지키고 있었다) ·
  자리 고르기를 취소하면 이식 가능 백업 임시본을 아무도 안 지웠다 · SAF 대기 산출물에
  구간이 서 있지 않았다. 훑는 판정은 `util/CacheSweep`으로 떼어 시험이 잠근다
  (뿌리 보존 · 빈 디렉터리 정리 · **심링크 탈출 봉쇄**).

## 4. 재현 기준선 — 손대기 전에 이 숫자부터 맞춘다

```bash
JARS_DIR=<스크래치패드> tools/setup_jvm_env.sh      # 세션마다 1회
JARS_DIR=<스크래치패드> tools/run_jvm_tests.sh      # 순수 JVM 시험
JARS_DIR=<스크래치패드> tools/probe_compile.sh /tmp/probe.txt
JARS_DIR=<스크래치패드> tools/probe_view_compile.sh /tmp/view.txt
for f in tools/check_*.sh; do "$f" || echo "FAIL $f"; done
for p in tools/verify_room_migration*.py tools/verify_reset_coverage.py; do python3 "$p"; done
```

**현행 값은 여기 적지 않는다 — 0장의 「기준선(판 끝 실측)」 한 줄이 정본이다.**
같은 수가 두 자리에 살면 한쪽이 반드시 낡는다(콜드 검토 2026.08.21: 이 자리가 실제로
`3533`·`541`을 든 채 0장과 갈려 있었고, 5장 착수 절차가 *"기준선을 재현한다(4장)"*이라
지시하므로 다음 세션이 자기 변경이 수십 건을 만들었다고 오독할 자리였다).
**손대기 전에 위 명령을 한 번 돌려 그 출력을 기준선으로 삼는다.**

- ℹ️ **프로브 541은 줄었다가 하나 는 값이고, 둘 다 스텁의 그림자다.** 검토 판이 프로브 스텁
  셋을 좁게 실타입화해(`Activity`·`ContentResolver`·`DocumentsContract.deleteDocument` —
  LruCache·B-190 전례) 종전 `Any?` 수신이 숨기던 미해석 33건이 걷혔고, 콜드 검토 수리가
  런처 콜백(스텁에서 `Any`)을 실타입 인자로 쓰는 자리 하나를 더해 같은 부류의 그림자가
  한 줄 늘었다(`ExcelTransferController` — 같은 줄이 기준선에 이미 있다).
  **손대기 전에 master에서 한 번 떠 보고 견줄 것**은 그대로다.

- ℹ️ `triage_unresolved.sh`는 master에서 종료코드 1이다 — 프로브가 뺀 타입을 그대로 이름으로
  보고하기 때문이고(`ExcelImporter`·`AppSettingsBindings`·`CappedScrollView`·`TaskProgressDialog`,
  2026.08.20부터 `AiKeyStore`), **결함이 아니라 범위의 그림자다.**
  **손대기 전에 master에서 한 번 떠 보고 견줄 것** — 안 그러면 남의 빨간불을 자기 것으로 읽는다.

- ⚠️ **`run_jvm_tests.sh`의 종료 코드는 시험 실패를 말하지 않는다** — 언제나 0이다.
  산출에서 `OK (` / `FAILURES!!!`를 볼 것.
- ⚠️ **프로브 기준선을 뜨기 전에 `git fetch origin master`를 먼저 한다.**
  낡은 `origin/master`로 뜨면 프로브가 거짓말을 한다(양방향으로).
- ⚠️ **문서의 숫자보다 실제 실행 결과를 믿을 것.**

## 왜 이 문서가 생겼나 — 실측

사용자 질문(2026.08.19): *"개발이 끝이 안 나는데 원인이 뭐고 어떻게 해결할 수 있을까?"*

| 재는 것 | 실측 |
|---|---|
| 백로그 **250건** 중 사용자가 연 것 | **1건** (나머지는 콜드 검토 20 · 점검 18 · 감사 12 · 앞 판/착수 대조…) |
| 최근 20판의 산출 | 앱 코드 **4,220줄** vs 문서 4,235 + 도구 2,448 = **6,683줄** |
| 앱 코드를 한 줄도 안 바꾼 판 | **20판 중 6판** |
| `remaining_work` 크기 | 5일 만에 16,342 → **21,691줄** |
| 앱에서 화면(`ui/`) 비중 vs 그걸 보는 시험 | 코드의 **48%** / 시험의 **8%** |
| **실기기 확인 통과** | **7건 · 마지막 2026-08-01 · 그 뒤 52판** |

**뿌리는 하나다.** 실기기 확인이 멈추자 화면 부채가 쌓였고, 세션은 그 부채를 갚을 수 없으니
**부채를 안 만드는 일**(도구·검사·문서)로 흘렀다. 화면을 자동으로 못 보니 검사를 만들었고,
검사는 자기가 볼 수 있는 것 — **자신과 다른 도구** — 을 검사하기 시작했다.
그 활동이 백로그를 자가발전시켰고(249/250), 문서를 키웠고, 커진 문서가
**부채를 은폐했다**(인수인계 판은 줄곧 "열다섯"이라 적었는데 실제로는 124건이었다).

**그래서 고친 것은 둘이다:** 판의 정의(1장)와 문서 크기(이 문서).
**고치지 않기로 한 것도 적어 둔다** — 콜드 검토·자기 등재·검사 신설은 사용자가 이번에
자르지 않았다. 다시 자가발전이 보이면 그때 다시 잰다.
