| | 종전 | 지금 |
|---|---|---|

| 값의 뜻 (정리) | 프롬프트에 **없음** | 값 줄에 `· 뜻:` + *"뜻이 다른 두 값을 합치지 마라"* |
| 대상 | — | 라이브러리 대상 필드 **전부**(restricted 한정 아님 — 규칙 9도 뜻이 필요하다) |
| 새 DB 비용 | — | **0** (두 경로가 부르는 조회가 이미 싣고 오던 칸이다) |
| 설명 예산 | — | 추천: 필드당 **300자**(`MAX_DESCRIPTION_PROMPT_CHARS` 참조) · 목록 예산과 **분리** |
| 시험 | 0건 | **15건** · 되돌려 빨간불 **열셋** |

**설계에서 갈라 둔 것이 둘이고, 둘 다 백로그 행이 경고한 자리다.**
ⓐ **예산을 목록과 나눴다** — 한 예산에서 함께 자르면 설명이 긴 필드일수록 **허용 목록 자체가
짧아진다.** restricted에서 그것은 절약이 아니라 '목록 밖' 표시를 늘리는 새 결함이다.
예시 선별은 손대지 않고 **이미 실리기로 정해진 값에만** 설명을 얹는다.
ⓑ **값에 섞지 않았다** — `북부(왕도 이북)`처럼 붙이면 모델이 그 통짜 문자열을 값으로 되돌려
주고, 목록에 없으니 '목록 밖'이 된다. **목록은 모델이 그대로 베껴야 하는 계약**이다.

받쳐주는 확장성 판정(체크리스트 6번, scalability 7장 4단계)은 **4장 상한 표**에 적었다 —
증가분이 `대상 필드 수 × 300자`로 **규모 무관 상수 상한**이라는 것이 판정의 몸통이다.

**콜드 검토가 잡은 것이 위 표의 둘째 줄이다.** 추천 경로만 고치고 닫을 뻔했는데, 정리 경로의
시스템 프롬프트가 이미 *"이 설명을 병합·분류 판단의 근거로 삼아라"*라고 말하면서 **필드 설명만**
주고 있었다 — 정작 병합 판단의 직접 근거인 값의 뜻은 안 갔다. 뜻으로 갈라 둔 두 값을 합치라고
제안하고 사용자가 받으면 **구별이 사라진다.** 그쪽은 자르지 않고(고지 채널이 없다) 대신
`chunkEntries`가 설명 몫을 함께 세게 해 **요청 수가 늘면 실행 전 비용 고지가 그대로 말한다.**
`ImageTagVocabulary`는 태그 낱말 목록이라 일부러 안 싣는다 — 세 소비처 중 둘이다.

## 1. 판의 정의 — **사용자가 앱에서 볼 수 있는 변화가 없으면 판이 아니다**

**2026.08.19 사용자 판정.** 종전에는 도구·검사·문서만 바꾸는 세션도 한 판으로 셌고,
그것이 실측으로 **최근 20판 중 6판(30%)**이었다. 같은 기간 앱 코드 4,220줄에
도구·문서 6,683줄이 붙었다 — **메타작업이 산출물의 1.6배**였다.

- **한 판은 사용자가 앱에서 볼 수 있는 변화를 하나 이상 낸다.**
- **도구·검사·문서 작업은 독립 판으로 열지 않는다.** 기능 판에 딸려 간다.
- **예외는 사용자가 지시했을 때뿐이다**(전례: 이 문서를 만든 판, 콜드 검토 지시).
- **검사·도구는 동결에 가깝게 다룬다.** 새 검사는 *같은 부류의 앱 결함이 실제로 두 번 난 자리*에만.
  현재 51종·14,937줄이고, 그것들이 잡은 것의 대부분은 **다른 검사와 도구의 결함**이었다.

### 완료의 정의

- **병합은 CI 초록으로 완료된다.** 실기기 확인은 병합을 막지 않는다.
- **실기기 확인은 별도 큐**(`device_walkthrough.md`)에 쌓고 **회차 단위로 소화**한다.
  종전 규칙(*"화면 변경은 실기기 확인 전까지 완료로 보고하지 않는다"*)은
  갚을 수 없는 부채를 만들어 **세션이 화면을 피하게 했다** — 그래서 바꿨다.

## 왜 이 문서가 생겼나 — 실측

사용자 질문(2026.08.19): *"개발이 끝이 안 나는데 원인이 뭐고 어떻게 해결할 수 있을까?"*

| 재는 것 | 실측 |
|---|---|
| 백로그 **250건** 중 사용자가 연 것 | **1건** (나머지는 콜드 검토 20 · 점검 18 · 감사 12 · 앞 판/착수 대조…) |
| 최근 20판의 산출 | 앱 코드 **4,220줄** vs 문서 4,235 + 도구 2,448 = **6,683줄** |
| 앱 코드를 한 줄도 안 바꾼 판 | **20판 중 6판** |
| `remaining_work` 크기 | 5일 만에 16,342 → **21,691줄** |
| 앱에서 화면(`ui/`) 비중 vs 그걸 보는 시험 | 코드의 **48%** / 시험의 **8%** |
| **실기기 확인 통과** | **7건 · 마지막 2026-08-01 · 그 뒤 52판** |

**뿌리는 하나다.** 실기기 확인이 멈추자 화면 부채가 쌓였고, 세션은 그 부채를 갚을 수 없으니
**부채를 안 만드는 일**(도구·검사·문서)로 흘렀다. 화면을 자동으로 못 보니 검사를 만들었고,
검사는 자기가 볼 수 있는 것 — **자신과 다른 도구** — 을 검사하기 시작했다.
그 활동이 백로그를 자가발전시켰고(249/250), 문서를 키웠고, 커진 문서가
**부채를 은폐했다**(인수인계 판은 줄곧 "열다섯"이라 적었는데 실제로는 124건이었다).

**그래서 고친 것은 둘이다:** 판의 정의(1장)와 문서 크기(이 문서).
**고치지 않기로 한 것도 적어 둔다** — 콜드 검토·자기 등재·검사 신설은 사용자가 이번에
자르지 않았다. 다시 자가발전이 보이면 그때 다시 잰다.
